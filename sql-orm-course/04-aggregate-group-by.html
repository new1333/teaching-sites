让数据库替你算报表：聚合与分组 ​

五万行 reduce 分桶，接口从 200 毫秒拖到超时 ​

运营周五下午要一张每日成交报表：多少单、多少钱。订单在数据库里躺着五万行，你在 Node 接口里把它们全查出来，写了一个 groupBy 工具函数，reduce 分桶求和。数据一万行时接口 200 毫秒；涨到五万行，同一份代码跑 9 秒，网关超时，报表页面转圈到下班。你去问后端，他跑了一条 SQL，两毫秒出结果——慢的从来不是算术，是你把五万行原料搬过网线、再在 Node 里开手工作坊。

第二个 bug 紧跟着来。groupBy 上线当天被提了两个工单：其一，金额列里混着空值，合计算出来是 NaN；其二，按天分桶的日期差了 8 小时，昨天的单算进了今天。两个工单一个病根：统计这件事发生在错误的地方，规则全靠自己发明。数据库不止会存和筛——它内置了一整套算数的动作，你在 Node 里手写的每一步，那边都有一等公民的写法。

这一章把这块能力搬回去。三样新工具：聚合函数（aggregate function）——数据库内置的、把很多行压成一个数的动作，数行数、求和、求平均都算；分组（GROUP BY）——按某列的值把行分进各自的桶，每个桶独立出一个数，运营要的「每个用户一个数」靠它；HAVING——专门筛桶的条件子句。沿着走：聚合五件套怎么用、NULL 在算术里怎么记账、桶怎么分、筛桶和筛行为什么是两件事。

聚合函数：数据库内置的 reduce ​

成因：报表要的不是行，是行折出来的数 ​

第 2 章把筛选搬回了数据库，但 WHERE 筛完还给你的仍是行——报表要的是数：行数、合计、平均。算一个数，需要任何一行离开数据库吗？不需要。五万行搬过网线、解析成五万个 JS 对象、折成一个数、对象扔掉——搬运全是白付的。关系模型的表能给你的原料就是行；把行折成数的活，数据库自己就能干。把多行压成一个数，行就不必离开数据库。这就是聚合函数的立身之本：折的动作发生在数据躺着的地方，穿过网线的只有最后那个数。至于引擎扫五万行为什么快——不序列化、不过网线是一半，另一半是索引的功劳，讲索引的那一章再拆。

载体：五个动作，一行进一个数出 ​

最常用的五个：COUNT 数行数；SUM 求合计；AVG 求平均；MIN 挑最小；MAX 挑最大。写法是函数包住列名，放在 SELECT 的位置：

sql
SELECT COUNT(*) AS n, SUM(amount) AS total, AVG(amount) AS avg,
       MIN(amount) AS low, MAX(amount) AS high
FROM orders;

两个要点。其一，聚合查询没有 GROUP BY 时，SQLite 官方文档写明：恒返回恰好一行——哪怕表是空的也返回一行，COUNT 给 0、SUM 给 NULL，而不是零行。其二，AS 给算出来的列起别名——不写的话结果列就叫 COUNT(*)，代码里取值很别扭；别名的规矩本章末尾单独说。

演算：对 8 笔订单手算五件套 ​

先立实验数据。orders 表 8 行，note 列没写非空约束，五行是 NULL：

text
// companion/tests/aggregate-group-by.test.ts · seedOrders 灌入的 8 行
┌────┬─────────┬──────────┬────────┬──────────┐
│ id │ user_id │ status   │ amount │ note     │
├────┼─────────┼──────────┼────────┼──────────┤
│ 1  │ 1       │ paid     │ 300    │ 加急     │
│ 2  │ 2       │ paid     │ 1200   │ NULL     │
│ 3  │ 2       │ pending  │ 90     │ 电话催付 │
│ 4  │ 1       │ refunded │ 150    │ NULL     │
│ 5  │ 3       │ paid     │ 300    │ NULL     │
│ 6  │ 2       │ paid     │ 90     │ NULL     │
│ 7  │ 3       │ pending  │ 750    │ 开票     │
│ 8  │ 3       │ paid     │ 320    │ NULL     │
└────┴─────────┴──────────┴────────┴──────────┘

对着表算：COUNT(*) 是 8——数行；SUM(amount) 是 300+1200+90+150+300+90+750+320 = 3200；AVG 是 3200/8 = 400；MIN 是 90，MAX 是 1200。同一件事在 Node 里是这样的：

js
// 用法示例：同一张表在 Node 里得先把 8 行搬过来
const rows = await fetchOrders()                        // 8 行先过网线
rows.length                                             // COUNT(*)
rows.reduce((s, o) => s + o.amount, 0)                  // SUM
rows.reduce((s, o) => s + o.amount, 0) / rows.length    // AVG

一行对一行，词都能对上。差别只有一个：左边要先付出搬运，右边只搬最后那个数。8 行时无所谓，五万行时就是 200 毫秒和 9 秒的差别。

锚点 ​

聚合函数就是数据库内置的 reduce：你给它一个列，它折完全部的行、还你一个值。折法不同（数数、求和、挑端值），折的位置相同——数据躺着的地方。

NULL 的记账规则：COUNT(*) 与 COUNT(列) 不是一回事 ​

NaN 工单在这里正面拆解。聚合函数遇到 NULL 怎么办，SQLite 官方文档一条条写死了：

  • COUNT(*) 数行——行本身就算数，行里的 NULL 不影响。
  • COUNT(X) 数的是 X 非 NULL 的次数——列里没值的格子不数。
  • AVG、SUM、MIN、MAX 只吃有值的格子。文档原话：AVG 返回组内所有非 NULL 值的平均；一个非 NULL 值都没有时，AVG 与 SUM 都返回 NULL（SQLite 另有一个 total 函数，此时返回 0.0）。

一句话记牢：NULL 不进分子，也不进分母。拿实验场那张 rates 小表演算——alice 打了 5 分又留了一条没打分的，bob 3 分，carol 整条没打分：

  • 全表：COUNT(*) = 4；COUNT(score) = 2；SUM = 5+3 = 8；AVG = 8/2 = 4——不是 8/4 = 2。
  • 只看 carol：COUNT(*) = 1；COUNT(score) = 0；AVG = NULL。

对照 JS 世界的两种下场：字段缺失是 undefined，一进加法整串变 NaN；字段是 null 时 JS 又当 0 算——哪种都和 SQL 的「安静跳过」不一样。手写 reduce 之所以上线当天吃工单，就是两边记账规则各说各话。排查口诀：COUNT(*) 与 COUNT(列) 一减，就知道这列有多少空格子；合计平白变小、平均分母对不上，先查 NULL。

分组（GROUP BY）：先分桶，再各自折算 ​

成因：全表压成一个数，报表嫌粗 ​

五件套把整张表压成一个数，可运营的报表要的是「每个用户一个数」「每天一个数」。聚合的粒度得能选。让聚合函数按桶分别跑，就是分组（GROUP BY）——按某列的值把行分进各自的桶，每个桶独立算一遍聚合。运营那句「按天」，只是把分组列从 user_id 换成日期；「天」从时间戳里怎么切、时区按谁算，是日期函数的事，本章用 user_id 把机制讲透。

载体：桶结构，与一条翻车规矩 ​

GROUP BY user_id 对着 8 行表分桶，一目了然：

text
按 user_id 分桶（分组时 NULL 视为相等，会落进同一个桶）
user_id=1（Alice）→ 行 {1, 4}      COUNT(*)=2   SUM=450
user_id=2（Bob）  → 行 {2, 3, 6}   COUNT(*)=3   SUM=1380
user_id=3（Carol）→ 行 {5, 7, 8}   COUNT(*)=3   SUM=1370

每个桶出结果里的一行：分组之后，一行不再是一笔订单，而是一个桶。翻车规矩只有一条：SELECT 里只放分组列和聚合表达式。分组列是分桶的依据，聚合表达式是对桶内行的折算——此外的列都不许出现。为什么？SELECT 里写个 status，桶 2 里三笔订单的 status 各不相同，出哪一个？多数数据库引擎直接报错；SQLite 官方文档把这叫「裸列」扩展——容许你写，值取组内某一行的，取哪行一般没有任何保证，纯属引擎的宽容（文档写明一个特例：查询恰有一个 MIN() 或 MAX() 聚合时，裸列取极值所在的那一行）。想按状态统计就把 status 写进 GROUP BY，桶分细一层。顺带和第 2 章对个账：NULL 与任何值比较都得未知，那两行 NULL 能落进同一个桶吗？能——文档写明分组时 NULL 视为相等。分组不是比较判断，是归堆：同是空值，就归同一堆。

演算：和手写 reduce 分桶对表 ​

milestone 的核心断言就是这张对表——同一份数据，SQL 的桶和 JS 的桶必须一模一样：

ts
// tests/aggregate-group-by.test.ts —— 第 4 章（节选：与手写 reduce 分桶对表）
    const bySql = db.all<{ user_id: number; n: number }>(
      'SELECT user_id, COUNT(*) AS n FROM orders GROUP BY user_id ORDER BY user_id'
    )
    const buckets = new Map<number, number>()
    for (const r of db.all<Order>('SELECT user_id FROM orders')) {
      buckets.set(r.user_id, (buckets.get(r.user_id) ?? 0) + 1)
    }
    const byReduce = [...buckets.entries()]
      .map(([user_id, n]) => ({ user_id, n }))
      .sort((a, b) => a.user_id - b.user_id)
    expect(bySql).toEqual(byReduce)

Map 的 key 就是分组列，map 里的加一就是 COUNT(*)，两边逐桶相等。差别还是那笔搬运账：左边只搬 3 行结果出来，右边要先把 8 行全搬过来。

锚点 ​

先 Map 分组、再各自 reduce——你手写过很多遍的分桶统计，GROUP BY 就是它的 SQL 拼写，只是桶在数据库里分、数在数据库里折。

AS 别名与排序：给算出来的列起名 ​

SUM(amount) 出来的列，默认列名就叫 SUM(amount)。AS total 给它改名，结果对象里取 r.total，代码立刻干净。别名还有排序上的用处：ORDER BY total DESC，按合计从大到小排——实验场那条断言就是这么写的，前三名 Bob 1380、Carol 1370、Alice 450。

别名能用在哪，各家文档划的线不一样。ORDER BY 和 GROUP BY 认别名——SQLite、MySQL、PostgreSQL 三家文档一致。WHERE 这条线要分开说：MySQL 与 PostgreSQL 都不许用别名，MySQL 文档给了原因——执行 WHERE 时，列值可能还没算出来。SQLite 又宽容了一次：实测 WHERE amt > 1000 认别名、能正确过滤，但官方文档没承诺这一点，跨库别依赖。HAVING 上两家分歧：MySQL 文档说别名能在 GROUP BY、ORDER BY、HAVING 里用；PostgreSQL 文档则写明输出列名不能用在 WHERE 和 HAVING 里，那里必须原样写出表达式；SQLite 实测同样宽容。跨库要安全的写法只有一种：WHERE 和 HAVING 里直接写 SUM(amount)，别指望 total。

排序还有一条要钉死：GROUP BY 不白送顺序。不带 ORDER BY 时，SQLite 文档说返回顺序未定义；PostgreSQL 文档说「按系统觉得最快的方式出」；MySQL 更进一步，8.0.13 起把 GROUP BY 列上写 ASC/DESC 的非标准扩展都移除了，官方示例统一改用 ORDER BY。要顺序就明写——第 2 章的排序配方（业务列加主键兜底）和分页（LIMIT/OFFSET）在分组结果上原样适用，结果一行是一个桶，切的页是一桶一桶的页。

HAVING 与 WHERE 的分工 ​

成因：组是分出来的，分之前不存在 ​

报表需求常常是两层的：「只看已支付」筛的是行——一笔订单自己就能回答；「只留合计超过 700 的用户」筛的是组——得先把一个用户的单全加起来才判得出。筛组的条件为什么不能塞进 WHERE？因为执行到 WHERE 那一步，行还是行、桶还不存在。SUM(amount) 要对「一个桶」求和，桶要等 GROUP BY 分完才成型——组在分组之前不存在，这是机制，不是语法洁癖。本章实验场的第一版测试就红在这：把 SUM(amount) > 700 塞进 WHERE，数据库拒收整条语句，报 misuse of aggregate: SUM()。于是 SQL 给筛桶单开一个子句：HAVING——长得像 WHERE，判的却是桶。

演算：一条查询，五个步骤 ​

本章的主角查询，把两层需求各就各位：

sql
SELECT user_id, COUNT(*) AS n, SUM(amount) AS total
FROM orders
WHERE status = 'paid'
GROUP BY user_id
HAVING SUM(amount) > 700
ORDER BY user_id;

SQLite 官方文档为 SELECT 画了处理次序表，文档同时声明这只是示意——引擎不必真按这个顺序执行，但结果等价。照着走一遍，每步都能对着 8 行表数出来：

text
① FROM：取行——orders 全部 8 行
② WHERE：逐行判 status='paid'，留 5 行：1(300)、2(1200)、5(300)、6(90)、8(320)
③ GROUP BY：按 user_id 归堆——桶1{300}、桶2{1200,90}、桶3{300,320}
④ HAVING：逐桶判 SUM>700——桶1 的 300 出局、桶2 的 1290 留下、桶3 的 620 出局
⑤ SELECT 与 ORDER BY：每桶折成一行、排序——最终一行 user_id=2, n=2, total=1290

WHERE 筛行在先，HAVING 筛组在后——一条查询一次讲清。三个推论逐条过：

  • WHERE 筛掉的行不进任何桶，也不进任何合计。第 4 行那笔 150 的退款单，在第②步就出局了，从此不存在于任何人的 total——这正是「只统计已支付」的本意。
  • 两个条件都是行条件，全放 WHERE；都是组条件（比如「合计超 700 且至少 2 单」），全放 HAVING——HAVING COUNT(*) >= 2 AND SUM(amount) > 700 完全合法，桶已经算完，怎么判都行。
  • 行条件放进 HAVING，SQLite 宽容、按桶内一行判也判得动；PostgreSQL 和默认配置的 MySQL 干脆拒绝非分组列。就算判得动，那也是先分桶再扔桶，白折一趟；先在 WHERE 筛掉，进桶的行更少。行条件归 WHERE，组条件归 HAVING，各司其职。

判别口诀一句话：条件里出现聚合函数（SUM、COUNT、AVG……），它一定是组条件，放 HAVING；条件里只有普通列，优先放 WHERE。

亲手搭实验场 ​

本章照旧不动 src——第 1 章的 db.ts 四方法继续够用，SQL 语法章的演进全在测试里。数据集是 3 位用户（第 3 章的外键 REFERENCES users(id) 指着他们的主键）加 8 笔订单：

ts
// tests/aggregate-group-by.test.ts —— 第 4 章（节选：数据集）
/** 8 笔订单：总额 3200、平均值恰为 400，note 三行有值五行空——聚合断言全靠这组数据可手算 */
function seedOrders(db: Db): void {
  db.exec(`
    CREATE TABLE orders (
      id INTEGER PRIMARY KEY,
      user_id INTEGER NOT NULL REFERENCES users(id),
      status TEXT NOT NULL,
      amount INTEGER NOT NULL,
      note TEXT
    );
  `)
  const rows: [number, string, number, string | null][] = [
    [1, 'paid', 300, '加急'],
    [2, 'paid', 1200, null],
    [2, 'pending', 90, '电话催付'],
    [1, 'refunded', 150, null],
    [3, 'paid', 300, null],
    [2, 'paid', 90, null],
    [3, 'pending', 750, '开票'],
    [3, 'paid', 320, null],
  ]
  for (const [user_id, status, amount, note] of rows) {
    db.run('INSERT INTO orders (user_id, status, amount, note) VALUES (?, ?, ?, ?)', user_id, status, amount, note)
  }
}

然后是本章最有教学价值的一次见红。按直觉写主角查询：既然都是条件，聚合条件塞进 WHERE 理应一样，WHERE status = 'paid' AND SUM(amount) > 700，期望查出 Bob 那组。跑 npx vitest run，红了。报错不是断言失败，是数据库拒收：Error: misuse of aggregate: SUM()。直觉撞上的正是本章的知识点——执行 WHERE 时桶还不存在。修正认知，条件拆进 HAVING，再补一条守护断言把这个拒收行为钉死，转绿：

ts
// tests/aggregate-group-by.test.ts —— 第 4 章（节选：先筛行再筛组，转绿后的形态）
  it('WHERE 与 HAVING 同现：先筛行、再分桶、后筛组，各司其职', () => {
    const db = createDb()
    seedUsers(db)
    seedOrders(db)
    // 只统计已支付：1 笔 300（Alice）、2 笔 1290（Bob）、2 笔 620（Carol）；再筛掉合计不足 700 的组
    const rows = db.all<{ user_id: number; n: number; total: number }>(
      `SELECT user_id, COUNT(*) AS n, SUM(amount) AS total
       FROM orders
       WHERE status = 'paid'
       GROUP BY user_id
       HAVING SUM(amount) > 700
       ORDER BY user_id`
    )
    expect(rows).toEqual([{ user_id: 2, n: 2, total: 1290 }])
  })

  it('把筛组条件塞进 WHERE：数据库直接拒绝，不给错误答案', () => {
    const db = createDb()
    seedUsers(db)
    seedOrders(db)
    expect(() =>
      db.all(
        `SELECT user_id, SUM(amount) AS total
         FROM orders
         WHERE status = 'paid' AND SUM(amount) > 700
         GROUP BY user_id`
      )
    ).toThrow(/misuse of aggregate/)
  })

同一文件里还有六条断言，原则段落里都见过：全表五件套一次算清；COUNT() 对 COUNT(note) 的 8 对 3；rates 表的 NULL 记账三连；reduce 分桶对表；SUM(amount) AS total 加 ORDER BY total DESC 排前三名；HAVING COUNT() >= 3 只留大分组——全部能对着那张 8 行表手数出来。

// 用法示例：五件套、分桶筛组、NULL 记账一次跑通，存成 try.mjs，node try.mjs 就能跑
import { DatabaseSync } from 'node:sqlite'
const db = new DatabaseSync(':memory:')
db.exec('CREATE TABLE orders (id INTEGER PRIMARY KEY, user_id INTEGER, status TEXT, amount INTEGER, note TEXT)')
const seed = [
  [1, 'paid', 300, '加急'], [2, 'paid', 1200, null], [2, 'pending', 90, '电话催付'],
  [1, 'refunded', 150, null], [3, 'paid', 300, null], [2, 'paid', 90, null],
  [3, 'pending', 750, '开票'], [3, 'paid', 320, null],
]
for (const [user_id, status, amount, note] of seed) {
  db.prepare('INSERT INTO orders (user_id, status, amount, note) VALUES (?, ?, ?, ?)').run(user_id, status, amount, note)
}
// 1) 全表五件套：8 行、合计 3200、平均 400、最小 90、最大 1200
const five = db.prepare('SELECT COUNT(*) AS n, SUM(amount) AS total, AVG(amount) AS avg, MIN(amount) AS low, MAX(amount) AS high FROM orders').get()
console.log([five.n, five.total, five.avg, five.low, five.high])   // [ 8, 3200, 400, 90, 1200 ]
// 2) COUNT(*) 数行，COUNT(note) 只数有值的格子：8 对 3
const count = db.prepare('SELECT COUNT(*) AS rows_all, COUNT(note) AS noted FROM orders').get()
console.log([count.rows_all, count.noted])                        // [ 8, 3 ]
// 3) 筛行、分桶、筛组各司其职：只剩 Bob，2 单合计 1290
const big = db.prepare(`SELECT user_id, COUNT(*) AS n, SUM(amount) AS total
  FROM orders WHERE status = 'paid' GROUP BY user_id
  HAVING SUM(amount) > 700 ORDER BY user_id`).all()
console.log(big.map((r) => [r.user_id, r.n, r.total]))            // [ [ 2, 2, 1290 ] ]
// 4) 全空的组：COUNT(列) 是 0，AVG 是 null——不是 0，也不是 NaN
db.exec('CREATE TABLE rates (id INTEGER PRIMARY KEY, rater TEXT, score INTEGER)')
db.prepare('INSERT INTO rates (rater, score) VALUES (?, ?)').run('carol', null)
const carol = db.prepare('SELECT COUNT(*) AS rows_all, COUNT(score) AS scored, AVG(score) AS avg FROM rates').get()
console.log([carol.rows_all, carol.scored, carol.avg])            // [ 1, 0, null ]

小结 ​

聚合函数是数据库内置的 reduce：COUNT 数行、SUM 求和、AVG 平均、MIN/MAX 挑端值；不带 GROUP BY 的聚合查询恒出一行，空表也不例外。NULL 记账按官方文档记：COUNT(*) 数行、COUNT(列) 只数有值的格子，SUM/AVG/MIN/MAX 跳过 NULL，全空时 SUM 与 AVG 出 NULL。分组（GROUP BY）按列的值分桶、每桶各出一行；SELECT 里只放分组列和聚合表达式，其余是 SQLite 才宽容的裸列。HAVING 与 WHERE 的分工一句话：WHERE 在分组前筛行，HAVING 在分组后筛组，条件里带聚合函数的必是组条件。AS 起的别名 ORDER BY 认；WHERE/HAVING 里用别名，MySQL 与 PostgreSQL 不认、SQLite 宽容但未承诺——跨库一律别用；GROUP BY 不白送顺序，排序要明写 ORDER BY。代码上本章只新增 tests/aggregate-group-by.test.ts，src 一行未动。
