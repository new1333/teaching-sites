收工对账：我们的 mini-ORM 与真实 ORM 差在哪 ​

面试官的第三问 ​

周五下午的视频面试，聊到项目经历，你说了实话：「我用 SQLite 亲手造过一个 ORM。查询构建器、脏跟踪、事务都有，一百多个测试全绿。」面试官点点头，抛出第三问：「那说说，它和 Prisma 差在哪？」

你答：「功能少一些。」

「具体少什么？」你脑子里翻了一圈：少……挺多的？「为什么这几样难？」彻底哑火。造过却不识货——简历上写得出「亲手实现」，追问两句就露底。问题不在记性：mini-ORM 是照着「每章验证一个原理」长出来的，没做的部分只在各章末尾顺口交代过一句「登记差异清单」，从来没有正面盘过一次。差在没有一张对账单——把没做的每件事摆在明面上，一格一格填清楚。

本章就是这张对账单。收官定位先立住：拿第 7 章的分层地图回头数一数，mini-ORM 的五件套都立起来了。然后逐项盘真实 ORM 的大件——迁移、连接池、类型推导、多对多、方言——外加一排小件。每项四个问题：是什么；为什么 mini-ORM 没做；真实 ORM 怎么做；影响什么场景。读完这一章，那道面试题你能答满三问：差在哪、为什么、怎么做。

先对账：五件套都立起来了 ​

第 7 章画过分层地图：上层管对象侧的活，中层把链式调用编译成 SQL，下层驱动连数据库。第三部分走完，地图上的座位是这样坐满的：

件户口干的活哪章立的
schema → DDLsrc/schema.tsdefineTable 用对象描述表，生成 CREATE TABLE 建表第 9 章
查询构建器src/builder.tswhere、orderBy、limit、offset 攒账，toSQL() 一步编译第 10 章
水合与脏跟踪src/table.ts行装成带 save() 的实例，只把脏列写回第 11 章
关联加载src/relations.tshasMany 与 belongsTo 声明，with() 两跳批量加载第 12 章
事务src/tx.tsdb.tx(fn) 捆绑成败，抛错自动回滚第 13 章

地基是第 1 章的 src/db.ts——内存库薄封装，四个方法、占位符传参。六个文件，105 个测试。SQL 那半边的手艺也全走过：WHERE 过滤、排序分页、约束守门、主键外键、聚合函数配分组、JOIN 缝表、索引与查询计划、注入与参数化。

骨架是全的。但每个座位上坐的都是「最小可行」版，而真实 ORM 还有几个我们一个字都没写过的大件。这不是偷懒，是课程的刀法：每章只造验证一个原理所需的最小实现。可「没做」要能说清楚，才算真懂——清单在此，全部取舍汇总在书末的差异清单附录里，正文声明的每处简化都在那里有着落。

差距一：迁移——表结构的 git 历史 ​

成因：存量数据改不起 ​

第 9 章建表是推倒重来式：每次 createDb，从零 CREATE TABLE。内存库随建随毁，无所谓。真实的库里有五百万行订单——要给 users 加一列 nickname，你不能把表删了重建，数据会跟着没。表结构必须像代码一样增量演进：这次加一列，下次改个约束，再下次拆一张表。演进还要面对三个现实：多台环境进度不同；同一份变更要按固定顺序重放；改坏了得有办法退。

迁移（migration）——把表结构的每次变更写成一个带序号的脚本，按序回放、只跑没跑过的。它就是表结构的 git 历史。

载体：编号文件加历史表 ​

text
migrations/
  0001_init.sql          CREATE TABLE users (...)
  0002_add_nickname.sql  ALTER TABLE users ADD COLUMN nickname TEXT

数据库里另有一张迁移历史表：
  0001_init          已应用
  0002_add_nickname  未应用    ← 下次执行只跑这一条

ALTER TABLE——在不删表的前提下改表结构的那族 DDL。加列、改名、改约束都是它的活。编号文件放在代码仓库里，历史表放在数据库里：文件说「应该长什么样」，历史表说「实际跑到哪」。

演算：两台环境各跑一遍 ​

开发库上，0001 与 0002 都已应用；生产库上只应用过 0001。发版那天，迁移器在两台库上各跑一遍：开发库对着历史表一看，没欠账，一条不发；生产库查出 0002 没跑，执行它，再往历史表记一笔。同一个动作，两台结果不同——差异全由历史表说话，不由人记。退回去这一手，TypeORM 的做法是每个迁移类配一个 down()——官方文档明说：down 要撤销 up 改掉的东西。

锚点 ​

git 历史：表结构的每次变更是个可回放、可回滚的提交，历史表就是本地的 HEAD。

真货怎么做，我们为什么没做 ​

三家路线不同，都写在各自官方文档里。TypeORM 的迁移是一个类：up() 写怎么改，down() 写怎么退，文件名带时间戳前缀。它还有个 synchronize: true 选项——启动时自动把实体同步成表结构；官方文档明说，库里一旦有了数据，生产上用它不安全——这正是迁移存在的理由。Prisma Migrate 从 schema 文件的变更生成一串 .sql 迁移文件，自述是声明式加命令式的混合：schema 声明目标长相，生成的 SQL 文件又完全可手改；原型期另给一条 db push，跳过迁移历史直接同步。Drizzle Kit 的分工最清楚：generate 对比上一版 schema 生成 SQL 文件，migrate 取出数据库里的历史、只应用没跑过的，push 不落文件直接同步。

mini-ORM 为什么没做：我们的表结构只活在测试里，每次内存库从零建起。迁移解决的是「存量数据的演进」，内存库没有存量，问题不存在。影响什么场景：任何要上线的项目。第 9 章那句「一份定义，两边生效」管结构与代码的对齐；迁移管结构与数据的对齐——两笔账挨着，但不是一笔。

差距二：连接池——建好的连接不扔 ​

成因：网络数据库的连接是花钱的 ​

第 1 章立过世界观：数据库是独立进程。SQLite 是单文件库，跟着你的 Node 进程走——实验场的 node:sqlite 打开一个 DatabaseSync，那就是唯一的连接，还是同步的。MySQL、PostgreSQL 是另一回事：它们是网络服务，每条连接是一次真实的网络往返加身份验证，几十毫秒起步。连接贵，还限流——PG 默认的连接数上限（max_connections）是 100。要是每个 HTTP 请求都现建一条连接、用完就扔，等于每个请求都付一次握手钱；高峰期数据库直接拒收第 101 个连接。

连接池（connection pool）——预先建好一组连接，请求来了领一条、用完还回去。建好的连接不扔，排队复用。

载体：一组连接加一个队列 ​

text
            ┌── 连接 1（忙）── 执行中
请求队列 →  ├── 连接 2（忙）── 执行中       还回去的连接回到池里，
            ├── 连接 3（闲）── 领给队首     下一个请求直接拿走
            └── 连接 4（闲）

演算：握手钱摊到哪 ​

拿假设数字算结构：握手 40ms，一条查询 2ms。100 个请求、每个现建连接，握手总账 100 × 40 = 4000ms；换成 10 条的池，握手只在启动时付 10 × 40 = 400ms，之后每个请求等的都是查询那 2ms。数字是编的，账是真的：握手费从「每请求一次」摊成「每连接一次」。这就是池的全部经济学。

锚点 ​

浏览器的 keep-alive：建好的 TCP 连接不关，下一个请求接着用。连接池就是把这招做进数据库驱动层。

真货怎么做，我们为什么没做 ​

TypeORM 的数据源选项里有一条 poolSize，文档写明是「池内最大活动连接数」。Prisma 客户端自带连接池，用 connection_limit 参数调大小（新版改按驱动适配器配置）。

mini-ORM 为什么没做：内存 SQLite 单连接、零建造成本，池没有存在的理由。但池化世界会反过来考验第 13 章的实现——事务占用的是连接，db.tx(fn) 必须把同一条连接借满整个回调。要是 BEGIN 走了这条连接、COMMIT 走了那条，事务当场散架。我们的 tx 天然安全，因为总共只有一条连接；这份「天然」到了多连接的世界，要靠池的借还纪律重造一遍。影响什么场景：任何 MySQL、PG 生产部署。单文件 SQLite 不需要池，这正是它「嵌入式」定位的另一面——第 1 章那张「数据库是独立进程」的图，在这里分出了两个世界。

差距三：类型推导——schema 顺手长出类型 ​

成因：第二份真相还活着 ​

第 7 章数过手写时代的两笔旧账，第一笔是「同一份数据结构，两处维护」。第 9 章清掉一半：表结构只剩 schema 一份，DDL 由它生成。另一半还欠着：Row 的列值在类型层是 unknown——第 11 章声明的取舍。原因那时写得诚实：「这张表每列叫什么、是什么类型」是运行时信息，TS 编译器看不见 schema 对象。于是查回来的行还得手写 interface 接着，仍旧是口头担保：列名改了，tsc 一声不吭。

类型推导（schema → 类型）——让 TS 类型从 schema 自动生成。一份定义，同时喂饱运行时和编译期。

载体：三条路线 ​

路线代表类型从哪来
生成式Prismaschema 文件跑 prisma generate，生成带类型的客户端代码
推导式Drizzle表定义对象自带类型信息，编译器就地推导，没有生成步骤
手写式TypeORM实体本身就是 TS 类，类型是你写的类；映射靠装饰器标注

Drizzle 文档的说法值得转述：查询结果的类型「基于表定义自动推断，含列的可空性」。TypeORM 的实体类本身就是类型，但 schema 与类型的对齐仍由你手写维护——装饰器在运行时读元数据，编译期帮不上这个忙。

演算：拿我们的 schema 推一遍 ​

规则两条，正好是第 9 章类型映射的编译期镜像：integer 推 number，text 推 string；没写 notNull 的列，添一个 | null。拿 users 试：

text
schema（第 9 章的写法）                推导出的类型
id: { type: 'integer', primaryKey }  →  id: number
name: { type: 'text', notNull }      →  name: string
nickname: { type: 'text' }           →  nickname: string | null

第 9 章的类型映射管「TS 写法与列类型」的运行时翻译；类型推导把同一份对照表搬进编译期。对照表是同一张，只是读它的人从 generateCreateTableSql 换成了 tsc。

锚点 ​

编译器——第 7 章立翻译器比喻时借过：tsc 从源码推类型。推导式 ORM 的 schema 就是源码，类型不用抄第二份。

真货怎么做，我们为什么没做 ​

mini-ORM 为什么没做：把运行时 schema 变成编译期类型，要么加一道代码生成工序，要么写一条很长的泛型推导链——都是「从值推类型」的专门手艺，不在本课程的刀法内。影响什么场景：这一项补上，列名拼错、列类型用错，就从「运行到查询那刻才炸」提前到 tsc 当场红线。第 7 章的第一笔旧账，到这里才算彻底销账。

差距四：多对多与透视表 ​

是什么：用户和角色——一个用户多个角色，一个角色又挂在多个用户身上，两边都是「多」。关系模型装不下它：外键是一列，只能指向一行，「一列存多个值」没有座位。解法是第三张表——透视表（pivot table）——只放两列外键，一个组合一行。多对多拆成两段一对多，第 12 章的 hasMany 两头各挂一次就是雏形。

为什么 mini-ORM 没做：我们的关联只有 hasMany 和 belongsTo，一对多的两个方向。多对多还差「组合」这层语义：两列合起来唯一、一行不许重复挂。第 12 章的两跳机制（IN 批量、分桶挂载）其实装得下它，缺的是声明层。

真货怎么做：Prisma 支持隐式多对多——两边只写数组字段，关系表由 Prisma 自动建、自动管理，文档连命名规矩都写明（如 _CategoryToPost）；要加额外字段（比如 assignedAt），就显式建模成普通模型配复合主键。TypeORM 用 @ManyToMany 配 @JoinTable，官方文档直接画出自动生成的第三张表：两列、各自外键、合起来做主键。Drizzle 走全显式路线：中间表是你自己定义的一张普通表，没有隐式魔法。

影响什么场景：标签、权限、收藏、文章分类——业务建模躲不开的一类关系。我们现在的写法就是「自己 defineTable 一张中间表」，能用，但挂载、去重、组合唯一全靠自己记。

差距五：方言——同一门 SQL，各地口音 ​

成因：各家独立长大 ​

第 2、3、4 章讲 SQL 时，每次都顺带标过方言：分页 MySQL 写 LIMIT offset,n，SQLite 和 PG 写 LIMIT n OFFSET m；自增主键 MySQL 用 AUTO_INCREMENT，PG 用 SERIAL，SQLite 干脆是 rowid 别名；HAVING 里用列别名，MySQL 认，PG 不认。各家数据库独立演化几十年，同一意图、不同措辞——这就是方言（dialect），各家数据库 SQL 的细微差异。

载体：一张对照表（回看） ​

意图SQLite / PGMySQL
跳过 20 行取 10 行LIMIT 10 OFFSET 20LIMIT 20, 10
自增主键INTEGER PRIMARY KEY（rowid 别名）AUTO_INCREMENT
HAVING 用列别名PG 不认认

演算：同一次调用，两种编译 ​

我们的构建器 .limit(10).offset(20) 编译出 LIMIT ? OFFSET ?——SQLite 语法。同一个查询要在 MySQL 上跑，得编译成 LIMIT ?, ?：偏移在前、个数在后，连参数顺序都换了个位。改动只在编译器末尾几行，但前提是编译器得知道自己给谁写 SQL。这就是方言层的全部含义：SQL 生成分家，上层 API 不动。

锚点 ​

同一门语言的各地口音——意思都懂，措辞各改各的。

真货怎么做，我们为什么没做 ​

TypeORM 官方自述支持 MySQL、PostgreSQL、MariaDB、SQLite、SQL Server、Oracle 等。Prisma 在 schema 的 datasource 里写 provider 选库。Drizzle 按数据库分驱动入口（如 drizzle-orm/node-postgres）。上层 API 一套，SQL 生成按方言分叉。

mini-ORM 为什么没做：我们绑死 SQLite 一家——没有第二家，方言层就没有存在感。影响什么场景：换库（SQLite 起家、上线换 PG）、多库并存。方言层把「换库」从改遍业务代码降级成改一行配置；不过各方言独有的行为差异（第 2 章的 LIKE 大小写、NULL 排序）仍要对着新库重新核对。

还差的小件 ​

四个更小的差距，每处都在当年声明的章节里挂着号，这里逐个销号：

  • 乐观锁与版本号（第 11 章）：脏跟踪把丢更新缓解到「只有同列冲突」，根治要给表加版本号列——UPDATE 带 WHERE version = ?、版本号加一；影响行数为 0，说明有人先动了这行，重读重试。TypeORM 文档里有现成的 @VersionColumn 装饰器。场景：管理后台两人同时编辑同一条记录。
  • 嵌套事务（第 13 章）：tx 里再调 tx，SQLite 单连接直接报错；通行解法是 SAVEPOINT——事务里立一个存档点，回滚可以只退到存档。我们从简不做，嵌套调用当场抛中文错误。
  • OR 分组、IN 与 BETWEEN（第 10 章）：where 只会 AND 叠加。表达 OR，得把条件从「列、操作符、值」的三元组升级成可嵌套的条件树，编译时按优先级补括号。TypeORM 的查询选项提供 In、Between、Not、And；Prisma 的 where 能写 OR 数组。同理，聚合函数与分组也没进我们的构建器——第 4 章手写的 GROUP BY 依旧是手写。
  • 驼峰映射（第 9、11 章）：schema 字段与列名同名，省掉一层映射，代价是 TS 里也得写蛇形。Prisma 的 @map 管字段、@@map 管表名，把 camelCase 字段映射到 snake_case 列；TypeORM 的数据源选项里专门有一项 namingStrategy。

再往后还有一排更细的：布尔与日期的列类型映射（第 9 章）、关联属性的 unknown 类型（第 12 章，归进类型推导那笔账）、嵌套关联与第二跳排序（第 12 章）、隔离级别（第 13 章）。每一处当年都在正文里声明过取舍，全部汇总在差异清单附录。声明的差异不是事故，没声明的才是。

你带走的是什么 ​

不是那五百多行代码——代码随时可以再写，mini-ORM 的仓库一抓一把。你带走的是那张分层地图，和每一层拆开看过的原理：驱动层知道数据库是独立进程、连接是资源；构建器层知道两阶段编译和占位符通道；上层知道水合、脏跟踪、两跳加载各自的账怎么记；贯穿三层知道事务捆的是连接上的语句。所以面试那三问，你有现成的骨架：差在哪——对账单上一格一格的清单；为什么——每个差距背后是「内存单连接、只教原理」的教学取舍，不是玄学；怎么做——迁移的编号文件加历史表、连接池的借还纪律、类型推导的生成或推断、透视表、方言分叉，每一项你都拆过它的最小原理。

第 7 章立的那句话，现在可以完整兑现：ORM 是 SQL 与对象两个世界之间的翻译器。这本书做的事，是把翻译器拆开看了一遍——五件套是它的骨架，差距清单是它还没长出来的肉。骨架在手，肉长在哪、为什么长那里，你都答得上来。

不进实验场也能亲手摸一次迁移。三十行的迷你迁移器，存成 try-migrate.mjs：

js
// 用法示例：三十行迷你迁移器——历史表记已应用，重放只跑缺的；存成 try-migrate.mjs
import { DatabaseSync } from 'node:sqlite'
const db = new DatabaseSync(':memory:')

const migrations = [
  { name: '0001_init', up: 'CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL)' },
  { name: '0002_add_nickname', up: 'ALTER TABLE users ADD COLUMN nickname TEXT' },
]

function migrate() {
  db.exec('CREATE TABLE IF NOT EXISTS _migrations (name TEXT PRIMARY KEY, applied_at TEXT)')
  const applied = new Set(db.prepare('SELECT name FROM _migrations').all().map((r) => r.name))
  let ran = 0
  for (const m of migrations) {
    if (applied.has(m.name)) continue // 历史表里有：跳过
    db.exec('BEGIN')
    db.exec(m.up) // 结构变更本体
    db.prepare('INSERT INTO _migrations (name, applied_at) VALUES (?, ?)').run(m.name, new Date().toISOString())
    db.exec('COMMIT') // 变更与记账同进同退——第 13 章的捆绑
    ran++
    console.log('应用', m.name)
  }
  if (ran === 0) console.log('没有待应用的迁移')
}

migrate()
migrate() // 重放：历史表里都有，一条不发
console.log(db.prepare("SELECT name FROM pragma_table_info('users')").all().map((c) => c.name))

跑 node try-migrate.mjs：

text
应用 0001_init
应用 0002_add_nickname
没有待应用的迁移
[ 'id', 'name', 'nickname' ]

pragma_table_info 是 SQLite 的内置工具，交出一张表的列清单。四行输出读完：前两行是首跑，第三行是重放——历史表挡住了重复应用；第四行是证据，nickname 列真的长出来了。还有一处值得看：迁移本体和记账捆在同一个事务里，变更成功、记账失败，或反过来，都不会发生——第 13 章的原子性在迁移器里当了一天守门员。Drizzle Kit 的 migrate「取历史、只应用没跑过的」，说的就是这三行输出背后的结构。

小结 ​

收官对账的结论压成三句。五件套立起来了：schema 生成 DDL、构建器两阶段编译、水合与脏跟踪、关联两跳加载、回调式事务——六个文件、105 个测试，第一部分攒下的 SQL 手艺全数用上。真实 ORM 的大件我们一样没做：迁移管存量数据演进、连接池管网络数据库、类型推导管编译期对齐、透视表管多对多、方言管多库——每项的四个问题，本章各有一格。小件也销了号：乐观锁、SAVEPOINT、条件树、驼峰映射。你带走的不是功能清单，是分层地图和每层的原理——下次有人问「它和 Prisma 差在哪」，你从地图讲到账单，三问问不倒。

你现在能做到：把 mini-ORM 放回分层地图说清它有什么；对任何一个大件，答出是什么、为什么没做、真货怎么做、影响什么场景。
