写完了 WebGL：Three.js、WebGL2 与 WebGPU ​

第 13 章收工的那个小世界，你还想再往上加东西。先想加一个投影阴影——物体在地上拖出影子。一查资料，第一页就告诉你这不是「往地上画一个灰色形状」：要让影子投对地方，得先站到光源的位置把整个场景再画一遍，把「每处离光多远」记进一张深度纹理。正式绘制时，每个片元再回头查这张纹理、比对遮挡。一整套深度纹理渲染流程。每一环你其实都有账户：深度你会算，纹理你会传，逐片元比远近你在深度测试里见过——但把它们装配成一条阴影管线，是几周工作量。

再想加载一个现成模型。美术发来一个 glTF 文件——glTF 是 3D 界通用的模型交换格式，把层级、网格、材质、动画打包成一个标准文件，作用类似照片界的 JPEG。翻开它的规范：结构用 JSON 描述，大块的顶点与索引装在二进制块里，纹理与材质各占一章。要把它读成你自己的缓冲区和材质对象，得写一个几千行的解析器。

每一项都是几周工作量。而用 Three.js（Web 上最常用的 3D 库）的人，建一件物体就是一行 new THREE.Mesh，加载模型、打开阴影各是几行配置。手写到这一步，图什么？

这一章一行新代码都不写，专门把这本账算清。先对账：你十四章手写过的东西，哪些正是库的公开概念，库真正的增值又在哪几件重活。再给一张决策清单：什么时候值得自己写，什么时候该直接上库。最后看向两扇更远的门——WebGL2（WebGL 的下一代规范，同一门手艺的新工具箱）与 WebGPU（WebGL 的继任者，对齐新一代本地图形 API 的接口）。第 13 章末尾欠下的两笔概念债——视锥剔除（帐篷外的物体整件不画）与实例化渲染（一次绘制调用画一排同样的物体）——也在这里还清。

库替你做了什么：先对账，再算增值 ​

你手写过的，正是它的公开概念 ​

先对完账你会安心：这门课教你的概念清单，几乎就是 Three.js 文档的目录。逐项对一遍：

你手写的（出处章）库里的公开概念账是否同一本
createCube 的 24×8 交错缓冲＋顶点属性布局（第 8 章）BufferGeometry——顶点数据连同读取布局打包成对象同一本：数据进缓冲区，布局仍是顶点属性
perspective 与 lookAt（第 6、7 章）PerspectiveCamera——fov、宽高比、near、far 就是它的公开字段同一本：内部还是投影与视图那两台矩阵
Phong 着色器＋材质参数包（第 10、13 章）MeshPhongMaterial同一条三件套公式
SceneNode 的局部矩阵与世界矩阵（第 11 章）Scene 与 Object3D 的父子层级，也就是场景图同一本链乘账
渲染清单加通用绘制循环（第 13 章）一行 renderer.render(scene, camera)清单替你收，还是那趟深度优先
雾的 mix 三行（第 13 章）scene.fog同一个按距离混色公式
viewBasis 漫游相机（第 12 章）PointerLockControls / OrbitControls偏航俯仰出基向量、球坐标出眼位，账相同

库没有发明另一门图形学。它把你会的每一步换成公开对象与公开参数，再往上加盖。所以第一个结论很朴素：你读得懂它的文档，每个词你都有账户。这不是巧合——这门课的路线本来就是沿着「库的使用者该懂什么」逆向拆出来的最小内核。

真正的增值：五件你还没写过的重活 ​

对完账，差价在哪？在这门课刻意没碰的五件重活上。

其一，模型格式解析。你的世界里每件物体都是代码摆的；真实项目的模型来自美术与模型库，载体就是 glTF 这类标准文件。解析器要把 JSON 里的层级还原成场景树、把二进制块拆成顶点与索引缓冲、把材质参数映射成着色器的进料。第 8 章你手工定过 cube 的顶点表，glTF 就是把别人做好的这些表打包给你读。库的 GLTFLoader 承包这整条流水线。

其二，资源管理与异步加载。你的纹理是代码现算的数组，即算即用；真实项目的纹理与模型是文件，从几十 KB 到几十 MB：下载排队、进度回报、解码、传进显存、不再用时释放。一整类不在原理里、却在工程里天天见的账。

其三，剔除与批处理。库会在收单前后替你做视锥剔除与实例化渲染，把「画哪些」和「怎么少发单」管起来。这两个词正是第 13 章欠下的概念债，下面两节各讲透一个。

其四，阴影与后期处理管线。开章那套「从光源再画一遍、深度存进纹理」的流程，在库里是几处公开开关的事：渲染器打开 shadowMap，光源打开 castShadow，物体标记投射与接收。泛光、景深这类后期处理（先把整帧画进一张纹理、再整屏加工的手法）是同一思路的另一条管线。概念你全见过，装配是几周量级的活。

其五，跨设备适配。能力探测与回退、像素比适配、显卡重置后的上下文恢复——每一项都要对着不同浏览器与机型分别对账。

五件有个共同点：原理你能看懂，装配是体力加工程。库收的差价，付的就是这部分。

视锥剔除：帐篷外的物体不进清单 ​

先还第一笔债。回看第 6 章：视锥体是从眼睛出发、被屏幕四边削出的一顶帐篷；帐篷外的顶点，GPU 在裁剪坐标系阶段自己会裁掉。那为什么 CPU 还要再剔除一遍？账在绘制调用上。帐篷外的顶点虽然上不了屏，但它已经进了流水线：顶点着色器照跑一遍。更要紧的是，每次绘制调用，CPU 侧都有一笔固定开销——换绑定的缓冲、设 uniform、发指令，与这件物体画多大无关。第 13 章 17 行清单只有 17 次调用，付得起；世界长到 1700 件物体，而你转身只看得见眼前几十件，身后那上千次调用每帧白付。视锥剔除把「画不画」的判断搬到收单之前：整件物体在帐篷外，整行清单不收。省的不是几个片元，是整次绘制调用。

判定对象用包围球——罩住整件物体的一个球：中心取物体中心，半径取中心到最远顶点的距离。柱高 3.5、粗 0.55 的柱子，最远顶点是三维角点，半径 = √(0.55² + 1.75² + 0.55²) ≈ 1.92。中心要过世界矩阵结算（第 11 章的快照），半径在均匀缩放下乘缩放倍数、非均匀缩放取最大轴的倍数——往大了保守。判定流程一张结构表说完：

text
逐行查渲染清单 → 算这一行的包围球
→ 与帐篷六个面逐面比对（near、far、上、下、左、右）
→ 任一面：整球在外 → 剔除，这行不画
   其余情况（整球在内 / 球穿帐布）→ 照收

拿纸笔推演一遍侧壁的账。相机在原点朝 −Z 看，透视投影 fov 60°。帐篷每面墙从眼点张开一个角。第 6 章的账本写明 fov 是上下方向的总张角，左右墙的张角由宽高比推出；这里取正方形画布（宽高比 1），左右墙与上下墙的半张角同为 30°（tan 30° ≈ 0.577），深度 d 处的帐内半宽 = d × 0.577。三根同样规格的柱子，都放在深度 20（帐内半宽 = 11.5）：

text
柱 A 中心横向偏 8 ：8 ＋ 1.92 = 9.92   < 11.5 → 整球在帐内，照画
柱 B 中心横向偏 15：15 − 1.92 = 13.08 > 11.5 → 整球在帐外，整行剔除，一次调用全免
柱 C 中心横向偏 10：10 − 1.92 = 8.08 < 11.5 < 10 ＋ 1.92 = 11.92 → 球穿帐布，照画

柱 C 值得多看一眼：球比柱子胖得多（半径 1.92，柱子半宽才 0.55），球穿帐布时柱子本体其实还全在帐内——判定吃了亏，但方向安全。剔除的规矩是宁可错画，不可错删：错画，GPU 在裁剪阶段顺手丢几个三角形，代价按片元计；错删，看得见的柱子凭空消失，代价按 bug 计。同理，near 面背后（你身后）与 far 面之外的物体也是整球在外、整行不收；六面各查一遍，任一面向外即剔。收尾一句：第 13 章那张点菜单送进后厨前，先把顾客看不见的菜划掉——划掉的是整行单子，不是菜里的一片肉。

实例化渲染：一次绘制调用画一排柱子 ​

再还第二笔债。回看第 1 章：GPU 赢在做一万遍同一道题。但 CPU 每发一次绘制调用，都有一笔固定成本——设状态、递指令，与这次画多少无关。第 13 章的柱廊：10 根柱子同一个 cube、同一份石头材质，却是 10 次 drawElements、10 圈「设模型矩阵、设法线矩阵、发指令」。10 次付得起；换成一圈几百根的栅栏、一片几万株的草地，CPU 会在 GPU 之前先累垮——瓶颈从「画不画得动」变成「单发不过来」。实例化渲染把「同一份几何、画 N 次」合并成一次绘制调用：几何还是那份，另附一张实例表，GPU 在这次调用内部把几何跑 N 遍，每遍套用表里的一行。

text
普通索引绘制：  一份顶点表 ＋ 一份索引表           → 画 1 件物体
实例化索引绘制：一份顶点表 ＋ 一份索引表 ＋ 实例表 → 一次调用画 N 件
实例表每行：    这一件的偏移（vec3；要旋转缩放就加宽这行）

机关在进料口。顶点属性多出一种「每实例前进」的走法：普通 attribute 每顶点走一步，它每实例走一步——WebGL2 里由 vertexAttribDivisor 这个公开开关控制。顶点着色器照常逐顶点跑，读到的偏移是「当前这件」的那行；第几号实例还有个着色器可读的编号（GLSL ES 3.00 的 gl_InstanceID）。柱子的每个顶点加上本柱偏移，落位与第 13 章的 T·S 模型矩阵殊途同归——平移这一维，从 uniform 挪进了实例表。

还是 100 根柱子，两本账摆在一起推演：

text
第 13 章写法（每帧）：100 次绘制调用；矩阵逐行必发：100 × 32 = 3200 个数（模型 16 + 法线 16）
实例化写法（每帧）：1 次绘制调用；实例表 100 × 3 = 300 个数，初始化传一次、此后每帧零下发
顶点总量两本账相同：24 × 100 = 2400 个顶点照跑

实例化不是少画，是少跑腿。省的是 99 次调用的固定开销；GPU 侧 2400 个顶点本就是它的甜点（第 1 章的并联账）。边界也记下：实例表要求同一份几何，材质不同要么拆批、要么把颜色编进实例表；一排柱子、一片草地是它的主场，十七行五花八门的清单帮不上忙。收尾一句：同一颗印章蘸一次油，按实例表的位置盖一百下——不必每盖一下重刻一颗。

什么时候自己写，什么时候上库 ​

账算清了，决策清单就短。

自己写值得，三种情形：

  • 学习目的。你要的就是「懂」。自己装配过一遍，黑屏时知道先查 InfoLog、先查 attribute 绑定；只调库的人只能删码重来。这门课的存在理由就在这条。
  • 极端约束。几 KB 体积预算的宣传页特效、几十万实例的专用粒子管线——库的通用层（场景树、材质系统、加载器）此时是体积与性能的负担。
  • 特殊管线。产品本身就是渲染技术：体渲染、风格化画面、研究原型——通用库的管线插不进去，本来就得自己搭。

直接上库，一种情形：

  • 常规业务 3D 展示。电商看房、车型配置器、模型查看器、数据大屏——需求是快出活、稳定维护；模型从美术的 glTF 来，阴影与后期开箱即用，适配的账库已替你对过。

中间态最常见，也是职业日常：库管装配，你写自己的着色器——用库的场景树与加载器，光照公式自己出手（Three.js 的公开扩展点 ShaderMaterial 就是干这个的）。

上库不等于不用懂原理，这门课的复利恰好在这里兑现。其一，调试输出读得懂：renderer.info 这类公开面板报出本帧的绘制调用数，场景卡先看它——上了千，就是该剔除、该合并、该实例化了。其二，性能瓶颈会归因：掉帧先分清是 CPU 侧发单发不过来，还是 GPU 侧片元太贵（全屏后期、着色器太长）——第 1 章的账反过来用。其三，文档与文章看得懂：参数名、迁移指南、概念词，你都有账户。

往哪走：WebGL2 与 WebGPU ​

WebGL2：同一门手艺，新一套工具 ​

WebGL1 的底座是 2007 年的 OpenGL ES 2.0。十年后硬件与 API 家族都往前走了，WebGL2 落在 OpenGL ES 3.0 上。定位一句话（MDN 口径）：WebGL 2 是 WebGL 1 的扩展——旧上下文的成员它全部实现，旧代码除少数边角行为外一字不改照跑。所以它不是换代，是几乎严格的超集：旧车间照开工，新车间按需进。概念级的差异清单：

能力WebGL1WebGL2
实例化绘制靠 ANGLE_instanced_arrays 扩展转正：drawArraysInstanced 一族内建
多渲染目标无一次片元着色器运行可写多张纹理
非 2 幂纹理受限（第 9 章绕过的坑）任意尺寸，功能全开
着色器语言GLSL ES 1.00GLSL ES 3.00（in/out 语法、gl_InstanceID）
顶点结果回存无变换反馈：顶点着色器的输出直接写回缓冲
深度纹理靠扩展原生能力

两笔纸面账。第一笔，非 2 幂：第 9 章的格子纹理只能取 2 的幂——演示用的 128×128；513×513 在 WebGL1 只许 CLAMP_TO_EDGE、配不齐过滤链；WebGL2 下同一张 513×513 直接 REPEAT 平铺。第二笔，多渲染目标：一次片元着色器运行写多张纹理，意味着「先把法线、深度、材质参数各画进一张纹理，第二遍取出来算光」成为常规路线。开章的投影阴影（深度存进纹理）属另一行账：WebGL1 里渲染到深度纹理要靠扩展凑，WebGL2 是原生——多渲染目标的最小应用是延迟着色那类一次写多张的路线。本章上一节的实例化，也在这里从扩展转正——你学的概念一件没作废，只是换了正式编制。

WebGPU：换一代底座 ​

WebGPU 的定位（MDN 口径）：WebGL 的继任者。动机有三。其一，OpenGL 家族已停更，新一代本地图形 API（Vulkan、Metal、Direct3D 12）的能力，WebGL 这条线永远拿不到；WebGPU 对齐这一代架构，还会持续长新能力。其二，WebGL 只为「画图到画布」设计，通用 GPU 计算——拿 GPU 的并联算非图形的题，机器学习推理是当下大头——支持得别扭；WebGPU 把计算管线做成一等公民。其三，逐物体渲染的 CPU 开销显著更低，物体多到 WebGL 吃力的场景是它的本钱。

概念级三件事。第一，计算着色器：不画图、只算数的第二类管线。第 1 章说过 GPU 本是几千通道的并联计算芯片，画图只是它的一份工——WebGPU 把另一半直接开放。连本章的剔除都能搬进去：把渲染清单整表交给计算着色器在 GPU 上判定、输出可见表，第 13 章的收单循环整个搬进 GPU 的路线。第二，显式管线：渲染管线不再是「改一个全局状态影响下一次绘制」的隐式状态机（第 2 章那套接线的脾气），而是显式创建的管线对象。布局、绑定、着色器入口在创建时一次说清，GPU 提前知道这趟怎么跑最省。第三，着色语言换成 WGSL，不再是 GLSL。三档并排看：

WebGL1WebGL2WebGPU
底座OpenGL ES 2.0OpenGL ES 3.0对齐 Vulkan / Metal / D3D12 一代
着色语言GLSL ES 1.00GLSL ES 3.00WGSL
实例化扩展内建内建
计算着色器无无一等公民
管线形态隐式全局状态隐式全局状态显式管线对象

一笔账看「验证时机前移」值多少。第 2 章的接线六步里，你改的每个状态都由驱动在绘制时当场检查，对不上就静默黑屏——那个「报错被吞」的痛点就是这笔账的形状。WebGPU 把「管线长什么样」提前到创建管线对象时一次验完、当场报错，每帧只往命令队列里提交录制好的活。还有一笔账要提前算清，免得期待错位：API 换代解决的是「怎么跟 GPU 对话」，不解决「怎么把世界装进文件」。即便上了 WebGPU，glTF 还是 glTF、解析器还是解析器——库的地位不降反升，只是底层换了发动机。

你学的每笔账换名不换账：uniform 换叫绑定，attribute 换叫顶点缓冲布局，三段接力还是顶点、光栅化、片元。从这门课带走的概念，三门 API 通用。

这门课为什么停在 WebGL1 ​

教学最小内核。WebGL1 是「把一个三角形弄上屏」所需概念最少的版本：着色器、缓冲、顶点属性、一张深度缓冲，六步接线就是最短路径；没有管线对象、绑定布局、命令队列这些「工程上更对、教学上是噪音」的层。而学会的每一笔账，向上全数通用：WebGL2 是超集，WebGPU 换名不换账。反过来，真实项目的新代码没必要从 WebGL1 起步——WebGL2 自 2021 年 9 月起在各大浏览器广泛可用，主流库也以它为默认目标。教学从最内核进，干活从新台阶起。
