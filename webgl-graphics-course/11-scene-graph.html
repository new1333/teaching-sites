场景树：坐标跟着上级走 ​

太阳系 demo 的最后一块是月亮。它要绕地球转，于是你在渲染循环里每帧手算它的世界坐标：月亮相对地球的位置用一套三角函数，地球相对太阳的位置再用一套三角函数，两个结果加在一起喂给模型矩阵。跑起来的第一分钟一切正常，第二分钟开始不对劲——地球在绕太阳公转，它的坐标系每帧都在转向，可你加到月亮身上的那份偏移从没跟着转过。两套坐标系互相打架，账越算越歪：月亮的轨道飘成随机曲线，一会儿切进地球肚子里、一会儿甩出老远。你调参、对角度、换 sin 和 cos 的符号，怎么修都不干净。这个坑不是算错了一个数，而是算的结构就错了——太阳、地球、月亮的层级关系早就写好了答案：月亮的局部变换只描述「绕地球」，剩下的事交给父节点链乘。本章把这份答案写成代码：一棵场景树，和一个每帧只做一次的结算动作。

出发前清点：单机作战十章的家底 ​

前三部攒下的家当，今天几乎全员复工。数学侧：向量、点积、叉积给打分与叉乘打杂，归一化只留方向，单位向量当尺子，向量投影量分量；矩阵是本章的主角——4×4 变换机器、列主序、齐次坐标补的那张「身份证 1」，全部原样值班。承重的是矩阵乘法那两条纪律：乘积从右往左作用（坐标先过右边的机器），以及顺序不可交换（T·R ≠ R·T）。第 5 章绕中心转的 T·R·T⁻¹ 已经演过「先搬回原点、转完再搬回去」——层级链乘是同一套纪律往多层推广。

矩阵家族其他成员就位：模型矩阵今天要换岗——前十章它是每件物体独享的一台机器，本章起它从场景树里结算出来；视图矩阵与透视投影组成 V·P，把世界搬进相机跟前再压进视锥体，透视除法与宽高比照旧；正交投影那台平行光路的机器本章歇班。裁剪坐标系、可变变量、统一变量这些进料口词汇不变：世界矩阵算完照旧走 uniform 进顶点着色器。管线侧：顶点着色器、光栅化、片元着色器三段接力，GPU 吃重复计算，帧率预算 16.7 毫秒、掉帧的账都照旧。缓冲区与顶点属性这次一动不动——本章改的是「坐标怎么算」，不是「坐标怎么传」。渲染循环与增量时间是层级动画的心跳。深度缓冲与深度测试继续裁决遮挡；索引绘制画球；缠绕方向从外面看逆时针、背面剔除开着。纹理那一套——UV 坐标、纹素、采样、过滤——本章歇班，第 13 章组装世界时再回来。光照全员复工：法线、法线矩阵、环境光、漫反射、高光，Phong 三件套直接给太阳系上色，太阳自己是光源。线性插值与缓动、精度限定符照旧带着。

清点完发现一件事：前十章的每件物体都是「单机作战」——各自领一台模型矩阵，互不知晓。这在一件物体、或者几件互不相干的物体身上没问题。一旦物体之间有了「谁跟着谁动」的关系，单机作战的模式就到头了。

层级：场景里到处都是 ​

打架的账为什么躲不开 ​

先别盯着太阳系，看看层级在场景里有多常见：车轮跟着车身转，车身跟着悬挂颠；角色手里的剑跟着手，手跟着手臂，手臂跟着肩膀；卫星跟着行星，行星跟着恒星。这些关系的共同点：下级只描述自己相对上级的运动，世界坐标由整条链结算。反过来写——每件物体独立计算自己的世界坐标——你就得在每个下级的公式里手工掺入所有上级的运动。两层还能忍，三层开始每加一层，所有下级的公式全部重写；哪个上级改了运动方式，它的所有下级跟着改公式。开章那个飘掉的月亮，只是这份连锁债务的第一期账单。

把「下级只管相对运动」写进数据结构，就是场景图（scene graph）——一棵父子上级的树。每个节点装一件物体（或一个逻辑分组），子节点的坐标在父节点的坐标系里描述，层层向上结算成世界坐标。它不引入任何新数学，只是把第 5 章的矩阵乘法按层级组织起来。

树长什么样 ​

太阳系的层级画出来是这样（演示组件用这份结构，测试搭的是它的骨架）：

text
sun（根：世界原点，local = I）
├─ sunMesh     local = R_y(太阳自转角) · S(1.2)      太阳网格：自转写在叶子上
├─ earthRing   local = S(4, 1, 4)                     地球轨道圈：世界固定
└─ earthOrbit  local = R_y(公转角) · T(4, 0, 0)       地球轨道节点：绕太阳
   ├─ earthMesh  local = R_y(自转角) · S(0.55)        地球网格：只管自转
   ├─ moonOrbit  local = R_y(月亮角) · T(1.5, 0, 0)   月亮轨道节点：绕地球
   │  └─ moonMesh  local = S(0.25)                    月亮网格
   └─ moonRing   local = S(1.5, 1, 1.5)               月亮轨道圈：跟着地球走

读法一句话：挂在谁的下面，就在谁的坐标系里说话。月亮轨道节点挂在地球轨道节点下面，它的 T(1.5,0,0) 是「离地球 1.5」——对太阳、对公转角一无所知；公转的事全记在地球轨道节点自己的 local 里。这就是开章痛点的解药：月亮的公式里永远不出现公转角。

直觉可以借一张组织架构图：员工的工位坐标先在部门内算——三排靠窗第二个位子；再由部门的办公楼地址搬进公司的世界坐标。员工换工位只改部门内的坐标，公司搬家只改部门的地址，两本账互不打架。

局部矩阵与世界矩阵 ​

局部矩阵：只写「相对父级」 ​

局部矩阵（local matrix）——节点相对父级的变换——是树上每个节点唯一要亲手维护的东西。动画师每天改的就是它：公转角前进一度，就把地球轨道节点的 local 重建一次；月亮角前进一度，就重建月亮轨道节点的 local。注意「重建」而不是「叠加」：每帧从角度现造一台 R_y(公转角)·T(4,0,0)，上一帧的矩阵扔掉——角度是唯一的真相，矩阵是角度的临时投影。这也顺带解决了浮点误差累积的老问题：位置不会在几万帧后漂掉，因为它从来没被累积过。

局部矩阵的另一个名字更直白：它就是子节点坐标系到父节点坐标系的换算表。月亮轨道节点的 local 说的是「月亮坐标系的原点在地球坐标系 (1.5,0,0) 处、姿态被月亮角转过」。

世界矩阵：从根链乘到本节点 ​

GPU 不认「相对地球」，只认世界坐标——顶点着色器那句 gl_Position = P·V·M 里，M 必须是这台物体在世界里的总变换。从树根到本节点，把沿途每级的 local 按顺序串起来，就是世界矩阵（world matrix）——物体在世界里的最终姿势。月亮的世界矩阵 = earthOrbit.local · moonOrbit.local（坐标先过月亮的、再过地球的），根到本节点逐级如此。

这正好接上第 7 章「坐标先过哪台机器」的流水线，往左再接一段：

text
月亮局部坐标 →(moonOrbit.local)→ 地球轨道节点坐标 →(earthOrbit.local)→ 世界坐标
世界坐标 →(V)→ 相机跟前 →(P)→ 标准操场 →(除以 w、视口)→ 屏幕

层数再多也是同一件事：MVP 里的 M 从「一台矩阵」升级成「一条链的乘积」，V 和 P 完全不知道树的存在。结合律保证这条链怎么分组乘都一样——逐级链乘（父算完传给子）和一次性全乘，结果相同；递归结算因此合法。

演算：公转 90° 那一帧，月亮落哪 ​

本章的承重演算，拿笔跟着算。设定：公转角 90°，月亮角 0°（月亮此刻在地球坐标系的 +X 方向上），公转半径 4，月亮轨道半径 1.5。

text
地球 local = R_y(90°) · T(4,0,0)          月亮 local = T(1.5,0,0)

月亮原点 (0,0,0) 一步一步过机器：
  ① 过月亮 local —— T(1.5,0,0)              → (1.5, 0, 0)
  ② 过地球 local 的右半 T(4,0,0)             → (5.5, 0, 0)
  ③ 过地球 local 的左半 R_y(90°)：
       x' = cos90°·5.5 + sin90°·0 = 0
       z' = −sin90°·5.5 + cos90°·0 = −5.5    → (0, 0, −5.5)

同一笔账分两笔记，验算一遍：

text
地球世界位置：R_y(90°)·(4,0,0) = (0, 0, −4)
月亮偏移跟着地球转：R_y(90°)·(1.5,0,0) = (0, 0, −1.5)
相加：(0,0,−4) + (0,0,−1.5) = (0, 0, −5.5)   对上

手算叠加版的答案：地球位置 + 不转的偏移
  (0,0,−4) + (1.5,0,0) = (1.5, 0, −4)        错——与真值差约 2.1 格

最后一行就是开章的坑：偏移 (1.5,0,0) 是在地球坐标系里量出来的，地球坐标系此刻被公转角转过 90°，偏移必须跟着转。月亮的轨道半径从头到尾都是 1.5，错的不是距离，是它在哪个坐标系里被量。每帧公转角都不同，错的方向逐帧旋转，连起来就是那条飘掉的轨道。这里要分清两种错法：像开章那样把两套三角函数一次性加在一起，错得「稳定」——月亮与地球的距离仍钉在 1.5，只是轨道圆心挪了位；演示里「手算版」的错法更糟，它把每帧的步子累加进世界坐标，误差逐帧滚雪球，距离也失守、读数乱跳。两种错法同根：偏移没有跟着坐标系转。

渐进实验：SceneNode 进仓 ​

原理有了，落进实验场。新模块 src/scene/node.ts，全章就一个导出：SceneNode。先看全貌：

ts
// 拼版（src/scene/node.ts 的 class，函数体与仓内逐字一致；模块头与方法上的 JSDoc 省去，正文下方逐条讲）
export class SceneNode {
  /** 局部矩阵：节点相对父级的变换（动画每帧改的就是它）。 */
  local: Mat4
  /** 子节点：层级关系的全部存储，顺序即遍历绘制顺序。 */
  children: SceneNode[] = []
  /** 世界矩阵：从根链乘到本节点的总变换，updateWorld 的结算结果。 */
  world: Mat4

  constructor(local: Mat4 = identity()) {
    this.local = local
    this.world = identity()
  }

  add(child: SceneNode): SceneNode {
    this.children.push(child)
    return child
  }

  updateWorld(parent?: Mat4): void {
    this.world = multiply(parent ?? identity(), this.local)
    for (const child of this.children) {
      child.updateWorld(this.world)
    }
  }
}

三个字段就是本章的概念表：local 是亲手写的账，children 是层级的全部存储，world 是结算出来的账。两处细节值得停一秒。其一，构造时 world 垫一台单位阵——没结算过的节点至少「站在原地」，不会拿旧账当新账。其二，updateWorld 里的 parent ?? identity()：不传父级就当根节点，world = I·local = local 的拷贝；传了父级，world = 父.world·local，随后把自己刚算出的 world 喂给每个子节点——一条递归把整棵树深度优先结算完。add 返回子节点本身，方便一句话搭三层：sun.add(orbit).add(mesh)。

顺带交代一个约定：本库惯例是纯函数，SceneNode 是圣经里声明的例外——children 的递归语义（节点持有节点）用 class 表达最直白。除此之外没有隐藏魔法，字段全部公开。

挂树与建模：自转不拖月亮 ​

树怎么搭，是建模决定。太阳系这份结构里有两处「叶子哲学」：太阳的自转写在 sunMesh（叶子）而不是根上——写在根上，整棵太阳系每转一圈，行星轨道全得跟着打转；同理地球的自转写在 earthMesh（叶子）上，月亮轨道节点挂在 earthOrbit 下、与自转网格平级——否则一天转一圈的地球会拖着月亮疯狂公转。挂谁的下面，就从谁的坐标系里说话——这一刀切在哪，是场景树给设计者的新自由，也是新的责任。测试搭的是这棵树的骨架（省去网格与轨道圈），层级挂法与上图一致：

ts
// tests/scene-graph.test.ts · buildSolarSystem（太阳系骨架，与演示同构）
  const sun = new SceneNode(identity())
  const earthOrbit = new SceneNode(multiply(rotY(rad(orbitDeg)), translate(4, 0, 0)))
  const earthMesh = new SceneNode(rotY(rad(spinDeg)))
  const moonOrbit = new SceneNode(multiply(rotY(rad(moonDeg)), translate(1.5, 0, 0)))
  sun.add(earthOrbit)
  earthOrbit.add(earthMesh)
  earthOrbit.add(moonOrbit)

月亮的世界坐标从此一行对账：transformPoint(moonOrbit.world, [0,0,0])——上一节的 (0,0,−5.5) 就是这么验的。地球自转 90° 也拖不动它：earthMesh 是叶子，rotY 只转网格自己的姿态，原点纹丝不动；月亮是它的兄弟，账面无关。两条断言都在测试里。

层级动画：每帧只改 local ​

updateWorld 还有一条语义值得单独锁住：world 是结算时刻的快照，不是 local 的活引用。改了 local 不结算，world 保持原样——「每帧改 local、结算一次」的节奏由这笔账定义。渲染循环里的三步舞：

ts
// 用法示例：渲染循环里每帧三步——角度前进、按角度重建 local、一次结算
orbitA += dt * orbitSpeed          // 增量时间缩放，帧率不匀也等速
moonA += dt * moonSpeed
earthOrbit.local = multiply(rotY(orbitA), translate(4, 0, 0))
moonOrbit.local = multiply(rotY(moonA), translate(1.5, 0, 0))
sun.updateWorld()                  // 全树一次结算：从根深度优先

注意改的只有两台 local：太阳照常发光、地球网格的自转角另算一台，互不牵连。公转 0°、90°、180° 三帧的世界坐标全部手算可得——地球 (4,0,0)、(0,0,−4)、(−4,0,0)，月亮 (5.5,0,0)、(0,0,−5.5)、(−5.5,0,0)——测试按这三帧逐帧对账。这就是层级动画（hierarchical animation）：动画量全部长在局部矩阵上，层级关系负责把它们组合成世界——父级一动，整棵子树自动跟上，一行传播代码都不用写。

遍历绘制：深度优先走一遍树 ​

画的时候，树要拉平成一串绘制调用。做法是遍历绘制（traversal drawing）：从根出发深度优先递归，访问到每个节点，就把它当时的 world 当模型矩阵画一次。树在递归里被拉直成了 draw 列表：

ts
// 用法示例：遍历绘制——深度优先走树，每个节点用它当时的 world 当模型矩阵
function drawNode(node: SceneNode, draw: (world: Mat4) => void): void {
  draw(node.world)
  for (const child of node.children) drawNode(child, draw)
}

每个节点画完自己的世界矩阵，再依次递归子节点；遮挡照旧交给深度缓冲，画完的顺序不影响结果。轨道圈这类「只画线、不发光」的节点也挂在树里——月亮轨道圈挂在地球轨道节点下，每帧结算出的 world 自动跟着地球走，这正是层级语义最直观的证据（演示里看得到）。

演示：把太阳系挂上树 ​

太阳自转 0.4 地球公转 0.5 地球自转 1.2 月亮公转 1.5

  • 灰圈是地球轨道（世界固定）；暗金圈是月亮轨道，挂在地球队列下、跟着地球走——层级语义的直观证据。
  • 太阳自转写在网格叶子节点上，不拖行星；地球自转写在地球网格上，不拖月亮——挂错层级的账另有风景。

场景树结算：月亮的 local 只写「绕地球」，地球的 local 只写「绕太阳」，世界坐标由链乘自动结算——月亮永远踩在自己的轨道圈上，轨道圈跟着地球走

演示是完整的场景树版太阳系：太阳自转（自发光加经度条纹，让转看得见）、地球公转加自转、月亮绕地球；上方四根滑杆分别调四个角速度，画布下方有三行实时读数。光照贴第 10 章同款 Phong——光源就是太阳自己，地球和月亮逐片元算漫反射。玩法按本章的账走：

  • 拨「地球公转」滑杆、月亮速度归零：看暗金色的月亮轨道圈跟着地球一路绕太阳走——圈是挂在地球轨道节点下的节点，它的世界坐标每帧被链乘结算，这正是「坐标跟着上级走」。
  • 拨「地球自转」到高速：地球条纹飞转，月亮纹丝不动地绕自己的圈——自转写在叶子网格上，拖不到月亮。
  • 勾上「手算版」：月亮立刻脱离场景树，改由每帧手算世界坐标——把月亮在地球坐标系里迈的步子直接加到世界坐标上（只做平移叠加、不做旋转链乘）。看读数第一行：月亮—地球距离在场景树版恒为 1.500，手算版开始来回乱飘、不再钉在 1.5；红色轨迹线就是开章那条飘掉的随机曲线，月亮周期性冲向地球。
  • 取消勾选：月亮回到轨道圈上，读数钉回 1.500——两套写法的差距，一个开关来回切。

验证：手算对账，门槛背书 ​

两道门槛在 companion/ 下跑：pnpm run typecheck 加 pnpm test——102 条断言全绿，旧 94 条一字未动，新 8 条是本章里程碑。手算挑几笔：公转 90° 时地球世界位置 (0,0,−4)、月亮 (0,0,−5.5)，与「地球位置 + 旋转后的局部偏移」的分笔记法逐分量对账；自转 90° 拖不动月亮（月亮世界坐标不动摇）；父级公转角从 0° 转到 180°，moonOrbit.local 的平移列原封 (1.5,0,0)，世界坐标却从 (5.5,0,0) 挪到 (−5.5,0,0)——local 不变、world 随父动；三层链 rotZ(90°)、T(2,1,0)、S(2,2,1) 的叶子 world 与手乘三连积逐元素相等，点 (1,1,0) 落 (−3,4,0)，长度恰 5——3-4-5 三角形又来上班。根节点那条快照语义也锁着：updateWorld 之后改 local，world 保持到下一次结算。

先红的账也如实交代。第一红：测试文件先写好、跑 pnpm test，报错 Failed to load url ../src/scene/node——模块还不存在，这就是渐进语义的机械证明。实现之后 101 绿 1 红，红的那条出在我测试自己的手算上。rotX(90°) 接在 rotY(90°) 后面，点 (1,0,0) 先被 rotY 转到 (0,0,−1)，再过 rotX——rotX 混的是 y、z 两根轴，(0,0,−1) 落 (0,1,0)。我起初想当然写了 (0,0,−1)。改测试、不动实现，全绿。哨兵不认人：实现对了、手算错了，它照样红给你看。

亲手开机：cd companion && pnpm test，看到 10 个测试文件 102 条全绿；再回到上面的演示勾「手算版」，亲眼看到开章那条飘掉的月亮轨道。

小结 ​

本章把「谁跟着谁动」写进了数据结构。场景图是一棵父子上级的树，子节点挂在谁的下面、就在谁的坐标系里说话；局部矩阵是节点相对父级的变换，动画只改它——公转角写进地球轨道节点、月亮角写进月亮轨道节点，谁也不掺和谁的公式；世界矩阵是从根链乘到本节点的总变换，updateWorld 深度优先一次结算，world 是快照不是活引用。建模的新自由与新责任：自转写在叶子网格上，才拖不动行星和月亮。绘制时深度优先遍历，每个节点拿它当时的 world 当模型矩阵——MVP 里的 M 从一台机器升级成一条链，V 与 P 对树一无所知。实验场进账一件：scene/node 的 SceneNode（local、children、world、add、updateWorld），测试总数 102。读者已能搭多层场景、把开章飘掉的月亮轨道解释成「偏移没跟着坐标系转」的一笔账。

概念去向：轨道相机怎么挂在树外由统一变量喂进 V（第 12 章），树加材质加雾怎么装配成可漫游的小世界（第 13 章）。

读完本章，下面几问应该能脱口而出：

  • 公转 90°、月亮角 0° 那一帧，月亮的世界坐标是多少？「地球位置 + 不转的偏移」给的是多少？差在哪一步？
  • 月亮轨道节点为什么挂在 earthOrbit 下、不挂在 earthMesh 下？两种挂法各会看到什么画面？
  • 每帧动画改的是 local 还是 world？改了 local 不调 updateWorld，屏幕上会看到什么？
  • 一条三层链，逐级链乘（父算完传子）与一次性全乘结果为什么相同？哪条数学性质在撑腰？
  • 遍历绘制时，第 7 章的 MVP 流水线图往哪边接了一段？V 和 P 需要知道树的存在吗？
  • 手算版为什么恰好错在「只做平移叠加」？轨道半径 1.5 在两个版本里各是怎么走丢和保住的？
