# 加密在防谁：机密性、完整性与 AEAD

## 5.1 前情：三笔挂了三章的账

三个问题，同一笔账：

- 第 1 章全景图里「加密隧道」那一格——第二跳为什么必须加密、防的到底是谁？
- 第 3 章末尾说「这条链路眼下完全明文」——谁加密、防谁，说好来算账的？
- 第 4 章末尾盘出了裸奔面——谁在哪个位置能看、能改什么，威胁模型等这一章展开？

三笔账同源，本章一次算清。算完你还会发现：「加密」这个词底下装着三样要分头买的东西——其中一样，多数人以为自己买了，其实没有。

## 5.2 防的是谁：把裸奔面换算成威胁模型

上一章末尾你亲手打出过那串十六进制：回执 `00`、长度头、载荷里的 `HTTP/1.1 200 OK`——全是明文。两跳链路的第二跳上，任何能抓包的人——抓包，指用工具把流经线路的字节抄下来看——都读得到这串字，包括 CONNECT 帧里你访问的域名与端口。

你大概以为「加密」要办的就是这件事：把字打乱，让人看不懂。这个直觉对了一半。本章的第一次实验会让你在密文上改一个字节，然后看着解密端若无其事地把内容吐出来——到那一刻你会亲口承认，「看不懂」和「改不了」是两回事，而「加密」要防的人也不止一种。先把「防谁」算成一笔明账。

### 5.2.1 两种对手：旁观者与中间人

给对手画像，用两个一般化的词就够了。

- 线路上的旁观者：流量路径上任何看得到经过字节的一方——同网络里抓包的人、沿途转发的机器。能看，不能改。
- 中间人：不止看，还动手——改字节、换内容、掐断连接。能看，也能改。

看与改要分开立账，因为它们是两种不同的伤害。对第 4 章那台明文中继来说：旁观者读到的是「你在访问谁、说了什么」；中间人还能把帧里的 `amount=100` 改成 `amount=500`——协议没有任何发现改动的手段。防看与防改，接下来要分头买。

### 5.2.2 按位置算账：哪段上锁、防到哪为止

先立词。威胁模型（threat model）——一张先说清「防谁、防什么、不防什么」的清单；不先画清单就谈加密，等于还不知道防谁就开始买锁。

这张表是第 4 章末尾裸奔面盘点的正式版。整条链路照旧是三条独立的 TCP 连接在接力，逐段过账。

| 段 | 谁在这段线上 | 结论 |
| --- | --- | --- |
| 第一跳：浏览器↔入口 | socket 两端都住在你机器的回环地址上，不出机器（第 1 章的系统代理告示牌也只是机器内部的一行设置） | 本书不给这段上锁 |
| 第二跳：入口↔远端 | 穿过网络路径：旁观者读得到 CONNECT 帧里的域名与端口、每一帧的全部内容；中间人还能改任何字节 | **要上锁的就是这一段** |
| 第三段：远端↔目标 | 远端替你直连目标，这段的安全性由目标自己的协议决定：HTTPS 站自带加密，明文 HTTP 站内容照裸 | 不归第二跳的锁管 |
| 远端进程本身 | 它必须知道目标才能代连，因此看得见、也改得动全部往返（HTTPS 的内容连它也只看得见密文；但转交与代连本身必须信它） | 这把锁从来就不打算防它 |

表尾一句诚实的话：加密第二跳，防的是「线路」，不是「远端」——远端是你自己选定、必须信任的一环；线路上的每一方，才是一概不信任的对象。

### 5.2.3 HTTPS 已经加密了，这一跳为什么还要再锁

算到这里，一个正当的疑问该冒出来：我访问的网站大多是 HTTPS，内容本来就有加密，这一跳还用得着吗？

用得着，因为**两把锁，锁的是两个不同的对象**。

- HTTPS 那把锁，锁的是「浏览器↔目标站」这对端点之间的内容。浏览器与目标站握手建立加密通道，任何第三方——包括你的两跳中继——看到的都只是密文。经过你的链路时，帧里搬运的已经是这段密文：内容这一层，确实已经有锁。
- 第二跳这把锁，锁的是「入口↔远端」之间的一切载荷。CONNECT 帧里的目标域名与端口，不在 HTTPS 那把锁的管辖里：就算内容已是密文，「你在访问谁」这条信息本身仍是明文过境。何况链路上还有明文 HTTP 目标——那类帧连内容一起裸。

一句收束：HTTPS 保护「说了什么」，第二跳的锁连「去哪儿」一起保护。对象不同，谁也替代不了谁。

「防谁、防什么、不防什么」都清了。下一节拆「加密」这个词本身——寄一份密件，要办三件事。

## 5.3 原理：寄一份密件要办的三件事

寄一份密件要想安全，要办三件事：信封上锁、封口火漆、火漆上盖你的私章。加密世界把这三件事叫三个目标：机密性、完整性、真实性——对应上锁、火漆、私章。本节逐个拆，每个目标配一段亲手跑的代码；三段代码加一段灾难复现，全部只用 Node 内建的 `node:crypto`，存成 `.mjs` 文件就能跑，不碰实验场。

### 5.3.1 机密性：信封上锁

机密性（confidentiality）——除了持有密钥的人，谁也读不懂内容。锚点：信封上锁——没有钥匙的人拿到信，手里只是一叠纸。

把一段 HTTP 请求封起来，再原样拆开。

```js
// 用法示例：存成 secret.mjs，node secret.mjs（Node ≥ 20）
import { randomBytes, createCipheriv, createDecipheriv } from 'node:crypto'

const key = randomBytes(32)   // 密钥：32 字节 = 256 位随机字节，上锁的那把钥匙——持有者才有
const nonce = randomBytes(16) // 随机数 nonce（number once，一次性编号）：每次加密必喂的新鲜随机数，5.3.5 专讲
const msg = Buffer.from('GET / HTTP/1.1\r\nHost: news.example\r\n\r\n')

const cipher = createCipheriv('aes-256-ctr', key, nonce) // 算法名读作：AES 算法 + 256 位钥匙 + CTR 模式
const sealed = Buffer.concat([cipher.update(msg), cipher.final()])
console.log('线上看到：', sealed.toString('hex')) // 抓包者的视角：看不出任何规律

const dec = createDecipheriv('aes-256-ctr', key, nonce) // 同一把钥匙 + 同一个 nonce，才拆得开
const back = Buffer.concat([dec.update(sealed), dec.final()])
console.log('持钥解回：', back.toString())
```

应看到两行输出：第一行 76 个十六进制字符——38 字节密文，与明文等长，逐位看不出规律；第二行把原文一字不差吐了回来。旁观者截到第一行，看到的就是噪声。

四个读点。其一，密钥（key）——加密所用的那段随机字节，本例 32 字节现造；真实世界的钥匙从密码按标准步骤派生（HKDF），那是第 6 章的活。其二，算法名 `aes-256-ctr` 的三段：AES 是一台一次只能处理 16 字节的块机器；模式是把它接成长流水线的用法；CTR 是其中一种，内部形状 5.3.2 就拆。其三，`createCipheriv` 与 `createDecipheriv` 必须喂同一个 key 加同一个 nonce，两端才对得上暗号。其四，也是本章最重要的一句伏笔：CTR 的解密器永远不会说「失败」——喂它什么字节，它都吐一段「明文」出来。这句先记下，两节之后兑现。

### 5.3.2 完整性：封口火漆

完整性（integrity）——内容在途中改过一个字节，接收方都能发现并拒收。锚点：封口火漆——漆面完好，信才没动过；漆裂了，整封拒收。

先复述一个你可能正持有的想法：「信都上了锁，内容总该动不得了吧？就算有人硬改密文的一个字节，解出来还不成了天书？接收方一看便知有诈。」——听着很稳。在只加密、不认证的模式里，这个想法活不过十行代码。

先猜后跑。预言三选一，写下再跑：中间人在密文里翻一个比特（比特——字节里的一个二进制位），解密端会报错？吐出天书？还是若无其事？

```js
// 用法示例：存成 tamper-ctr.mjs，node tamper-ctr.mjs —— 只加密、不认证的下场
import { randomBytes, createCipheriv, createDecipheriv } from 'node:crypto'

const key = randomBytes(32)
const nonce = randomBytes(16)
const msg = Buffer.from('order=5&amount=100') // 第 15 字节是字符 '1'（0x31）

const cipher = createCipheriv('aes-256-ctr', key, nonce)
const sealed = Buffer.concat([cipher.update(msg), cipher.final()])

const open = (c) => {
  const dec = createDecipheriv('aes-256-ctr', key, nonce)
  return Buffer.concat([dec.update(c), dec.final()]).toString()
}
console.log('原样解回：', open(sealed))

const broken = Buffer.from(sealed)
broken[15] ^= 0x04 // 中间人只翻一个比特：'1'（0x31）与 '5'（0x35）只差这一位
console.log('改动后解回：', open(broken)) // 全程没有任何报错
```

应看到两行：`order=5&amount=100` 与 `order=5&amount=500`。没有报错，没有天书——只有那一个字符变了。而且改动可以是瞄准的：`'1'` 与 `'5'` 只差一个比特，中间人不知道钥匙，但只要知道消息的格式，就能把 100 定点改成 500、900 或任何他想要的数。

为什么瞄得这么准？CTR 的内部形状此刻正好用上。CTR——计数器模式：把一个不断加一的计数块喂给 AES，逐块吐出一串与明文等长的密码流，再把密码流与明文逐字节做异或（xor）——按位比对两个字节，相同出 0，不同出 1。于是密文与明文逐字节一一对齐：密文第 15 字节翻一个比特，明文第 15 字节就翻同一个比特，中间那层密码流完全挡不住。

破产的时刻到了。**只加密，买到的是「看不懂」，买不到「改不了」**——机密性与完整性是两样东西，得分开买。完整性要的是一种「改动必被发现」的手段：好比不只要上锁，还要在封口滴一道火漆——漆面上任何一点破损，收信人都看得出。

### 5.3.3 真实性：火漆上的私章

还有第三件事。前两件防的是「内容动了」；真实性（authenticity）防的是「来信换了」——证明这份密文确实出自持有钥匙的一方，不是中间人整封塞进来的假货。锚点：火漆上盖私章——只有握章的人盖得出这枚印，收信人验漆如验人。

对两跳链路，这一样不是奢侈品：远端中继收到一帧，得知道「这真是入口封的」。第 4 章的远端本来就不设认证，谁连上都请得动它代连。好消息是不用另买——火漆天然兼职私章：漆要用钥匙才算得出，验漆通过，就等于验明「封信的人握着钥匙」。实验就在下一节第三场。

### 5.3.4 认证加密：自带火漆的信封

三样东西分头买，坏在分头拼装：加密与校验的拼法次序错一点就是一整类漏洞，拼法本身就是一门安全课题。现代密码学干脆把它们打包成一件，不许你自己拼。认证加密（AEAD，authenticated encryption with associated data）——一次加密同时买齐机密性与完整性，顺带验明出处：拆信之前先验漆，验不过，整封作废。（名字里的 associated data 指「不加密但一并验」的附加数据，本课用不上，见名不慌即可。）

最常用的 AEAD 具体算法是 AES-GCM——AES 负责加密，GCM 负责算火漆，Node.js 的 crypto 内建。GCM 也是 AES 的一种模式：加密内核正是 5.3.2 那套 CTR 密码流异或，外面多裹一层由密钥与全部密文算出的校验——校验就是火漆。

先猜后跑，右半场。同一个单比特改动（`'1'` 翻成 `'5'`），这回交给自带火漆的信封——预言解密端会怎样？写下再跑。

```js
// 用法示例：存成 aead.mjs，node aead.mjs —— 同样的改动，交给自带火漆的信封
import { randomBytes, createCipheriv, createDecipheriv } from 'node:crypto'

const key = randomBytes(32)   // 只有入口与远端知道的共享钥匙
const nonce = randomBytes(12) // GCM 的惯例长度：12 字节（96 位）
const msg = Buffer.from('order=5&amount=100')

const cipher = createCipheriv('aes-256-gcm', key, nonce)
const ct = Buffer.concat([cipher.update(msg), cipher.final()])
const tag = cipher.getAuthTag() // 16 字节火漆：密文全部到齐后，由钥匙与全部密文算出

const open = (k, c, t) => {
  // 接收端：先递上随信到达的火漆；update 吐出的只是未验漆的草稿，final 才验漆
  const dec = createDecipheriv('aes-256-gcm', k, nonce)
  dec.setAuthTag(t)
  return Buffer.concat([dec.update(c), dec.final()]).toString()
}

const broken = Buffer.from(ct)
broken[15] ^= 0x04 // 与 tamper-ctr.mjs 完全相同的单比特改动
try { console.log('改动后：', open(key, broken, tag)) }
catch { console.log('改动后：拒收（火漆对不上，整封作废）') }

try { console.log('错钥匙：', open(randomBytes(32), ct, tag)) }
catch { console.log('错钥匙：拒收') }

console.log('原样：', open(key, ct, tag)) // 原封不动 + 正确钥匙，才放行
```

应看到三行：改动后拒收、错钥匙拒收、原样放行。对照 5.3.2 那两行——同一个攻击，只加密的模式照单全收，AEAD 整封作废。

火漆的 API 语义，四条钉死。其一，`getAuthTag()` 必须在 `final()` 之后调用：16 字节的火漆要等密文全部到齐才算得出，它是「这一整封密文」的检验章，不是逐段的散记。其二，火漆不保密——它跟着密文明文上路。它的价值不在藏，而在改不得：动密文或动火漆，验证必不过（5.5 有亲手验它的动作）。其三，解密端先 `setAuthTag(tag)` 递上随信到达的火漆，再 `update` 与 `final`；验漆发生在 `final()`，不对就抛错，Node 的报错文案是 `Unsupported state or unable to authenticate data`，大意为「无法认证数据」。其四，`update()` 吐出的明文只是未验漆的草稿——工程规矩：走完 `final()` 确认不抛，才许使用解出的内容。

三场对号入座：改一字节拒收，完整性在办事；错钥匙拒收，真实性在办事——漆只有握钥匙的一方算得出，验漆即验人；原样且持钥放行，机密性照常。**上锁、火漆、私章，一封信全办**。

### 5.3.5 随机数 nonce：每次都要新

回头看 5.3.1 留下的那味原料。随机数 nonce（number once，一次性编号）——AEAD 每次加密都要喂的新鲜随机数：同一段话封两次、密文不同，全靠它。

为什么非它不可？因为加密本体是一台死板的确定性机器：同一把钥匙加同一段输入，永远得到同一串输出。不带 nonce，同一段明文每次都封成同一串密文——「这两条连接在发同一个请求」这种等值规律本身，就是泄露。带上了，每封信至少多一味每封不同的随机佐料，规律被打散。

纪律用规范的话说（对照 NIST SP 800-38D，GCM 的规范性文件）。同一把密钥之下，nonce 绝不重复——这是 GCM 的头号纪律。用随机数当 nonce 时，同一把密钥的调用次数有上限：规范把随机用法的加密次数限在 `2^32` 次以内，撞车概率才小到可以忽略。长度有惯例：12 字节（96 位）——`aead.mjs` 里那行 `randomBytes(12)` 就是它，而 `secret.mjs` 的 CTR 用 16 字节，两种模式各按各的惯例。

nonce 本身不保密：它跟着密文明文上路毫无损失——它防的是「重复」，不是「被看见」。真正的灾难不是 nonce 泄露，是 nonce 复用。有多灾难？下一节亲手复现。

## 5.4 演练：nonce 重复的灾难现场

本章最后一场先猜后跑。两段明文只差四个字母：`news.example` 与 `mail.example`。同一把钥匙、同一个 nonce，各封一次。旁观者把两段密文逐字节异或——结果长什么样？一串乱码？全零？还是别的什么？写下预言再跑。

```js
// 用法示例：存成 nonce-reuse.mjs，node nonce-reuse.mjs —— 同一把钥匙、同一个 nonce，用两次
import { randomBytes, createCipheriv } from 'node:crypto'

const key = randomBytes(32)
const nonce = randomBytes(16) // 全场只此一个：灾难就藏在这一行
const first = Buffer.from('GET / HTTP/1.1\r\nHost: news.example\r\n\r\n')
const second = Buffer.from('GET / HTTP/1.1\r\nHost: mail.example\r\n\r\n') // 只差四个字母

const seal = (msg) => {
  const c = createCipheriv('aes-256-ctr', key, nonce) // 同 key + 同 nonce → 同一串密码流
  return Buffer.concat([c.update(msg), c.final()])
}
const ca = seal(first)
const cb = seal(second)

const xored = Buffer.alloc(ca.length)
for (let i = 0; i < ca.length; i++) xored[i] = ca[i] ^ cb[i] // 旁观者的全部功课：逐字节异或
console.log('密文异或：', xored.toString('hex'))

const guess = Buffer.alloc(ca.length)
for (let i = 0; i < ca.length; i++) guess[i] = ca[i] ^ cb[i] ^ first[i] // 再猜中其中一段明文
console.log('还原另一段：', guess.toString())
```

应看到第一行 76 个十六进制字符：头 22 个字节全是 `00`，中间 `03 04 1e 1f` 四个非零字节，剩下的又全是 `00`。第二行把第二段明文整段打了出来——而旁观者手里只有两段密文。

读图。那四个非零字节的位置，恰好是 `news` 与 `mail` 相异的四个字母位；数值也逐对对得上：`n` 与 `m` 异或是 `03`，`e` 与 `a` 是 `04`，`w` 与 `i` 是 `1e`，`s` 与 `l` 是 `1f`。**密文的差，恰好就是明文的差**。原因一句话讲完：同一把钥匙配同一个 nonce，两段用的是同一串密码流；异或的数学里那串流自己消掉，只剩「密文一异或，等于明文一异或」。

再升一级。旁观者若猜中其中一段——HTTP 请求头是公开格式，猜中并不难——另一段就整段还原：脚本第二行就是这么算的，一个字节的钥匙都不需要。这不是「有朝一日密钥可能算出来」的远期风险，是差异结构当场挂在线上。

结论与纪律：nonce 复用的灾难不等将来、不用破钥，密文的规律当场可见。GCM 同样逃不掉——它的加密内核就是 CTR，这道数学原样成立；NIST 把「同一把密钥下 nonce 唯一」列为头号纪律，分量就在这里。工程做法很朴素：每条连接现生成一个新随机 nonce，随首帧发给对端——第 6 章把这套连同密文帧一起接进两跳链路。

## 5.5 验证：四个动作，先猜后跑

1. 依次跑 5.3 与 5.4 的四个脚本，核对关键输出。应看到：`secret.mjs` 一行噪声密文加一行解回原文；`tamper-ctr.mjs` 的 `100` 变 `500` 且全程无报错；`aead.mjs` 两条拒收一条放行；`nonce-reuse.mjs` 的 `00` 串夹 `03 04 1e 1f` 加整段还原。
2. 火漆也是受验的对象。在 `aead.mjs` 里复制一份火漆并翻一个比特——`const t2 = Buffer.from(tag); t2[15] ^= 1`，把 `t2` 传给 `open`。跑之前先预言：放行还是拒收？应看到拒收。火漆自己动了，同样整封作废。
3. 差多少，漏多少。把 `nonce-reuse.mjs` 第二段明文里的 `mail.example` 换成 `mews.example`——与第一段的 `news.example` 只差一个字母。先预言非零字节还剩几个。应看到恰好一个非零字节（`n` 与 `m` 异或出的 `03`）——明文差一个字节，异或图上就亮一个点。
4. 确定性机器。在 `secret.mjs` 末尾用同一把 key 与同一个 nonce 再封一次同一段话，再用同一把 key 配一个新 nonce 封第三次。先预言两次密文。应看到：前者与第一次逐字节相同，后者全然不同——让输出「变新鲜」的唯一入口，就是 nonce。

## 5.6 收束：看不懂，与改不了

回到开篇那个直觉：「加密就是把字打乱」。现在你能亲口讲出另一半：打乱只买到机密性；只加密的模式面对改一个比特的密文，若无其事地照解不误——5.3.2 里你亲手把 100 改成了 500。AEAD 把三样一次配齐：先验火漆、再拆信，改一字节或换钥匙都整封作废；而火漆担保的前提，是 nonce 从不重复——5.4 那张异或图就是复用的下场。

三笔挂账，这一章一起清。第 1 章问「第二跳为什么必须加密、防的是谁」；第 3 章问「这条链路明文，谁加密、防谁」；第 4 章要「裸奔面的威胁模型」——答案就是 5.2 那张表：上锁的是入口↔远端这一段，防的是线路上的旁观者与中间人；不防、也不打算防远端进程，它必须知道目标才能代连；HTTPS 是另一把锁，锁的是浏览器↔目标站的内容，替代不了这一把。

你手里的新能力是可迁移的：用 `node:crypto` 完成封缄、定点篡改、验拒、复用灾难四类实验——不进实验场，一台 node 就够。概念去向地图：

- 明文帧换密文帧——下一章主角：每条连接现配钥匙（盐与 HKDF 派生）与 nonce，载荷逐帧 AEAD 封缄，第 4 章留好的帧接缝正是为此；
- 谁走哪条线（规则引擎）、名字怎么接管（fake-ip）——第三部分接着拆。
