# 打开 Clash 之后，流量经历了什么

## 1.1 同一个开关，两种结局

你大概见过这一幕：点开 Clash 的开关，托盘图标亮起，某些一直转圈打不开的网页，刷新一下竟然开了。没有重装任何应用，也没改一行代码——变化的只是系统设置里多了一个「系统代理」的小勾（操作系统里一条『本机代理在哪』的告示，1.3 节拆开讲）。

同一台机器上还藏着另一半现象：一个没重启的命令行工具，去访问同一个站点，照样连不上。

同一个开关，浏览器立刻见效，命令行纹丝不动。这不是玄学，也不是故障——它是一条指纹，指向同一件事：**开关背后没有总闸，只有一块告示牌**。这一章先画出流量经过的完整全景图，再补齐看懂它所需的最小地基。读完你能亲口解释那台命令行为什么连不上，也能说出接下来每一章在造哪个零件。

## 1.2 三个角色：一次请求的完整路径

先回答书名那个问题：流量到底经历了什么。

Clash 这类工具在流量里扮演的角色，叫正向代理（forward proxy）——替客户端去访问服务器的中间人：你把请求交给它，它替你跑腿，目标站只看到它，看不到你的机器。锚点：公司前台代收快递——你把包裹交前台，前台替你跑腿，收件方只见前台。

> 边界说明：代理与隧道技术在不同地区受不同法规约束。本书只讨论协议与工程原理，全部实验都在本机内部完成，不提供任何真实节点信息——请在遵守当地法律法规的前提下学习。

（有个方向相反的亲戚叫反向代理（reverse proxy）——替服务器收请求的中间人，用户只见它、见不到真正的服务器。本课只做正向这一侧，这个词到此为止。）

正向代理不是一根直通的管子，里面是三个角色接力：

```text
浏览器 ──① 交出──▶ 本地入口（住在本机内部，门牌形如 127.0.0.1:7890）
                       │
                       ② 分流决策：这条连接走哪条线？
                       ├── 直连 ─────────────▶ 目标站 A
                       └── ③ 加密隧道 ──▶ 远端服务器 ──④ 代访──▶ 目标站 B
```

拿「浏览器打开目标站 B」把全程走一遍：

1. 浏览器看一眼告示牌（系统代理设置），得知入口住在本机内部。它不自己连 B，改连入口，并说明「我要去 B」。
2. 入口把「B」交给分流决策——拿目标查规则表、决定这条连接走哪条线的部件。判决两种：直连，或走隧道。
3. 判决是隧道：入口把请求装进加密隧道（内容先加密再上线的通道），发给远端服务器——替你出网的那台机器上的中继程序。
4. 远端服务器收到、解开，替浏览器去敲 B 的门。**目标站 B 看到的敲门人是远端服务器，不是你的机器**。
5. 响应原路返回：B → 远端服务器 → 入口 → 浏览器。

三个角色各管一段：入口负责「把流量从应用手里接过来」，分流决策负责「谁走哪条线」，隧道与远端负责「换一个位置出网」。隧道这一跳为什么必须加密、防的到底是谁——第 5 章专门算这笔账，这里先记下。

图里那串 `127.0.0.1:7890` 是入口的门牌。看懂它、也看懂后面所有实验，需要五个地基词，每个配一段你能亲手跑的代码——下一节逐个拆。

## 1.3 为什么命令行连不上：告示牌，不是总闸

现在拆开 1.1 的谜。

你可能以为：开关的名字叫「系统代理」，听着就像全机总闸——一开，整机所有流量自动改走代理。这个直觉很自然：不这样想，怎么解释浏览器立刻见效？

但「总闸假设」活不过那台命令行。反事实摆在眼前：**假如开关真是总闸，它没有理由放过命令行**——总闸不挑应用。现实是命令行工具照旧自己连目标、照旧连不上。能同时解释两种结局的只有一个结论：根本没有总闸。

系统代理的真实身份朴素得多：操作系统设置里的一条记录，内容大致是「本机代理在 `127.0.0.1:7890`」。它不拦任何流量，也不接管网卡，只是一块告示牌。应用自愿读它：

- 浏览器这类守规矩的应用，发请求前看一眼告示，把流量交给入口——于是走了代理，某些网络环境下经直连不可达的站点，经由远端就可达了。
- 大多数命令行工具默认不理会这行设置（它们认的是另一套环境变量——操作系统递给每个进程的一张配置小抄），照旧自己直连目标——直连不通的，照样不通。重启它也一样：它从头就不看这块牌子。

**系统代理是自愿的，不是强制的**。读告示的走代理，不读的留在外面。这也埋下本书后段的一条动力线：自愿机制罩不住的应用，得换一种从网络层收口的接管方式才治得了——那招叫 TUN 虚拟网卡，第 9 章动手写它的报文解析。

## 1.4 地基实验：五个必须亲手摸过的词

五个地基词按依赖顺序一个个来：先懂连接，再懂数字门牌，然后是本机内线，最后是字节的本性。每个词一句人话、一段代码——把代码存成 `.mjs` 文件用 node 跑：零依赖、不联网、全程不出你这台机器。

### TCP 连接与 socket：先拨号，再说话

TCP 连接（TCP connection）——两台机器之间先「拨号接通」、再双向传字节、传完「挂断」的一条可靠通道。socket——程序里代表这条连接的那个对象：往里写字节、从里读字节、关掉它，全是对它做操作。锚点就是打电话：拨号接通、双向说话、挂断。

```js
// 用法示例：存成 tcp.mjs，node tcp.mjs（Node ≥ 20）
import net from 'node:net'

const server = net.createServer((socket) => {    // 每接通一条连接，回调交给你一个 socket
  socket.on('data', (buf) => socket.write(buf))  // 收到什么就原样写回去：回声
})
server.listen(0, '127.0.0.1', () => {            // 端口一栏填 0：请系统随手分一个空闲的
  const { port } = server.address()
  const client = net.connect(port, '127.0.0.1', () => {
    console.log('接通了——一条 TCP 连接建立')      // 拨号接通
    client.write('hello')                        // 对着 socket 写字节
  })
  client.on('data', (buf) => {
    console.log('听到回声：', buf.toString())     // 从 socket 读字节
    client.end()                                 // 挂断
    server.close()
  })
})
```

应看到两行输出：先「接通」，后「回声 hello」。这段代码同时给了两个词的实体——「接通了」那行是 TCP 连接的建立；代码里的 `socket` 和 `client` 是这条连接两端的把手，读写字节全靠它们。本书后面的所有角色——浏览器、入口、远端、目标站——两两之间都是这样成对的 socket。

### 端口：楼栋里的房间号

端口（port）——同一台机器上区分不同服务的房间号：IP 找到楼，端口找到房间。一台机器同时跑几十个服务，全靠端口互不串门。

```js
// 用法示例：存成 port.mjs，node port.mjs（两行输出先后不定）
import net from 'node:net'

const server = net.createServer(() => {})
server.listen(0, '127.0.0.1', () => {
  const { port } = server.address()
  // 敲一间几乎不可能有人的房间：1 号端口平时没有任何服务
  net.connect({ port: 1, host: '127.0.0.1' })
    .on('error', (e) => console.log('敲没人的房间：', e.code))   // ECONNREFUSED
  // 再开一个服务器，抢占同一个已占的端口
  const dup = net.createServer(() => {})
  dup.listen(port, '127.0.0.1')
  dup.on('error', (e) => console.log('抢占已占的房：', e.code))  // EADDRINUSE
})
setTimeout(() => process.exit(0), 500)           // 演示收尾：半秒后退出
```

两个报错各说一件事：ECONNREFUSED——这间房没人监听，门敲不开；EADDRINUSE——房间已有主，一个端口同一时刻只归一个进程。回头看告示牌里的「7890」：那是 Clash 入口占的房间号，浏览器的流量都往这间房送。

### 回环地址：自己打给自己的内部分机

回环地址（loopback address）——`127.0.0.1`，「自己连自己」的内部地址：流量不出网卡、不出机器，在你电脑内部转一圈就到。锚点：大楼里的内部分机，拨了只在楼内转接，从不占外线。

```js
// 用法示例：存成 loopback.mjs，node loopback.mjs（把 Wi-Fi 关掉再跑，照样通）
import net from 'node:net'
import os from 'node:os'

const lan = Object.values(os.networkInterfaces()).flat()
  .find((i) => i && Number(i.family) === 4 && !i.internal)?.address
const server = net.createServer((s) => s.end())
server.listen(0, '127.0.0.1', () => {            // 只在内部分机上「开业」
  const { port } = server.address()
  const inner = net.connect(port, '127.0.0.1', () => {
    console.log('127.0.0.1：接通（流量没出这台机器）')
    inner.end()
    if (!lan) { console.log('本机没有其他地址，跳过对照'); return server.close() }
    const outer = net.connect({ port, host: lan })
    outer.on('connect', () => { console.log('外线竟然通了：这台机器网络特殊，少见'); outer.end(); server.close() })
    outer.on('error', () => { console.log(`本机网卡地址 ${lan}：敲不开`); server.close() })
  })
})
setTimeout(() => process.exit(0), 1000)          // 演示收尾：外线若被防火墙静默丢弃也不至于挂死
```

多数机器上你会看到两行：内线接通、网卡地址敲不开（报 ECONNREFUSED）。这正是「内部分机」的含义：只绑在 `127.0.0.1` 上的服务，只有本机的进程够得着。系统代理指向 `127.0.0.1`，等于宣布「入口就住在你自己机器里」。也正因为它，本课全部实验不用出门：入口、远端、目标站，全开在你本机的回环地址上。

（那流量怎么「出去」？真实部署里，远端服务器在另一台机器上；教学版把它也搬进本机——链路的形状一点不变，只是两端都住在你家里。「两跳链路」一章会把这两跳真正接起来。）

### 字节流：TCP 不保管「消息」边界

字节流（byte stream）——TCP 交给你的只是一串先后到达的字节，没有「一条消息」的边界：写两次，可能拼成一段到。这是全书最要紧的一课，先猜后跑。

先猜：客户端接连写了 `'hello'` 和 `'world'` 两条「消息」，服务端的 `data` 事件会触发几次？写下你的预言，再跑：

```js
// 用法示例：存成 stream.mjs，node stream.mjs
import net from 'node:net'

let events = 0
const server = net.createServer((socket) => {
  socket.on('data', (buf) => {
    events += 1
    console.log(`第 ${events} 次 data：${buf.toString()}`)
  })
})
server.listen(0, '127.0.0.1', () => {
  const { port } = server.address()
  const client = net.connect(port, '127.0.0.1', () => {
    client.write('hello')                        // 第一条「消息」
    client.write('world')                        // 第二条「消息」
    client.end()
  })
})
setTimeout(() => process.exit(0), 300)
```

多数机器上你会看到一次 `data`，内容是 `helloworld`——你写的两次，在接收端合成了一个事件。TCP 承诺的只是「字节按顺序到、不丢不重」，从不承诺「按你写的次数到」。**边界要靠协议自己画**：HTTP 的头部用换行画（正文的画法第 2 章拆），你后面要写的 SOCKS5 和加密帧用「先报长度、再给内容」画——这本书一半的代码，都在给字节流画边界。

## 1.5 验证：把全景图串成你自己的话

三个动作，每个都有应看到的结果：

1. 依序跑 1.4 的四个实验。应看到：tcp.mjs 两行输出；port.mjs 两个报错码 ECONNREFUSED 和 EADDRINUSE；loopback.mjs 内线接通；stream.mjs 的 `data` 次数不多于 write 的次数。
2. 再来一次先猜后跑：把 stream.mjs 的两次 write 改成间隔 100 毫秒（提示：用 `setTimeout` 把第二次 write 推迟）。跑之前先写下预言。应看到 `data` 大概率变成两次——时间把两段字节分开了；但边界依然没人标记，只是「碰巧」分开。
3. 打开你操作系统的代理设置页（Windows：设置 → 网络和 Internet → 代理；macOS：系统设置 → 网络 → 详细信息 → 代理）。装着 Clash 且开着的话，应看到形如 `127.0.0.1:7890` 的一行。现在你能说出它的两个成分：回环地址——入口住在本机内部；端口——入口占的房间号。没装也不影响：那一栏本来就是关的——告示牌一直在那，写没写字而已。

## 1.6 收束：托盘图标亮起时，发生了什么

回到开头的开关。现在你能亲口讲出两种结局的完整因果：开关做的事，只是往系统设置的告示牌上写一行「入口在 `127.0.0.1:7890`」。浏览器守规矩，读告示、连入口，流量进入「入口 → 分流决策 → 加密隧道 → 远端」的接力，经远端可达的站点于是打开；命令行工具不读告示，照旧直连，直连不通的照样不通。**没有总闸，只有告示牌——读告示的走代理，不读的留在原地**。

你手里已经有全书的地基词汇：正向代理、系统代理、socket、TCP 连接、端口、回环地址、字节流；你已经在回环地址上亲手建立过 TCP 连接、见过端口报错、验证过内线外线、目睹字节流合并。接下来把这些词造成零件——概念去向地图：

- 入口怎么把流量接过来：HTTP 与 SOCKS5 两种入口协议，接下来两章；
- 加密隧道防的是谁：「加密在防谁」和「加密隧道」两章，第二部分；
- 谁走哪条线：规则引擎、域名解析的接管、罩住全机流量的 TUN，第三部分；
- 配置文件、代理组与端到端总装，第四部分。

### 自查

1. 预测：把 stream.mjs 两次 write 之间的间隔去掉（恢复成背靠背连写），`data` 会触发几次？如果某台机器上仍看到两次，能说明「消息边界」存在吗？
2. 指认：一次经隧道访问目标站 B 的请求，B 站的站长事后查连接日志，他看到的来源 IP 属于谁？从浏览器到 B，一共几条独立的 TCP 连接？
3. 迁移：把浏览器的代理设置指向 1.4 的回声服务器 tcp.mjs，浏览器还能正常上网吗？为什么？

::: details 参考答案与锚点
1. 多半一次。仍看到两次也不能说明边界存在——TCP 只保证字节按序到达，分组（网络上一次运的那一小包字节）只是碰巧；边界要靠协议自己画（回查 1.4「字节流」一节）。
2. 来自远端服务器的地址。浏览器→入口、入口→远端、远端→B，共三条独立的 TCP 连接在接力——代理链路从来不是一根管子穿到底（回查 1.2 全景图与五步路径）。
3. 不能。浏览器会按代理的规矩对它说话，但回声服务器听不懂任何规矩，只会把收到的字节原样弹回去，浏览器等不到合法应答，报错收场。这说明入口是一项「必须按协议办事」的服务——随便一个监听端口当不了入口，接下来两章就写它必须听懂的两种话。
:::
