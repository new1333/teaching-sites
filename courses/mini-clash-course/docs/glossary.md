# 术语表

全书术语按中文词条排列，每条一句话大白话定义；正文中每章首教的术语以「术语（英文）——解释」的形态就地展开，本表是集中翻查的那一份。

| 术语 | 英文 | 一句话定义 |
| --- | --- | --- |
| 正向代理 | forward proxy | 替客户端去访问服务器的中间人——你把请求交给它，它替你跑腿，目标网站只看到代理。 |
| 反向代理 | reverse proxy | 替服务器接收请求的中间人——用户只看到它，看不到后面真正的服务器（与正向代理方向相反，本课只做对照）。 |
| 系统代理 | system proxy | 操作系统级的一个开关：应用「自愿」读取它并把流量交给代理——不读它的应用就不走代理。 |
| socket | socket | 程序里代表一条 TCP 连接的对象——可以往里写字节、从里读字节、关掉它。 |
| TCP 连接 | TCP connection | 两台机器之间先「拨号接通」再双向传字节、传完「挂断」的一条可靠通道。 |
| 端口 | port | 同一台机器上区分不同服务的房间号——IP 找到楼，端口找到房间。 |
| 回环地址 | loopback address | 127.0.0.1——「自己连自己」的内部地址，本课全部实验都在它上面跑，不出机器。 |
| 字节流 | byte stream | TCP 给你的只是先后到达的一串字节，没有「消息边界」——切分要靠协议自己约定。 |
| HTTP 报文 | HTTP message | HTTP 通信的基本信件：信封（请求行/状态行 + 头部）+ 信纸（正文），按固定格式拼的字节。 |
| 请求行 | request line | HTTP 请求的第一行：方法 + 目标 + 版本，如 GET http://a.com/ HTTP/1.1。 |
| 绝对地址形式 | absolute-form | 走代理时浏览器把请求行里的目标写成完整 URL（含 http://域名）——这是「告诉代理去哪」的信号。 |
| CONNECT 隧道 | CONNECT tunnel | HTTPS 走代理的办法：先让代理拨通目标，之后代理只当双向透传的管道，看不到加密内容。 |
| SOCKS5 | SOCKS Protocol Version 5 | 一个字节级的代理协议：先握手协商认证方式，再报目标地址，成功后透传任意字节。 |
| 大端序 | big-endian | 网络字节序：多字节数字「高位在前」的排法，如端口 80 写成 00 50。 |
| 字节协议 | binary protocol | 报文里没有「行」也没有分隔符、只有位置的一种协议——第几个字节是什么意思，全靠双方约定的表，任何字节值都合法出现、永远不需要转义。 |
| 目标地址类型 | ATYP | SOCKS5 报文里声明目标地址形态的一个字节：1=IPv4、3=域名、4=IPv6。 |
| 两跳链路 | two-hop chain | 浏览器→本地代理是第一跳，本地代理→远端服务器是第二跳，目标网站只见远端服务器。 |
| 中继 | relay | 把两条 socket 对接起来、双向搬运字节的操作——代理数据面的主体。 |
| 帧 | frame | 自定义链路上的一段定界数据单元：头部写清长度，后面跟载荷，字节流因此有了边界。 |
| 机密性 | confidentiality | 加密要防的第一件事：除了持有密钥的人，谁也读不懂内容。 |
| 威胁模型 | threat model | 一张先说清「防谁、防什么、不防什么」的清单——不先画清单就谈加密，等于不知道防谁就开始买锁。 |
| 真实性 | authenticity | 加密要防的第三件事：证明这份密文确实出自持有钥匙的一方，不是中间人整封塞进来的假货。 |
| 完整性 | integrity | 加密要防的第二件事：内容在途中被改过一个字节，接收方都能发现并拒收。 |
| 认证加密 | AEAD | 同时做到加密+防篡改的现代加密方式：先验「火漆」再解密，验不过整段作废。 |
| AES-GCM | AES-GCM | 最常用的 AEAD 具体算法：AES 加密配 GCM 校验，Node.js crypto 内建。 |
| 随机数 nonce | nonce | AEAD 每次加密都要喂的「一次性编号」——同一段话加密两次密文不同，全靠它；重复使用是灾难。 |
| 盐 | salt | 每次会话随机生成的公开字节串——掺进密钥派生，让每条连接的密钥都不同，旧密文不被攒起来统一破解。 |
| 密钥派生 | key derivation / HKDF | 不直接拿密码当密钥，而是用密码+盐按标准步骤（HKDF）现配一把本会话密钥。 |
| 长度前缀分块 | length-prefixed chunking | 把字节流切成小块、每块先发「加密后的长度」再发「加密后的内容」——既恢复边界又防篡改长度。 |
| 规则引擎 | rule engine | Clash 的分流大脑：拿目标（域名/IP）按配置的规则顺序逐条试，命中即决定走直连还是代理。 |
| 域名后缀规则 | DOMAIN-SUFFIX | 「以某域名结尾就走这条线」的规则，如 DOMAIN-SUFFIX,google.com 匹配 mail.google.com。 |
| 网段规则 | IP-CIDR | 按目标 IP 所在网段匹配的规则，如 192.168.0.0/16 匹配 192.168.x.x 全部地址。 |
| IP 地址与 CIDR | IP address & CIDR | IP 地址是 32 位编号的点分写法（每段 8 位）；CIDR 在它后面加斜杠前缀长度，如 /24 表示前 24 位是网段——刀口想落在哪一位都行。 |
| 兜底规则 | MATCH | 规则表的最后一条「其余全部」——前面都没命中时按它走，Clash 里通常写作 MATCH,DIRECT。 |
| DNS | Domain Name System | 把域名翻译成 IP 的电话簿系统——应用连网前通常先查它。 |
| A 记录 | A record | DNS 电话簿里「域名→IPv4 地址」的那一行。 |
| DNS 污染 | DNS poisoning | 查询被半路截胡、塞回一个假 IP——浏览器拿着假门牌当然连不上。 |
| DNS 泄露 | DNS leak | DNS 查询本身是明文的：链路上每个中转都看得见你要访问哪个域名——哪怕后续连接全走加密。 |
| fake-ip | fake-ip | Clash 的一招：DNS 查询不真去查，先发一个保留网段的假 IP 应急，同时把真域名记在账上，连接时再还原。 |
| TUN 虚拟网卡 | TUN device | 操作系统里一根「虚拟网线」：整机流量先流进它，交给用户态程序处理——系统代理罩不住的应用也逃不掉。 |
| 五元组 | 5-tuple | 识别一条 TCP 连接的五项信息：源 IP、源端口、目的 IP、目的端口、协议——代理进程靠它把一包包字节归回各自的连接。 |
| IP 头部 | IP header | 每个 IP 包开头 20 字节左右的固定格式元数据：版本、总长、源/目的 IP 等。 |
| 报文段 | TCP segment | TCP 层的包：头部（端口、序号、标志位）+ 载荷，多个段按序号重组成字节流。 |
| 声明式配置 | declarative config | 只写「要什么」不写「怎么做的」的配置文件——Clash 的 YAML 就是它（本课用 JSON 教同构语义）。 |
| 代理组 | proxy group | 把若干节点打包成一个可切换出口的虚拟节点——应用永远只见组，组内选谁由策略定。 |
| 自动测速组 | url-test group | 一类代理组策略：定期对组内节点发探测请求，谁延迟低选谁。 |
| 延迟探测 | latency probe | 给节点发一个小请求并掐表——衡量节点「快不快」的标准动作。 |
| 直连 | DIRECT | Clash 里的特殊出站：不走任何代理节点，本机直接连目标。 |
