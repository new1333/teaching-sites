# 回望：Electron、Tauri 与原生绑定的同一原理

面试或选型时被问「Electron 为什么装出来 100 多 MB、Tauri 只要几 MB」「为什么 Electron 应用常驻内存动辄几百 MB」「该选哪个」，背营销话术的人给出的答案是「Electron 笨重、Tauri 轻快」。这种回答的问题不在结论对错，而在**说不出为什么**——追问两句就露馅。这门课写到第 10 章，你手里已经有一个自制内核，所有流派的方案都能拆成它的零件，差异一目了然。这一章做一次总装验收：同一原理，三种取舍。

## 先把原理钉成一句话

十章浓缩成一张图：**原生世界（窗口资源表 + 消息循环）↔ 序列化边界（binding）↔ JS 世界（注入的全局 API）**，事件从队列回流成回调，能力从桥借出成函数。所有「JS 做桌面端」的方案无一例外是这个结构，它们只在一个问题上分道扬镳：**渲染进程那一侧的「界面引擎」从哪儿来**。

## Electron：背一整个浏览器来

Electron 的渲染进程 = 完整的 Chromium（Blink 渲染引擎 + V8 + 整套 Web API）+ 一层桥接口。第 7 章说过这个选择的动因：「用 Web 技术写桌面界面」的完整含义是 DOM、CSS、全套浏览器行为，自己造等于重写浏览器，所以干脆链接一个进来。

用自制内核对照：我们的 `renderUI` 换成「把 UI 树画成像素」的完整实现（Chromium 干的就是这个），`manager` 换成真窗口管理，binding 换成 C++ 级绑定，其余结构原样保留。代价与收益都来自这一个决定：收益是界面层生态全盘继承（npm 前端库、CSS、DevTools）、跨平台行为高度一致（每台机器都跑同一版 Chromium，不必管系统差异）；代价是体积（Chromium 本体）与内存（每个渲染进程一套引擎）。另外它继承了第 7 章的多进程模型：崩溃隔离与权限收缴做得很完整，主/渲染/preload 三层职责清晰——**100MB 不是「没优化」，是「把一致性装进了安装包」**。

## Tauri：用系统自带的，桥换成 Rust

Tauri 的答案：渲染层不背引擎，用操作系统自带的 WebView（Windows 上 WebView2、macOS 上 WKWebView、Linux 上 WebKitGTK）；系统层的 binding 与主进程换成 Rust 程序。对照自制内核：`manager` 和桥（binding 层）由 Rust 实现，渲染侧还是「某个 Web 引擎 + 注入的 JS API」，只是这个引擎是 OS 的、按需拉起。

于是取舍反转：安装包只剩你的代码加一层壳（几 MB），内存基线也低。但一致性账单换了债主——**不同系统的 WebView 行为有差异**（老 Windows 还得考虑 WebView2 分发），你的界面实际上跑在「N 个不同版本引擎」上，跨平台调试成本从「打包体积」转移到了「行为差异」。IPC 语义也更严：Tauri 的命令桥 Rust 侧显式声明、参数走 serde 序列化——第 8 章那条「只过纯数据」的规则，在它那里是白纸黑字的编译期约束。

## Qt 绑定 / 原生 FFI：不要 Web 界面

第三条路（如 Qt 的 JS 绑定、Node 的原生 GUI 绑定）：界面根本不用 Web 技术做。JS 直接绑到原生 GUI 工具包——对照自制内核：我们 `renderUI` 的 UiNode 树换成 Qt 的控件树，每个控件都是 binding 暴露的句柄（第 5 章的遥控器直接对应 Qt 的对象代理）。这条路的收益是性能与包体（没有浏览器引擎，控件是原生绘制）；代价是**界面生态全靠自己**——没有 CSS、没有现成组件库，binding 面有多大你能用的控件就有多少，且原生绑定层的维护成本（版本升级、内存安全、线程规则）真实存在。它适合控件不多、追求轻量的工具类应用。

## 同一张零件表

| 零件（自制内核） | Electron | Tauri | Qt 绑定 |
|---|---|---|---|
| 界面引擎（renderUI 的真身） | 自带 Chromium | 系统 WebView | 原生控件，无引擎 |
| binding 层 | C++ 绑定 | Rust 命令桥 | 语言绑定/FFI |
| 进程模型 | 完整多进程 | 壳进程 + WebView | 通常单进程 |
| 序列化边界 | 结构化克隆 | serde 显式声明 | 各绑定自定义 |
| 一致性 | 每机一致 | 依赖系统版本 | 依赖工具包版本 |

表里没有「谁更好」，只有参数不同：要 Web 生态和绝对一致，付体积；要轻，付行为差异；要极致性能，付生态与维护。选型时先问「界面复杂度和团队技能在哪儿」，再对照这张表付账——这就是原理视角与调包视角的差距。

## 这门课的终点自查

合上书之前，用三个问题验收自己（都能在自制内核里指出对应代码）：

1. 从 `win.show()` 到窗口出现，经过了哪几站？（句柄 → 桥 invoke → 序列化 → 注册表 → 原生 manager → OS）
2. **从用户点击到 JS 回调，消息走了哪条路？**（OS 消息 → 队列 → 泵 → 两级路由 → 动作名反查 → 回调）
3. **为什么函数永远过不了边界、跨进程对象 `===` 永远 false？**（序列化只复制数据；闭包与引用绑定在各自的内存世界）

三问答得上来，「调包侠」三个字就可以摘掉了——以后再打开任何一个桌面端框架的文档，你看到的不是一堆 API，而是这张零件表上的已知参数。

## 小结

Electron 背引擎买一致性，Tauri 借系统引擎买轻量，Qt 绑定绕开 Web 买性能——三种方案是我们十章内核的三组不同参数，原理结构一条不差。课程终点达成：你拥有一个约五百行、45 条断言背书的 mini-Electron 内核，以及把它映射到任何真实框架的能力。接下来最好的练习：给自制内核加一个「系统对话框」的 binding，或者把 IPC 通道接进 createApp 让渲染侧也能 invoke 主进程——你会发现，每一次扩展都在重走这十章的某一段。
