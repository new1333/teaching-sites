# JS 没有 GUI：运行时是被嵌入的

一个每个 JS 开发者都撞过的报错：同一段代码，浏览器里跑得好好的，搬进 Node 脚本立刻 `ReferenceError: window is not defined`；写 Electron 时更迷惑——主进程文件里 `window` 没有、`document` 没有，渲染进程里却都有，还能多出一套 `ipcRenderer`。很多人把这当成「环境不同，背下来就好」。但只要追问一句「JS 语言规范里哪一章定义了 window」，整个幻觉就塌了：**没有任何一章。`window`、`document`、`process`、`ipcRenderer` 全都不是 JS 的东西，它们是宿主（host）塞进来的**。这一章讲清塞的动作是怎么发生的，因为下一章我们要亲手当一回宿主。

## 引擎只是一台可租赁的机器

把「JS 运行时」拆开看，里面是分层的。最底下是引擎（V8、JavaScriptCore、QuickJS……），它只认识 ECMAScript 规范：语法、类型、函数、原型链、Promise，外加一个空的执行环境。引擎是个库（C++ 写的库），它自己不会出现在进程列表里，也不认识屏幕、文件、网卡。规范层面它唯一知道的「外部世界」是一个叫全局对象的槽位——引擎启动时它是空的。

谁来填这个槽位？宿主。宿主是一个原生程序（浏览器、Node、Electron 的某个进程），它做三件事：

1. 把引擎当库链接进自己，创建隔离的执行环境（V8 里叫 isolate + context——「隔离」意味着里面的全局对象互不可见，一个页面污染不了另一个页面）；
2. 把自己的能力包装成函数和对象，逐个挂到全局上（浏览器挂 `document`/`window`，Node 挂 `process`/`require`，Electron 渲染进程挂网页 API 加 `ipcRenderer`）；
3. 提供执行驱动：什么时候跑你的脚本、事件循环归谁管（Node 的循环在 libuv 里，浏览器的循环嵌在标签页的渲染管线里）。

这叫嵌入（embedding）。所以「JS 能做 GUI」是个错觉——JS 从头到尾没获得过 GUI 能力，是某个宿主恰好有 GUI 能力、又恰好愿意把它包装成 JS 函数挂出来。**引擎提供计算，宿主提供世界**。

## 同一个引擎，三个世界

用这个分层回看开头的报错，一切就对齐了：

- 浏览器：宿主是浏览器进程，挂上 `window`（框选、弹窗）、`document`（DOM）、`fetch`（网络栈）。JS 之所以「能画画」，是因为宿主把渲染管线的一部分以 DOM API 的形式租给了它。
- Node：宿主是 Node 可执行文件，它压根没有 GUI，自然什么都不挂，只挂 `process`、`fs`、`require`。`window is not defined` 不是出错，是宿主诚实地告诉你「我这里没有这玩意」。
- Electron 主进程/渲染进程：这是最有趣的一个——同一个 App 里有两个宿主角色。主进程的宿主是「Node + 窗口/系统能力」，渲染进程的宿主是「Chromium 网页环境 + 一小撮桥接口」。同一份 V8，两个世界注入的全局完全不同。为什么拆成两个进程、两边怎么通信，是第 7、8 章的正题；本章只需要确认：**判断「这段 JS 里有什么可用」，看的从来不是 JS 版本，而是宿主是谁**。

还有一个常见误区顺便拆掉：「`setTimeout` 是 JS 的函数吗？」不是。引擎只保证 Promise 的语义；`setTimeout`、`setInterval`、`requestAnimationFrame` 都是宿主挂出来的，计时由宿主实现。这也解释了为什么不同宿主的 `setTimeout` 最小间隔、精度各不相同——同一台租赁机器，房东给的配件不一样。

## 宿主注入的最小示意

下一章的实验场要写的 `createRuntime`，骨架用十行伪码就能说清：

```ts
// 原理示意：宿主如何造出一个「JS 世界」
const runtime = createRuntime('main')      // 相当于创建 isolate + context
runtime.globals.createWindow = wrap(创建窗口的原生实现)
runtime.globals.setTitle    = wrap(改标题的原生实现)
runtime.run(() => {                        // 把你的 JS 脚本放进这个世界执行
  // 脚本眼里：createWindow 是「天生就有的」
})
```

注意两个要点。其一，`globals` 是宿主单方面填的字典：宿主挂什么，JS 就有什么，反过来 JS 在自己全局上乱挂的东西，宿主完全不知情——边界是单向透明的。其二，`wrap` 不是直接赋值：原生函数与 JS 函数的参数、返回值要跨语言边界，需要一层转换——这层转换就是下一章的主角绑定层（binding），`window.alert` 能跑，是因为有人替它把字符串从 JS 字符串翻译成了原生字符串。

宿主与第 2 章的关系也在此接上了：宿主提供世界，而原生世界的 heartbeat 是消息循环——宿主注入的很多「同步函数」，内里其实往某个队列里塞了消息。等第 9 章事件回流时你会看到这条环闭合的样子。

## 小结

引擎是一台不认识世界的计算机，宿主负责把它搬进自己的世界、再把世界的能力挂到它的全局上。`window` 与 `process` 的差异、Electron 两个进程 API 面的差异，全是宿主注入清单的差异。理解了「注入」这个动作，你就再也不会问「JS 怎么获得 GUI 能力」——它从来没获得过，它只是被放进了一个恰好有 GUI 的程序里，并且拿到了那个程序的遥控器。下一章我们把遥控器的电路板拆开：binding 层——JS 函数调用怎么穿过语言边界、进入原生代码，参数怎么序列化、返回值怎么回来。
