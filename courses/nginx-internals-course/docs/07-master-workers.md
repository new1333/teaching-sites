# master 与 worker：一个老板一队员工

两个你大概率遇到过、却未必能讲清的问题。第一个：周五发版，你执行 `nginx -s reload`，老板在群里问「在线用户的下载会断吗」——你凭经验回答「不会」，但心里没底，因为你说不出凭什么。第二个：上周监控显示一个 worker 进程被内核 OOM 杀掉了，可整站无感，流量像水一样滑给了别的 worker，几秒后进程数恢复正常——你知道是那个管理进程干了什么，但不知道具体是什么。这一章把这两个「凭什么」一次讲透。没有代码，全是机制，但讲完之后你能把这两个问题给人讲明白。

先看全家福。`ps` 里那群 nginx 进程长这样：

```text
root     1234  nginx: master process /usr/sbin/nginx
www      1235  nginx: worker process
www      1236  nginx: worker process
www      1237  nginx: worker process
www      1238  nginx: worker process
```

一个 **master 进程**（老板）——只管不接待：读配置、管员工、收指令，自己不碰任何客户端连接。一群 **worker 进程**（员工）——真正伺候连接的，每个 worker 就是前六章讲的那个「单线程事件循环」，一人一摊、互不打扰。你配置文件里那行 `worker_processes auto;`，决定的就是招几个员工（auto 通常等于 CPU 核数）。

## 为什么是多进程，而不是多线程

第 1 章算过多线程的账：共享内存要加锁，锁竞争拖垮吞吐，一个线程写坏内存全家阵亡。多进程把这两笔账直接抹掉——进程之间内存完全隔离，没有共享就没有锁，你写坏自己的内存只死你自己。隔离还送了一份保险：**worker 崩了，整站活着**。一个 worker 因为恶意请求触发了 bug 段错误退出，损失的是它手里那几条连接；监听端口不在它手里（下一节讲在哪），其他 worker 各干各的，master 察觉后几毫秒内再招一个新人顶上。这就是上周那次「无感事故」的全部机制——没有魔法，只有隔离加替补。

那为什么不是「每连接一进程」？第 1 章已经埋葬过那个模型——进程数得跟连接数一样多。这里进程数的账不一样：worker 数量跟 CPU 核数走，不跟连接数走。一个核跑一个事件循环，一个事件循环管几千上万条连接——**多进程解决的是「用满多核」，事件循环解决的是「单核管万连」**，两层各管各的，叠起来才是完整答案。

还有一笔容易忽略的账：多进程让 reload 和升级成为可能。配置换新、二进制换新，本质都是「换掉干活的人」——而人可以一个一个换，机器不能中途换。这个下面细讲。

## 老板手里攥着的那部总机

master 有一个关键动作：**监听 socket（第 2 章那部电话机）是 master 创建的**。它在启动时读配置、绑定端口、打开监听 socket，然后才 fork 出一群 worker。fork 的语义是复制进程——于是每个 worker 出生时手里都攥着同一部总机的钥匙（同一个监听文件描述符的副本）。

新连接来了怎么办？所有 worker 都在盯着同一部总机。早期实现里内核会把「来客了」广播给所有盯梢的 worker：一群 worker 同时惊醒、抢着去接，最后只有一个接到，其余白醒一趟。这个现象叫**惊群**（thundering herd，一窝蜂醒来多数白忙）。惊群浪费不大但烦人，现代内核和 nginx 已经用「只叫醒一个」的机制解决了它。你只需要记住结论：多个 worker 抢同一部总机，内核负责把每个新连接恰好交给一个 worker。谁接了这条连接就归谁管到关闭——连接从生到死只属于一个 worker。这也再次解释了为什么 worker 之间永远不需要锁。

master 的职责清单到此齐了：读配置、建总机、招 worker、盯生死、收指令。它自己一行业务代码都不跑——老板越闲，系统越稳。

## 信号：操作系统给进程的对讲机

master 怎么「收指令」？进程之间不能直接调用对方的函数——各自的内存空间互相看不见。操作系统为此提供了一条官方通道：**信号**（signal）——发给进程的对讲机暗号，一行命令就能喊：`kill -HUP 1234` 就是「给 1234 号进程发 HUP 暗号」。nginx 给这些暗号定了含义：

| 暗号 | 含义 | 谁收 |
|---|---|---|
| TERM / QUIT | 立即退出 / 优雅退出（QUIT：送完手头的客人再走） | worker 或 master |
| HUP | 重新读配置（reload） | master |
| USR2 | 热升级：启动新二进制 | master |
| WINCH | 让旧 worker 优雅退休（配合热升级） | master |
| CHLD | 「你有个孩子退出了」（内核自动发的） | master |

最后那行 CHLD 是防线的地基。任何 worker 死掉，内核都会自动给 master 发 CHLD；master 收到就去收尸（拿到退出状态），然后补招新 worker——「崩了自动满血」靠的就是这条暗号，不需要任何轮询。

## reload 的时序推演：为什么下载不断

现在把周五那个问题一行行推演出来。你敲 `nginx -s reload`，实际发生的是向 master 发 HUP，master 依次做六件事：

```text
1. master 收到 HUP
2. 重新读 nginx.conf —— 解析失败（比如第 6 章那种未闭合的块）？
   → 直接报错放弃，旧 worker 一个都不动，线上无感（这就是「先验配置再动手」的价值）
3. 用新配置 fork 一批新 worker —— 新 worker 出生时就带着新规则
4. 向所有旧 worker 发 QUIT
5. 旧 worker：从总机上摘掉自己（不再接新客），但手里已有的连接继续服务到底
6. 每个旧 worker 送完最后一个连接，退出；master 收尸
```

正在下载的用户为什么不断线？他的连接在步骤 5 被旧 worker 捧在手里——QUIT 的语义不是「挂断」，是**优雅关闭**（graceful shutdown）——「不再接新客，把手头的客人送完再下班」。新客则从第一步换血开始就全部落到新 worker 手里，全程没有任何一条存量连接被掐。代价要说清：旧 worker 会一直活到最长的那个连接结束（长轮询、大下载），所以 reload 后你 `ps` 会短暂看到两代 worker 并存——这不是 bug，是优雅的账单。

热升级（换 nginx 二进制本身）是同一套把戏的极致版：USR2 让 master 启动新二进制的进程，新进程继承总机的钥匙，起自己的 worker；确认新版没问题后，WINCH 让旧 worker 优雅退休，最后 TERM 送走旧 master——换发动机，不熄火。

## tinysrv 为什么停在单进程

公开说清楚边界：tinysrv 是单进程的（一个事件循环），没有实现这套模型——因为本课的教学焦点在单循环内部的机制，而进程编排属于另一层。但这一章你获得的是「读得懂」的能力：Node.js 的 `cluster` 模块就是这套架构的现成翻版——`cluster.fork()` 出的子进程默认共享同一个监听端口、由内核分发新连接，正是「总机 + 一队员工」。练习附录里给你留了一条用 cluster 把 tinysrv 变成多进程的路，机制你已经全懂了。
