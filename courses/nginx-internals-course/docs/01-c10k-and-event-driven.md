# C10K：一万个连接怎么把老牌服务器打爆

1999 年，工程师 Dan Kegel 在自己的网站上写下一篇著名的文章，题目就叫「The C10K problem」。C 是 ten 的缩写，C10K——一万（K）个连接。他要回答的问题是：怎么让一台服务器同时伺候一万个客户端连接。这在当年被多数人当成不讲理的需求。而他判断这很快会变成家常便饭：每个用户开一个浏览器，浏览器同时开好几条连接下载页面、图片、样式。一万个人访问你的网站，就是上万条同时挂着的连接。

当年的标准答案是 Apache。而 Apache 当年的默认工作方式叫 prefork：服务器启动时提前复制（fork 的本意就是「复制进程」）出一批子进程，比如 150 个，每个进程专门伺候一个连接。平时这很稳。但当 5000 个并发涌进来，灾难的链条是这样的：150 个员工全部在忙，新客人还在进门，系统只好不停地复制出新进程——复制进程是个重动作，要把整个进程的家当复制一份，几毫秒、几兆内存；新进程带着 PHP 之类的运行时，一个就要吃掉几 MB 到几十 MB；5000 个进程挤在一台机器上，内存以 GB 为单位往上蹿，开始动用硬盘当内存（交换分区），而交换分区比内存慢几个数量级；与此同时，CPU 的时间被切碎给几千个进程轮流用，每次轮换都要保存上一个进程的现场、恢复下一个的现场——这个动作叫上下文切换，它不生产任何东西，纯付费。最讽刺的是：绝大多数连接根本没在发数据，它们只是挂着——长连接、慢客户端、等待用户操作——但它们对应的进程一个个都站在工位上，占着内存，等着切换到自己的那一小片 CPU 时间。

服务器没有宕机，监控上进程都活着。但用户的请求排队越来越长，页面从 200 毫秒变成 10 秒。它没死，它只是不会干活了。

## 先把话说清：一万个连接是什么意思

这里有个最容易搞混的概念，先掰开。并发连接数——同一时刻挂在服务器上的「通话中」数量；它不是每秒新来多少请求。一个挂着长轮询的手机 App，一小时发一次请求，但它的连接始终占线；一万个这样的客户端，就是一万个并发连接，而实际流量可能低得可怜。反过来说，伺候好一万个并发连接，靠的不是算得快，而是「挂着不费钱」。

这就撞上了老模型的死穴：进程数和连接数绑死了。连接越多，进程越多；进程多了，光养着它们就把机器吃穷了。C10K 问题的本质不是「请求处理不过来」，而是「连接挂不起」。

## 每连接一进程：一笔算不过来的账

把这笔账算明白，你就知道后来的架构为什么非变不可。

**内存账**。一个带脚本运行时的服务进程，保守按 2 MB 算。跟着算一遍：1000 个并发连接就是 2 GB，5000 个就是 10 GB，一万个就是 20 GB——这还只是进程自己，系统里还有内核为每个连接缓存的收发缓冲区。2000 年前后的服务器，内存普遍以百 MB 计。这笔账在任何一栏都对不上。

**切换账**。让 5000 个进程轮流用 CPU，假设每个每秒切进来一次，就是每秒 5000 次上下文切换。每次切换本身只要几微秒，看着不贵。但真正的代价藏在后面：切换之后，CPU 里为上一个进程预热好的缓存（把热数据留在手边的小抽屉）全作废了，新进程要从内存里重新搬数据进来，这一步比切换本身慢几十倍。进程越多，每个进程的缓存命中越差，全体变慢。

**凭据账**。还有一个更早撞上的墙：**文件描述符**——操作系统发给每个「正在打开的东西」的编号凭条，socket 连接也算一种打开的东西。当年多数系统默认一个进程只发 1024 张。你精心优化了半天内存，第 1024 个连接一来，系统直接报错「Too many open files」。C10K 时代的第一课，往往是改这个默认值。

## 换成线程行不行

进程太肥，那换成线程呢？线程和进程的区别你大概知道：进程是独门独户，各家有自己的内存；线程是同一户里的几个人，共享同一份内存。省下的正是内存——不用复制全家当。

但两个新问题立刻顶上来。第一，每个线程仍然要有自己独立的调用栈（记录「程序执行到哪、函数套了几层」的作业本），默认配置动辄几 MB。一万个线程照样是几十 GB 的虚拟内存。第二，共享内存意味着全家共用一个账本，谁读写都得先锁门——同一时刻只有一个线程能动。抢锁的队伍一长，CPU 又全花在排队上。还有更狠的：一个线程把共享内存写坏了，整个进程连带所有线程一起崩，没有隔离。

所以多线程把账从「内存」挪到了「锁」，总账依然算不平。

## 非阻塞 I/O：不占着工位死等快递

换个思路。前面那笔账之所以算不平，是因为每个进程的大部分时间在干嘛？在读 socket——等对端发数据。而「等」这件事，在阻塞模式下必须占着整个人。

阻塞 I/O（blocking I/O）就是「占着工位死等快递」：你调用一次「读」，如果还没数据到，这次调用就不返回，你整个人钉在这里，什么都干不了。prefork 模型里那 5000 个进程，绝大多数正钉在这种等待上。

非阻塞 I/O（non-blocking I/O）换个姿势：你问一句「有数据吗」，没有就立刻回答「还没有」，你该干嘛干嘛，回头再问。工位腾出来了——一个线程理论上可以同时照看一万个连接，挨个问一圈「有你吗」。

但「挨个问一圈」本身就是新问题。一万次询问，绝大多数得到「没有」，白跑。而且每次询问都要从应用软件跑一趟操作系统内核（数据到底有没有，只有内核知道），这一来一回本身就不便宜。连接数一大，光是问一圈的时间就超过了处理数据的时间。

## epoll：把「问」变成「等通知」

**epoll**——Linux 内核在 2002 年提供的一套机制，名字里的 e 是 event（事件）的缩写。它解决的就是「挨个问」的蠢办法，思路一句话：**别问，留话，有事叫你**。

打个比方：传达室大爷。你把一万个门铃的值守交给内核这位大爷，自己去睡觉；任何一个门铃响了，大爷记下号码，等你来取的时候把今天响过的号码名单递给你。你处理的每一个，都是真正有事的那一个，一次都不白跑。

它的工作形状是这样的：

```text
// 原理示意（伪码）：事件驱动服务器的主循环
把要盯的连接编号都登记给内核（epoll_ctl）
循环 {
    名单 = 等着取「谁有事件」的回报（epoll_wait）  // 没事时整线程睡觉，不耗 CPU
    对名单里的每个连接 {
        是来数据了 → 读出来，交给处理逻辑
        是可写了   → 把憋着的响应发出去
    }
}
```

登记给内核的那些编号，就是前面说的文件描述符——所以 epoll 的本质是：**你把一万个文件描述符的「盯梢」外包给内核，只接收增量通知**。这套机制有个通用学名，叫 **I/O 多路复用**（multiplexing，「多路信号走一条通知线」的意思）。在 epoll 之前有 select、poll 两个前辈，它们的问题正是每次都要把一万个编号全量重报一遍给内核，连接一多就垮。epoll 赢在「登记一次、增量回报」。

2004 年，Igor Sysoev 发布 nginx，正好踩在 epoll 成熟的这一波上。nginx 从第一天起就是为「上万个连接挂着不费钱」设计的——这也是这门课要一层层拆开看的东西。

## 事件循环与回调：服务器的心跳与留言

上面那个「循环 { 等名单 → 逐个处理 }」的形状，有个名字：事件循环（event loop）——服务器的心跳，一圈一圈，每圈处理一批到货的事件。而你留给系统的那个「有数据了请打这个电话」的处理函数，叫回调（callback）——一句留言：「事来了，打这个电话」。

这一族架构在业界统称 reactor 模式（反应器模式：事件来了，反应一下）——单个线程守着一个事件循环，事件来了就分发给对应的处理逻辑。nginx、Redis、Node.js、Envoy，全都是这一族的。你写业务代码时用的 Node.js，它的 `net`、`http` 模块底下就是这套——这也是本课程实验场选 TypeScript 的原因。我们不需要自己造内核大爷，只借 Node 已经包好的 epoll，亲手造大爷管辖之下的那些东西：连接的账本、请求的解析、连接的复用。

最后说这套架构的命门，它正是后面所有章节的主线来源：事件循环是单线程的，一圈里任何一个处理动作干了慢活——同步读一块大文件、算一个死循环——整个循环卡住，一万个连接全体等待。所以这个流派的所有功夫，都花在「把每件事切得足够小、绝不占着循环不放」上。数据没到齐怎么办（第 3 章的状态机）？发送对端收不动怎么办（第 8 章的缓冲）？一件工作的内存怎么拿怎么还最省事（第 5 章的内存池）？把每件事都切成「来了就办、办完就让位」，单线程才玩得转上万个连接。
