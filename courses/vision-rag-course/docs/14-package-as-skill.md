# 从脚本到 skill：让 AI 知道何时调用你

三个月攒下的脚本，你打包发给同事：渲染、建索引、提问、导出预览，一应俱全。他手头明明有一份 120 页的验收报告要查，第二天却跑来问：「这个怎么用？」你愣了一下才意识到——每个脚本你都会用，可这个压缩包里没有一页说明书。先跑哪个、参数怎么给、出了错看哪里，全在你的脑子里，不在包里。

后来你把脚本装进 AI 助手，指望它替你记住用法。结果更糟：助手也不知道什么时候该掏出这套工具。你问「付款条款在第几页」，它客气地说自己读不了 PDF——不是做不到，是它根本不知道你手边有一套专门干这活的脚本。工具躺在文件夹里吃灰，不是因为功能不行，是因为没人知道它的存在条件。

会做，与用得上，中间隔着一页说明书。这页说明书有两种读者：同事是人，助手是机器。写给机器的那一种，就是本章的主角，也是全书地图上的最后一块骨头。

## 工具的死穴：会做，不等于会被找到

先看清调用关系变了什么。以前工具的用户是人：人翻 README、试命令、看报错，不对再问同事。这份探索的成本，人愿意付，因为人有耐心也有上下文。

AI 助手不做探索。每一轮对话，它做的是匹配：手边装着一列工具，每个工具配有一段介绍文字；听到你的话，它在这些介绍里找与这句话对得上的那一个。对上了，就照介绍里的步骤执行；对不上，它礼貌地说自己不会——哪怕能干这活的脚本就在硬盘上。助手的调度逻辑，主干就这么点：

```python
# 原理示意（伪码）：助手的工具调度，决策输入只有那段介绍文字
for skill in installed:                     # 手边装着的技能清单
    if mentions(skill.x_words, user_text) and wants(skill.y_words, user_text):
        follow(skill.steps)                # 照步骤调脚本，产出转述给用户
```

各家助手内部怎么实现各不相同，但决策的输入是同一样东西：你写的那段介绍。介绍里写了「什么时候用」，助手才有机会掏出你的工具；写的是实现术语，用户的话永远对不上。**触发逻辑不在代码里，在说明书里**——这是脚本与技能的分界线。

这套交付形态业界已有通用叫法：agent skill——一份写给 AI 助手的工具说明文件，写明这个工具干什么、什么时候用、按什么步骤调；助手把它装在手边，认出对应的活，就照步骤自动运行你的脚本。skill 在这里不是新代码，是给既有脚本的一层说明包装：脚本还是那堆脚本，多出来的是一份机器读得懂的说明书。

## 说明书的三块内容与一条铁律

一份最小可用的技能说明，三块内容加一条铁律：

- **名字与触发描述**：一个稳定的工具名，配一段「什么时候用」；
- **工作流**：编号步骤，每步一条命令、一句期望输出；
- **回答规范**：拿到脚本输出后怎么转述——保留引用标记、如实转告拒答；
- 铁律：密钥绝不写进文件。

第三块其实是全书的回声。答案只落在已索引的页与段上、索引覆盖不全要声明、拒答原样透传、时间戳提醒是采样估计——第 7、8、11 章立下的诚实纪律，在说明书里原样重抄一遍，助手转述时才不会替模型「美化」。你在这本书里给机器立的规矩，最后一并交给替你说话的那位。

铁律只需要回忆第 2 章的教训：密钥写死在代码里，代码一上 GitHub 就得连夜换钥。技能说明文件比代码更容易被分享——它生来就是要发给别人的。所以说明里只写一句「密钥从环境变量 `GLM_API_KEY` 读取」，文件本身永远不含凭证。密钥是门禁卡，说明书是公告栏，卡不贴在栏上。

## 触发描述：替助手回答「什么时候用你」

触发描述（description）是说明书最前面的那几行——助手决定用不用你，依据只有它。可用的句式固定：

「用户提到 X，且想做 Y 时，使用本 skill。」

X 是素材词：用户嘴里会出现的材料——PDF、文档、报告、手册、扫描件。Y 是意图词：用户想干的事——提问、查找、总结、问在哪一页。X 和 Y 都要从用户的话语里取词，不从你的代码里取。再补一句引用形态——回答带 [第N页] 引用、给证据页图——助手就知道用完该交付成什么样子。

反例最能说明问题。把触发描述写成「基于三层漏斗的检索增强生成管线」：工程上准确，触发上是灾难。没有用户会说「我要一条漏斗」；助手拿着这句话，等一个永远不会出现的暗号，工具照旧吃灰。**触发描述的读者是用户的话语，不是你的实现**。

两个相近的工具怎么不打架？差异化同样落在素材词与引用形态上。第二份技能写：用户提到视频、监控、录像，想定位事件、问什么时候发生、要时间戳引用时使用——回答带 [MM:SS]，并切出可播放片段；再诚实声明一句：视觉大模型只看画面、听不到声音。同一副骨架，两张名片，各认各的活。

下面这份示范可以当模板改。文件头那两行三连短横线夹着的一段，是机器最先读的字段清单——工具名与触发描述都住在里头：

```markdown
# 用法示例：一份技能说明文件，自包含示范
---
name: pdf-vision-qa
description: 对 PDF 与扫描文档做视觉问答与内容检索。
  用户提到 PDF、文档、报告、论文、手册、扫描件，
  并想提问、查找、总结或理解其内容，或问"在哪一页"、要原文引用时，使用本 skill。
  支持表格与图表；回答带 [第N页] 引用，并导出命中页图片。
  API 密钥从环境变量 GLM_API_KEY 读取，本文件不含密钥。
---

## 工作流
1. 建索引，每份 PDF 只做一次：python ingest.py "<pdf 路径>"
   首次为分钟级，重复运行命中缓存
2. 提问：python ask.py "<pdf 路径>" "问题"
   输出答案（带 [第N页]）、引用页图与自包含 HTML 预览的落盘路径
3. 展示：把预览或页图的本地路径给用户双击打开，不要只贴文字

## 回答规范
- 以脚本输出为事实基础组织回答，保留页码标记
- 索引只覆盖部分页时，如实说明
- 资料里没有的内容，照脚本的拒答原文转告，不自行补充

## 排错与细节
调参、报错、引擎差异：先读 references/api-notes.md（实测行为记录）
```

写完自查。这份清单不装任何助手也能做：

- 遮住名字念给别人听：没用过的人能说出「什么时候用它」，触发才算写清了；
- 拿三句话试匹配：「这份手册的退货政策是什么」应命中；「把这段话翻成英文」不应命中；「监控里第几秒有人进门」不应命中 PDF 版、应命中视频版；
- 数一数素材词与意图词：各有不到三个，就还有用户的话你对不上；
- 搜一遍实现词：漏斗、管线、精排这类词出现在描述里，就是写给了错误的读者。

## 渐进披露：一页常驻，细节进抽屉

说明书要薄，不是审美偏好，是预算约束。助手也有上下文窗口——第 1 章那张「桌面就这么大」的桌子，对助手同样成立。装进助手的每份技能说明都常驻桌面：每一轮对话都占它的预算；装的工具越多，每份说明摊到的注意力越稀。第 1 章那条规律原样适用于此：**资料越厚，把握越稀**。

所以文档要分层。这套组织法叫渐进披露（progressive disclosure）——一页精要常驻桌面，细节文档收进抽屉、用到再读，省的是上下文预算。像工具箱：箱盖上只贴一张封面卡，详细说明书放在抽屉里；干活只看封面卡，卡上没答案，才拉开抽屉。

技能包的形状：

```text
技能包的形状：一页常驻，抽屉按需

  SKILL.md          <- 常驻：名字、触发描述、工作流、回答规范（一页）
  references/
    api-notes.md    <- 抽屉：引擎实测行为记录，排错时才读
    clipping.md     <- 抽屉：切片参数、格式细节
  scripts/          <- 代码本体：助手不读、只运行
```

再算一笔账。数字是假设的口径，量级关系是真的：

```text
假设口径：助手手边常驻 20 份技能说明

全量常驻：每份 2000 token × 20 = 4 万 token，每轮对话都要摊
渐进披露：每份精要 200 token × 20 = 4 千 token 常驻；
         真正用到某个工具时，才读它的抽屉，多花 2000 token
```

常驻开销压到十分之一；抽屉的那点钱，只在真用到时花。这正是全书成本漏斗在文档世界的镜像：**粗筛读的是一页卡片，深读才摊开原图**。你的技能包内部，是一座两层小漏斗——说明书自己在实践这本书教的经济学。

## 收束全书：地图兑现为机器

第 1 章出发时发过一张地图，此刻逐条对账。

PDF 主线（第 3~8 章）把漏斗三层从零建了一遍：页面渲染成图、页码与图像绑死；整本写成读书卡；本地粗筛免费圈候选；视觉精排看图补词面盲区；深读带邻页高档作答；引用回收出可双击核对的自包含预览。视频主线（第 9~12 章）把同一个漏斗换素材再走一遍：按时长定抽样密度、帧卡归堆成段、回答带时间戳、可疑窗口换显微镜重看。工程两章收口：第 13 章换引擎只动传输一层、重要结论双引擎互验；本章补上最后一块——说明书，让助手知道什么时候调用这套家当。

你此刻的家当，照全书里程碑的口径：一套千行级（连注释与文档串约 1900 行、纯代码约 1100 行）、假模型驱动的最小视觉检索增强生成管线，PDF 与视频问答全流程可跑通。开机自检两步，在 companion 目录下：

```bash
python -m pytest -q
```

141 个测试全绿——11 个动手章各留一组测试，是你造过的每块骨头的收据。再跑一遍第 8 章「亲手开机」一节那行 python -c 一行命令，双击 out 目录里的 preview.html：灰底答案、页码引用、引用页图同屏。全书的终点不是这页文字，是这台你随时能开机验证的机器。

诚实的边界最后念一遍：实验场用假模型按剧本回放，不联网、不花真钱；真引擎隔着一层可替换的传输接口；课程声明的简化与真实世界的差异，登记在附录的差异清单里。术语表与练习路线也在附录——清空 src 从红到绿重走一遍，是把这套机器变成自己东西的最短路径。

离开前自查四问：

- 触发描述必须同时写清哪两类词？为什么实现词是灾难？
- 渐进披露省的是什么预算？主文件与抽屉各放什么？
- 为什么密钥永远不进技能说明文件？
- 技能包内部的两层小漏斗，各对应全书漏斗的哪一层？

答得上来，说明书就写得出，机器就交得出。第 1 章说「带上地图出发」；到这里，地图兑现为机器，机器配上说明书。查手册这件小事，从两分钟几十块，走到了一句话、可核对、可转交。
