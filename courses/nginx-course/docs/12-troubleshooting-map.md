# mini-nginx vs 真实 Nginx：差异地图与 502/504 排障手册

周五晚八点，订单接口开始批量报 502。工单在三个群里流转：前端说页面报错但请求参数正常，后端说服务进程活着、日志没有异常，运维说 Nginx 机器 CPU 内存都正常。两个小时后有人翻了 Nginx 的 error.log，才看到每分钟几十条 `connect() failed (111: Connection refused) while connecting to upstream`——后端实例 OOM 被系统杀了又拉起，拉起的三分钟里实例端口根本没人监听。三个团队都没做错什么，缺的只是同一张地图：**502 的现场证据在哪、由谁读**。

终章做两件事收束全书：先把 mini-nginx 与真实 Nginx 的差异摆成一张地图——你需要知道手里这 600 行和线上那个工业软件之间隔着什么；再给 502/504 一份从日志出发的排障决策树——这是全书知识在事故场景里的合体调用。

## 差异地图：你写了什么，没写什么

十二条差异按「教学保真 / 语义近似 / 未实现」分档。前两档是刻意为之的蒸馏，第三档是生产与玩具的真正距离：

| # | 维度 | mini-nginx | 真实 Nginx | 档位 |
|---|---|---|---|---|
| 1 | 进程模型 | 单进程 | master + N worker，`nginx -s reload` 平滑重载 | 未实现 |
| 2 | 事件模型 | Node 事件循环 | C 手写 epoll + 非阻塞 I/O（思想同构，实现层级不同） | 教学保真 |
| 3 | location 匹配 | 五步算法逐条对齐 | 一致（正则块下 proxy_pass 不做前缀替换，`src/proxy.ts` 里注明了这条对齐方式） | 教学保真 |
| 4 | try_files / 内部重定向 | 10 次上限 + 500 | 一致 | 教学保真 |
| 5 | X-Forwarded-For / Host | 链式追加 / `$proxy_host` 默认 | 一致 | 教学保真 |
| 6 | WebSocket 升级 | 代理块自动透传 Upgrade | 需显式 `proxy_set_header Upgrade ...`（严格遵守逐跳头不转发） | 语义近似 |
| 7 | 负载均衡 | 权重展开序列 `[a,a,b]` | 平滑加权轮询（把权重摊开成 `a,b,a`，避免连续打同一台） | 语义近似 |
| 8 | 代理缓冲 | 双向 pipe 直通 | `proxy_buffering on`：先收完上游响应再发给客户端，慢客户端拖不垮上游 | 语义近似 |
| 9 | 失败重试的请求体 | 直通管道，POST 中途失败难以安全换台重试 | 默认缓冲请求体，连接失败可整包重发 | 语义近似 |
| 10 | gzip × ETag | 压缩时仍输出强 ETag | 压缩响应用弱验证 `W/"..."`（同一资源两种表示，强验证不成立） | 语义近似 |
| 11 | add_header 生效范围 | 所有响应 | 默认仅 2xx/3xx 部分状态码，`always` 才覆盖 4xx/5xx | 语义近似 |
| 12 | HTTP/2、sendfile、open_file_cache、access_log、多 server（server_name） | — | 全部在线上服役 | 未实现 |

读这张表的正确姿势：**档位说明差距的性质**。「教学保真」的五条，你写下的逻辑与 Nginx 的行为可以互为答案；「语义近似」的六条，比例与方向一致、边角不同——正是第 8 章 fetch 透明解压、本章排障这类"边角"事故的高发区；「未实现」的两条，是性能与运维能力的护城河，也是「能重实现核心」与「能替代生产软件」之间的诚实分界。全书 642 行 src 配 55 个测试，换来的是前十行的完整理解——这笔交易是值得的。

## 502/504 排障：证据在日志里，不在猜测里

排障的第一原则：502 和 504 都是**网关在报上游的错**——请求到了网关，网关去敲上游的门，出了事。所以证据的第一现场是网关日志，第一嫌疑人是上游，第一句该问的话是「上游那一刻到底在不在」。

真实 Nginx 的 access_log 加上上游字段后长这样（`log_format` 里配 `$upstream_addr/$upstream_status/$upstream_response_time`）：

```text
10.2.3.4 - - [15/Aug/2026:20:03:11 +0800] "POST /api/order HTTP/1.1" 502 157
  upstream: "127.0.0.1:8081, 127.0.0.1:8082" status: "502, 502" rt: "0.001, 0.002"
```

一行日志同时记录**试过哪些实例、各拿到什么状态、各花多久**——上面这行说的是：两台都被试了、都立刻失败（rt 毫秒级），这是连接被拒的典型形态。配合 error.log 里的系统级 errno，决策树如下：

```text
线上 5xx，先看是什么错
│
├─ 502（bad gateway：上游没应答或应答不合法）
│   ├─ error.log 有 "Connection refused (111)"
│   │    → 上游进程不在：挂了/OOM/发版窗口 → 第 7 章的分组与重试是解药
│   ├─ error.log 有 "Connection reset by peer (104)"
│   │    → 上游进程在但掐了连接：崩溃重启中 / 接收缓冲打爆
│   ├─ error.log 有 "no live upstreams"
│   │    → 组里全灭或全被 max_fails 拉黑 → 先恢复实例，再查为什么集体死
│   └─ 502 但上游日志完全没收到请求
│        → 连接根本没建立成功：防火墙/安全组/端口配错（proxy_pass 指错了门牌）
│
├─ 504（gateway timeout：上游应了但太慢）
│   ├─ error.log 有 "upstream timed out (110)"
│   │    → 上端真慢：慢查询/下游依赖卡死 → 加大 proxy_read_timeout 只是止痛，
│      根治要么治上游，要么第 8、9 章的压缩缓存减负
│   └─ 只在高峰出现 → 容量问题：连接池打满/线程池排队 → 上游扩容（第 7 章的组随时可加实例）
│
└─ 504 且 upstream rt 接近精确的整数十秒
     → 撞的是网关自己的默认超时（60s）：确认谁设的、该不该这么长
```

三个提速技巧。**绕过网关直敲上游**：`curl -H 'Host: api.internal' http://127.0.0.1:8081/health`——通，则问题在网关配置；不通，问题在上游本身，把「三方对峙」立刻变回两方。**用第 6 章的头知识定位链路**：让上游日志打印 `X-Forwarded-For`，流量有没有穿过网关、穿的哪一层，一目了然。**用第 9 章的缓存知识解释"幽灵故障"**：上游明明恢复了，部分用户还在报错——先怀疑客户端/CDN 的强缓存，再怀疑代码。

前端在这个流程里不是旁观者：你是**第一 noticing 的人**，报障时带上三个信息，能把定位时间从两小时压到十分钟——状态码（502 还是 504）、时间点（精确到分钟，运维好对日志）、范围（全量用户还是部分、哪些接口）。本章开头那场事故，最后复盘的结论就是：如果前端第一分钟报了「20:03 起订单接口 502」，运维 20:04 就能 grep 到那串 `Connection refused`。

## 延伸阅读：从 mini 到官方文档

全书按特性走，官方文档按模块组织，对照入口如下：

- 静态与路由：`ngx_http_core_module`（root/alias/try_files/location）
- 代理：`ngx_http_proxy_module`（proxy_pass/proxy_set_header/proxy_next_upstream）
- 压缩与缓存：`ngx_http_gzip_module`、`ngx_http_headers_module`（expires/add_header）
- 跨域：没有专门的 CORS 模块——就是 headers 模块的 add_header 组合，本章与第 10 章的配置即全部
- 日志：`ngx_http_log_module`（log_format 的全部变量，排障字段的出处）

读官方文档前你已经有的优势：每个指令你都用 TypeScript 写过一遍行为等价物，文档里的每句"注意事项"你都能翻译成「哦，那个 if 分支」。
