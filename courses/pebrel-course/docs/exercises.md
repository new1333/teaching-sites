# 练习：为未知 CLI 写屏幕证据规则

练习顺序沿验证依赖排列：每题需要的每项能力都已在正文示范过。做题前先回看对应章节的演练槽，再独立完成；全部练习只需锁定 clone 与纸笔，不需要安装或构建目标仓库。

## 练习 1：给 Gemini CLI 写一条含负向证据的 idle 规则

回看[第 10 章](./10-screen-evidence.md)的演练与 gemini.toml 一节：真实仓库的选择是「无 idle 规则、不凭提示符伪造空闲」。你的任务是推翻它——假设新版 Gemini CLI 的空闲画面底部固定有一行 `» ` 输入框提示，且回合进行中会出现 `· Working` 角标。写出你的 TOML 规则：区域选哪个、正向条件是什么、负向证据（not）挡什么、优先级定多少、与 working 规则的相对次序怎么排。写完后回答：如果 `· Working` 角标偶发闪现半秒，你的规则会误判吗——这正是真实仓库选择不写规则的理由。

## 练习 2：单句柄吞吐上限的变体演算

回看[第 7 章](./07-sftp-engine.md)的封顶公式（分块 ÷ RTT）。对下面两条链路各算出单句柄上限与填满管道所需句柄数，并判断是否撞上窗口 64：

| 链路 | RTT | 带宽 |
|---|---|---|
| 跨城专线 | 30 ms | 200 Mbps |
| 卫星链路 | 600 ms | 50 Mbps |

算完后用一句话解释：为什么卫星链路的结论会让「多句柄分段」从优化变成必需。（对照口径：分块 32 KiB，按十进制带宽换算，填满需向上取整。）

## 练习 3：为 git 分支设计一个补全源

回看[第 15 章](./15-completion-engine.md)的 Completer trait 接缝。写出 `GitBranchCompleter` 的 `fetch` 签名与返回值类型，回答三个问题：候选从哪里来（提示：你不需要在 trait 里执行 git 命令——静态列表源的构造器形态是什么）；返回的 `Vec<SemanticSuggestion>` 里每项装什么；这个类型为什么天然不依赖任何终端视图。最后指出：匹配与排序发生在你实现的代码里，还是 CandidateMatcher 里——「源只产候选」的分工线画在哪。

## 练习 4：摘叶预言

回看[第 4 章](./04-split-tree.md)的树叶集合不变式与[第 5 章](./05-gpui-shell.md)的 close_pane 链。画一棵三叶树：根为 LeftRight 分割，左侧是叶子 1，右侧是 TopBottom 分割（上叶 2、下叶 3）。依次执行 `remove_leaf(2)`、`remove_leaf(1)`，每步写出：树的形状、`leaves()` 的返回、`RemoveOutcome` 的变体、focused 移交给谁。如果第二步删的是不存在的 99 呢？

## 练习 5：恢复护栏推演

回看[第 11 章](./11-session-persistence.md)的四步次序（load → should_restore → quarantine → mark_boot_attempt）与「先落盘计数」的次序合同。对下表每种初始状态，写出下一次启动的裁定（恢复 / 放弃恢复）与裁定后盘上的 boot_attempts 值：

| 初始盘上 boot_attempts | tabs | 上次启动存活？ |
|---|---|---|
| 0 | 非空 | 是 |
| 1 | 非空 | 否 |
| 2 | 非空 | 否 |
| 3 | 非空 | 否 |
| 0 | 空 | — |

再回答：为什么 mark_boot_attempt 必须「先落盘再恢复」——把两步换序，表里哪一行会变成死循环？
