# 动起来：uniform 与渲染循环

第 2 章收工时留了个念想：三角形画出来了，可它钉在屏幕上一动不动。你大概已经想到最直接的招：把第 2 章的接线代码包进一个循环，每帧用 JS 算出旋转后的 9 个顶点坐标，重新 bufferData 整块重传，再 drawArrays。跑起来没问题——三角形乖乖转了，60 帧稳稳的。一个三角形才 9 个数，怎么造都不心疼。

坑在放大的时候现身。把同样的写法搬进第 1 章那个 10 万粒子的场景：每个粒子 3 个分量，10 万粒子就是每帧重算 30 万个浮点数、新分配一个数组、再把整块数据重传进显存。页面从 60 帧一路掉到 12 帧——掉帧的账两边都在记：CPU 这边每帧重建缓冲是纯粹的重复劳动；GPU 这边每帧都要等一整块新数据爬完总线才能开工。而画面的变化其实小得可怜：所有粒子整体转了一个新角度。

这里藏着本章的主句：**GPU 每帧需要的只是一个新的角度，不是一箱新顶点**。角度这种「全场一样」的量，有一条专用通道直通着色器，不必经过缓冲区——它就是第 2 章预告过的主角 uniform（统一变量）。这一章讲清三件事：uniform 这条通道怎么用；浏览器里的逐帧循环怎么搭；动画的数学底料——插值与缓动。顺手还两笔第 2 章的债：uniform 的完整用法，和片元着色器开头那行 `precision mediump float;` 到底是什么。

## 让三角形转起来：两种写法

旋转的数学只要半个高中的复习。单位圆：半径为 1 的圆上，角度 θ 对应的点是 (cos θ, sin θ)。任意点 (x, y) 绕原点转 θ 角，公式是：

```text
x' = x·cos θ − y·sin θ
y' = x·sin θ + y·cos θ

跟着算：顶点 A (−0.6, −0.5) 转 90°——cos 90° = 0、sin 90° = 1
x' = −0.6 × 0 − (−0.5) × 1 = 0.5
y' = −0.6 × 1 + (−0.5) × 0 = −0.6     落点 (0.5, −0.6)，纸笔可复算
```

有了公式，两种写法摆上台面。写法一：JS 每帧对 3 个顶点各套一遍公式，得到新的 9 个数，整块重传缓冲，再画——就是开头那个反面教材。写法二：顶点数据上传一次、从此不动，公式搬进顶点着色器，JS 每帧只把新角度 θ 送给 GPU。两种写法画出的画面逐帧一致，账单天差地别。

| | 写法一：CPU 重算 + 重传 | 写法二：只送角度 uniform |
| --- | --- | --- |
| 每帧 JS 干什么 | 重算全部顶点、拼新数组 | 算出一个角度数 |
| 每帧跨总线传什么 | 整块缓冲数据 | 一个 4 字节的 float |
| 10 万粒子时 | 30 万分量每帧重建——12 帧 | 仍然一个数——60 帧 |
| 顶点着色器里 | 原样透传坐标 | 多算一对 sin 和 cos |

最后一行是写法二的代价与回报。旋转计算从 CPU 挪进 GPU 的顶点段：3 个顶点是 3 次调用，10 万个粒子也只是一次 drawArrays 里的 10 万次并行调用。第 1 章算过这笔账——同一道题重复上万遍，正是 GPU 的主场，CPU 卸下的恰恰是它最不擅长的重复计算。

## uniform：一次绘制里全场统一的公告栏

第 2 章给过一句人话：uniform 是全场统一的公告栏——一次绘制里，每个顶点、每个片元读到的都是同一份。现在把细节补齐。

先回答「为什么存在」。三种进料口按「数据变不变」分工：顶点属性（attribute）逐顶点各一份，装在缓冲区里由 GPU 按格子取料；可变变量（varying）从顶点车间流向片元车间；而旋转角度、当前时间、光源位置这类量，对一次绘制的所有顶点和片元都一样——给每个顶点各存一份纯属浪费，每帧重传一遍更是折腾。所以 GLSL 留了第三条通道：声明一次，一次写入，全场可读，着色器谁都改不了它。

用法三连，GLSL 声明、JS 找位置、JS 写值：

```glsl
// 用法示例：uniform 在两段着色器里都这样声明（本章只用顶点段）
uniform float u_angle;
```

```js
// 用法示例：uniform 的找位置与写值
const loc = gl.getUniformLocation(prog, 'u_angle')
gl.uniform1f(loc, angle) // 1f = 一个 float；vec3 用 uniform3f，矩阵用 uniformMatrix4fv
```

`getUniformLocation` 的名字对不上时返回 null——不报错，往 null 里写值也静默无效。第 2 章那句「错误永远在等你去拿」的脾气，在这里一模一样，拿不到位置先查名字拼写。

理解 uniform 的关键词是「一次绘制内」：**「统一」指的是一次 drawArrays 期间全场同一份；两次绘制之间，值随便你改**。动画的正规姿势正是钻这条缝：每帧写入新角度，drawArrays，下一帧再写新角度。本章演示里速度滑杆之所以实时生效，就是它在改每帧要写的那个数——顶点缓冲从初始化之后就再没碰过。

### 顶点着色器里的旋转

角度进了公告栏，公式住进顶点着色器：

```glsl
// 用法示例：旋转写在顶点着色器里，角度从 uniform 进来
attribute vec2 a_position;
uniform float u_angle;
void main() {
  float c = cos(u_angle);
  float s = sin(u_angle);
  vec2 p = vec2(a_position.x * c - a_position.y * s,
                a_position.x * s + a_position.y * c);
  gl_Position = vec4(p, 0.0, 1.0);
}
```

GLSL 内建的 cos、sin 语义与 JS 相同，浮点数喂弧度。三次顶点着色器调用各转各的顶点，读到的 u_angle 却是同一个——「全场统一」在每一帧里替你广播。第 1 章说过：要点动起来，动的算法就在顶点段逐点执行——现在执行的就是这两行三角函数。

## 渲染循环：动画的心跳

WebGL 是立即模式的 API：drawArrays 画完就忘，显存里没有常驻的「场景」，画布只是最后一次绘制的快照。所以动画别无他法——每帧把整幅画面重画一遍。驱动重画的就是渲染循环（render loop）——每帧「清屏 → 更新 → 重画」的循环，动画的心跳。记一句：还是第 1 章那部翻页动画：每秒翻 60 页，页页都是现场新画的。

浏览器给循环配的设施是 requestAnimationFrame（下称 rAF）：把一个回调排到「下一次屏幕刷新之前」执行；回调末尾再排下一帧，循环就转起来。它比 setInterval 强在两处：跟着显示器的刷新节拍走，60Hz 的屏每拍约 16.7ms——第 1 章的帧率预算账；标签页切到后台自动暂停，不空烧电。

```js
// 用法示例：渲染循环骨架（清屏 → 更新 → 重画）
let last = performance.now()
function frame(now) {
  const dt = (now - last) / 1000 // 增量时间：与上一帧的差，单位秒
  last = now
  gl.clearColor(0.05, 0.067, 0.09, 1)
  gl.clear(gl.COLOR_BUFFER_BIT) // 每帧先擦干净——第 2 章立的纪律
  angle += SPEED * dt // 用 dt 缩放，帧率不匀也等速
  gl.uniform1f(uAngleLoc, angle) // 只送一个数，缓冲纹丝不动
  gl.drawArrays(gl.TRIANGLES, 0, 3)
  requestAnimationFrame(frame) // 排队下一帧
}
requestAnimationFrame(frame)
```

骨架三件事各司其职：clear 是纪律，规范不保证画布自动清空；update 用增量时间推进动画状态；draw 只送 uniform。回调参数 now 是浏览器给的时间戳，比自己在回调里调 performance.now() 少一次误差。

### 增量时间：帧率不匀的解药

增量时间（delta time，简称 dt）——本次回调与上一次的时间差。为什么必须用它，而不能「每帧加固定步长」？因为帧间隔从来不均匀：浏览器要处理事件、要跑垃圾回收，某几拍 16.7ms，某几拍 50ms。设目标转速 90°/s，两种写法对账：

```text
写法一（每帧固定转 1.5°）：              写法二（angle += 90° × dt）：
60 帧：16.7ms → 1.5°，每秒 60 × 1.5 = 90°   16.7ms → 90° × 0.0167 = 1.5°
30 帧：33ms   → 1.5°，每秒 30 × 1.5 = 45°   33ms   → 90° × 0.033  = 3°
12 帧：83ms   → 1.5°，每秒 12 × 1.5 = 18°   83ms   → 90° × 0.083  = 7.5°
帧率掉一半，转速跟着掉一半                 每秒合计恒为 90°，与帧率无关
```

写法一在 60 帧时恰好正确，帧率一掉转速就慢动作——12 帧时只剩每秒 18°，是目标的五分之一。写法二每帧按实际流逝的时间补足角度，不管一秒翻多少页，每秒合计恒 90°。再补一个防御细节：dt 通常要封顶（演示里取 `Math.min(dt, 0.1)`）——切后台再回来，恢复的第一帧可能一次跨了好几秒，不封顶的话动画瞬间跳没影。

## 还第 2 章的债：精度限定符

第 2 章让你照抄的片元着色器第一行 `precision mediump float;`，欠的解释现在还。精度限定符（precision qualifier，日常常写 precision 限定符）——写在类型前、声明这类数按哪一档精度来算的前缀。为什么 float 还分档？你在 JS 里写的 number 是固定的一种浮点（64 位双精度）；GPU 为了省电、省带宽、省电路，把浮点拆成几档精度，档位越低越便宜。光栅化铺出的片元以百万计，逐片元的计算每省一点，全屏就省一大片。GLSL ES 定了三档：

| 档位 | 规范保证的精度 | 规范保证的范围 | 典型用途 |
| --- | --- | --- | --- |
| lowp | 2^-8（绝对精度） | ±2 | 颜色分量 [0,1] |
| mediump | 2^-10（相对精度） | ±16384 | NDC 坐标、一般动画量 |
| highp | 2^-16（相对精度） | 远大于 mediump | 大世界坐标、精密计算 |

接着是那句必须记住的规矩：**片元着色器必须声明 float 的精度，漏了这一行，着色器编译直接失败**，InfoLog 里写着「没有为 float 指定精度」一类的话。这不是某个驱动的怪癖，是规范原文：顶点着色器预置了默认精度（float 默认 highp），片元着色器偏偏没有默认。道理落在工作量上——片元的调用量比顶点多出几个数量级，精度档位对性能和功耗影响巨大，规范索性把选择权连同义务一起交给写的人。选哪档？裁剪坐标系的 [-1,1] 和颜色分量的 [0,1] 都远在 mediump 的 ±16384 以内，2^-10 的相对精度画动画绰绰有余——本课程的片元一律 mediump；等世界坐标大到几十万，才轮到 highp。另有一处兼容性后门：规范允许移动端 GPU 的片元不支持 highp（GL_FRAGMENT_PRECISION_HIGH 宏可探测），mediump 则到处都有——照抄那行开场白，两边都稳。

## 渐进实验：把插值拿到 JS 手里

动画每帧要送的「新角度」从哪来？`angle += 90° * dt` 是最朴素的一种。但动画还有一大类问题：从一个值过渡到另一个值——颜色从红渐到蓝、透明度从 0 升到 1。这类问题的学名是插值：按一个比例，算出两个值之间的中间值。本章的实验场模块 `src/math/interpolate.ts` 就装三个最常用的插值工具。

先说一个会让你会心一笑的事实：**插值这件事，GPU 从第 2 章起就替你干了**。渐变三角形里，边 AB 中点的颜色 (0.5, 0.5, 0)——那正是「红与绿各取一半」，也就是对每个颜色通道各做一次 lerp；光栅化硬件对 varying 的逐片元加权，干的活就是插值。本章把同一件事从硬件请到 JS 手里：动画参数的中间值得先在 JS 里算出来，才能送进 uniform。

```ts
// src/math/interpolate.ts · lerp 与 clamp
/**
 * 线性插值：按比例 t 取 a 到 b 之间的值。
 * t = 0 得 a，t = 1 得 b，t = 0.5 得中点；t 越界按直线外推，不钳制。
 * 手算样例：lerp(0, 10, 0.5) = 0 + (10 − 0) × 0.5 = 5。
 */
export function lerp(a: number, b: number, t: number): number {
  return a + (b - a) * t
}

/**
 * 把 v 收拢进 [min, max]：小于 min 得 min，大于 max 得 max，界内原样返回。
 */
export function clamp(v: number, min: number, max: number): number {
  return v < min ? min : v > max ? max : v
}
```

线性插值（lerp）的公式一行看懂：从 a 出发，沿 (b − a) 这段路走 t 的比例。打个比方：从 A 走到 B、走了六成，人就在六成处。t = 0.5 取中点、t = 0 和 t = 1 各归端点。clamp 是它的护栏搭档，也是 smoothstep 的内部零件。

### 对账 GLSL：一个放行、一个收拢

越界行为是本章与 GLSL 对账的重点。GLSL 的内建 mix(x, y, a) 就是 lerp——公式一字不差，同样对 a 不钳制：mix(0, 10, 1.5) 结果是 15，沿直线外推。规范就是这么定的，而外推有时正是你要的（预测、过冲效果）。smoothstep 则正相反，实验场版：

```ts
// src/math/interpolate.ts · smoothstep
/**
 * 平滑阶梯：x 在 e0 之前得 0，在 e1 之后得 1，中间用 t²(3−2t) 过渡。
 * 与 GLSL smoothstep 同公式同语义——先归一化并钳制 t，再套 S 曲线。
 * 手算样例：中点 0.5² × (3 − 1) = 0.5；t = 0.25 得 0.0625 × 2.5 = 0.15625。
 */
export function smoothstep(e0: number, e1: number, x: number): number {
  const t = clamp((x - e0) / (e1 - e0), 0, 1)
  return t * t * (3 - 2 * t)
}
```

GLSL 规范对同名内建的描述：x 小于 e0 返回 0.0，x 大于 e1 返回 1.0，中间先归一化并钳制 t，再套 t²(3 − 2t)。实验场版逐句对上——同一个公式、同一套越界行为，JS 里算出的数能和着色器里算出的数互相对账。同名家族里「mix 放行、smoothstep 收拢」这对差异最容易踩，所以测试两边都下了断言锁死。

```ts
// tests/uniforms-and-animation.test.ts · 锁住「lerp 不钳制」
it('t 越界不钳制（沿直线外推）：lerp(0, 10, 1.5) = 15，lerp(0, 10, -0.5) = -5', () => {
  // GLSL 的 mix(x, y, a) = x(1-a) + ya 对 a 不做钳制——超出 [0,1] 原样外推。
  // 「lerp 不钳制、smoothstep 钳制」是本章的教学点之一，测试锁住差异。
  expect(lerp(0, 10, 1.5)).toBeCloseTo(15, 4)
  expect(lerp(0, 10, -0.5)).toBeCloseTo(-5, 4)
})
```

```ts
// tests/uniforms-and-animation.test.ts · 锁住「smoothstep 收拢」
it('端点外收拢：x < e0 得 0，x > e1 得 1', () => {
  // GLSL 规范：smoothstep 对归一化 t 先 clamp 到 [0,1] 再套曲线——
  // 与 mix 的「不钳制」恰好相反，差异同样被测试锁住。
  expect(smoothstep(0, 1, -0.2)).toBeCloseTo(0, 4)
  expect(smoothstep(0, 1, 1.3)).toBeCloseTo(1, 4)
})
```

最后是 smoothstep 存在的理由：缓动（easing）——先把比例 t 整一次形、再送去插值的手法。匀速插值的观感是机械的：现实里没有瞬间满速的东西，起步要加速，停止要减速。t²(3 − 2t) 是给 t 整形的最短公式：曲线两端斜率为 0（起步、收尾都不生硬），中段提速。手算两个点感受形状：t = 0.25 得 0.0625 × 2.5 = 0.15625，只有匀速的六成出头（缓入）；由对称性 t = 0.75 得 0.84375（缓出）；中点 0.5² × 2 恰好还是 0.5。缓动曲线族远不止这一条（回弹、过冲、弹跳），底料都是同一句话：**先整形 t，再 lerp**。第 13 章讲雾的「按距离混色」时，还要回来用 mix 对这本账。

演示侧，按这个清单玩：

- 拖速度滑杆：转速与颜色呼吸同变——改的是每帧写入的 u_speed 这一个 uniform；拖相位滑杆改的是 u_phase；面板上「本帧 uniform 写入 4 次、buffer 重传 0 次」全程不变。
- 勾「反面教材」：画面一模一样，buffer 重传从 0 变 1、累计数开始狂奔——写法一与写法二同台，肉眼看到的差别只有这个计数器。
- 开线框模式：三个顶点、三条线，转的是顶点、变的是 uniform。
- 拖相位滑杆：颜色呼吸的波峰整体平移——sin(u_time × u_speed + u_phase) 里的相位项。
- 看缓动小图：两个动点同一时刻出发，lerp 的匀速领先前半程，smoothstep 中段反超、终点同时到——两条曲线就是「先整形 t，再 lerp」的整形器本器。
- 点暂停：画面与计数器同时冻结，检查任何一帧的 uniform 读数。

## 小结

动画的正解是把「变的东西」从顶点数据里拆出来：坐标进缓冲区、上传一次不再动；随时间变的量走 uniform（统一变量）——一次绘制里全场统一、两次绘制之间随便改，每帧只送一个新角度。旋转公式 x' = x·cos θ − y·sin θ 住进顶点着色器，sin 与 cos 是高中单位圆的那一对。循环由 requestAnimationFrame 驱动：清屏、更新、重画；更新必须用增量时间缩放，帧率不匀时每秒合计量才恒定，dt 还要封顶防后台恢复的大步长。片元着色器必须声明 float 精度——规范没给它默认值，lowp/mediump/highp 三档是精度与功耗的价目表，NDC 与颜色用 mediump 足够。插值是过渡动画的底料：lerp 与 GLSL 的 mix 同公式、越界不钳制；smoothstep 同名内建同语义、越界收拢，曲线 t²(3 − 2t) 是最短的缓动整形器——先整形 t，再 lerp。实验场新增 math/interpolate：lerp/clamp/smoothstep 三件套，9 条断言与 GLSL 规范行为逐条对账。

读完本章，下面几问应该能脱口而出：

- 10 万粒子逐帧重算重传为什么掉帧？同样的动画用 uniform 改写后，每帧跨总线的是什么？
- uniform 的「统一」到底统一到什么范围？为什么这个范围恰好容得下「每帧改一次」的动画？
- 60 帧正常的旋转动画，机器负载升到只剩 12 帧时，两种写法（固定步长、增量时间）各表现出什么？
- lerp(0, 10, 1.5) 得多少？smoothstep(0, 1, 1.5) 又得多少？谁在越界时收拢、谁在放行？
- 片元着色器漏写 precision 声明会发生什么？为什么顶点着色器不用写？
