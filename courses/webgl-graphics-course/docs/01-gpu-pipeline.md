# 为什么你的画布卡成幻灯片：GPU 与渲染管线

周一早上九点，大厅那块 4K 大屏前的演示差点翻车。你做的数据大屏要实时呈现两万个粒子的流动：开发机上本地预览 60 帧，丝般顺滑；投上大屏，帧率（fps，每秒画出的完整画面数）直接掉到 5——粒子一顿一顿地爬，跟放幻灯片一样。任务管理器里的现象更奇怪：CPU 十六个核，画图的始终只有一个，单核跑满，风扇起飞，其余十五个核几乎在围观。

代码简单到不好意思发帖求助：每帧遍历两万个粒子，逐个算位置，逐个调 Canvas 2D 的 fillRect 画一个 2×2 的小方块。两万次循环，两万次画矩形，没有任何花活。本地跑得好好的，为什么换块屏就掉帧掉成这样？核这么多，为什么画图的只有一个？把粒子数减半，帧率只翻倍——5 帧的场景减半也才 10 帧，离 60 还差六倍，治标不治本——你隐隐觉得这不是代码写错了，是画法本身到头了。

这一章回答这两个问题、验证那一个怀疑，顺便打下全书的地基：GPU 为什么快、渲染管线怎么分工、帧率的账怎么算。后面十三章都在这几块地基上盖楼。

## 一个核的独角戏

先看第一问。你在浏览器里写的 JS 跑在页面的主线程上，一个线程同一时刻只用一个核。for 循环是串行的：第 1001 个粒子必须等第 1000 个画完才轮得到自己。一般来说，浏览器也不会自动把一个 JS 循环拆给多个核——并行需要你显式安排，画布的 2D 接口又恰好不提供这种安排。所以十六个核里，十五个干看着。

再算一笔账，看看这个核背的活有多重。以本地 1080p 屏为准，假设每个粒子一趟 0.8 微秒：算一次坐标，调一次 fillRect。两万个粒子约 16 毫秒——记住这个数，讲完帧率再算总账。这里先给结论：**瓶颈不是粒子多，是所有粒子在排一条队**。队排多长，决定权在你画图的方式，不在机器的核数。

## GPU：把一万道相同的题分给一万个人

GPU（Graphics Processing Unit，图形处理器）不是「更快的 CPU」，它走另一条路线。路线由图形计算的脾气决定：对每个粒子、每个像素做的计算几乎一模一样，只是喂进去的数不同。两万个粒子算漂移，是同一道题做两万遍；一百万个像素定颜色，是同一道题做一百万遍。

通用 CPU 的晶体管大把花在聪明机关上：预测分支、缓存数据、打乱指令顺序，目标是把一件事尽快做完。图形计算用不上这些聪明——它要的不是一件事快，是一亿件一样的事同时做完。于是 GPU 反着造：砍掉大部分聪明机关，把省下的晶体管全变成简单计算单元，几千个并联。

```text
CPU：少量大核（一般 4~16 个），每个都复杂——你的循环只占其中一个
[ 大核 ][ 大核 ]
[ 大核 ][ 大核 ]

GPU：几千个简单通道同时开工，同一条指令、各喂各的数据
▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪
▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪
▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪  （实际是成千上万行）
```

拿真实数字跟一遍。设这块 GPU 有 2000 个计算通道（真实硬件一般更多）。两万个粒子 ÷ 2000 = 每通道 10 个。每个通道算 10 个粒子，还按每粒子 0.8 微秒算，一个通道共 8 微秒；所有通道同时进行，加上调度开销，总耗时也就是几十微秒的量级——对比单核的 16 毫秒，差出三个数量级。

说句公道话：单个 GPU 通道比单个 CPU 核简单，也比它慢，单挑一道题未必赢。GPU 赢的从来不是单挑，是人多。记一句：**一百个小学生各算一道加法，比一个教授一道一道算快**。小学生是 GPU 通道，教授是 CPU 大核；图形计算恰好全是「加法题」。

## 渲染管线：从一串坐标到满屏像素

知道了 GPU 是几千个通道并联，下一个问题来了：画图这件事怎么拆，才能让几千个通道互不等待、各干各的？答案是拆成三段固定工序，段内高度并行，段间像工厂流水线一样接力。这条流水线叫渲染管线（rendering pipeline），是 GPU 世界的主动脉，也是全书反复经过的主干道。

```text
你的数据             第一段：顶点阶段          第二段：光栅化           第三段：片元阶段
（一串坐标）    →    「东西在屏幕哪里」   →   「哪些格子要涂色」   →   「每个格子涂什么色」   →   屏幕
```

三段各自回答一个问题，各配一句能复述的话：

- 顶点阶段：回答「东西在屏幕哪里」。顶点（vertex）就是构成形状的角点——三角形有三个顶点，演示里的每个粒子就是一个顶点。这一段把每个角点的坐标按你的规则算成屏幕上的位置；要点动起来，动的算法也在这里逐点执行。
- 光栅化：回答「这一片盖住屏幕上哪些格子」。光栅化（rasterization）这个中文译名完全看不出含义，它干的其实是翻译：把「连接 A、B 两点的线」翻译成「屏幕上哪些格子该涂色」。
- 片元阶段：回答「每个格子涂什么颜色」。光栅化圈出来的每个候选格子叫片元（fragment）——它还不是像素，涂上颜色之后才成为屏幕像素。这一段逐格子算颜色。

其中第一段和第三段各运行一个你写的小函数，这种写给 GPU 的小函数叫着色器（shader）：管位置的叫顶点着色器，管颜色的叫片元着色器，用一种叫 GLSL 的小语言书写。着色器怎么写是下一章的主菜，本章只需要知道流水线上有这两个岗位。

拿一个粒子走一遍流水线：顶点阶段算出它此刻落在屏幕 38% 宽、64% 高的位置；光栅化圈出它盖住的那个格子；片元阶段把格子涂成天蓝色。两万个粒子，就是这条流水线跑两万遍——段内并行，段间接力。

### 光栅化细看：一条线变成五个格子

三段里，顶点阶段和片元阶段好懂（挪位置、涂颜色），光栅化最像黑箱，单独拆开看。

它存在的理由：你的数据是连续的几何——坐标、线段、三角形；屏幕却是离散的格子阵列。连续到离散之间必须有个翻译层，这个翻译就是光栅化。

跟着算一遍，在纸上就能复现：

```text
在 5×3 的格子上画线段 A(0,0) → B(4,2)：每列 x 选一行 y，取 y = round(2x ÷ 4)
x=0 → y=0               x=3 → y=2（1.5 四舍五入取 2）
x=1 → y=1（0.5 取 1）   x=4 → y=2
x=2 → y=1
该涂色的格子：(0,0) (1,1) (2,1) (3,2) (4,2)
```

给你任意一条线段，你都能在纸上数出该涂色的格子。GPU 里的光栅化每秒做几亿次这样的事，量不同，活相同——所以它天生适合几千个通道分着干。

## 帧率与掉帧：16.7 毫秒一拍的考试

为什么屏幕要一帧一帧地要新画面？屏幕不听你的，它按自己的节拍刷新：一般每秒 60 次，每次取一张「当前画好的完整画面」显示。每秒交出多少张完整画面，就是帧率；一帧没赶上下一次刷新、那一拍只能重复旧画面，就是掉帧。低于四五十帧，画面里的快速运动就开始显得一顿一顿——60 帧因此被当作及格线。

```text
60Hz 屏幕：每 16.7ms 一拍，每拍要交出一帧新画面
拍1: 帧 A 画好 ✓       拍2: 帧 B 画好 ✓
拍3: 帧 C 没画完 ✗ —— 掉帧：这一拍只能再显示帧 B
拍4: 帧 C 终于上屏 ✓
```

现在算总账。60 帧的预算：1000 ÷ 60 ≈ 16.7 毫秒一帧。本地 1080p 每粒子约 0.8 微秒，两万个粒子 ≈ 16 毫秒，踩着线过——本地预览的「60 帧丝般顺滑」不是快，是刚好不超支。投上 4K 大屏呢？4K 的像素总数是 1080p 的四倍，同一笔 fillRect 要涂的物理像素变多，画布上每个格子的开销跟着涨，每粒子的耗时按 10 微秒粗算：两万个粒子 = 200 毫秒，1000 ÷ 200 = 5 帧。和你在现场看到的现象对上了。打个比方：帧率是翻页动画的翻页速度；掉帧就是该翻页时那一页还没画完，只好把上一页再放一遍。

## 实验：同一批粒子，两种画法

下面的演示把两种画法摆进同一屏。两边画的是同一批粒子（同一份确定性随机数据），跑同一个漂移动画；粒子数从 1 万到 50 万由滑杆统一驱动，默认 2 万——正是翻车现场的规模。

左边是 4K 大屏上翻车的原版思路：每帧 JS 循环遍历全部粒子，逐个算出此刻位置，逐个 fillRect。活全在主线程的一个核上，串行排队。

右边换 WebGL，每帧只有三步。第一步，开工前把最多 50 万个粒子的起始坐标和速度一次性装进显存（GPU 自带的内存）里的一块缓冲区（buffer，装原料的整箱货运）；之后不管滑杆怎么拉，这份数据不再重传。第二步，每帧把当前时间这个数更新给 GPU。第三步，发一次 draw call（draw 是「画」、call 是「调用」，也就是 CPU 对 GPU 发出的「照单作画」指令）：`gl.drawArrays(gl.POINTS, 0, 粒子数)`。每个粒子漂到哪，由顶点着色器在 GPU 上逐点算——几千个通道同时算；第 2 章再逐行拆开这个黑盒。

```js
// 用法示例：每帧绘制的核心差异——那个 for 循环归谁
// 左：Canvas 2D——JS 逐个算、逐个画，两万次循环在一个核上串行
for (let i = 0; i < count; i++) {
  const p = positionAt(i, t)       // 算第 i 个粒子此刻在哪
  ctx.fillRect(p.x, p.y, 2, 2)     // 画它
}
// 右：WebGL——数据早已在显存，每帧只发一次画图指令
gl.drawArrays(gl.POINTS, 0, count) // 位置在 GPU 上逐点并行算
```

差距的来源一句话讲完：**一次上传，一次指令，剩下的活在 GPU 里并行**。左边把两万件一样的小事排成一列交给一个核；右边把它们连成一份清单交给几千个通道。粒子数翻倍，左边的队伍长一倍、耗时跟着涨；右边的清单长一倍，每个通道只多分到几个粒子，耗时几乎不动。这正是开头那笔账的现场版。

读数口径说明一句：演示让两边在同一个绘制循环里跑，各自只计自己那段的耗时，再换算成「假如只跑它自己」的等效帧率。60 是多数屏幕的刷新上限，读到「≥60 fps」就是「毫无压力」。数字因机器而异，趋势不变。

## 验证：亲手拉一下滑杆

- 默认 2 万：两边都流畅，但看每帧耗时，左边已比右边高一个数量级——卡顿还没发生，账已经欠下了。
- 拉到 10 万：左边等效帧率肉眼可见地下滑，右边纹丝不动。
- 拉到 50 万：左边成了幻灯片，页面其他动画也跟着顿一下（它堵的是同一个主线程）；右边通常仍然满帧。
- 独立验证：拖着滑杆，打开任务管理器的性能页看 CPU——总占用不高，却有一个核顶着不松。这就是「单核跑满」的现场，不是比喻。

## 小结与全书地图

四块地基到位：GPU 靠几千个并联通道，赢在人多不赢在单挑；渲染管线把画图拆成顶点（在哪）、光栅化（哪些格子）、片元（什么颜色）三段接力；帧率的账是 1000 ÷ 帧率 = 每帧毫秒预算，60 帧即 16.7 毫秒；掉帧就是没赶上刷新节拍。再带走一条经验判断：**像素多、重复多的活交 GPU；逻辑复杂、步骤互相等的活留 CPU**——全书反复用它决定一段代码该写在哪边。
