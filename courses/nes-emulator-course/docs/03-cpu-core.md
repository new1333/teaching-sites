# 6502 最小核心:寄存器、复位与取指循环

你把上一章拆出来的 PRG-ROM 灌进模拟器,写了个循环直接从 0 号地址开始执行。CPU「跑起来了」,寄存器每步都在变,你打日志跟了十条指令,发现取回来的全是 0——而你明明把程序放在了 $8000。半小时后你想起来去查文档:真机上电后,第一条指令不是从 0 取的,而是先到 $FFFC/$FFFD 这两个字节里读出一个 16 位「复位向量」,跳过去才开始执行。

更阴险的是,这个错误在早期几乎不报错:零地址读出 0、0 还是合法 opcode(BRK),CPU 沿着空内存一路「执行」下去,寄存器看似随机地变化,你只会觉得「模拟器不稳定」。**上电跑飞,是 6502 模拟器的第一个经典事故,而根因是一个字节的疏忽**。

这一章把 CPU 的最小可运行核心立起来:七个寄存器、一个取指-译码-执行循环、一个老老实实读复位向量的 `reset()`。指令先只要七条,但结构从第一天起就是能长到 151 条的样子。

## 寄存器:七个数字,一台计算机

6502 的全部状态就是七个寄存器,每个都只有一个字节宽(PC 除外):

| 寄存器 | 宽度 | 职责 |
|---|---|---|
| A | 8 位 | 累加器,算术与逻辑的主战场 |
| X / Y | 8 位 | 变址寄存器,循环计数、指针偏移 |
| SP | 8 位 | 栈指针,预递减;栈在 $0100-$01FF 这一页 |
| PC | 16 位 | 程序计数器,下一条指令的地址 |
| P | 8 位 | 标志位包:N V U B D I Z C,每 bit 一个开关 |

P 寄存器值得单独记:N(负)、V(溢出)、Z(零)、C(进位)是运算的结果标志,I(关中断)和 D(十进制)是控制开关,B 只在压栈时有意义,U 恒为 1。复位后的合法初值是「I 置位、其余结果标志清零」,也就是 `P = FLAG_I | FLAG_U`。

栈的约定是 6502 的性格:SP 复位为 $FD,压栈先减 SP 再写,弹出先读再加。第一章说过机器只有 2KB RAM——栈和变量全挤在里面,这是真机游戏必须精打细算的原因,也是后面手写测试程序时要时刻留意的边界。

## CPU 不认识内存,内存是注入的

模拟器分层的第一刀切在这里:**CPU 只通过 `read(addr)` / `write(addr, val)` 两个回调访问世界,不关心地址后面是 RAM、PPU 还是卡带**。真机上这正是「地址总线」的含义——CPU 只把地址放到总线上,谁应答是主板布线的事。

```ts
// src/cpu.ts · CpuMemory
export interface CpuMemory {
  read(addr: number): number
  write(addr: number, val: number): void
}
```

本章的测试用一块平坦的 64KB `Uint8Array` 冒充所有内存;到总线一章,会把这两个回调接到真正的路由器上。CPU 代码从此一行不用改——**依赖注入在模拟器里不是设计洁癖,是硬件架构的直接映射**。

## 取指-译码-执行:三行循环

CPU 的一生就是同一个循环:从 PC 取一个字节当 opcode;查表得到「做什么、操作数在哪、花几个周期」;执行。实验场里的 `step()` 每执行一条指令返回它消耗的周期数——这个返回值现在是测试的断言对象,到帧时序一章就是 PPU 追赶的节拍来源,值得从第一天就写对。

```ts
// src/cpu.ts · step(节选)
step(): number {
  const at = this.PC
  const opcode = this.fetch8()
  const op = OPS[opcode]
  if (!op) {
    throw new Error(`未知 opcode $${u8(opcode).toString(16).padStart(2, '0')} @ $${at.toString(16)}`)
  }
  const operand = op.mode === 'imm' ? this.fetch8() : op.mode === 'abs' ? this.fetch16() : 0
  op.run(this, operand)
  return op.cycles
}
```

指令表 `OPS` 是「一个 opcode = 助记符 + 寻址模式 + 周期数 + 行为函数」四元组的字典。本章只有七条,但表结构就是完整指令集的形状——后面两章只是往这张表里填条目,`step()` 本身不再变。

`fetch8` 每读一字节就把 PC 前进一格,并做 16 位回卷(`u16`)。这类「静默回卷」在 8 位机里无处不在,实验场统一放在 `src/util.ts` 的 `u8`/`u16` 里,后续所有运算都经过它们——一个忘了回卷的进位,足以让程序在 $FFFF 边界上跳进深渊。

## 复位:读向量,不是猜地址

```ts
// src/cpu.ts · reset
reset(): void {
  this.SP = 0xfd
  this.P = FLAG_I | FLAG_U
  this.A = 0
  this.X = 0
  this.Y = 0
  this.PC = this.read16(0xfffc) // 复位向量:$FFFC 低字节、$FFFD 高字节
}
```

$FFFC/$FFFD 里存的是什么?是卡带 PRG-ROM 的最后两个字节——卡带在制造时就把「程序入口」烧在那里。这也解释了上一章的一个细节:为什么 NROM 卡带要把 16KB 程序镜像到 $8000-$FFFF——**复位向量在 $FFFD,卡带必须出现在那个地址,机器才找得到入口**。

同理,$FFFA/$FFFB 是 NMI 向量、$FFFE/$FFFF 是 IRQ/BRK 向量。中断一章会回到这张向量表,现在先把位置记住。

## 验证

`tests/cpu-core.test.ts` 用手写机器码逐项断言:复位后 PC 指向向量内容、寄存器初值、`LDA #$05` 装入 A 且耗 2 周期、`LDA #$80` 置 N 标志、绝对地址读写、`JMP` 跳转后从新地址继续取指、未知 opcode 抛出带地址的错误。九个用例,全绿。

值得看一眼测试的组织方式——程序就是十六进制字面量数组,每行注释助记符:

```ts
// tests/cpu-core.test.ts · makeCpu(节选)
const ram = new Uint8Array(0x10000)
ram.set(program, org)          // 程序放 $8000
ram[0xfffc] = org & 0xff       // 复位向量低字节
ram[0xfffd] = org >> 8         // 复位向量高字节
const cpu = new Cpu({ read: (a) => ram[a], write: (a, v) => { ram[a] = v } })
cpu.reset()
```

这个「内存注入 + 复位向量」的小架子,后面每一章的 CPU 测试都会复用。

## 小结

CPU 的可运行核心不过百行:七个寄存器、一张 opcode 表、一个读复位向量的 `reset()`。三条设计决策要带走:内存靠注入(CPU 不认识路由)、指令表四元组(为补全 151 条留好形状)、`step()` 返回周期数(为时钟同步埋线)。下一章往表里填的不是指令,而是指令的「取数方式」——13 种寻址模式。
