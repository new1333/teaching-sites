# 三块芯片的合奏:NES 硬件全景与时钟同步

动手写模拟器的第一晚,大多数人会踩同一个坑:抄半张 6502 指令表,搭一个执行循环,让 CPU 全速跑——每秒几百万条指令,风驰电掣。然后盯着一片黑的屏幕发呆。没有报错,没有崩溃,一切看起来都「正常」,只是画面永远不出现。

问题不在指令表抄没抄对,而在于你模拟的本来就不是一个「CPU」,而是一台由多块芯片协作的机器:CPU 只负责算,画面由另一块芯片按自己的节拍生成,而两者的时间必须严格对齐——CPU 每走一个周期,图形芯片要走三个点。缺了这个对齐,游戏里「等垂直消隐再上传画面数据」的代码永远等不到时机,于是什么都画不出来。

这一章不写代码。先把整台机器的地图装进脑子,后面每一章都是在这张地图上施工。

## 真机上是三块芯片在合奏

把一台 NES 拆开,和模拟器有关的是三块芯片和一张卡带,像一支四人乐队:

- **中央处理器(CPU)**:核心是一颗 6502(任天堂定制版叫 2A03),8 位,主频约 1.79MHz。它执行卡带里的程序,靠十几种寻址模式取操作数,是唯一「会思考」的角色——主唱。
- **图形处理器(PPU,2C02)**:独立于 CPU 的绘图芯片,频率是 CPU 的三倍。它不执行程序,只按固定节拍把显存内容变成电视信号——吉他手,不 听 主唱的,只听节拍器。
- **声音处理器(APU)**:和 CPU 封装在同一颗 2A03 里,负责方波、三角波和噪声。本课程主线不实现它,但会留好接口与路线。
- **卡带**:它不是外设,而是总线上的第一等公民。卡带里有两块 ROM——PRG-ROM 存程序(给 CPU 读),CHR-ROM 存图形数据(给 PPU 读),板子上还有映射器(mapper)电路,决定这两块 ROM 如何出现在地址空间里。

最后一个角色是节拍器:一颗约 21.47MHz 的主晶振,经分频后驱动所有芯片。**整台机器的秘密全在「谁在什么节拍上做什么」**。

## 两条总线:CPU 总线与 PPU 显存

CPU 眼中只有一个 64KB 地址空间,但这个空间被硬件划分给了不同设备:

```text
CPU 总线(16 位地址空间 $0000-$FFFF)
┌──────────┬─────────────┬───────────────┬─────────────────┐
│ $0000    │ $2000       │ $4000         │ $4020           │
│ 机器内部  │ PPU 的      │ APU 与手柄    │ 卡带窗口        │
│ RAM 2KB  │ 8 个寄存器   │ 的寄存器      │ (PRG-ROM 在此) │
└──────────┴─────────────┴───────────────┴─────────────────┘
```

注意第一栏:机器内部 RAM 只有 2KB,却占着 8KB 的地址段——同一块 RAM 在 $0000-$1FFF 里重复出现四次,这就是镜像(mirroring)。同样的把戏在 PPU 寄存器段($2000-$3FFF 每 8 字节重复一次)和显存里都存在。模拟器如果只认「第一个」地址,真机程序写到镜像地址的数据就会凭空丢失——这是新手模拟器最常见的一类「无声无息的 bug」。

PPU 还有自己的第二条总线,连接显存:命名表(nametable,记录「屏幕每个 8×8 格子画哪个瓦片」)、图块表(pattern table,瓦片的位图库)、调色板(palette,把像素值映射成 64 种系统色之一)。CPU 不能直接访问这条总线,只能通过 $2006/$2007 两个寄存器一点一点地读写——这个「绕道」是很多真机程序的写法根源。显存之外还有一块 256 字节的精灵内存(OAM),记录 64 个精灵的位置与图案;PPU 画图时把瓦片数据装进移位寄存器,再一个像素一个像素地吐到屏幕上。

## 3:1 的时钟,与一帧的形状

CPU 和 PPU 各自跑在自己的频率上,但锁定为 3:1——CPU 一个周期里,PPU 走三个点(dot)。PPU 用「扫描线与点」组成的二维坐标来计时:

```text
一帧 = 262 条扫描线 × 341 点 = 89342 个 PPU 周期(约 60Hz)
├─ 扫描线 0-239:可见区,每线画出 256 个像素
├─ 扫描线 240:后渲染,歇一口气
├─ 扫描线 241-260:垂直消隐(VBlank),不画图,显存开放写入
│    └─ 进入时 PPU 拉起不可屏蔽中断(NMI),通知 CPU「现在可以上传了」
└─ 扫描线 261:预渲染,为下一帧重置内部状态
```

游戏的主循环几乎都长一个样:垂直消隐一开始,PPU 就拉起不可屏蔽中断(NMI);游戏在中断处理例程里趁这段时间更新显存,回到主循环算游戏逻辑,等下一次 NMI。所以模拟器只要把「CPU 执行指令耗掉 N 个周期 → PPU 前进 3N 个点 → 到点触发 NMI」这条链对齐,画面自己就会出来。

## 模拟器怎么切模块

按硬件边界切,代码就不会拧成一团乱麻。本课程的伴生实验场最终长这样:

| 模块 | 对应硬件 | 职责 |
|---|---|---|
| `ines.ts` | 卡带的外壳 | 把 .nes 文件(iNES 格式)拆成 PRG、CHR、映射器号、镜像模式 |
| `cpu.ts` / `opcodes.ts` | 2A03 的 6502 核心 | 寄存器、取指执行、全部官方指令与周期数 |
| `ppu.ts` | 2C02 | 寄存器、显存、背景与精灵渲染、帧时序 |
| `bus.ts` | 主板上的连线 | 地址路由与镜像,把上面三者连成整体 |
| `controller.ts` | 手柄接口 | 把按键变成 CPU 可读取的串行数据 |
| `nes.ts` | 整机外壳 | 时钟同步主循环:`runFrame()` 跑出一帧 |

推进策略采用指令级追赶(catch-up):CPU 每执行一条指令,返回它消耗的周期数,主循环立刻让 PPU 补走三倍的点。这是「能正确跑起来」与「工程量可控」之间的最佳平衡点;更精细的逐周期模拟、更复杂的映射器,留到最后一章的精度阶梯再谈。

## 小结

NES 是三块芯片加一张卡带的总线合奏:CPU 执行程序,PPU 按三倍节拍画面,卡带是总线上的普通设备;时间以「一帧 262 线 × 341 点」计量,游戏的呼吸节奏由 VBlank 与 NMI 驱动。模拟器的模块边界就画在硬件边界上,推进用指令级追赶。接下来,先从把一张卡带拆开开始。
