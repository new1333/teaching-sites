# 寻址模式:操作数从哪里来

你从一份老游戏的反汇编清单里抄了三行初始化代码到自己的测试程序里,跑起来程序就飞了:PC 莫名其妙跳到一段空内存,然后是无穷无尽的乱序执行。逐条排查两小时,凶手指向 `JMP ($10FF)`——按你的直觉,它应该读 $10FF 和 $1100 拼出目标地址;但真机读的是 $10FF 和 $1000。就差这一个字节,CPU 跳进了完全不同的世界。

这不是你抄错了,这是 6502 芯片自己的 bug:间接跳转的指针加一时,进位被丢弃,只翻转低字节。1983 年之后所有的软件都绕着它走,而模拟器必须**忠实地复现这个 bug**——「按直觉修正」的模拟器,反而跑不对为真机写的程序。

这一章把 13 种寻址模式统一成一层「算出操作数在哪」的逻辑,并原样实现零页绕回、间接跳转页 bug 这类硬件怪癖。它们是 6502 的地形,踩不准,后面 151 条指令全是雷。

## 一个操作数,十三种取法

同一条 `LDA`,操作码不同,取数方式就不同:`LDA #$05` 取常数 5;`LDA $05` 读零页 5 号;`LDA ($05),Y` 先到零页 5 号读一个 16 位基地址,再加 Y。寻址模式(mode)描述的正是这层「从操作码字节到操作数本体」的路径:

| 模式 | 汇编写法 | 路径 |
|---|---|---|
| 隐含 imp | `INX` | 没有操作数,目标在寄存器里 |
| 累加器 acc | `ASL A` | 目标就是 A |
| 立即 imm | `LDA #$05` | 操作码后跟的就是值 |
| 零页 zp | `LDA $05` | 1 字节地址,高字节恒 0,快 1 周期 |
| 零页,X zpX | `LDA $05,X` | 零页地址加 X,**绕回零页** |
| 零页,Y zpY | `LDX $05,Y` | 同上,换 Y |
| 绝对 abs | `LDA $0300` | 2 字节完整地址 |
| 绝对,X absX | `LDA $0300,X` | 完整地址加 X,16 位正常进位 |
| 绝对,Y absY | `LDA $0300,Y` | 同上 |
| 间接 ind | `JMP ($1000)` | 地址里存的是目标地址(仅 JMP 用) |
| (零页,X) indX | `LDA ($10,X)` | 先加 X 找到指针,指针里存目标地址 |
| (零页),Y indY | `LDA ($10),Y` | 先读指针基地址,再加 Y |
| 相对 rel | `BEQ +2` | 1 字节带符号偏移,相对下一条指令 |

设计上只有一个决策:实验场把这 13 条路径全部收进 `operand(mode)` 一个函数。指令表里的每条指令只声明「我用哪种模式」,执行时拿到统一语义的操作数——内存类模式给地址,imm 给值。指令的实现因此完全不去碰地址算术:

```ts
// src/cpu.ts · step(节选)
this.pageCrossed = false
this.branchTaken = false
const operand = this.operand(op.mode)
op.run(this, operand)
```

## 绕回:零页是圆环,不是数轴

零页($00-$FF)是 6502 的「寄存器堆」——访问它比访问其他页快一个周期,所以游戏代码里挤满了零页寻址。代价是所有零页运算都只有 8 位:`zpX` 模式算出的地址高字节永远不进位:

```ts
// src/cpu.ts · operand(节选)
case 'zpX': {
  // 零页绕回:$FF + 1 = $00,不进位到第二页
  return u8(this.fetch8() + this.X)
}
```

`STA $FF,X` 在 X=5 时写到 $0004,不是 $0104。同一个算式在 `absX` 模式下却是 16 位正常进位——`(zp),Y` 更刁:基地址来自零页(取指针那一步绕回),基地址加 Y 那一步却正常进位。三种规则并存的根源是芯片里不同的加法器路径,模拟器没有捷径,只能逐条按硬件来:

```ts
// src/cpu.ts · operand(节选)
case 'indY': {
  const base = this.read16ZpWrap(this.fetch8()) // 基地址来自零页(自身绕回)
  return u16(base + this.Y) // 但加 Y 是 16 位正常进位
}
```

测试里专门有一条:`LDA ($20),Y`,基地址 $02F0、Y=$20,目标必须是 $0310——差一个进位,你得到的就是 $0200 段的另一个字节。

## 间接跳转的页 bug

`JMP ($1000)` 的语义是「到 $1000/$1001 读 16 位目标」。硬件实现里,指针自增只发生在低字节上,于是 `JMP ($10FF)` 读低字节用 $10FF、读高字节却回到 $1000:

```ts
// src/cpu.ts · read16NoPageWrap(仅 JMP 间接寻址使用)
private read16NoPageWrap(p: number): number {
  const lo = this.mem.read(p)
  const hi = this.mem.read((p & 0xff00) | ((p + 1) & 0xff))
  return lo | (hi << 8)
}
```

函数名直接叫 NoPageWrap,把「这是故意的不跨页」写在脸上——否则未来某次重构手滑把它「修好」,就会以最隐蔽的方式毁掉兼容性。`(zp,X)` 的指针读取也有同类绕回(指针 $FF 加 X 后回到 $00 开头读两个字节),同样原样实现。

## 相对寻址:分支只带一个字节的行李

条件分支(BEQ、BNE 一族)不存绝对目标,只存「离下一条指令多远」的带符号偏移,范围 -128 到 +127。好处是代码整体搬位置时分支不用重定位——游戏卡带里代码块经常被搬来搬去。执行时把偏移按带符号数解释:

```ts
// src/cpu.ts · branch
branch(taken: boolean, offset: number): void {
  this.branchTaken = taken
  if (!taken) return
  const from = this.PC // PC 已越过操作数
  const target = u16(from + i8(offset))
  this.pageCrossed = (from & 0xff00) !== (target & 0xff00)
  this.PC = target
}
```

`i8` 把 $FC 解释成 -4 而不是 252——测试里 `BEQ -4` 从 $8004 跳回 $8000,断言的就是这个带符号语义。注意 `branch` 顺手记录了两件事:是否跳了、是否跨页——它们对应真实硬件「跳转成功多花 1 周期、跨页再多 1 周期」的计费,周期表补全一章会来对账。

## 验证

`tests/addressing-modes.test.ts` 十四个用例,每种模式至少一条:零页与绝对的基础路径、`zpX` 的 $FF+5 绕回、`(zp,X)` 指针表与指针自身绕回、`(zp),Y` 的正常进位与写入、`JMP ($10FF)` 页 bug(还放了个 $1100 的干扰字节,读错高字节立刻现形)、相对寻址的正负偏移与不成立路径。连同前两章的 19 个用例,33 个全部通过。

其中页 bug 那条测试值得再看一眼——**断言写的是「错误」的地址 $ABCD**:

```ts
// tests/addressing-modes.test.ts(节选)
ram[0x10ff] = 0xcd // 低字节正常取 $10FF
ram[0x1000] = 0xab // 高字节取 $1000——硬件 bug,不读 $1100
ram[0x1100] = 0x99 // 干扰项:如果实现错了会读到它
cpu.step()
expect(cpu.PC).toBe(0xabcd)
```

给「怪癖」写测试时,放一个「正确实现才会踩中」的干扰项,是最便宜的回归保险。

## 小结

13 种寻址是 6502 全部指令的取数骨架:零页是绕回的圆环,绝对与变址正常进位,间接跳转带着出厂 bug,分支只带一字节行李。实验场用一个 `operand()` 统一了这层地形,顺手埋好了跨页与跳转成功的周期记账。下一章往表里填满 151 条官方指令,把 N/V/Z/C 四个标志位一个不漏地做对。
