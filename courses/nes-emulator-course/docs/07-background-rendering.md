# 背景渲染:8 个点画一块瓦片

你先写了个「整帧画位图」的渲染器:扫一遍命名表,32×30 个格子挨个解码瓦片,直接铺满一个 256×240 的画布。跑几个自制场景,画面居然都是对的——你开始怀疑那些讲「fetch 流水线」的文章是小题大做。直到你加载一个带状态栏的真游戏:画面上半部分是滚动的地图,底部状态栏纹丝不动,而你的渲染器整帧错位、上下撕裂,滚动越快撕得越狠。

原因:游戏在**一条扫描线的中途**改写了滚动寄存器——状态栏那几行用一个滚动量,上面用另一个。整帧画位图的模型里根本不存在「中途」这个概念;而真机是每 8 个 dot 取一块瓦片、装进移位寄存器、一个像素一个像素吐出来的,滚动寄存器什么时候改,就从什么时候生效。这一章把这套流水线按 dot 复刻出来。

## 画面的三层组织

先把数据模型立起来。NES 的背景是一面「瓦片墙」:

- 图块表(pattern table,$0000-$1FFF):256 个 8×8 瓦片的位图库。每瓦片 16 字节——8 行 × 2 个位平面,两个平面同一位叠出 0-3 的像素值。
- 命名表(nametable,$2000-$2FFF):32×30 的格子,每格 1 字节存「画哪个瓦片」;紧随其后的 1KB 属性表,每字节管 16×16 像素(2×2 格)用哪组调色板。
- 调色板(palette,$3F00):32 字节,前 16 项给背景。像素值 0 是透明,直接显示 universal 底色 $3F00。

一个像素的诞生:命名表给出瓦片号 → 图块表按 v 寄存器里的 fine-Y 取第几行、两个位平面各取一位 → 属性表给出 2 位调色板号 → 拼成 4 位地址查调色板 → 64 色系统色 → RGB。第一章说的「移位寄存器逐像素出图」就藏在这一步。

## 每 8 个 dot 一拍:fetch 序列

PPU 画一条扫描线的节拍是固定的,周期为 8:

```text
组内相位  0-1      2-3      4-5       6-7
取什么    命名表   属性表   图块低位   图块高位
```

每 8 个 dot 取齐下一块瓦片的全部数据,装进一对 16 位移位寄存器的低 8 位;高 8 位存的是「正在画」的瓦片,每 dot 左移一位,像素从第 15 位读出。**两块瓦片在寄存器里接力,画完一块,下一块恰好从低 8 位移到高 8 位**——流水线深度正好两块,这就是为什么每条扫描线的头两块瓦片要由上一条线(dot 321-336)提前取好。实验场的核心循环:

```ts
// src/ppu.ts · tick(节选)
// 像素先于移位读取(读-后-移):bit15 恰好是当前瓦片最左未画的像素
if (visible && this.dot >= 2 && this.dot <= 257) this.renderPixel()

if ((visible || preRender) && rendering) {
  const c = this.dot
  if ((c >= 2 && c <= 257) || (c >= 321 && c <= 337)) {
    this.shiftBg()
    switch ((c - 1) & 7) {
      case 0: {
        this.loadBgShifters()
        this.ntLatch = this.ppuRead(0x2000 | (this.v & 0x0fff))
        break
      }
      // case 2 属性 / case 4、6 两个位平面 / case 7 推进 coarseX
    }
  }
  if (c === 256) this.incVert()
  if (c === 257) this.v = (this.v & ~0x041f) | (this.t & 0x041f)
}
```

有一个顺序细节值得专门踩一遍:像素必须在**移位之前**读。第一版把 `renderPixel()` 放在移位之后,测试全黑——每个像素读到的是「已经移出去的下一位」,整幅画往左错一格、且跨界处全糊。这类 bug 没有报错,只有像素不对,靠断言单点颜色才抓得出来。

## v 寄存器:一边画一边走的取数指针

fetch 用哪个瓦片,由 v 寄存器决定——上一章存进去的那些位段,现在开始行走:

- 每取完一块瓦片(dot 8 的倍数)incHorz:coarseX +1;到 31 折回 0,并翻转位 10(跳到水平相邻命名表)。所以水平滚动到屏幕边缘会自动进入下一块表——512 像素宽的关卡场景就是两张表来回倒着用。
- 扫描线末尾(dot 256)incVert:fine-Y +1;到 7 归零后 coarseY +1,到 29 归零并翻转位 11(跳到垂直相邻表)。这就是「下一个瓦片行」的推进。
- dot 257 水平回抄:v 的水平位(位 10 + coarseX)从 t 复制回来;预渲染线(dot 280-304)再把垂直位也抄回去。游戏在 VBlank 里写进 t 的新滚动量,由此在新一帧生效——**中途改 $2005/$2006,生效时机全在这两个回抄点**,这就是状态栏分屏的硬件机制。

fine-X 不参与 v,它是像素读位时的选择器:`bit = 0x8000 >> fineX`,同一套移位流里从第 fineX 位开始读。测试里 fine-X=3 的断言恰好验证这一点:屏幕第一个像素是瓦片内第 4 个像素,而不是「前一格的尾巴」。

## 像素合成

```ts
// src/ppu.ts · renderPixel(节选)
const bit = 0x8000 >> this.x
const p0 = this.bgShiftLo & bit ? 1 : 0
const p1 = this.bgShiftHi & bit ? 1 : 0
const a0 = this.atShiftLo & bit ? 1 : 0
const a1 = this.atShiftHi & bit ? 1 : 0
const pix = (p1 << 1) | p0
const clipped = x < 8 && !(this.mask & 0x02) // 左侧 8 像素裁剪
const v = clipped || pix === 0 ? 0 : (((a1 << 1) | a0) << 2) | pix
color = this.palette[v]
```

属性位也进移位寄存器——把 2 位调色板号展开成全 0/全 1 的字节,与图案位平面同步移位,读的时候再取一位,天然保持对齐。像素值 0 一律显示 universal 底色,这为精灵的「透明」留了位置。最后经 `rgbOf()` 查 64 色表写进 256×240×3 的帧缓冲——这个数组就是后面所有验证的断言对象。

## 验证

`tests/background-rendering.test.ts` 七个用例,全部断言帧缓冲里的具体像素:瓦片左半 4 像素是调色板 color1、右半与空白格是底色;渲染关闭时整帧底色;一帧恰好 89342 个 dot、tick 帧尾返回一次 true;fine-X=3 时首像素来自瓦片内 px3;垂直镜像下选命名表 1 画面来自物理表 1;属性字节低 2 位让左上象限整体换调色板。

有一个测试设计细节要交代:像素断言前都先跑两帧。冷启动的第一帧,第 0 行的前两块瓦片还没被预取过(预取发生在上一帧的预渲染行),按硬件行为就是空白——这不是 bug,是流水线深度为 2 的直接推论,真机上电第一帧同样如此。另外,「一帧 89342 dot」说的是偶数帧;渲染开启时奇数帧会在预渲染行少走最后一个 dot(89341),这个跳点属于帧时序的话题,帧时序一章会实现并验证。

## 小结

背景渲染的关键不是「会画瓦片」,而是把取数、移位、滚动推进绑在正确的 dot 上:每 8 dot 一拍 fetch、移位先于像素或后于像素差一格、v 的水平/垂直回抄决定滚动生效时机。开章那个「状态栏撕裂」的病根——整帧渲染没有时间维度——已经消除。下一章让第二层画面登场:精灵、OAM,和那个著名的 sprite 0 hit。
