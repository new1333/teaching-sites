# 精灵、OAM DMA 与 sprite 0 hit

精灵画出来了,颜色位置都对,你加载一个真游戏——卡死在标题画面。按 Start、按方向,毫无反应。打日志跟踪 CPU,发现程序在一个轮询循环里出不去了:它在等 $2002 的第 6 位,精灵零命中(sprite 0 hit)标志,等不到就永远等下去。

这个标志是 NES 分屏的基石:游戏把 0 号精灵放在状态栏底边,等它和背景重叠的那一刻——「扫描线画到这里了」——再改滚动寄存器,状态栏以下的画面就能用另一套滚动量。你的模拟器没实现这个置位,所有依赖分屏检测的游戏就停在第一帧。这一章把精灵层完整接进上一章的 dot 循环:OAM、每线 8 个的取舍、翻转与优先级、$4014 整块搬运,最后是那个要命的 hit。

## OAM:64 个精灵,每人 4 个字节

精灵内存(OAM)是 256 字节的独立显存,切给 64 个精灵,每个 4 字节:

| 字节 | 含义 |
|---|---|
| 0 | y 坐标(注意:硬件画在 y+1 行) |
| 1 | 瓦片号 |
| 2 | 属性:bit0-1 调色板 / bit5 前后 / bit6 水平翻转 / bit7 垂直翻转 |
| 3 | x 坐标 |

「y 写 10、画面出现在第 11 行」这个差一不是实现细节,是硬件事实,测试里专门断言了它。CPU 侧经 $2003(地址)/$2004(数据)一字一字访问,但游戏几乎不这么干——256 字节挨个写太慢,大家都用 $4014 DMA 让 DMA 电路整页搬运。

DMA 的实现分两半:Bus 记下挂起的源页,真正搬运在指令间隙执行:

```ts
// src/bus.ts · runPendingDma
runPendingDma(): boolean {
  if (!this.dmaPending) return false
  this.dmaPending = false
  for (let i = 0; i < 256; i++) {
    this.ppu.oamWrite(this.read((this.dmaPage << 8) | i))
  }
  return true
}
```

为什么不直接在 write 里搬完?因为 DMA 要**偷走 CPU 的 513 个周期**,这段时间 PPU 还在走——这个周期账要记在整机主循环头上,下一章的 catch-up 循环就是为此设计的。

## 每线 8 个:二级 OAM 的取舍

硬件画每条扫描线时只养得起 8 个精灵:扫描线末尾的 dot 257 起,PPU 扫一遍 OAM,把「y 覆盖下一条线」的前 8 个搬进 32 字节的二级 OAM,第 9 个开始丢弃并置溢出标志。实验场把这个「挑选 + 取图案」合在 `evaluateSprites(nextLine)` 里,时机同样是 dot 257:

```ts
// src/ppu.ts · evaluateSprites(节选)
const y = this.oam[i * 4]
const dy = nextLine - y - 1 // OAM 的 y 是「屏幕行 - 1」
if (dy < 0 || dy >= height) continue
if (count < 8) {
  // 取两个位平面,翻转在取数阶段完成
  ...
  count++
} else {
  this.spriteOverflow = 1
}
```

三个语义点:数组序即优先级序(OAM 里排前面的精灵赢);溢出标志是「正确计数」的简化版——真机的溢出判定有个著名硬件 bug,会在特定模式下误报,这里按语义实现、精度差异记进最后一章;翻转在取数时一次完成,垂直翻转对 8×16 精灵是整幅上下翻,包括上下两个瓦片的选择。

## 合成与 sprite 0 hit

渲染像素时,背景层算完后叠精灵层。判定链很短:**第一个碰到不透明像素的槽赢;它若声明「在背景后」,且该处背景不透明,精灵就不显示**:

```ts
// src/ppu.ts · renderPixel 精灵段(节选)
const p = (((u.hi >> sb) & 1) << 1) | ((u.lo >> sb) & 1)
if (p === 0) continue
if (u.isSprite0 && bgPix !== 0 && this.mask & 0x08) this.sprite0Hit = 1
const behind = (u.attr & 0x20) !== 0
if (bgPix !== 0 && behind) break // 精灵在背景后:背景赢
sprPix = p
sprColorIdx = 0x10 | ((u.attr & 3) << 2) | p
```

sprite 0 hit 的置位条件就一行:精灵 0 的不透明像素与背景不透明像素重叠。三个边界也做了:左侧 8 像素裁剪开着时那一段不算重叠;精灵或背景任一层关闭时不算;标志在预渲染行开头清零。测试里观察标志要趁帧内——预渲染行一过标志就没了,这正是真机轮询循环必须「及时」的原因。

还有一个容易漏的细节:左侧裁剪对背景和精灵是两个独立的开关(mask 的 bit1 与 bit2),游戏可以「背景裁掉、精灵保留」。取数阶段的 8×16 模式也值得一提——瓦片号的 bit0 选图块表、bit1-7 给瓦片对,行号 bit3 决定取上瓦片还是下瓦片,这套编址让大精灵只用一个瓦片号就能表达,取数代码里三个位运算完成全部映射。

## 验证

`tests/sprite-rendering.test.ts` 九个用例:精灵出现在 y+1 行、x 列,左半 4 像素着色右半透明;水平翻转后图案镜像;前景精灵盖住背景、透明处露出背景;背景后精灵在不透明背景上完全不可见;sprite 0 hit 重叠置位、不重叠不置位;同线第 9 个精灵被丢弃且溢出标志置位;$4014 DMA 整页搬运与一次性语义;$2004 写入推进 OAMADDR、DMA 从 OAMADDR 起写满回卷。累计 81 个用例全绿。

这章的测试还有一个值得留意的组织:像素类断言跑两帧后查帧缓冲;标志类断言(sprite 0 hit、溢出)用 `tickToLine` 把时间推进到帧内特定扫描线再读——**标志是「瞬态」的,观察时机本身就是要测的语义**。

## 小结

精灵层的全部秘密是「每线 8 个的取舍 + OAM 序优先级 + 一个置位条件」;$4014 DMA 把搬运成本转移给主循环记账。至此 PPU 的像素部分完工,但时间轴还缺最后一块:VBlank 何时来、NMI 怎么触发、CPU 和 PPU 怎么按 3:1 焊在一起。下一章是整机的 heartbeat。
