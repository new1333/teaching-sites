# 整页替换 vs 双语对照：两种翻译世界观

## 同一个页面，两次翻译

找一个你常逛的英文页面。技术文档最好：有正文段落，有顶部导航，还有一段示例代码。在这个页面上，做两次不同的翻译操作。

第一次，点浏览器自带的「翻译此页」。页面闪一下，整页变成中文——这是整页替换。原文消失了，想核对一个词的原始含义，只能在「显示原文 / 显示译文」之间来回切。那段示例代码也常遭殃：`<pre>` 里的关键字和函数名一起进了机器，代码被翻译得面目全非——它本来就不是写给人翻的。

第二次，换一类工具——沉浸式翻译这类「双语对照」工具：原文一字不动，译文紧贴在每段原文的下面。按下快捷键，页面几乎没动。每段英文下方慢慢多出一行浅色中文，导航还是导航，代码块原封不动。而且译文逐段出现：第一段先落地，你已经开始读了，第五段还在路上。往下滚动，新加载的内容也跟着被翻。

同一个页面，同样叫「翻译」，行为差别为什么这么大？这不是功能多少的差别，是两种世界观：一个把网页当一串文本，一个把网页当一棵活的对象树。这本书要造的是后者。先把两种世界观各自展开看一遍。

## 字符串世界观：一个说得圆、但站不住的想法

先把那个「错」的想法说圆，因为它一点都不傻。

如果你把网页看成一个 `.txt` 文件——一串字符——那「翻译网页」最自然的做法就是：拿到 HTML 字符串，找出英文，换成中文，再塞回去。整页替换给你的观感正是这一路数：页面是一件可以整体换掉的东西。我们不去猜某家浏览器内部怎么实现，只看它呈现的世界观——整体换掉。

这个想法错在前提。**网页不是一串文本，是一棵活的对象树**。浏览器把 HTML 解析成 DOM 树（Document Object Model，文档对象模型）：页面上每个标签都是树上的一个节点对象，段落是节点，`<a>` 是节点，连一段文字本身也是节点。「活」有两个含义。

其一，对象上改一笔，页面立刻变。任何页面的控制台里，跑这三行：

```js
// 用法示例
// 浏览器控制台，任意页面可直接跑
const p = document.querySelector('p');  // 从树上摘一个段落节点
p.style.background = '#ff9';            // 改它的属性
// 页面当场高亮——中间没有「保存」「刷新」这些步骤
```

其二，事件监听器挂在这些节点对象身上，不在 HTML 里。你写的每个 `addEventListener`，登记的都是「某个具体节点对象」与回调的对应关系。这层关系存在内存里，HTML 字符串里找不到它，序列化（把内存里的对象转回一串字符）也带不走它。

理解了「活」，再看字符串替换实际做了什么：把整棵树砍掉，用解析字符串得来的一批全新节点重建。新树看起来和旧树一模一样，但那是另一批对象——像用同一张底片又洗了一张照片：画面相同，照片是两张。于是四笔账一起到期：

- **事件全灭**。旧节点连同监听器一起进了回收站；新按钮长得一样，身上什么都没挂。
- **状态全灭**。你在输入框里打的字、展开的折叠面板、视频播到第几分钟——都活在节点对象的属性里，序列化一趟就丢了。
- **原文消失**。替换即销毁，想对照只能整页切回去。
- **代码遭殃**。对一串字符来说，`<pre>` 里的内容和正文没有本质区别，都是「待翻文本」。

还有第五笔：真实页面是活的。信息流往下滚，页面脚本不断往树上挂新节点，你替换好的字符串很快就会被页面自己的更新冲掉。

这五笔账，下面演练槽里你会亲手验一笔最疼的。

## 树上世界观：不动原文，挂一根新枝

为什么会有「双语对照」这种产品形态？因为读外文页面的人常常要核对原文：技术文档里一个术语译得对不对，法律文本里一句话的原始含义，都得回头看。整页替换恰恰把「回头看」的路堵死了。对照是需求，不是装饰。

这类工具眼里是同一棵 DOM 树，做法整个反过来：一个字都不动原文，只往树上挂新枝。为什么这样就安全？因为「插入新节点」不销毁任何旧对象——原文节点、它身上的监听器、它记住的状态，全都站在原地。

对每个装着正文文字的段落节点：取它的文本，送去翻译；译文回来，新建一个节点，插到原文的正下方。于是原文与译文成了一对兄弟节点，一段原文领着一段译文。

```js
// 用法示例
// 控制台继续跑：给刚才那个段落挂一根「新枝」
const zh = document.createElement('p');
zh.textContent = '【假译文】这一段的意思是……';
p.after(zh);  // after()：把 zh 插到 p 的正后方当兄弟节点
              // 等价于 insertBefore(zh, p.nextSibling)，只是省事
```

开篇的四个现象，到这里全部有了着落：

- 原文不消失——它根本没被碰过，核对原文就是看上一行；
- 代码不遭殃——译文是「挑出来的节点」才有资格领的，挑节点时把 `<pre>` 排除在外即可；
- 页面其余部分纹丝不动——链接能点、按钮能按，它们的节点对象和监听器原封未动；
- 译文逐段出现——树上挂枝天然是增量操作：第一段的译文回来就插第一段，不必等全页翻完。

「挑节点」按什么单位挑？页面的段落感来自一类默认独占一行的元素——`p`、`h1`、`li`，习惯叫块级元素；另一类默认待在行内、不截断一行——`strong`、`a`、`code`，叫内联元素。双语引擎以段落为单位发翻译、插译文，靠的就是这对概念。至于块级 / 内联到底是谁规定的——它并不是标签与生俱来的属性，真身藏在浏览器的默认样式表里。这段辨析，连同「几千个节点里怎么挑出该翻的那几百个」，都是第 2 章的正题。本章记住人话版就够：独占一行的是块，待在行内的是内联。

挂新枝还有两个小讲究，先记两个名词：

- 插进去的译文节点要打记号——一个 `data-` 开头的属性，比如 `data-duo="1"`，这叫标记属性。引擎靠它认出「这个节点是我插的」：重复翻译时不重复插，页面变化时也不会把自己的译文再当原文翻一遍。
- 挂枝要节制。每插一个新节点，浏览器都要重新计算这一带的布局——重排（reflow）。一百段译文若一段一个时机、分一百次插，就可能重排一百次，页面会卡。所以真实引擎攒一批、一次插进去。

## 四个部件：引擎拆开长这样

把「在活树上做翻译」拆到能动手的程度，不管工具叫什么名字，这类引擎都是四个部件：

```text
页面：一棵活的对象树（DOM 树）
 ① 抽取（extract）：遍历树，挑出直接装着正文文字的节点（可译块），
    代码块、脚本、导航文字在这一步排除 ——交出去一批纯文本
 ② 翻译（translate）：文本进、译文出；网络、批量、缓存、失败重试
    都围着这一步转
 ③ 渲染（render）：新建译文节点，打上标记属性，插到原文正下方
 ④ 装配（assemble）：把 ①②③ 串成流水线，管住节奏与意外——
    谁先谁后、失败了怎么办、页面又变了怎么办
产出：还是那棵树，只是多了一排译文节点
```

四个部件缺一个都不成。没有抽取，导航和代码会一起进翻译，等于退回整页替换的老问题；没有翻译，剩下两个部件只能把原文原样端回来；没有渲染，译文没有落脚的地方；没有装配，一次性的脚本对付不了真实页面——无限滚来的新内容、失败的请求、第二次进入的页面。

这四个部件就是全书剩下八个动手章的骨架：先各造一块，再拼成引擎，最后装进浏览器。

## 演练：亲手废掉一个按钮

道理讲完了，现在亲手把「字符串世界观」的账算一遍。找个无害的页面（一篇文档页就好），打开控制台，按步骤跑。

第 1 步，造一个活按钮：

```js
// 用法示例
const btn = document.createElement('button');
btn.textContent = 'Submit';
btn.addEventListener('click', () => console.log('按钮还活着'));
document.body.appendChild(btn);
```

点它，控制台打印「按钮还活着」。记住这个状态：监听器挂在 `btn` 这个节点对象身上。

第 2 步，用字符串的方式「翻译」这个页面——把 body 序列化成字符串，再原样塞回去：

```js
// 用法示例
document.body.innerHTML = document.body.innerHTML;
```

页面上那个 Submit 按钮还在，看起来分毫未动。再点它——控制台一片安静。

发生了什么：`innerHTML` 赋值把 body 的子节点全部扔掉，把字符串重新解析成一批全新的节点。页面上这个按钮和半分钟前的按钮长得一样，但它是另一个对象，身上没有任何监听器。整页替换对整个页面做的，就是这一步的放大版。

加试：找一个页面上现成的输入框，打几个字进去，再执行一遍第 2 步——你打的字没了。用户输入活在节点属性里，从字符串里过一遍就丢。

第 3 步，换树上世界观——不碰按钮，往它后面挂一根新枝：

```js
// 用法示例
const zh = document.createElement('span');
zh.textContent = '【译文】提交';
btn.after(zh);
```

再点 Submit——控制台又打印「按钮还活着」。原文一个字没改，监听器所在的节点从没被换过，所以一切都活着。两种世界观的差别，你的手指已经摸到了。

## 验证：先猜，再跑

别直接跑。每一步先在脑子里写下预言，再看结果。猜错的地方最有价值：错在哪，理解就补在哪。

1. 先猜：`document.querySelector('p') === document.querySelector('p')` 返回 `true` 还是 `false`？跑一下。
   应看到：`true`。两次查询取到的是同一个对象——「活的对象」的意思就是：树上的节点是稳定的对象，谁来取都是它。
2. 先猜：演练第 2 步之后，旧变量 `btn` 的 `btn.isConnected`（`isConnected`：这个节点是否还挂在文档树上）是 `true` 还是 `false`？跑一下。
   应看到：`false`。旧节点连人带监听器一起被摘下树了；页面上的 Submit 是另一个新对象。
3. 先猜：把演练第 3 步原样再执行一遍，页面上会出现几个「【译文】提交」？跑之前先猜，跑完再想一个问题：真实引擎靠什么避免这种重复？
   应看到：两个。多出来的那个，就是「标记属性」要解决的问题——插译文之前，先认一认哪些节点是自己插的。

## 小结：现在你能解释那两次翻译了

回头看开篇。点「翻译此页」：页面闪一下、原文消失、代码面目全非——这是字符串世界观的路线：换掉整棵树，事件、状态、原文一起没了（这笔账你在演练第 2 步亲手验过）。按双语工具的快捷键：页面纹丝不动、译文逐段落下——它在树上世界观里逐段挂新枝：抽取挑节点，所以代码幸免；渲染只插入、不重写，所以原文还在、链接还能点；装配管节奏，所以译文逐段出现、跟得上你滚动。

这一章没写引擎的一行代码，但你已经拿到了全书的底图：**双语对照 = 在活的对象树上做增量；引擎 = 抽取、翻译、渲染、装配四个部件**。

### 自查三问

先自己答，再展开对照。

::: details 1. 同事抱怨：他的表单页被前端框架重新渲染后，「提交」按钮看着完好，点击却没反应了。用本章的概念指出：断掉的是哪一层？
框架重渲染往往走「字符串 / 模板 → 重建节点」的路线：新按钮是另一个节点对象，而监听器登记在旧对象身上、序列化带不走——断的不是按钮的外观，是「节点对象 ↔ 监听器」的绑定。回查：「字符串世界观」一节的第二个含义，「演练」第 2 步的放大版。
:::

::: details 2. 你在控制台给页面里某个 `<a>` 挂了自己的点击监听器，随后用双语对照工具翻译了整个页面——为什么你的监听器还活着？若换成整页替换式翻译呢？
双语对照走「插入」路线：只挂新枝、不重写原文节点，`<a>` 对象没被换过，绑定还在。整页替换把树砍掉重建，新 `<a>` 是另一个对象——绑定随旧对象一起消失。回查：「树上世界观」的插入示例与「演练」第 3 步。
:::

::: details 3. 预测：如果把译文节点用 appendChild 插成原文段落的「子节点」，而不是 `after()` 那样的「兄弟节点」，最可能先出什么问题？
译文落进了原文的结构里：它继承段落的排版，更麻烦的是被算作原文的一部分——引擎下次抽取时，会把「原文 + 旧译文」当成新原文再翻一遍。回查：「树上世界观」的插入示例，「验证」第 3 问。
:::

### 全书地图：四个部件排进九章

今天点过名的概念，去向都在这张表里。每个新词配一句人话，此后各章再逐一做实：

| 章 | 部件 | 动手做出 | 顺手拿到的新武器 |
|---|---|---|---|
| 02 | ① 抽取 | 遍历树，按规则挑出可译块 | 块级 / 内联的真身、树遍历、跳过规则 |
| 03 | ③ 渲染 | 译文节点插入原文下方，重复调用不重复插 | 标记属性（`data-*` 记号）、幂等（做一次和做多次结果相同） |
| 04 | ② 翻译 + ④ 装配 | 引擎不认识任何具体翻译服务，管线一键跑通 | 依赖注入（翻译服务当参数传进引擎）、假翻译器（输出固定不变的假翻译，让全链路离线可测） |
| 05 | ③ 渲染进阶 | 译文里保住加粗、链接与行内代码 | 内联切分（按行内边界拆开翻再拼回）、占位标记（先给标签占个座，译文回来再换回真节点） |
| 06 | ① 抽取进阶 | 认出正文区，别把额度花在导航栏 | 链接密度（一块文字里链接字符的占比）、启发式（用经验规则猜答案，快但不保证全对） |
| 07 | ④ 装配进阶 | 重复段落只翻一次，请求有节奏地飞 | 并发上限（同时在飞的请求就这么多，超出的排队）、内容寻址缓存（拿内容本身的哈希当键，同一段话永远命中同一条） |
| 08 | ④ 装配进阶 | 无限滚动的页面也跟得上 | MutationObserver（浏览器「DOM 变了」就通知我）、自触发循环（自己插的译文又触发自己，译文生译文） |
| 09 | 上线 | 装进 Chrome，真实页面亲眼验证 | content script（扩展注入网页里跑的脚本）、manifest（扩展的身份证兼配置清单） |

从下一章起，每章都先在测试里让行为变绿，再配一个 `demo` 脚本打印引擎眼中的页面。等第 9 章把扩展装进浏览器，你可以回到今天这个英文页面——只不过那个翻译按钮，换成你自己写的。
