# 背景渲染：从图块编号到一整屏像素

第一个马赛克事故：把 nametable 里的图块编号直接当颜色填进画面，满屏是整齐的色块格子——像把图书馆的书架号当书印在了墙上。第二个更隐蔽：老老实实去图案册里查了每个编号的图案，屏幕上图形对了、颜色全错——因为忘了「调色板选的是 4 色组里第几号」这层间接。图形对一半、颜色错一套，这种 bug 比「全黑」折磨十倍：它看起来离成功只差一步，其实差的是对整条流水线的理解。

这一章把流水线走通：布局图上的一个编号，如何变成屏幕上一个具体的颜色。

## 一、流水线总览

先看全景。渲染背景就是回答 960 次同一个问题（屏幕 32×30 格）：这一格贴哪块图案、用哪盒颜料？

```text
nametable 布局        pattern 图案册           调色板颜料盒          帧缓冲
┌────────────┐  编号  ┌──────────────┐  2bit  ┌────────────┐  间接  ┌───────────┐
│ 格(2,3)=17 │ ─────▶ │ tile 17 的    │ ─────▶ │ 调色板 k 的 │ ─────▶ │ 256×240   │
│ 用调色板 k │        │ 16 字节图案    │        │ 0-3 号色    │        │ 像素色号   │
└────────────┘        └──────────────┘        └────────────┘        └───────────┘
```

四站依次是：查布局、取图案、合并出颜色编号、去颜料盒换成真颜色。逐站拆开。

## 二、图案册：一个字节装八个像素

pattern table（图案表）——卡带 CHR 里的图案册，每块图块（tile）占 16 字节：前 8 字节是低平面（一行一字节），后 8 字节是高平面。这种劈法叫位平面（bit planes）——把每个像素 2 bit 的颜色编号拆成两张「镂空板」分开放的存储方式：低平面每字节存一行 8 个像素的第 0 位，高平面存第 1 位，两板叠起来才拼出每像素 0-3 的色号。

为什么劈开存、而不是 2 bit 打包？算笔账会发现存储一字节没省——省的是电路：PPU 渲染时用两根 1 位移位寄存器并行吐位，同一时刻低平面出一位、高平面出一位，拼起来就是色号。**存储格式就是渲染电路的形状**，这是硬件设计里反复出现的模式。

跟着算一遍。tile 3 的低平面一行是 `$AA`（10101010）、高平面同行 `$CC`（11001100）：

```text
低平面 $AA：  1 0 1 0 1 0 1 0
高平面 $CC：  1 1 0 0 1 1 0 0
合并色号：    3 2 1 0 3 2 1 0   ← 每列：高 bit 在前拼二进制
```

左起第一个像素色号 3，第二个 2……给我任意 16 个字节，你都能在纸上画出这块图块长什么样。走到这步，「位平面」就不再是黑话。

## 三、属性表：16×16 像素换一盒颜料

每个 tile 只能从 4 色里选色（2 bit 色号的直接代价），可屏幕明显不止四种颜色——靠的是换颜料盒。nametable 末尾的 64 格是属性表（attribute table）——给屏幕分区指定调色板的登记表。每格管 32×32 像素（4×4 个 tile）；格内一个字节塞 4 个 2 bit 象限值，每个象限 16×16 像素（2×2 个 tile）选一盒 4 色调色板。

象限的边界是本章实测踩过的一个坑：tile 列 0 和列 1 同属左象限，列 2、3 才是右象限——我最初把「第二个 tile」当成了「右象限」，断言的颜色差了一整盒颜料。位运算把这层约定写得很紧凑：

```ts
// src/ppu/index.ts · renderBackground 的属性切面（节选）
const attr = this.vram[ntBase + 0x3c0 + (row >> 2) * 8 + (col >> 2)]
const shift = ((row & 2) << 1) | (col & 2) // 2×2 tile 定象限 → 2bit 对齐
const palette = (attr >> shift) & 3
```

`row & 2`、`col & 2` 各取 tile 坐标的第 1 位——0 或 2，恰好落进属性字节的 2bit 档位：左上 bits0-1、右上 bits2-3、左下 bits4-5、右下 bits6-7。一行位运算，四象限全配完。

## 四、间接换色与透明

最后一站。色号 0-3 只是「第几号」，真颜色在调色板 RAM 里等着：

```ts
// src/ppu/index.ts · renderBackground 的像素落点（节选）
for (let x = 0; x < 8; x++) {
  const bit = 7 - x
  const colorIdx = (((hi >> bit) & 1) << 1) | ((lo >> bit) & 1)
  // 色号 0 是透明：永远落通用背景色 $3F00
  const palAddr = colorIdx === 0 ? 0x3f00 : 0x3f00 + palette * 4 + colorIdx
  this.frameBuffer[(row * 8 + y) * 256 + col * 8 + x] = this.paletteRam[palAddr & 0x1f]
}
```

两处间接值得停：其一，色号 0 的特殊待遇——它不查本组调色板，直接落通用背景色。这不是缺陷而是设计：色号 0 定义为「透明」，背景的镂空、精灵的轮廓全靠它（第 9 章精灵合成立刻用到）。其二，最终写进帧缓冲（frame buffer——一整帧像素的数组，渲染的终点产物）的不是 RGB，是 NES 系统调色板的色号 0-63。真机把这个号交给电视电路换算成颜色；我们保留色号，把它留到第 12 章上屏时再查 RGB 表——教学上少一层转换，帧与帧比对也只比色号。

## 五、测试卡带：图案是手画的

这一章的测试数据全部手绘。给 tile 1 填全 1 的低平面（整块 1 号色）、给 tile 3 填 `$AA/$CC`（3-2-1-0 循环条纹），再把调色板 0 配 `[黑, 01, 02, 03]`、调色板 1 配 `[黑, 11, 12, 13]`。每个断言的期望值都是手算出来的，不依赖任何「跑起来看看对不对」。

```ts
// tests/08-background-rendering.test.ts · 手绘 CHR 图案（节选）
const chr = makeChr({
  1: { lo: full(0xff), hi: full(0x00) }, // 全 1 号色
  3: { lo: full(0xaa), hi: full(0xcc) }, // 逐像素 3 2 1 0 循环
})
```

自产卡带的价值在渲染章最能体现：图案、布局、调色板三样全在你手里，期望帧可以逐像素写在断言里。跑完 70 个测试（累计），包括「61440 像素全有着落」「PPUCTRL bit4 选右半图案表」这类结构级检查。第二排测试顺带验证了一个真实机制：游戏可以带两套图案册（左表 $0000、右表 $1000），背景和精灵各用一套或共用，由 PPUCTRL 的两个开关分别指定。

## 小结

- 渲染流水线四站：布局编号 → 图案 16 字节 → 双位平面合并出 0-3 色号 → 调色板间接出系统色号。
- 位平面劈开存不省存储、省电路：两根移位寄存器并行吐位，存储格式就是电路形状。
- 属性表每格管 32×32 像素、四象限各 2bit；象限以 2×2 tile 为界——列 1 属左不属右。
- 色号 0 是透明，永远落通用背景色；帧缓冲存 NES 色号，RGB 留到上屏。
