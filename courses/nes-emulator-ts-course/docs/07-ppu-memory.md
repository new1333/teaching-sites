# PPU 的记忆：图块、拼贴与颜料盒

第一次给 PPU 递数据的程序员，几乎都栽在同一段代码上：往 `$2007` 连写三个字节，满心期待画面出现点什么——结果纹丝不动。排查半天才发现，`$2007` 只是个「投递口」，投到哪个格子，取决于之前有没有用 `$2006` 正确地装填地址；而 `$2006` 自己还要写两次才拼得出一个地址。没走完这套节奏，写再多字节都是投递到错误的地方。这不是 PPU 刁难人，是它的工作方式：画师的档案室不对外开放，你只能隔着八个小窗递单子。

这一章装好画师的全部记忆和八个小窗的礼仪。它本身还画不出任何东西——但下一章开始，渲染的每一步都要在这里取数据。

## 一、为什么记忆分家

第 2 章的整机图里画过：PPU 与 CPU 分家，它有自己的记忆，CPU 的 64KB 门牌摸不到其中一个字节。为什么这么设计？两个原因。其一，CPU 的门牌空间寸土寸金（2KB RAM 都要靠镜像省），而一屏画面数据远超这个量级，塞进 CPU 地址空间不现实。其二，显存要被 PPU 以远高于 CPU 的频率访问（每帧几十万次像素取数），独占专用记忆才不打架。于是架构变成：PPU 自带档案室，CPU 只通过 `$2000-$3FFF` 段的八个小窗（每 8 个门牌重复一次）下指令、递数据。

档案室里有三块记忆，各有各的用处：

```text
nametable（拼贴布局图）   2KB │ 屏幕上每一格放哪个图块的编号 + 属性
palette RAM（颜料盒）     32 格 │ NES 全部 64 色里的 32 个选择
OAM（贴纸登记表）        256 字节 │ 64 个活动贴纸的位置/图案/翻面记录
（还有一块 CHR 图案区在卡带上，下一章取用）
```

nametable（名称表）——记录「屏幕 32×30 格每格贴哪个图块」的布局图。NES 屏幕一帧 256×240 像素，以 8×8 的图块（tile）为单位分成 32×30 格，每格存一个图块编号。为什么叫「名称」表？每格写的正是那块图案的「名字」（编号），名副其实。

调色板 RAM——NES 总共能显示 64 种颜色（编号 $00-$3F），但同屏只能选用 32 格：1 格通用背景色 + 8 组 4 色（背景 4 组、精灵 4 组）。32 格装的是「从 64 色大 palette（调色板，颜色的可选清单）里挑出来的编号」。

OAM（object attribute memory，对象属性内存）——64 个精灵 × 4 字节：Y 坐标、图块号、属性（调色板/翻转/前后景）、X 坐标。第 9 章逐字段拆。

## 二、八个小窗的礼仪

| 门牌 | 名字 | 读/写 | 语义 |
|---|---|---|---|
| $2000 | PPUCTRL | 写 | 位打包的设置：自增步长、nametable 基址、NMI 开关 |
| $2001 | PPUMASK | 写 | 渲染开关：显示背景/精灵、裁边、配色 |
| $2002 | PPUSTATUS | 读 | 状态：VBlank、sprite 0、溢出 |
| $2003 | OAMADDR | 写 | OAM 指针 |
| $2004 | OAMDATA | 读写 | 读写 OAM 一格，指针顺移 |
| $2005 | PPUSCROLL | 写×2 | 背景滚动量（两步写入） |
| $2006 | PPUADDR | 写×2 | 档案室指针（两步写入） |
| $2007 | PPUDATA | 读写 | 按指针读写数据，随后自增 |

两个礼仪要重点交代。

**两步写入。** CPU 数据总线一次只有一个字节，而 PPU 指针是 14 位——怎么办？写两次拼起来。`$2006` 第一次写高 6 位、第二次写低 8 位，内部一个 `writeToggle` 开关记录「下一步该写哪半」。这个开关还有个连带礼仪：读一次 `$2002` 会把它复位——否则上次没写完的地址会把下次写入的节奏带偏。滚动的 `$2005`、间接接通滚动的 `$2006` 共用这套两步节奏。

```ts
// src/ppu/index.ts · writeReg 的 $2006 分支（节选）
case 6:
  if (!this.writeToggle) {
    this.v = (this.v & 0x00ff) | ((val & 0x3f) << 8) // 第一步：高 6 位
  } else {
    this.v = (this.v & 0xff00) | val                  // 第二步：低 8 位
  }
  this.writeToggle = !this.writeToggle
  break
```

**自增。** `$2007` 每读写一次，指针按 PPUCTRL 第 2 位选定的步长前进：默认 1（逐格填布局图），置 1 后是 32（一列图块竖着填——每个 nametable 恰好 32 格宽，步长 32 就是「竖着走」）。开头那个「写了没反应」的 bug，正确姿势是：`$2006` 两步设好首地址，然后连写 `$2007`，数据顺着自增一格一格排队进档案室。

## 三、镜像：档案室也有「一房多名」

第 3 章 RAM 的四段镜像在这里有两个 PPU 版变奏。

**nametable 镜像**：地址空间里安排了四块逻辑 nametable（$2000/$2400/$2800/$2C00），但 PPU 只有 2KB 物理 VRAM——装两块。哪两块共用，由卡带上一根连线决定，也就是 iNES 头里的 mirroring 位：水平镜像时 $2000 与 $2400 是同一块（上下接续的卷轴用），垂直镜像时 $2000 与 $2800 共用。四块折两块的映射一小段查表搞定：

```ts
// src/ppu/index.ts · ntIndex（四块逻辑 nametable 折进 2KB 物理）
private ntIndex(addr: number): number {
  const table = (addr >> 10) & 3 // 第几块逻辑 nametable（0-3）
  const offset = addr & 0x3ff
  const physical = this.mirroring === 'horizontal' ? [0, 0, 1, 1][table] : [0, 1, 0, 1][table]
  return physical * 0x400 + offset
}
```

**调色板镜像**：32 格里，背景色那一格（$3F00）在 $3F10、$3F14、$3F18、$3F1C 有四个分身。精灵调色板组的第 0 格物理上不独立存在，全指向通用背景色。往 $3F10 写值，读 $3F00 能读回它；渲染透明像素时落的也是它。

## 四、OAM DMA：别自己一趟一趟搬

游戏每帧要更新几十个精灵的位置，也就是往 OAM 写上百字节。用 `$2003/$2004` 逐字节写，每字节都是一条完整指令——几百个时钟拍就为了搬数据。于是 6502 做了一件当时很奢侈的事：一根专用搬运通道。CPU 往 `$4014` 写一个「页号」，DMA（direct memory access，直接内存访问——绕过 CPU 逐字节搬运、让数据直通目的地的通道）就替 CPU 把那一整页 256 字节灌进 OAM。一条指令，顶 256 次手工投递。实现上只是总线多一个分支。

```ts
// src/bus.ts · write 的 $4014 分支
if (addr === 0x4014 && this.ppu) {
  const page = val << 8 // 页号 × 256 = 源地址
  this.ppu.oamDma(i => this.read(page + i))
  return
}
```

这就是「sprite 表更新」在真机游戏里的标准姿势：把 64 个精灵的新数据先在 RAM 里排好（通常放在 $0200 页），一帧一次 DMA 整体换新。

```text
$ pnpm test
 ✓ tests/07-ppu-memory.test.ts (10)
   · $2006 两步拼地址、$2007 写读一致

   · 读 $2002 返回 VBlank 位且读一次即清
   · $2000-$3FFF 每 8 门牌镜像（写 $3FF0 即写 $2000）
   · OAM 指针读写推进；$4014 DMA 整页搬运 256 字节
   · 调色板独立读写 + $3F10/$3F00 镜像
   · nametable 水平/垂直镜像各就各位
```

64 个断言全绿（累计）。调试这一轮还白捡一个真机行为：`$2004` 的读也会推进 OAM 指针——我最初只写了「写推进」，测试第二条读数立刻抓出来。便签、指针这类「隐式状态」，永远比看上去的多走一步。

## 小结

- PPU 档案室三块记忆：nametable 拼贴布局、32 格调色板、64 精灵的 OAM；CPU 只能经 $2000-$3FFF 的八个小窗访问。
- 两步写入礼仪：$2006/$2005 拼宽位数，readStatus 会复位写入节奏；$2007 按步长 1/32 自增。
- 镜像三连：nametable 四折二（卡带决定方向）、调色板 $3F10 系列是背景色分身、寄存器每 8 门牌重复。
- OAM DMA 一条指令换 256 字节，游戏更新精灵的标准姿势。
