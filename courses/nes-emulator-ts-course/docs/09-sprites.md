# 精灵：会动的一切

玩家角色明明摆在那儿，屏幕上就是没有——它排在背景后面。子弹和敌机重叠时，该压在前面的反而沉到了底下。最诡异的是第三个：游戏一切正常，只是死活不肯往下走。反汇编才发现，它在等一个哨兵信号（sprite 0 hit——PPU 报告「画面已画到这一行」的信号，本章第 4 节细说），等不到就永远卡在圈里。精灵系统的三个经典翻车点：优先级（重叠时谁压住谁）、翻转（贴纸水平或垂直翻面）、命中检测，一次全部撞上。

这一章实现精灵（sprite）——不受背景网格约束、可逐帧自由摆位的活动图层，以及它和背景的合成规则。

## 一、OAM：64 张贴纸的登记表

第 7 章装好的 OAM 就是贴纸登记表：64 个精灵，每个 4 字节，字段固定。

```text
字节 0  Y 坐标     注意：实际显示从 Y+1 行开始（真机偏移，马上细说）
字节 1  图块编号   8x8 模式直接用；8x16 模式只取偶数基址
字节 2  属性       bits0-1 调色板 | bit5 优先级（1=躲到背景后）| bit6 水平翻转 | bit7 垂直翻转
字节 3  X 坐标     列方向无偏移
```

游戏让角色「动起来」，本质就是每帧改写 OAM 里的坐标和图块号。上一章的 OAM DMA 正是为此而生：在 RAM 里排好 64 条新记录，一条指令整页灌入。

先交代那个 Y 偏移，因为它是本章实测踩过的第一个坑。真机精灵显示在「Y+1」行起：OAM 写 Y=10，图案出现在扫描线 11。我把 OAM 的 `$FF` 想当然当成 -1、以为能让精灵顶到第 0 行——测试立刻纠正：OAM 字节是无符号的，`$FF + 1 = 256`，直接滚出屏幕。精灵最早只能出现在扫描线 1。为什么有这个偏移？真机取精灵行数据需要提前一行准备，电路就这样设计的；模拟器照抄，靠测试把这个「差一行」焊死成断言。

## 二、逐扫描线的两条铁律

精灵不是「一张张贴上去」，而是逐扫描线处理，两条规则都带硬件时代的成本核算。

**每线最多 8 个。**PPU 每条扫描线只配了 8 组取图电路——一条线上同时最多渲染 8 个精灵，超出的直接不画。游戏画面精灵再多，同线也只有前 8 个（按 OAM 顺序）能露脸。这就是某些 NES 游戏精灵密集处会「消失」的原因，也是「第 9 个精灵被裁」这条断言复刻的行为。

**低序号在上。**多个精灵重叠时，OAM 里序号小的压住序号大的。实现上从高序号往低序号画，让低序号后落笔覆盖前者：

```ts
// src/ppu/index.ts · renderSprites 的逐线骨架（节选）
for (let line = 0; line < 240; line++) {
  const active: number[] = []
  for (let s = 0; s < 64 && active.length < 8; s++) {
    const y = this.oam[s * 4]
    if (line > y && line <= y + height) active.push(s) // 显示行从 y+1 起
  }
  for (let k = active.length - 1; k >= 0; k--) {
    // 绘制体在下一节连同三方合成一起展开
  }
}
```

收集这一半读完就能理解「每线 8 个」的实现：内层收集循环带着 `active.length < 8` 的闸门，按 OAM 顺序扫，取满 8 个就收工——第 9 个同线精灵连候选都进不了。

## 三、三方合成的规则表

精灵像素落到画布前，要过两道判断，参与判决的有三个角色：精灵像素的色号、背景像素的色号、精灵的优先级位。

```text
精灵色号 = 0（透明）        → 不落笔，背景保留
精灵非透明，优先级位 = 0    → 精灵覆盖（哪怕背景也非透明）
精灵非透明，优先级位 = 1    → 背景非透明则让路；背景透明才露出
```

透明是整个合成体系的地基：第 8 章背景渲染时色号 0 落通用背景色的伏笔在这里兑现——精灵图案里色号 0 的像素是「镂空」，镂空处透出下面的背景。优先级位（属性字节 bit5）则给了美术一个分层开关：把角色阴影的优先级设为 1，阴影就只出现在背景的空旷处，走过实心墙面时自动「藏」进去。

判断「背景是否透明」需要背景的色号底账，所以 `renderBackground` 顺手多填了一份 `bgColorIdx`——每像素的 0-3 色号。帧缓冲里存的最终色号回答不了这个问题（两种透明来源都已经被换成背景色了），底账是合成阶段唯一可靠的证据。

绘制体的完整落笔长这样——上一节骨架里那个倒序循环的真实内容，三方合成判决、双翻转取样、8x16 寻址全在这三十行里：

```ts
// src/ppu/index.ts · renderSprites 的绘制体（节选）
for (let k = active.length - 1; k >= 0; k--) {
  const s = active[k]
  const y = this.oam[s * 4]
  const tile = this.oam[s * 4 + 1]
  const attr = this.oam[s * 4 + 2]
  const x = this.oam[s * 4 + 3]
  const palette = attr & 3
  const behindBg = (attr & 0x20) !== 0   // 优先级位：1 = 躲到背景后
  const flipH = (attr & 0x40) !== 0
  const flipV = (attr & 0x80) !== 0
  const rowIn = line - (y + 1)           // 行内第几行（0 起）
  const row = flipV ? height - 1 - rowIn : rowIn // 垂直翻转：换算取样行
  // 8x16：偶数基址、bit0 选左右表、下半块是基址 +1；8x8：普通寻址
  const patternAddr = height === 16
    ? ((tile & 1) ? 0x1000 : 0) + (tile & 0xfe) * 16 + (row >= 8 ? 16 : 0) + (row & 7)
    : spriteTable + tile * 16 + row
  const lo = this.chrRom[patternAddr]
  const hi = this.chrRom[patternAddr + 8]
  for (let i = 0; i < 8; i++) {
    const sx = x + i
    if (sx > 255) break
    const bit = 7 - (flipH ? 7 - i : i)  // 水平翻转：换算取样列
    const colorIdx = (((hi >> bit) & 1) << 1) | ((lo >> bit) & 1)
    if (colorIdx === 0) continue          // 透明像素不落笔——规则表第一行
    const fbIdx = line * 256 + sx
    const bgOpaque = this.bgColorIdx[fbIdx] !== 0
    if (s === 0 && bgOpaque && sx > 0 && sx < 255) {
      this.sprite0Hit = true              // 哨兵，下一节细说
    }
    if (behindBg && bgOpaque) continue    // 优先级让路——规则表第三行
    this.frameBuffer[fbIdx] = this.paletteRam[0x10 + palette * 4 + colorIdx]
  }
}
```

对着规则表读一遍：`colorIdx === 0` 跳过是第一行（透明让背景）；正常路径直接覆盖是第二行（优先级 0 盖一切）；`behindBg && bgOpaque` 让路是第三行。精灵调色板从 `$3F10` 段取（`0x10 + palette * 4 + colorIdx`），与背景的 `$3F00` 段各占 16 格、互不串门。

## 四、sprite 0 hit：游戏的哨兵

0 号精灵有个特殊使命：它是游戏的画面哨兵。当它的非透明像素与背景的非透明像素在同一坐标相遇，PPU 在状态寄存器亮起 bit6——sprite 0 hit（0 号精灵命中——它撞上了不透明背景的信号）。

游戏拿它干什么？判断「画面画到这一行了」。最经典的用法是状态栏：超级马里奥兄弟顶部那行分数金币，就是让 0 号精灵压在状态栏图案上。hit 信号一亮，说明扫描线已经画过状态栏区域，此刻再改下方卷轴寄存器，两层画面各滚各的、互不撕裂。我们的哨兵逻辑三行：

```ts
// src/ppu/index.ts · renderSprites 内（节选）
if (s === 0 && bgOpaque && sx > 0 && sx < 255) {
  this.sprite0Hit = true // 0 号精灵撞上非透明背景：游戏的「画到这里了」哨兵
}
```

边界规则要按真机说清楚：x=255 那一列恒不触发；x=0-7 只有在 PPUMASK 开启「左列裁剪」时不触发，没开裁剪时可以触发。本课程没实现裁剪开关，统一简化为「两侧都不触发」——就是代码里那个 `sx > 0 && sx < 255`，这是一条声明过的简化（附录的差异清单里有记录）。第 10 章把它和 VBlank 一起接进时序，游戏「等窗口、等哨兵」的等待循环就能真正转起来。

## 五、8x16 与翻转

两种高度模式由 PPUCTRL bit5 选择。8x8 直接用背景那套图案表选择；8x16 略绕：图块编号强制取偶数（`tile & 0xFE`）作基址，编号的 bit0 反而去选左右图案表，上半 8 行用基址图块、下半 8 行用基址 +1。绕这一圈换来的是「一次取两块」的电路简单——寻址公式就是上面绘制体里的 `patternAddr` 三行。

翻转不碰图案数据，只在取样时换算坐标：水平翻转取 `7 - x` 列（绘制体里的 `7 - (flipH ? 7 - i : i)`），垂直翻转取 `height - 1 - y` 行。条纹图块 `$AA/$CC`（色号 3-2-1-0）水平一翻就成了 0-1-2-3，测试里左右两个像素各断言一次。美术靠翻转让一张向左的贴纸同时表现向右，图案存储量直接减半——省字节的思路又一次贯穿始终。

顺带交代本轮第二个实测坑：断言颜色时我把「色号 3 → 调色板第 3 号色」写成了「色号 3 → 0x27」，而调色板里 3 号位放的是 0x18。色号是「第几个」，颜色是「那格放的什么」——间接层多走一跳，人和代码都容易在这儿拐错弯。修完这两处，累计 80 个用例全绿（本章 10 个；`pnpm typecheck` 同轮通过）。

## 小结

- OAM 四字节：Y（显示从 Y+1 起）、图块、属性（调色板/优先级/双翻转）、X。
- 逐线两条铁律：每线最多 8 个（OAM 顺序取前 8）、低序号压高序号。
- 三方合成：透明让背景、优先级 0 盖一切、优先级 1 让非透明背景；背景色号底账 `bgColorIdx` 是判决证据。
- sprite 0 hit 是「画面画到这里了」的哨兵；边界不触发是课程简化（真机仅 x=255 恒不触发）。
- 8x16 偶基址 + bit0 选表；翻转只换算取样坐标，不动数据。
