# 一条请求的旅程：全栈地图

你大概经历过这样的早晨。用户说网站打不开了，你打开 DevTools 的 Network 面板，那条请求躺在列表里，状态一直是 Pending，标签页的图标转圈。你刷新、换浏览器、切换 Wi-Fi 与流量，它还是转圈。

前端工具能告诉你的到此为止：请求没有回来。至于它坏在哪一层——名字没解析、证书过期、进程崩了，还是数据库满载——面板一概不说。这些坏法共享同一张脸。

打不开是一张脸，不是一种病。要区分这些病，得先看清一条请求从浏览器走到响应的完整路径——**请求旅程**（request journey）。本书就用这条旅程当全书地图。贯穿全书的载体是一个短链接服务：创建短链、点击后 302 跳转到原网址——302 就是告诉浏览器「换个地址，再去一次」的状态码。这个服务随后会逐步长出登录、缓存、限流、统计、容器与部署。你敲下一条短链、按下回车的那个瞬间，恰好把整张地图踩了一遍。

## 先立字据：本章的证据包

这是一张纯地图章：不写代码，不装环境。作为交换，先把要交付的结论、结论的支撑、学会的标准摆上台面，读完回来对账。

**结论清单：** 读完这章，你应当能：

1. 把「打不开 / 转圈」从一张脸拆成六个有名字的站点，对一个具体故障说出它归哪一层、该找什么技术；
2. 对反向代理与无状态服务各讲一个反事实——删掉它，具体坏什么，理由能从机制推出来；
3. 拿到一条新需求（登录、统计、限流……），先判它落在旅程的哪一站，再谈技术选型。

**支撑来源：** 每一站的「凭什么存在」都用反事实回答——没有它会发生什么、故障长什么样。涉及版本与时点的数字（比如 Node 的维护窗口）取自官方发布口径，正文一律标注 2026-09 时点。全部判断力最后压在 8 道场景判定题上：先猜后对，答案离散可对照。

**迁移判据：** 8 题至少对 7 题，而且理由是现场推的，不是背的；另外能做到不看小节，向同事讲清一次点击经过哪几站、每站坏掉各自长什么样。两条都满足，这章就算立住了。

## 「后端」不是一个东西

拆图之前，先搬开一块挡路的直觉。

在你的日常视角里，「后端」确实是一个东西：一个 baseURL。`fetch('/api/links')` 扔出去，JSON 回来，Network 面板里它只是一行。在这个范围内把后端当黑盒不但合理，甚至是好习惯——契约就是它唯一需要露出的脸。

但「打不开」的排障恰好发生在黑盒内部。一句「后端挂了」摊到地图上，至少对应四种不同的故障：域名没有解析出 IP、入口的证书过期、应用进程崩了、数据库满载。它们的修法不同，负责的人不同，报警出现的位置也不同。把后端当一个东西，你只能把故障报成「它坏了」——既修不了，也说不清。

所以第一步：把黑盒拆成站点。

## 旅程解剖：一次点击的六站

现在把你放回地址栏。你敲下一个短链，比如 `https://s.example/a1b2`，按下回车，几十毫秒后浏览器已经把你送到目标网页。这几十毫秒里，请求走了六站：

| 站点 | 担当技术 | 一句职责 |
| --- | --- | --- |
| ① 名字 | DNS 解析 | 把域名翻译成服务器 IP |
| ② 入口 | 反向代理 + TLS 证书 | 对外门面：解密、按域名转发 |
| ③ 应用 | Node.js 进程 | 读请求、做决定（如 302 跳转） |
| ④ 缓存 | Redis | 热数据的快速垫层 |
| ⑤ 数据 | PostgreSQL | 活得比进程久的记录本 |
| ⑥ 异步 | 消息队列 + worker | 先答应、稍后完成的副作业 |

逐站走一遍。

第一站，查名字。浏览器只认 IP，人只记得住域名，DNS 这套全球目录系统负责两者之间的翻译。电话簿查不到人，后面全部免谈。

第二站，进门。公网上先接待你的不是你写的代码，而是反向代理（reverse proxy）：挡在应用进程前面、代客户端把请求转交给后端的服务。它同时完成加密握手——浏览器与入口凭 TLS 证书建立加密连接，密码与跳转目标不会在网络上明文裸奔。

第三站，进应用。一个 Node.js 进程常驻在服务器上，监听一个内网端口。它收到请求后读路径、查数据、做决定——对短链服务来说，决定通常是「302，去这个原网址」。

第四站与第五站，是应用拿数据的两个去处。热的先查缓存：数据在内存里，微秒级，但重启即空。冷门的和要长期保存的进数据库：磁盘，毫秒级，活得比进程久。

第六站在响应返回之后才真正干活。点击统计这类副作业先丢进队列，由一个专职的 worker 进程（专职取件、执行任务的独立进程）稍后写进数据库。你被跳转走的那一刻，统计其实还没发生。

最后补一笔回路：302 响应回到浏览器后，浏览器会自己再发一次请求，这次才是去原网址。一次点击、两条请求——这个双跳你在 Network 面板里其实见过。

六站连起来，就是开头说的那条请求旅程。Network 面板只显示两端——请求发出与响应回来，旅程补上的正是中间那几站。把路径当一个整体来记，是为了排障时先定站、再谈技术：任何故障先问「坏在哪一站」，而不是笼统地问「后端怎么了」。

### 第三站的住户：Node 进程与时点事实

应用的载体是 Node.js 进程，和你前端工具链是同一个运行时。差别在于它构建完不退出，而是常驻监听端口。版本上认准偶数号的 LTS（长期支持）线。2026-09 时点：Node 24 是 Active LTS（维护到 2028-04-30），Node 22 是 Maintenance LTS（维护到 2027-04-30），Node 20 已于 2026-04-30 停止维护；本课验证环境跑在 Node 22 上。这类窗口随时间移动，核对入口是 Node.js 官网的 previous-releases 页面，所以本课正文只标时点、不写「最新」。

## 逐层反事实：每一站凭什么存在

地图上每个站点都要能回答同一个问题：删掉它，具体坏什么？答案不是「服务不可用」这种废话，而是长相各异的故障。逐站过一遍。

### ① 名字坏了：连状态码都没有

DNS 出问题时，浏览器第一步就卡死，报「找不到服务器的 IP 地址」。这种打不开有个鉴别特征：请求根本没发出去，Network 面板里连状态码都看不到——错误发生在一切开始之前。

### ② 入口为什么存在：反向代理的三笔账

聚焦第二站。设想删掉反向代理，让应用进程直接对公网开门，会接连发生三件具体的事：

1. 证书没人管。TLS 证书的申请与续期得写进每个应用自己的代码，业务代码开始兼职门卫。
2. 一台服务器挤不下两个应用。80 与 443 端口全局唯一，第二个应用上线就得改代码换端口，用户还得在网址里记端口号。
3. 公网流量直接怼在业务进程上。慢客户端、恶意扫描、大文件传输，全都占用应用的连接与内存。

反向代理把这些活从应用身上剥出来单独安放：它监听 80/443，完成 TLS 解密，按域名把 `s.example` 的流量分给短链服务、把 `blog.example` 分给博客进程，转发前还能顺手压缩与限速。前端同学其实早就用过它的近亲——Vite 开发服务器的 `server.proxy` 配置把 `/api` 转给后端，就是同一个动作的桌面版；反向代理把这个动作搬到公网入口，服务对象从你自己的浏览器变成全世界。本书里这个角色由 Caddy 扮演。

一句话记分工：**应用管业务，入口管门面**——证书、域名分发、公网防身，都不该是业务代码的职责。

### ③ 应用坏了：没人接电话

第三站的反事实最直白：进程崩了，端口上没人监听。入口还在，数据库也还在，但请求转过去无人应答——用户看到 502，含义是「门面活着，门内无人」。更麻烦的是，裸跑的进程崩了不会自己站起来；「崩了有人拉起」属于部署侧的职责，不属于应用代码。

### ④ 缓存坏了：不报错，只是变慢

删掉缓存，跳转照样成功——只是每次点击都要去数据库现查一次。单次查询不过几毫秒，但短链跳转是全场最热的路径，乘上去就是高峰期数据库先撑不住、然后用户才看到超时。缓存买的东西很单纯：同样的答案，不问数据库第二遍。这种「只是变慢」的故障最容易被忽略，因为它不产生任何报错。

### ⑤ 数据坏了：一半是丢失，一半是变慢

数据库的反事实分两半。写的一半：记录只存在进程内存里，进程一重启全部蒸发，昨天建的短链今天全变 404。读的一半：数据都在，但没有索引，每次跳转都要全表逐行扫描，数据量涨多少倍，延迟就涨多少倍。前一半要求数据活得比进程久，后一半要求查得快——这是两个独立的需求，数据库同时接下。

### ⑥ 异步坏了：副作业的失败会传染

点击统计如果同步做——跳转前先写一条统计记录——统计的延迟和失败就混进了跳转本身：数据库抖一下，用户就盯着短链多等几秒；统计写入失败，跳转陪着报 500。队列把「先答应」（立刻返回 302）与「稍后完成」（worker 落库统计）拆开，统计坏了不再传染主路径。代价是统计永远滞后几秒——这个滞后在下面的判定题里会再遇到。

### 横切的一条纪律：无状态服务

六站之外还有一条贯穿全程的纪律，值得单独一块。

先替一个流行的直觉说句公道话：「服务器记住登录态，靠的是服务器自己的内存」。在单进程、永不重启的世界里，这个做法完全成立，内存也确实是那里最快的地方。直觉还有个前端来源：你在页面里就是把状态放在组件里、放在内存里，「服务端也有内存」是很自然的迁移。

边界恰好出在进程的本性上：进程会崩、会被重启、会复制成多份。登录态放在进程内存里，一遇重启就全体用户掉线；一遇多份复制就各说各话——请求轮到哪一份，就得在哪一份那里重新登录。

所以纪律只有一条：**应用进程不保存跨请求的数据**——会话放数据库或缓存，业务数据放数据库，进程只负责计算与转发。遵守它的服务叫无状态服务（stateless service）。这条纪律反过来解释了地图的一半：数据要活过重启，所以有数据库；多份进程要认同一份登录态，所以会话放在进程外；队列敢把任务丢出去，因为谁捡到都能做。判断一个数据该放哪，只问一句：**进程重启后，它该不该还在**？该在的，就不属于进程。

你在前端早就遵守着同一条纪律：组件里的状态一刷新就没，所以重要的数据你从不只放在组件里。进程的重启，就是服务端的刷新。

## 八个场景判定题：先猜后对

规则只有一条：每题先把归属写下来——六站之一，或横切纪律——再展开答案对照。猜错最有价值：错在哪一站，就回那一站的反事实重读一遍。

### 题 1：迁移之后，一半人在旧机器上

你把服务迁到新服务器，域名控制台里的解析记录也改指向了新 IP。一小时后，一部分用户已经用上新机器，另一部分还在访问旧机器。应用与数据库一切正常。归属哪一站？

<details>
<summary>展开答案</summary>

归属：① 名字（DNS 解析）。担当技术：解析记录与解析缓存的存活时间（TTL）。理由：你改的不是机器，是电话簿；旧记录还留在各级缓存里，要按存活时间陆续到期，用户因此分批切换。

</details>

### 题 2：满屏红色警告

用户手机浏览器打开站点，直接弹「您的连接不是私密连接」，详情里写着证书已过期。换浏览器、换设备都一样。服务器上应用进程与数据库的日志一片安静。归属哪一站？

<details>
<summary>展开答案</summary>

归属：② 入口（TLS 证书）。担当技术：证书的签发与续期。理由：浏览器在见到任何应用代码之前先校验证书；证书挂在入口，过期是入口的病，与应用无关。

</details>

### 题 3：应用明明活着，用户全打不开

用户侧全员打不开，入口日志显示最近一小时一个请求都没进来。你在本地 dig 这个域名，解析结果正常指向这台服务器的公网 IP；登录服务器，直接向应用监听的内网端口发一个请求，秒回 200。归属哪一站？

<details>
<summary>展开答案</summary>

归属：② 入口（反向代理）。担当技术：入口进程的存活与端口监听。理由：解析正常排除了名字这一跳，内网直连 200 说明应用活着——请求连门都没进来：门面进程没在监听对外端口，入口日志自然一条都没有。屋子再亮，门没开也没人进得来。

</details>

### 题 4：大片 502

入口访问日志里出现成片的 502。登录服务器一查，Node 进程根本不在进程列表里；手动重启后一切恢复。归属哪一站？

<details>
<summary>展开答案</summary>

归属：③ 应用进程。担当技术：进程守护与重启策略（部署侧）。理由：502 的语义是「门面活着、门内无人接电话」——进程崩了，而且没有机制把它拉起来。

</details>

### 题 5：老链接能跳，新建短链全失败

热门短链一切正常，页面也打得开；但创建短链持续 500，日志里是数据库连接被拒绝。归属哪一站？

<details>
<summary>展开答案</summary>

归属：⑤ 数据库。担当技术：数据库的连接与容量。理由：热路径有 ④ 缓存兜着，热门链接照跳；创建是写路径，绕不开数据库——冷的与写的部分先暴露。

</details>

### 题 6：没报错，但全线变慢

一次例行维护窗口之后，跳转没有失败，但平均耗时从 20ms 涨到 200ms，高峰期开始零星超时。维护窗口里重启的机器守护的是哪一站？故障为什么长这个样子？

<details>
<summary>展开答案</summary>

归属：④ 缓存。担当技术：Redis 与回源策略。理由：重启的是缓存服务器。缓存缺席的故障长相是「变慢而非报错」——内存清空后每次点击都回源直查数据库，延迟抬高一个数量级。

</details>

### 题 7：跳转正常，报表停更三天

跳转功能无恙，但点击统计报表三天没有新数据；worker 进程的日志里堆着一批失败重试。归属哪一站？

<details>
<summary>展开答案</summary>

归属：⑥ 异步（队列与 worker）。担当技术：worker 的重试与失败任务处置。理由：队列把主路径和统计解耦，解耦的表现正是「坏了不传染」；报表停更暴露的是消费一侧积压——重试用尽的任务会被搁置起来等人处理，而不是无限空转。

</details>

### 题 8：一扩容，用户集体掉线

服务从一份实例扩成两份分担流量。之后用户频繁掉线：刚登录完，下一次刷新又要重登，偶尔又自己恢复；单实例时期从未如此。归属哪一站，或哪条纪律被违反？

<details>
<summary>展开答案</summary>

归属：横切纪律——无状态被违反。担当技术：无状态服务（会话外置到数据库或缓存）。理由：会话记在进程内存里，两份实例各记各的；请求落到没记住你的那一份，你就「没登录」。修复方向：把会话挪出进程。

</details>

## 收束：转圈不再是一张脸

回到开篇那个早晨：用户说打不开，面板里请求 Pending，图标转圈。这张脸现在有了内部结构。同样是转圈——可能是名字没解析（连状态码都没有）、证书过期（红色警告）、入口断流（应用活着但用户全打不开）、进程崩了（502）、数据库满载（写失败、冷查询失败），也可能是缓存缺席的「只是变慢」。现象同一张脸，病灶各归各站，修法各找各处。

带走三样东西：

- 一张地图：六站加一条横切纪律，任何故障与新需求先在上面找归属；
- 两块积木：反向代理（应用管业务，入口管门面）与无状态服务（进程重启后该还在的数据，不放进进程）；
- 一个习惯：先猜、后对，错了回那一站读反事实。

自查一遍（先答再看）：

1. 某个内部工具出了毛病，同事的「重启大法」百试百灵。这个「灵」本身暴露了什么？重启必然丢掉的东西，应该住到地图的哪一站？
2. 公司要在同一台服务器上再部署一个博客站点，和短链服务都想监听 80 端口。哪一站负责让两边相安无事？靠什么区分谁的流量？
3. 你用手机流量打不开这个站点，换办公室 Wi-Fi 就正常；同事在他家两种网络下都正常。最先排查哪一站？为什么基本可以排除应用进程？
4. 产品要求「点击跳转后 1 秒内，统计必须入库并在报表可见」。这条需求放在哪一站最合适？如果它与「跳转必须快」冲突，问题出在需求还是出在架构？

<details>
<summary>展开参考答案</summary>

1. 重启能治的病，多半是状态堆在进程内存里（横切纪律被违反）。重启必然丢的是进程内存里的全部跨请求数据，常见如会话与临时计数；该住到 ⑤ 数据库或 ④ 缓存——判断口径回查「横切的一条纪律」。
2. ② 入口（反向代理）：两个应用各监听不同内网端口，80/443 只由入口持有，按域名里的主机名分发——回查「入口为什么存在」。
3. 先查 ① 名字与网络路径（两种网络环境对该域名的解析或出口不同）。基本可以排除应用进程，因为应用对所有来源一视同仁——「按人群分裂」的故障几乎都发生在请求到达服务器之前。
4. 统计的本性属于 ⑥ 异步。「1 秒内入库可见」若是硬承诺，等于要求统计同步化，把落库的延迟和失败背进跳转本身；更合理的做法是和产品把承诺改成「最终一致」。冲突的根源在需求把「稍后完成」写成了「立刻完成」。
