# 两个世界：调试器为什么难做

周一早上，你给新接手的项目装上了 Vue DevTools 浏览器扩展，刷新页面，扩展图标却是灰的，悬停提示「未检测到 Vue」。可你明明看到页面上渲染着组件——按钮能点，弹窗能开。更诡异的是隔壁工位：他用 Vite 跑同一个项目，按住 Alt+Shift+D，调试器从页面底部弹了出来，组件树清清楚楚。同一个项目，一个看不见，一个看得见。这不是玄学，是两个世界之间的一道边界没有被正确跨越。

再来看一个更隐蔽的案例。一个微前端页面：主应用是一个 Vue 应用，中间嵌了一个 iframe，iframe 里跑着另一个 Vue 应用。你在面板里展开组件树，只看到主应用那几层——iframe 里的子应用像一个不存在的世界。你甚至怀疑过「是不是子应用的生产构建把调试信息剥掉了」。都不是。问题出在：调试器代码与你的应用代码，默认情况下根本不在同一个 JavaScript 世界里。

## 应用与工具：两份独立的代码

先把这个默认处境钉死：你的应用代码和调试器的代码，是两份互不知道对方存在、加载时机也不受彼此控制的程序。

- 它们来自不同的构建产物。你的应用是你的应用，调试器是别人写的另一个程序。
- 它们的加载顺序不确定。扩展脚本可能在你的应用之前注入，也可能之后；Vite 插件注入的脚本挂在开发服务器身上，跟你的入口文件谁先谁后，取决于解析时序。
- 在浏览器扩展的形态下，它们甚至不在同一个 JavaScript 执行环境里——扩展的世界与页面的世界彼此隔离，连 `window` 对象都不是同一个。

但调试器的全部工作，恰恰是「读你应用内存里的东西」：组件树长什么样、每个组件的 state 是什么、路由跳到了哪。要读内存，就得拿到你应用里对象的引用；要拿引用，两份代码就得先碰上面。于是第一个问题出现了：它们在哪里碰面？

答案是全书第一个关键设计：在两个世界共享的最外层全局对象上，约定一个名字。页面脚本在 `window` 上找 `__VUE_DEVTOOLS_GLOBAL_HOOK__` 这个属性——找到，说明工具已经就位；找不到，说明工具还没来。这个对象就是**会合点**：像两个人约在一个广场，靠一句暗号相认。谁先到广场，谁就等；后到的人对上暗号，双方就建立了联系。

碰面还有第二个麻烦：时序。你的应用可能在工具之前就完成了初始化——框架挂载完毕、组件树已经建好、该发的事件都发完了。等工具后到，错过的信息怎么办？解决思路朴素得惊人：先到的一方把「等对方来了要做的事」写成一个队列留下，后到的一方接管会合点时，把队列逐个重放一遍。第 2 章会亲手实现它。

## 第二道边界：工具内核与 UI 客户端

会合点解决的只是「应用 ↔ 工具内核」的相遇。但你看组件树的那个界面——带侧栏、能点开 state 的那个面板——又是另一回事。它是一个独立的 UI 程序（本书称**UI 客户端**），几乎不可能和应用跑在同一个上下文里：

- 在 Vite 宿主里，UI 客户端是开发服务器上的一个独立页面，跑在一个 iframe 里，嵌在你的应用页面中。
- 在浏览器扩展宿主里，UI 客户端跑在 DevTools 面板里，那是一个与页面完全隔离的扩展世界。
- 还可以是一个独立的 Electron 窗口。

于是整体结构是三段：

```text
┌─ 应用所在的世界 ──────────────┐      ┌─ UI 所在的世界 ─────────┐
│                              │      │                       │
│  你的 Vue 应用               │      │   UI 客户端            │
│     │  通过 window 上的      │      │   （组件树面板、        │
│     ▼  会合点对话            │      │    state 面板……）      │
│  工具内核（页面内）           │      │                       │
│                              │      │                       │
└──────────────┬───────────────┘      └───────────▲───────────┘
               │        编码后的消息过「通道」      │
               └──────────────►───────────────────┘
```

中间那条线是全书第二个关键设计：**通道**。两个世界之间没有共享内存，能传的只有消息；而消息里不能塞活的对象引用——函数传不过去，循环引用传不过去，甚至超出结构化克隆规则的东西都会直接抛错。所以每次跨线都得先编码（这是贯穿全书的一种**编码传输**思路）成能过桥的形态，过桥后再解码还原。「过桥」这个比喻会贯穿后面讲序列化的章节。

方向也是双向的。UI 要向内核要数据（「把当前组件树给我」），内核也要反过来调 UI（「树变了，刷新一下」）。所以通道上跑的不是简单的单向通知，而是一套双向的远程调用协议——你在 UI 里点开一个组件看到 state，背后是「UI 发起请求 → 内核执行 → 结果编码过桥 → UI 解码渲染」的完整回路。

## 调试器要做的三件事

把上面两道边界合起来，一个调试器内核要做的事可以收拢成三句：

1. **能看见**：从活着的组件实例出发，按需产出组件树快照与状态快照——不是应用主动上报，而是「你要我才给」。
2. **能对话**：UI 客户端与内核互相调用对方的函数，请求与响应可靠配对。
3. **能修改**：你在面板上改一个值，修改要一路写回页面里活着的那个对象——你改的是本体，不是照片。

这三句话就是全书的三个部分。

| 部分 | 回答的问题 | 对应的三件事 |
| --- | --- | --- |
| 第一部分 · 连接前夜 | 应用与工具如何相遇、如何记账（应用记录与实例表） | 相遇的机制（看见的前提） |
| 第二部分 · 看见 | 组件树与状态如何被遍历器快照、编码、回写 | 能看见、能修改 |
| 第三部分 · 对话 | UI 与内核如何双向互调、通道与中继如何落地各宿主 | 能对话 |

## 你将亲手做出什么

本书的伴生实验场是一个用 TypeScript 写的**最小调试器内核**，约几百行：全局钩子与重放队列、事件系统、应用登记处、组件树遍历、状态快照、循环引用编码、编辑回写、插件与检查器、双向 RPC 与通道。它不依赖浏览器、不依赖任何真实框架——我们用虚拟节点风格的模拟实例来扮演「你的应用」，把全部注意力留给机制本身。

每章你都会先踩一个真实的坑，再亲手实现解决它的那一小块，最后用断言验证原理成立。等走完最后一章，你再回头看开头的两个案例，答案会自己浮现：「未检测到 Vue」是会合点没有建立——要么扩展没有注入到那个世界，要么加载时序让相遇失败了；iframe 里的子应用看不见，是因为每个 iframe 有自己独立的全局对象，会合点得一个世界一个世界地找。到那时，你不只知道现象，还能讲清每一层为什么这样设计。
