# 宿主形态：Vite、扩展与中继

扩展开发者的第一个「灵异现场」：他在 DevTools 面板脚本里写 `window.__VUE_DEVTOOLS_GLOBAL_HOOK__`，想直接拿页面里的钩子——得到 `undefined`。可他明明能在面板的 Elements 里看到页面上跑着 Vue。换个思路，用 `postMessage` 往页面发消息，页面里也监听不到——不是被谁拦了，是**发出去的消息根本进了另一个世界**。扩展面板的脚本跑在 DevTools 的隔离环境里，它与页面共享的只有「你看的那个标签页」这个概念，不共享任何 JavaScript 对象。没有一座桥，两个世界连一句话都说不上一句。

这是全书最后一块拼图。内核、树、快照、编码、回写、插件、RPC——零件在前面十章全部造齐了；这一章看它们被装配进三种宿主，以及扩展世界里那座绕不开的三跳中继。原则章不写代码，但每个环节你都已经亲手做过对应的最小版本，这里只做装配推演。

## 宿主一：开发服务器（Vite 插件形态）

Vite 宿主是三者里最「顺」的：插件跑在开发服务器进程里，页面上的一切它都够得着。装配分四步。

第一步，**托管客户端**。插件在开发服务器上挂一个中间件，把调试器 UI 客户端的构建产物 serve 在一个约定路径下——你在终端里看到的那行 `Vue DevTools: Open http://localhost:5173/__devtools__/` 就是它。UI 客户端是个完整的独立页面，与你的应用同源不同址。

第二步，**注入内核**。插件向应用入口注入一个 script 标签（或在模块图里追加一段 import），让页面加载调试器内核脚本——内核就位后调用安装函数，把钩子挂上 `window`，重放等待队列。第 2 章的会合机制在这里上场。

第三步，**架通道**。页面内的内核与服务器上的插件之间用 WebSocket 连一条通道：内核侧把 RPC 消息 `post` 进 WebSocket，插件侧收到后转发给 UI；反方向亦然。第 10 章的通道抽象在这里兑现——WebSocket 包上 `post/on` 两个函数，就是一条合法通道。UI 客户端在自己的 iframe 里通过 `window.parent.postMessage` 与宿主页面（也就是内核所在的世界）对话，那是另一条通道，同样两个函数。

第四步，**指令到齐**。编辑器里点开一个组件源码位置想跳转编辑器？那是插件进程里的能力（它能起进程打开编辑器），UI 通过 RPC 调它。三个世界（页面、服务器、UI 页面）由两条通道串成一线，全程跑的是同一套两种信封的协议。

## 宿主二：浏览器扩展（含三跳中继）

扩展宿主要难一个量级，因为参与方从两个世界变成四个：页面世界、内容脚本世界、扩展后台、DevTools 面板（UI 客户端所在）。扩展的隔离模型决定了：**没有任何两方共享 JavaScript 对象**。

解法是三跳中继，每一跳用的都是那两个函数的通道语义：

```text
DevTools 面板（UI）
   │  ①扩展内部的端口通信（panel → background）
   ▼
扩展后台（中继中枢）
   │  ②扩展端口（background → content script）
   ▼
内容脚本（页面的「邻居」）
   │  ③window.postMessage（content script ↔ 页面内核）
   ▼
页面内核（钩子、树、快照……都在这里）
```

第 ③ 跳值得单独说：内容脚本是扩展唯一被允许「贴近页面」的形态，它与页面共享同一个 DOM——但不共享 JavaScript 堆。所以它用 `window.postMessage` 与页面内核互发消息：内核把 RPC 信封 post 出去，内容脚本监听到，塞进扩展端口；反方向，端口里来的信封由内容脚本 post 回页面。内容脚本自己不解析信封——它不关心消息是拉树还是改值，只做转发。**中继的职责是搬运，不是理解**，这正是通道抽象的胜利：三跳串起来，逻辑上仍是一条 `post/on` 通道，第 10 章的 RPC 在上面跑，一行都不用改。

第 ① 跳里还有个细节：DevTools 面板不是常驻的——用户关掉 DevTools 窗口，面板上下文就销毁。中继因此要学会处理「对端消失」：端口断开时通知另一头shutdown，等面板重新打开再重建通道。会合点的故事在扩展的世界里又演了一遍：谁先谁后不确定，就约定会合位置、后到者重放。

## 宿主三：iframe 与多应用

第 1 章的第二个谜案在这里结案：iframe 里的子应用看不见，是因为每个 iframe 有自己独立的 `window`，也就有自己独立的钩子。扩展的内容脚本通常只注入顶层页面；iframe 里的世界它没进去，会合点自然无从谈起。要让子应用可见，得让内容脚本（或注入逻辑）进入每一个相关 iframe——`all_frames` 一类的注入策略就是干这个的。于是多个会合点并存，每个 iframe 一个；登记处里出现多条应用记录，面板上的应用切换器由此而来——第 4 章的 `setActive` 在真实产品里对应的正是那个不起眼的下拉框。

## 回望第 1 章

现在可以把两张灰色图标的故事讲完整了。「未检测到 Vue」：扩展注入的内容脚本在那个页面世界里没找到钩子——可能是页面根本没跑 Vue，可能是生产构建禁用了调试钩子，也可能是加载时序里会合失败了；排查思路因此非常具体：去那个世界（不是你所在的世界）里找那个约定名。iframe 子应用不可见：那个世界没有会合点。你还能读懂更多从前灰色的东西：为什么 Vite 形态开箱即用（注入与通道都是插件主动架好的），为什么扩展要申请那么多权限（中继的每一跳都要授权），为什么调试器在生产环境默认关闭（钩子的性能开销与安全暴露）。

你的实验场此刻也值得重新清点一遍家底：内核的入口是钩子与重放队列，守门转发靠事件系统，身份记账在应用记录与实例表；看见的一侧，遍历器按需拉树、状态快照分类清洗、编码传输摆平环与共享；修改的一侧，回写把面板的编辑送回本体；生态的一侧，插件缓冲护住第三方库的注册、检查器交出面板的树与状态；对话的一侧，双向RPC 与通道把两个世界缝成一条双向车道——而这一章做的，只是把它架进每一种宿主。

全书收束到一张完整的图：

```text
┌─ 页面世界 ────────────────────────────────┐
│  应用 ──会合点/重放──▶ 内核                │
│       （钩子→事件系统→登记处）              │
│         树/快照/编码/回写/插件/检查器       │
└──────────────┬───────────────────────────┘
               │ 通道（post/on）：postMessage / WebSocket / 三跳中继
┌──────────────▼───────────────────────────┐
│  UI 客户端（iframe / 开发服务器页 / 面板）  │
│        双向 RPC ── call / 函数表           │
└───────────────────────────────────────────┘
```

你的伴生实验场里躺着这台机器的最小版本：十一块零件，七十四条断言背书。它不能调试一个真实的 Vue 应用——那需要对接真实框架的内部结构——但 Vue DevTools 的每一个核心决策在里面都有对应物：会合点的幂等与重放、守门的转发、登记处的身份签发、按需的树、降级为数据的错误、对象表的编码、写回本体的回放、缓冲的插件、两种信封的协议、两个函数的通道。下次打开调试器点开一个组件时，你看到的不再是一个黑盒面板，而是一条你亲手铺过一遍的链路。
