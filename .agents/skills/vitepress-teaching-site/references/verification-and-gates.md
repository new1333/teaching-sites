# 验证物与门槛（先验证物后文）

执行者：**章写作智能体**（串行模式整章执行；并行模式拆为验证物线=本循环全部、正文线=写正文+lint——模板与文件所有权见 `subagents.md`）。

> v4 更名说明：本文件原名 companion-and-gates.md。v3 把「伴生实验场（代码）」当成唯一验证物，非 coding 课程被迫硬套；v4 泛化为**验证物**——测试、核对脚本、任务清单、探针、页面工程都是验证物，代码只是其中一种。profile 决定用哪种（形态总表见 `course-profiles.md`）。

## 验证物是什么

`companion/` 是**验证物工程**——读者课程结束时拥有的最小验证工程。它的存在只为回答一个问题：**这条原理/这道演算/这个操作真的成立吗？**围绕备课阶段拆出的特性清单逐章搭建，规模几百行（或几十道题、十几条任务）；命名服务于教学清晰，不与任何真实库刻意对齐，不追求功能完整——够验证即可。它是全书的共享状态：每章演进一次，正文的演练/验证段落引用它的真实产物。

为什么先验证物后文（SKILL.md 原则 2，公理 3 的化身）：长篇课程的一致性无法靠模型记忆或长上下文保证——门槛命令、核对脚本、探针输出是外部硬信号，验证物的连续性由它们背书。所以每个动手章都是两次生成：**先演进验证物并过门槛，再基于真实产物写正文**；正文数字与断言一律以验证物输出为事实源。

不变量只有一条：**每章有一个机械或可判定的验证信号；门槛是外部的、机械的，过了才写正文**。形态收敛不出时按 SKILL.md「何时不适用」与用户前置澄清，不要硬生成。

## 每章门槛循环（按验证形态实例化）

### code-lab（测试 + 实现；v3 现行循环，四变体 library / cli-golden / config-validate / dom-test）

| 变体 | 适用 | 双硬门槛 |
|---|---|---|
| library（默认） | 库 / 框架内核 | `tsc --noEmit` + `vitest run`；Go 等价物 `go vet` + `go test ./...` |
| cli-golden | CLI、解析器、构建工具 | 构建 + golden 输出比对（固定输入 → 比对输出文件） |
| config-validate | Nginx / Terraform / k8s 配置类 | `nginx -t` / `terraform validate` / `kubectl apply --dry-run=client` |
| dom-test | 浏览器组件 | 构建 + DOM 断言（vitest + jsdom / testing-library） |

1. **快照**：复制 `companion/src` 到 `.course/snapshots/pre-ch-{N}/`（失败回滚点）。
2. **写本章测试（红）**：现写 `companion/tests/{slug}.test.ts`，断言该章 milestone 的**行为**；先跑一次，必须失败——这就是渐进语义的机械证明。`tests/` 是 append-only：只新增本章测试，绝不动旧章测试；旧章测试持续全绿，就是公共 API 向后兼容的哨兵。
3. **演进代码**，纪律：文件级变更、增量演进；不改旧章测试；遵守圣经代码约定与既有风格；备课文件仅在拿不准原理真实行为时查阅（zero-trace 档），不照抄代码、不改编测试。
4. **双硬门槛**（cwd = `companion/`）：先确认本章新测试已转绿，再全量跑一遍——全部测试必须通过。
5. 失败：把报错尾部作为下一轮修复的输入，回到步骤 3。**最多 3 轮**。
6. 3 轮仍败：**回滚快照** → 本章降级为占位章 → 滚动摘要注明「验证物保持上一章形态」→ **继续下一章，不中断全书**。
7. **写完正文后过引用一致性闸门**：正文标注 `src/…` 的代码块必须与验证物**当前形态**逐字一致（教学注释除外）；lint 的 snippet 系列检查 + final-check 的逐字 diff + 评审智能体一致性核对。验证物演进后正文还挂着旧形态的代码，是最伤信任的缺陷之一。

### canvas-app（可运行页面工程 + 现场产出资产）

渲染/音频/可视化课程。门槛循环在 code-lab 之上追加两条：

- **资产再生成门槛**：正文嵌入的每张图/每段音频由 companion 内可重跑的生成脚本现场产出（固定种子、纯计算、零时间戳——两次运行输出逐字节一致，a-share 的 export-docs 模式）；门槛 = 脚本跑通 + 再生成输出一致 + 演示组件 `import` 的是实验场代码/数据脚本产物而非平行手抄（webgl 平行手抄组件是反面教材）。
- **build 门槛**：页面工程可构建（typecheck + test + build 全绿）。
- 可感知性硬语义（011 P1-5）：**测试输出不算可感知面**——milestone_verify 写「看到画面/听到声音/看到曲线」，正文嵌真实产出的资产。

### worksheet（题目 fixture + 唯一数值答案 + 核对脚本）

数值/演算/决策类知识课（股票、统计、金融）。

1. **快照**（题目与答案文件的回滚点）。
2. **先写本章题目 fixture 与唯一数值答案（红）**：`companion/fixtures/{slug}.json`（题面参数）+ 期望答案表；核对脚本先跑出红（期望答案未由演算实现产出）。
3. **实现演算**（`companion/src/` 的纯计算模块）转绿：`npm run check-answers` 全绿。
4. **export-docs 守门（正文数字的事实源）**：正文每处承重数字（图表数据、演算示例、统计结论）由导出脚本从 fixtures/实现现场导出到 `docs/assets/data/`——固定种子、两次运行逐字节一致；正文断言与导出输出不一致时，守门脚本 throw。手写数字一律视为待核对占位。
5. 3 轮仍败 → 回滚 → 占位章 → 不中断（同 code-lab 第 6 步）。
6. 门槛等价物 = **答案核对脚本通过 + 正文数字与脚本导出一致**（final-check 数字断言比对）。

### observation（验证任务清单）

实地操作/工具使用/现象观察课程。验证物不是代码，是**可判定的任务清单**：

- 每章产出本章任务清单（`- [ ]` 勾选式，放正文验证槽）：每条 = 读者操作 + 应看到的具体现象（可对照描述：看到什么、显示什么值、返回什么、报什么错）。
- **可判定性审查**（门槛等价物）：现象描述具体到可对照——「运行 X，第二行输出应为 `Y`」过；「感受一下」「体验一下」「注意观察」不过。lint 的 observation 检查机械扫黑名单，评审轴核对语义。
- 依赖环境不可复现的任务（需真实账户/特定硬件）：任务改为「可判定描述 + 环境要求声明」，验证面如实降级并在 README 写明——不假装可验证。

### repo-probe（探针脚本，配 guided-walkthrough）

源码走读课。验证物 = 对锁定 ref 跑的探针脚本集：

1. **大纲期锁定 ref（commit SHA）**，全书引用以它为唯一事实源。
2. 每章先写本章探针（`companion/probes/{slug}.mjs`）：在 clone 上跑 grep 断言/最小运行/日志检查，断言「正文将声称的机制真实存在」（红：断言先写、跑出失败或空结果 → 人工核对探针写法 → 转绿 = 机制确认）。
3. 探针全绿后才写正文；正文每个机制断言与探针输出一致。
4. 正文代码块**必须**标注 `owner/repo@sha:path` 且与锁定 ref 逐字一致——lint/final-check 机械比对（这是「先验证物后文」在走读课的化身）。
5. 读者验证 = checkout 锁定 ref、跑探针脚本：「亲眼看到」优先于「听我转述」。

## 脚手架（阶段 2 确认后、第一章之前建好）

以 code-lab library 形态（TS + vitest）为例；其他形态用等价脚手架。`companion/package.json`：

```json
{
  "name": "companion",
  "private": true,
  "type": "module",
  "scripts": { "typecheck": "tsc --noEmit", "test": "vitest run" },
  "devDependencies": { "typescript": "^5.6.0", "vitest": "^2.1.0" }
}
```

`companion/tsconfig.json`：`strict: true`、`target/module: ESNext`、`moduleResolution: bundler`、include `src` 与 `tests`。建好后跑一次 `npm install`（后续章不再装）。

等价变体：worksheet 加 `"check-answers": "node src/check-answers.mjs"` 与 `"export-docs": "node src/export-docs.mjs"`；repo-probe 加 `"probes": "node probes/run-all.mjs"`；canvas-app 加 `"build"` 与资产再生成脚本。形态与门槛命令写进大纲 `companion` 字段随章节表确认。

## 重构回写义务

验证物是全书共享状态，第 N 章的重构可能改掉第 M（M＜N）章正文引用过的函数/答案/图表数据。规则只有一条：**正文引用的验证物内容必须始终等于终态**。触发即回写——改正文里的代码块/数字/图表为当前形态（必要时顺带补两句新词汇解释），修完重跑该章 lint。快照目录（`.course/snapshots/`）是内部状态，读者不可达——「本章当时的形态」不能作为正文引用的出处；确需展示历史形态时按「拼版·教学示意」标注并注明终态去向（chapter-writing 硬要求 12）。

## 测试写法要点（code-lab 写「红」测试时的自检）

- 每个动手章一个 `tests/{slug}.test.ts`；只依赖实验场自身，不依赖网络、不 sleep 等待。
- **测试自设**：断言原理行为（「scope.stop 之后 watcher 不再触发」），从零设计，不从任何官方/上游测试改编。
- 断言 milestone 的**行为**（调用什么、得到什么），不断言实现细节；若某内部行为本身就是教学承诺，先写进圣经 API 契约再按契约断言。
- 渐进语义由「先红」机械保证：写出来先跑、看到红，才开始实现。

## 测试梯子：可选交付给读者的练习

`tests/` 按章 append-only、先红后绿——这份渐进结构天然是 TDD 作业梯子，全部验证形态皆然（worksheet 的答案核对、repo-probe 的探针、observation 的任务清单，都是「给出实现让验证转绿」的靶子）。

大纲声明 exercises 附录时，组装期一页成文，不占章节预算。玩法三句：clone companion、清空实现目录、按章序让验证从红转绿。**练习可行性门槛**：成文后在干净副本按梯子逐级执行（或机械校验验证物的 import 依赖图 vs 阶梯顺序拓扑一致）；梯子行内写明超前的运行时依赖（如「第 6 步前先保留 proxy 桩文件」）；毕业项目用到的每项技能须已在正文示范过，否则附分步提示卡。这页练习路线同时是正文「贴关键切面而非全量倾倒」的正当性来源。

## 断点续跑与单章重生成

- 每章完成即落盘：章 md、`.course/rolling.json`（滚动摘要 + 是否降级 + 章文件名）、本章新开承诺并入 `.course/promises.json`。会话中断后从未完成的章继续。
- 「从第 N 章重生成」：恢复第 N-1 章的快照/滚动摘要，删去第 N..末章的测试/探针/fixture 文件，重跑 N..末章（后续章依赖前章滚动摘要，必须连锁重算）。
