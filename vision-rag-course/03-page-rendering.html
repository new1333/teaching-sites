把页面变成图：渲染分辨率与文字层 ​

周五你要查一份供应商合同里的保修条款。这份 PDF 有八十多页，大部分是正经排版的，可当年签章那几页是扫描版——传真机或扫描仪把纸拍成照片贴进文件的页，整页只是一张图。你想走便宜路：先用文本抽取工具逐页抽字，本地建个可检索的索引。跑到签章页，工具吐出来的是空字符串——一个字都没有。可那一页明明印着「整机保修一年」，你亲眼看着它躺在屏幕上。

你换了条路：把整本合同渲染成图（把每一页画成图片），交给视觉大模型。索引这回建得很顺，扫描页也认得出了。然后月底账单来了：图片费用比预想高了十倍。你只不过把渲染档位从 110 拧到了 300 DPI（dots per inch，每英寸铺多少个像素点——渲染清晰度的旋钮），肉眼看字只清楚了一点点，账单却翻了这么多。

两件事都值得拆到底。字抽不出来，是因为那一页根本没有文字层——PDF 里机器能直接抽出的那层隐形文字，抽出来是空字符串正是它缺席的铁证。账单爆炸，是因为图片进视觉模型按分辨率计费——按图片的像素量算钱，清晰度本身就成了成本旋钮。这一章实验场落两块新板：bitmap.py 定义「图」，document.py 定义「页」与渲染。它们是 PDF 主线的第一步——每页一张带页码标签的图。

一份 PDF 里住着两种页 ​

先讲第一宗罪的成因。正经排版的 PDF，存的是排版指令：哪个字、放在哪、多大字号。字本身就在文件里，屏上的页面是照着指令画出来的。机器要抽字，不必看图——把指令里的字按顺序连起来就行，零成本。这份「机器可直接抽出的字」，就是文字层：书页上的一层隐形文字，排版页生来就有。

扫描版走的另一条路：扫描仪把纸页拍成一张照片塞进 PDF。整页没有排版指令，字是照片里的墨点。传真签章、盖章发票、老图纸，都是这么进数字世界的——拍照省事，代价是文字层根本不存在，抽取工具在这一页只能交回空字符串。

text
同一页纸的两种身世

排版页：排版指令（字就在文件里）→ 文字层可抽，零成本
扫描页：扫描仪拍的照片 → 屏上一样的字，抽取只得空字符串

所以「抽出来是空的」不是工具坏了，是这页真的无字可抽。这件事程序自己就能发现——文字剥掉空白后什么都不剩，就是没有：

python
# src/vision_rag/document.py · Page
class Page:
    """文档的一页：文字层 text + 这页的位图。

    真实 PDF 里两个都从原文件读出。扫描页的 text 是空字符串——
    字印在图片上，文字层根本不存在。
    """

    def __init__(self, text: str, bitmap: Bitmap):
        self.text = text
        self.bitmap = bitmap

    @property
    def is_scanned(self) -> bool:
        """程序检出「这页没有文字层」：文字剥掉空白后什么都不剩。"""
        return not self.text.strip()

一个诚实的边界当场说清：空白页的文字层也是空的，同样会被 is_scanned 判为真。这个检测回答的是「有没有文字层」，不是「是不是扫描件」。要把两者分开，得再看渲染出的图上有没有墨——扫描页的图满是内容，空白页的图干干净净。实验场把「有没有墨」留在测试里当辅助判断，is_scanned 只守住最稳的那条语义。

那扫描页还有救吗？扫描页正是整套系统必须「看图」的铁证——文字层帮不了它，只有视觉模型读得了图里的字。文字层也没有失业：第 4 章的兜底卡、第 5 章的免费粗筛、第 7 章深读时的精确措辞，全都吃它。两条腿缺一不可。

渲染：把页变成图，顺手把页码焊上去 ​

Page 的另一个字段 bitmap，就是渲染出来的页图。实验场里的「图」是字符位图 Bitmap——等宽字符网格，一个字符当一个像素。整块板不长：

python
# src/vision_rag/bitmap.py · Bitmap
class Bitmap:
    """等宽字符网格。不变量：至少一行、行行同宽——破坏即 ValueError。

    crop(x, y, w, h) 与 center_crop(w, h) 已随第 12 章微观放大加入。
    """

    def __init__(self, rows: list[str]):
        if not rows:
            raise ValueError("位图至少要有一行")
        width = len(rows[0])
        if any(len(row) != width for row in rows):
            raise ValueError(f"位图各行必须等宽：首行 {width} 字符，存在不等宽的行")
        self.rows = list(rows)

    @property
    def width(self) -> int:
        """横向字符数（这张「图」的宽）。"""
        return len(self.rows[0])

    @property
    def height(self) -> int:
        """纵向字符数（这张「图」的高）。"""
        return len(self.rows)

    def render(self) -> str:
        """铺成一段文本：行与行以换行相连。"""
        return "\n".join(self.rows)

这是本章声明的第一处简化：真实世界渲染出的是 PNG 字节，实验场用字符网格代替——图看得见、像素数得清、测试能逐字符断言。第 2 章的 img_block 只认 render() 方法，所以 Bitmap 零改动就能流进请求，data URL 那层的简化第 2 章已声明过。

渲染在真实世界是「排版指令换算成像素」，旋钮下一节讲。在实验场里它落在两件东西上。装页码的叫 PageImage（SynthDoc 只是一列 Page 的壳，真实世界里这列页来自 PDF 阅读库，其余照旧）：

python
# src/vision_rag/document.py · PageImage
class PageImage:
    """一张带页码的页图。页码在渲染那一刻与图像绑定，不可再分。"""

    def __init__(self, page_no: int, bitmap: Bitmap):
        self.page_no = page_no
        self.bitmap = bitmap

    @property
    def label(self) -> str:
        """进请求时贴在图前的页码标签——模型引用页码的物理出处。"""
        return f"[第{self.page_no}页]"

跑渲染的叫 render_pages——一个循环：逐页取位图、从 1 起编号、一起装进 PageImage：

python
# src/vision_rag/document.py · render_pages
def render_pages(doc: SynthDoc, dpi: int = BASE_DPI) -> list[PageImage]:
    """逐页出图：页码从 1 起编号，与缩放后的位图一起装进 PageImage。

    dpi 是清晰度旋钮：110 为存储形态原样出场，220 边长翻倍、
    像素与成本翻四倍；页码标签不受旋钮影响——第 3 页永远是第 3 页。
    """
    if dpi <= 0:
        raise ValueError(f"dpi 必须是正数，收到 {dpi}")
    scale = dpi / BASE_DPI
    images = []
    for page_no, page in enumerate(doc.pages, start=1):
        bm = page.bitmap
        new_w = max(1, round(bm.width * scale))
        new_h = max(1, round(bm.height * scale))
        images.append(PageImage(page_no, Bitmap(_resample(bm.rows, new_w, new_h))))
    return images

重点在 label。页码不是事后补的备注：循环里 enumerate 数到第几页，这个数就和那页的位图一起装进 PageImage，label 属性再从它拼出页码标签。送进模型时，第 2 章的 img_block 把标签装成图前面的文本块——标签与图同一次请求、同进上下文。

页码引用的精确性，物理来源就在这里。模型答「见第 3 页」时，不是在三百页里回忆定位，而是在照抄它眼前文本块里的字符。照抄是复制任务，复制不走样——这正是第 1 章说的「让页码绑定物理事实」的落点。还有一层保险：清晰度旋钮随便拧，第 3 页永远是第 3 页，编号来自循环计数，与分辨率是两个互不相干的自由度。后面的精排层还会校验模型吐出的页码确实在候选集合里——绑定加校验，双保险。

DPI：清晰度是旋钮，成本是平方 ​

现在复盘第二宗罪。先补上渲染的原理：PDF 页面存的不是像素，是排版指令，打开或渲染时才换算成像素点阵。换算要回答一个问题——一英寸的纸面铺多少个像素点？答案就是 DPI。数字越大，同样的版面铺越多的点，字越锐利。PDF 的坐标单位是 1/72 英寸，所以 72 DPI 就是「一点一像素」的原生比例，往上拧都是在加密度。

而图片进视觉模型，按分辨率计费——按图片的像素量收费，像洗照片：像素越高越清楚，也越贵。像素 = 长 × 宽，两条边都随 DPI 等比涨，于是成本随 DPI 的平方涨。用纸笔复算一遍（一页美式信纸 8.5 × 11 英寸；计费用本书声明的口径，每 750 像素折 1 token——简化模型，不是任何平台真实价格）：

text
纸笔演算：信纸页 8.5 × 11 英寸，750 像素 = 1 token（声明口径）

110 DPI：边长 935 × 1210 像素 → 113 万像素 ÷ 750 ≈ 1509 token
220 DPI：边长各 ×2 → 像素 ×4 → ≈ 6034 token（约四倍——两次向上取整会差一点点，比例律看像素 ×4 最干净）
300 DPI：边长 ×2.7 → 像素 ×7.4 → ≈ 11,220 token

第 1 章对账用的「一页约 1500 token」，就是 110 DPI 这档算出来的数。现在看你的十倍账单：从 110 拧到 300，直觉以为贵不到三倍（边长才 2.7 倍），平方律给出 7.4 倍。再叠加一条——文本抽取时代，扫描页是空字符串、从不进账本；改成整本渲染后，它们张张计费。单价涨七倍多、计费页数又变多，月账单冲上十倍，一点不冤。真实工具把默认档定在 110 而不是更高，也是这个道理：再清晰的边际收益，抵不过平方的边际成本。有的工具还会给长边封顶——一条边不许超过某个像素上限，防单图撑爆请求；实验场从简，旋钮不设上限，这处简化登记在附录差异清单。

实验场把计费口径写成一个不到十行的函数：

python
# src/vision_rag/document.py · approx_tokens
def approx_tokens(bitmap: Bitmap, pixels_per_token: int = 750) -> int:
    """声明的简化计费模型：像素总数 ÷ 每 token 像素数，向上取整。

    与任何平台真实价格无关——只保留一条方向性事实：
    图越清晰（像素越多）越贵，成本随两条边长按平方涨。
    """
    if pixels_per_token <= 0:
        raise ValueError(f"pixels_per_token 必须是正数，收到 {pixels_per_token}")
    pixels = bitmap.width * bitmap.height
    return -(-pixels // pixels_per_token)  # 向上取整：不足一个 token 也算一个

那行 -(-pixels // ...) 是 Python 里向上取整的惯用写法：负的地板除（//，除不尽时向更小的整数取：-2 // 750 是 -2 而不是 0）再负回来。DPI 旋钮本身则是最近邻缩放——新网格的每格，抄离它最近的原格字符，实现只有一个函数。

python
# src/vision_rag/document.py · _resample —— DPI 旋钮的全部实现
def _resample(rows: list[str], new_w: int, new_h: int) -> list[str]:
    """最近邻缩放字符网格：新格 (x, y) 抄最近的原格字符。

    放大时每个字符长成一块（2×2、4×4……），肉眼看就是「图变清楚了」；
    缩小时按步长抽样。DPI 旋钮的全部实现就是这一个函数。
    """
    h, w = len(rows), len(rows[0])
    out = []
    for y in range(new_h):
        src = rows[min(h - 1, y * h // new_h)]
        out.append("".join(src[min(w - 1, x * w // new_w)] for x in range(new_w)))
    return out

实验场：一本六页的合成手册 ​

课程的固定素材是一本自产手册，六页凑齐全部页型：

python
# src/vision_rag/document.py · make_handbook
def make_handbook() -> SynthDoc:
    """课程自产示例手册：封面、目录、正文、表格、扫描页、空白页，共 6 页。

    第 5 页是扫描件——位图上画着保修条款，文字层却是空字符串：
    「看得见的字」与「机器能抽出的字」在这一页上故意不是一回事。
    """
    cover = Page(
        "设备维护手册\nMODEL-X 系列\n第 3 版",
        _draw(["设备维护手册", "", "MODEL-X 系列", "", "第 3 版"]),
    )
    toc = Page(
        "目录\n1 安装 3\n2 保养 4\n3 保修 5",
        _draw(["目 录", "", "1 安装 ······ 3", "2 保养 ······ 4",
               "3 保修 ······ 5"]),
    )
    body = Page(
        "2 保养周期\n每 90 日更换滤芯，每 180 日校准一次温度探头。",
        _draw(["2 保养周期", "", "每 90 日更换滤芯，", "每 180 日校准一次",
               "温度探头。"]),
    )
    table = Page(
        "耗材与周期\n耗材 周期\n滤芯 90 日\n皮带 180 日",
        _draw(["耗材与周期", ""] + _table_rows()),
    )
    scanned = Page(
        "",  # 扫描页没有文字层：字印在图上，抽出来只能是空字符串
        _draw(["3 保修条款", "", "整机保修一年，", "易损耗材不在",
               "保修范围内。", "", "（盖章处）"]),
    )
    blank = Page("", _draw([]))  # 空白页：图上无墨，文字层也没有
    return SynthDoc([cover, toc, body, table, scanned, blank])

排版杂务由两个小工具代劳：_draw 把文本行居中画进 50 × 30 的网格，_table_rows 画表格线——与原理无关，样子在仓里。第 5 页是全场主角：位图上画着保修条款和盖章处，文字层却是空字符串。翻开它、再拧一格旋钮，两件事都亲眼可见：

python
# 用法示例：翻开扫描页，再拧一格成本旋钮（companion 目录下，先设 PYTHONPATH=src）
from vision_rag.document import make_handbook, render_pages, approx_tokens

doc = make_handbook()
page5 = doc.pages[4]
print(page5.is_scanned)    # True：程序一眼检出没有文字层
print(repr(page5.text))    # ''：抽取结果就是空字符串
print("\n".join(r for r in page5.bitmap.render().splitlines() if r.strip()))
# 位图上「整机保修一年」「（盖章处）」一行行躺得整整齐齐——字在图里

for dpi in (110, 220):
    total = sum(approx_tokens(img.bitmap) for img in render_pages(doc, dpi=dpi))
    print(dpi, total)      # 110 12  →  220 48：一格旋钮，整本成本翻四倍

两个数要在心里对准刻度。合成页是 50 × 30 的袖珍页，一页 1500 像素、折 2 token，整本 12——绝对数与真实信纸页不同（那是约 1509 token），但比例律完全一致：边长翻倍，像素翻四倍。放大到 220 后，render() 里的「（盖章处）」一行变成「（（盖盖章章处处））」——每个字符长成 2 × 2 的一块，这就是最近邻缩放的肉眼证据。声明过的两处简化：字符位图代替真实 PNG；袖珍页的绝对成本不代表真实页面——差异都收在附录差异清单。

验证：跑什么，看到什么 ​

本章的里程碑全部写成测试，钉在 tests/test_page_rendering.py 里。三组断言各验一事：

  • 扫描页可程序检出——第 5 页 text 恰为空字符串且 is_scanned 为真；空白页同样过检（语义如此）；排版页为假；
  • 页码与图像一次绑定——render_pages 产出 [第1页] 到 [第6页] 顺序标签；img_block 里标签排在图前、base64 解开恰好是那页的 render()；
  • 一格旋钮、四倍成本——dpi=110 与 dpi=220 逐页对比，approx_tokens 恰好多四倍（2 → 8，整本 12 → 48）；另有纸笔可复算的取整断言（756 像素也折 2 token）。

收线：两条纪律的归宿 ​

回头看开头的两件事。空字符串不是工具坏了，是扫描页根本没有文字层——检测只要一行，出路是把页变成图交给看得见的模型。十倍账单不是平台坑人，是平方律加「扫描页开始计费」——清晰度是成本旋钮，默认档要挑在「模型读得清」与「账单不炸」的平衡点上。

离开前自查四问：

  • 同一页纸，排版页与扫描页进 PDF 后差在哪？程序靠什么检出扫描页？
  • 为什么说页码引用的精确性来自「标签与图像一次绑定」？模型引用页码时在做什么？
  • 110 拧到 300 DPI，一页信纸的成本涨几倍？为什么是平方而不是线性？
  • 空白页为什么也会被判成「没有文字层」？真要把空白与扫描分开，还差什么信息？
