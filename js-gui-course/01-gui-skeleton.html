桌面 GUI 程序的骨架：窗口与消息循环 ​

先看一个事故。有人写了这样的桌面端代码：点击按钮后执行一个三秒钟的死循环去「同步处理数据」，循环期间整个窗口白屏、按钮点不动、连拖动窗口都无响应；更早的新人版本则是把窗口创建好之后什么都没写，main 函数跑完直接退出，窗口闪了一下就消失。这两个现象方向相反——一个是「卡死」、一个是「秒退」——但根因是同一个：写代码的人不知道 GUI 程序靠什么活着。

答案是一句话：桌面 GUI 程序的生命线，是一条「取一条消息、处理、再取下一条」的消息循环（message loop，也叫 run loop）。循环活着，界面就活着；循环退出，程序结束；循环被一段代码占住不放，界面就冻结。这一章不讲任何 JS，先把这块所有桌面端共用的地基打牢——因为无论 Electron、Tauri 还是原生 Qt，最终都要落到这个骨架上。

窗口不属于你，属于操作系统 ​

第一个要纠正的直觉：你以为「我的程序创建了一个窗口」，其实窗口是操作系统（的窗口管理器）创建并持有的资源。你的程序做的事是向 OS 申请：「给我一块窗口资源，宽 800 高 600，标题叫 Counter」。OS 同意后，发回给你一个标识——句柄（handle）。此后你对窗口的一切操作（改标题、显示、隐藏、关闭）都是拿着这个句柄向 OS 发请求，窗口本体自始至终住在 OS 那边。

这不是学术区分，它直接决定了后面所有章节的代码形态：JS 侧拿到的 win 对象里没有一个字节是「窗口本身」，它只是一个遥控器。遥控器丢了可以再做一个，窗口还在；窗口被 OS 销毁了，遥控器就成了指向空气的失效句柄。第 5 章实现 WindowHandle 时你会亲手碰到这条边界。

界面上发生的一切，都变成消息排队 ​

第二个地基：用户不会「调用你的函数」。用户按下按钮、拖动窗口、敲键盘，这些动作首先发生在 OS 层——OS 的输入系统把它们翻译成一条条消息（message/event），投递到「属于哪个窗口」的那个队列里。你的程序想获知用户的动作，唯一的途径就是在消息循环里把消息取出来、看类型、分发给对应的处理逻辑。

text
// 原理示意（伪码）：一切 GUI 主线程的心跳
while (true) {
  msg = 队列取出下一条消息()      // 队列空就等待（不烧 CPU）
  if (msg.type === 'quit') break
  分发给对应处理函数(msg)          // 点击 → 按钮处理；绘制 → 重画窗口
}

现在回头看开头两个事故：死循环版占了循环不放，三秒内 OS 投递的绘制消息、输入消息全堵在队列里没人取，界面自然冻结——注意，消息没有丢，只是没人处理，「白屏」是「最后一次绘制之后再也没有绘制过」；秒退版压根没写循环，main 结束进程退出，窗口资源随进程一起回收。一个 GUI 程序哪怕什么都不做，也必须留一个活着的循环在那儿取消息，这就是「Hello Window」程序也有几十行模板代码的原因。

序列化边界：消息里能装什么 ​

消息从 OS 世界跨进你的程序，这一步已经出现了全书最重要的约束：跨边界传的是数据副本，不是引用。OS 不可能把「按钮对象」塞给你——它给你的是 { type: 'click', 目标: 按钮句柄, 坐标: {x, y} } 这样的纯数据。这条规则会一路升级：第 4 章 JS 调原生函数时参数要做序列化（serialization）校验，跨进程通信时 payload 同样只能过纯数据。边界两边交换的永远是可复制的数据，引用、闭包、对象本体过不去——把这个印象留在脑子里，后面每一章都是它在变形。

那 JS 在哪儿 ​

有了骨架就能摆正 JS 的位置：JS 语言本身没有窗口、没有消息循环、也没有绘制能力——window、createWindow、requestAnimationFrame 全都不是 JS 的一部分，而是宿主（host）注入的。宿主把 JS 运行时嵌入自己体内（embedding），再把它自己的能力包装成全局对象递给 JS。浏览器、Node、Electron 主进程的 API 各不相同，就是因为注入能力的宿主不同。这个话题是第 3 章的主菜，此处只需要记住结论：JS 接入 GUI 的全过程，就是宿主把「消息循环 + 窗口操作」这两样东西以某种方式暴露给 JS 的过程。

顺着这句话可以提前看到课程终点的地图——也正是真实 Electron 内部发生的事：

  1. 消息循环在原生世界转着，OS 不断投递消息（本章）；
  2. 手写一个最小循环，把「取—分发」变成肌肉记忆（下一章）；
  3. 宿主把 JS 引擎嵌入，注入全局 API；
  4. JS 通过绑定层（binding）调用原生函数：注册、转发、序列化；
  5. 窗口以句柄形式出现在 JS 侧；
  6. 耗时的原生调用走异步：结果进入任务队列（task queue），回投 JS 单线程；
  7. 界面与系统权限拆进渲染进程/主进程（renderer process / main process），跨进程用进程间通信（IPC）借能力，一问一答靠请求-响应（invoke/handle），通知靠事件推送（send/on）；
  8. 反方向：用户点击经订阅（subscription）回到 JS 回调；
  9. 全部零件拼成 createApp，点按钮改状态刷新界面全程走桥；
  10. 真机两章：真的跨一次语言边界（WebAssembly），再把内核跑成可交互的应用。

小结 ​

窗口在 OS、消息进队列、程序靠循环活着——这是所有桌面 GUI 的公共骨架，与语言无关。JS 想做桌面端，就要想办法把自己挂到这个骨架上：要么宿主带着 JS 引擎进入骨架（Electron 的路），要么 JS 直接去撬原生 GUI 工具包（绑定的路）。下一章先把这条循环亲手写出来——只有几十行，但写完你对「GUI 主线程每一毫秒在干什么」就不再有神秘感。

本章没有代码作业，但请务必能回答三件事：窗口本体住在哪一侧？用户点击以什么形态到达你的程序？循环卡住时丢的是什么、不丢的是什么？
