分支是一个文件,HEAD 是个指针的指针 ​

建分支这件事,快得反常。在项目里敲 git branch hotfix,回车还没松手,分支已经建好,没有任何进度条。同一个动作换成你熟悉的备份手段——复制整个项目文件夹——进度条要走半天,文件夹吃掉几个 G。建分支到底建了什么,凭什么不要钱？

另一幕你多半也撞见过。想看看某个历史版本长什么样,或者 checkout 一个 tag,屏幕忽然打出一大段英文,头一行是 You are in 'detached HEAD' state——红字,一大段警告。切个版本而已,git 在警告什么？detached HEAD 是什么东西,这算出错了吗？

两件事共用一个答案,答案在上两章已经备齐了零件。第 5 章末尾把话说死过,原话是「readHeadHash 是本章的临时讲法,只服务 status」,又说「ref: 指向另一个引用」的解析规则要正式化成 refs.ts 的 resolveHead。分支建立/切换/detached,全踩在它上面。同章实验里你还手写过 echo $C > .git/refs/heads/main 才让提交挂上分支——那个别扭也是本章要拆的机关。先剧透半句:那行 echo 手写的「引用」,就是分支的实体；它是一个内容只有 40 位十六进制的小文件。本章拆三样东西:分支到底是什么,HEAD 的两种形状,以及 mini-git 第一条端到端的 porcelain 命令 commit。它把第 5 章的暂存区清单、第 3 章的树、第 4 章的提交对象串成一条流水线。

分支是一个 41 字节的文件 ​

先兑现上一章的账。第 5 章读 HEAD 走的两跳——先读 HEAD 文本,见到 ref: 开头就去读它指的小文件——那个被指向的小文件,就是本章的主角。**引用(ref)——一个只装着一行 40 位对象名的小文件,按路径住在 .git/refs 下；分支是引用,标签是引用,它们只是住在不同的子目录里。目录布局的正本,是官方文档 gitrepository-layout。本章关于目录职责的描述,都以它为准。文档对 refs/heads/ 下每个文件的说明,英文原话一句:「records tip-of-the-tree commit objects of branch name」。翻译:记录名叫 name 的分支的最新一笔提交。

拿上两章的实验场亲手验一遍。三层 fixture,一笔提交之后,.git 里的引用长这样:

bash
# 用法示例 · 提交之后,引用的原始内容
cat .git/HEAD          # ref: refs/heads/main
cat .git/refs/heads/main
# bf05977bd740a2b2fa530935475587501704d0cc
ls -l .git/refs/heads/
# -rw-r--r-- 1 you 197609 41 ... main

一个文件,41 字节:40 个字符的提交名,加一个换行。主分支的全部实体,就这 41 字节——再加上 HEAD 里那行指路文本。建分支为什么快,答案已经在你眼前:建分支就是往 refs/heads/ 里再写一个 41 字节的文件,内容抄一遍当前的提交名——那个由内容算出来的 SHA-1 名字。写一个文件,当然比复制一份历史快。把数字换个体感:不管你的仓库有 3 笔提交还是 3 万笔,这个文件永远是 41 字节；分支的「重量」与历史规模无关。

现在清算第一个流传很广的直觉:分支是整份历史的副本。先替它说句公道话。这个直觉有清楚的来源——你备份项目的方式就是复制文件夹,而分支用起来确实像「另开一个世界」,每个分支有自己的历史。在「历史很占空间」的常识里,「开新世界=复制一份」听上去顺理成章。不成立的地方在实物上:上章建的提交图里,对象库是全体分支共享的,一笔提交、一棵 tree、一个 blob,谁都不为谁复制。分支只是贴在提交图某个节点上的一张标签。反事实一戳就破:假如建分支真是复制历史,那么 3 万笔提交的仓库建分支要等好几秒,对象库体积直接翻倍；实际测一下,建分支前后对象库里的文件数一个都没多——本章演练里那条测试会把这个「一个都没多」钉死。

HEAD:指针的指针 ​

分支的本体解决了,还差「当前在哪个分支」。这就轮到 HEAD,以及本章第二个新词。**符号引用(symbolic ref)——内容不是对象名,而是 ref: <另一个引用的路径> 的一行间接指针；HEAD 是最常用的一个。**这个语法的正本出自官方文档 git-symbolic-ref。定义的英文原话:「A symbolic ref is a regular file that stores a string that begins with ref: refs/」。文档还给了例句:你的 .git/HEAD 就是一个普通文件,内容是 ref: refs/heads/master。翻译:符号引用是一个普通文件,存着一句以 ref: refs/ 开头的字符串。所以 HEAD 与分支是两个文件、两层指针:HEAD 指向 refs/heads/main 这个路径,refs/heads/main 再指向某个提交名。「指针的指针」,章名里说的就是它。

顺带一个历史注脚,出自官方文档的 NOTES 一节。早年 .git/HEAD 真的是一个符号链接(symbolic link),切分支靠 ln -sf。后来因为符号链接的可移植性差,换成了今天这种普通文本文件加 ref: 前缀。间接指针不用操作系统的链接机制,自己一层层读就行——这正好是 mini-git 能自己写的部分。

兑现承诺的时刻。第 5 章那两跳的临时讲法,现在正式化成 refs.ts 的 resolveHead。先把三种可能的 HEAD 内容摆成一张表。拿着它你就是人肉解析器,不打开 companion 也能推。

.git/HEAD 的内容resolveHead 的走法状态
ref: refs/heads/dev,且该文件存在跟一跳,读出提交名附着在 dev 上
ref: refs/heads/dev,但该文件不存在返回 nullunborn:dev 还没生过提交
40 位提交名不跟跳,直接返回detached HEAD
其他任何内容报错HEAD 已损坏

unborn 值得停一拍:mini-git init 写完 HEAD 的那一刻,refs/heads/main 还不存在,HEAD 指向空处。第 5 章 status 在新仓库能跑全靠这一形状返回 null——「没有 HEAD」不报错,是设计出来的口径。

第二个直觉清算:HEAD 就是当前分支本身。公道话先说:日常口语「HEAD 在 main 上」「把 HEAD 移到 dev」在附着状态下八九不离十,团队里没人会误解。恰好不成立的地方在实体上:HEAD 是一个文件,内容是一句指路文本,分支本体是另一个文件,装着提交名。两份 41 字节量级的东西,谁也不是谁。两个极端形状立刻把这个区分放大——unborn 时分支文件压根不存在,HEAD 已经在岗；detached 时 HEAD 记着一个提交名,任何分支都不在场。把 HEAD 当成分支本身,这两种状态就没法解释了。

detached HEAD:警告在怕什么 ​

表里第三种形状是本章第三个新词。**detached HEAD——HEAD 直接记录某个提交名、不再指向任何分支的状态。**官方文档对它的命名,原话出自 gitrepository-layout:「Such a state is often called detached HEAD」。前一句说的是:HEAD 也可以直接记录一个具体的提交,而不作指向当前分支的符号引用。措辞值得注意,文档叫它 state(状态),不叫 error。

第三个直觉清算:detached HEAD 是一种错误状态。公道话:那段输出确实是红字、确实一大段,长得像 git 在骂人；而且多数人第一次见到它,都是在「本想切分支、却给了哈希」的误操作里,「出错」的印象由此而来。但注意它出现的合法场合:checkout 一个 tag 看旧版本、检出历史提交复现旧 bug、在固定版本上构建发布物——这些操作 git 全程照办,没有拦你。所以状态本身不是错,那警告在怕什么？

怕的是你在这个状态下做新提交。回忆本章已经立起的事实:commit 推进的是当前分支的引用文件。detached 时没有分支在场,你的新提交推进的是 HEAD 自己——提交对象正常落库,但没有任何 refs/heads/ 下的文件指着它。再切回任何分支,这些提交就从所有引用的视野里消失了:对象还在对象库里,cat-file 读得到,log 也走得动,可你只能靠 40 位哈希找回它们。哈希不是好记的东西。警告的全文其实说得很直白:他告诉你「你不在任何分支上」,是提醒接下来的提交没有兜底,不是宣判你操作违法。

至于没有引用兜底的提交最终命运如何——会不会一直躺在对象库里,还是哪天被清理掉——这个判断需要「可达性」这把尺子,第 8 章讲祖先与 merge-base 时回来收这笔账。本章先把现象踩实:演练与验证里你会亲手制造一笔「只能靠哈希找回」的提交。

refs.ts:引用的读写与 HEAD 的解析 ​

先看本章的心脏,解析器全家共用一个形状函数:

ts
// src/refs.ts · parseRefText 与 resolveHead(拼版:两段之间略去 readHead——它只负责把 HEAD 文件原文读成字符串)
/** 把一段引用文件原文拆成「符号引用目标」或「对象名」;两头不是当场报错。 */
function parseRefText(text: string, where: string): HeadTarget {
  if (HASH_RE.test(text)) {
    return { kind: 'hash', hash: text }
  }
  if (text.startsWith(SYMREF_PREFIX)) {
    const ref = text.slice(SYMREF_PREFIX.length).trim()
    if (!ref.startsWith('refs/')) {
      throw new Error(`${where} 已损坏:'${text}' 指的 '${ref}' 不在 refs/ 命名空间里`)
    }
    return { kind: 'ref', ref }
  }
  throw new Error(`${where} 已损坏:内容 '${text}' 既不是 ref: 形状也不是 40 位提交名`)
}

export function resolveHead(gitDir: string): string | null {
  let target = readHead(gitDir)
  for (let hops = 0; ; hops++) {
    if (target.kind === 'hash') {
      return target.hash // detached:HEAD 直接写着提交名
    }
    if (hops >= MAX_SYMREF_HOPS) {
      throw new Error(`HEAD 的符号引用链超过 ${MAX_SYMREF_HOPS} 跳,几乎必是环:'${target.ref}'`)
    }
    const text = readRefText(gitDir, target.ref)
    if (text === null) {
      return null // unborn:分支存在但从没生过提交,HEAD 指向空处
    }
    target = parseRefText(text, `引用 '${target.ref}'`)
  }
}

跟第 5 章的两跳版本比,升级在两处。其一,循环代替单跳:符号引用是一条链,HEAD 可以指 refs/heads/top,refs/heads/top 又指别处。真 git 的 symbolic-ref 默认就把链跟到底,mini-git 对齐。其二,链上加了 5 跳的上限:a 指 b、b 又指 a 的环,读到上限就报错,好过死循环。那张三形状表在这里一行行落地:裸哈希直接返回,ref: 跟一跳,文件不存在返回 null,内容两头不是判损坏。

引用本体的读写则是纯文件操作,没有任何二进制——这一章用不着 Buffer,也用不着十六进制转储,引用文件就是一行文本。它们指向的,依旧是第 2 章那些带对象头、zlib 压缩后落盘的松散对象；引用不进对象库,它只是贴在对象库外面的标签。

点开看:readRef/updateRef/listBranches 与 attachHead/detachHead(src/refs.ts 其余四件)。
ts
// src/refs.ts · readRef 与 updateRef
/** 读一个引用:返回它记录的对象名;引用不存在返回 null;内容是 ref: 形状判损坏——引用文件里该是对象名。 */
export function readRef(gitDir: string, ref: string): string | null {
  const text = readRefText(gitDir, ref)
  if (text === null) {
    return null
  }
  if (!HASH_RE.test(text)) {
    throw new Error(`引用 '${ref}' 里不是 40 位对象名,而是 '${text}'`)
  }
  return text
}

/** 写一个引用:把 40 位对象名写进 .git/<ref>,目录不存在就建。 */
export function updateRef(gitDir: string, ref: string, hash: string): void {
  if (!HASH_RE.test(hash)) {
    throw new Error(`updateRef:'${hash}' 不是 40 位十六进制,写不进引用 '${ref}'`)
  }
  const path = join(gitDir, ref)
  mkdirSync(dirname(path), { recursive: true })
  writeFileSync(path, `${hash}\n`, 'utf8')
}

updateRef 会建目录,所以 feature/ui 这样的嵌套分支名也只是一条路径。listBranches 递归扫 refs/heads/,把分支名连同斜杠摊平成字典序列表；attachHead 往 HEAD 写 ref: <路径>,detachHead 往 HEAD 写裸哈希——两个方向,各四行。这三个的全文在 companion/src/refs.ts,结构与上面两件同款。

commit:四步流水线 ​

本章最提气的一步。第 5 章的 add 与 status 已经摸到日用层,但真正把改动写成历史的,之前只有手工拼装的底层命令；commit 是 mini-git 第一条端到端的 porcelain。它没有发明任何新机制,只是把三章的零件串起来:

ts
// src/cli.ts · cmdCommit
function cmdCommit(cwd: string, args: string[]): string {
  const usage = '用法:mini-git commit -m <消息>;收暂存区清单,生成提交并推进当前分支'
  let message: string | undefined
  for (let i = 0; i < args.length; i++) {
    if (args[i] !== '-m') {
      throw new Error(`${usage};不认识参数 '${args[i]}'`)
    }
    const msg = args[++i]
    if (msg === undefined || message !== undefined) {
      throw new Error(`${usage};恰好一个 -m,后面跟消息文本`)
    }
    message = msg
  }
  if (message === undefined) {
    throw new Error(`${usage};-m 不能省`)
  }
  const gitDir = requireGitDir(cwd)
  const tree = writeTreeFromIndex(gitDir, loadIndex(gitDir))
  const parent = resolveHead(gitDir)
  const hash = commitTree(gitDir, {
    tree,
    parents: parent === null ? [] : [parent], // unborn 分支上的第一笔:没有父提交
    author: identityFromEnv(),
    message: message.endsWith('\n') ? message : `${message}\n`,
  })
  const head = readHead(gitDir)
  const firstLine = message.split('\n')[0]
  if (head.kind === 'ref') {
    updateRef(gitDir, head.ref, hash) // 推进当前分支;其他分支的引用文件一个都没碰
    const name = head.ref.startsWith('refs/heads/') ? head.ref.slice('refs/heads/'.length) : head.ref
    return `[${name}${parent === null ? '(根提交)' : ''} ${hash.slice(0, 7)}] ${firstLine}`
  }
  detachHead(gitDir, hash) // detached:HEAD 自己前移,任何分支都不动
  return `[HEAD detached ${hash.slice(0, 7)}] ${firstLine}`
}

参数检查之后就是四步。loadIndex 收暂存区清单；writeTreeFromIndex 把清单拼成 tree 对象；commitTree 打包出提交对象,父提交由 resolveHead 给出,unborn 时为空；最后按 HEAD 的形状落引用。附着状态,updateRef 推进当前分支,别的分支一个字节不动；detached 状态,引用这步换成 detachHead 让 HEAD 自己前移——上一节「警告在怕什么」的全部机制,浓缩在这两个分支里。第 5 章末尾手写 echo $C > .git/refs/heads/main 的那个别扭,从此消失。

点开看:checkout 的恢复逻辑(src/cli.ts 终态,含后文合并章拆出的 restoreToTree;从简口径见下方文字)。

本章动手时,恢复逻辑是一整只函数;后面写合并时,合并结果落盘要走同一段「删旧、检出、重建清单」,主体因此被拆成 restoreToTree。下面的代码块是拆分后的终态,函数头部的职责没变:restoreWorktree 验明目标提交并取出 tree,restoreToTree 收尾三步。

ts
// src/cli.ts · restoreWorktree 与它的主体 restoreToTree(合并章拆出,落盘复用)
function restoreWorktree(gitDir: string, workDir: string, commitHash: string): number {
  const { type, body } = readObject(gitDir, commitHash)
  if (type !== 'commit') {
    throw new Error(`checkout:'${commitHash}' 是 ${type} 不是 commit,检不出工作区`)
  }
  return restoreToTree(gitDir, workDir, parseCommit(body).tree)
}

/** restoreWorktree 的主体:给定 tree,删旧清单文件、检出、重建 index——merge 产出树后也走这条路落盘。 */
function restoreToTree(gitDir: string, workDir: string, tree: string): number {
  const dirs = new Set<string>()
  for (const e of loadIndex(gitDir)) {
    rmSync(join(workDir, e.path), { force: true })
    for (let i = e.path.indexOf('/'); i > 0; i = e.path.indexOf('/', i + 1)) {
      dirs.add(e.path.slice(0, i)) // 收集祖先目录,等文件删完再顺手清空壳
    }
  }
  for (const d of [...dirs].sort((a, b) => b.length - a.length)) {
    const abs = join(workDir, d)
    if (existsSync(abs) && readdirSync(abs).length === 0) {
      rmSync(abs, { recursive: true })
    }
  }
  checkoutTree(gitDir, tree, workDir)
  const entries = [...flattenTree(gitDir, tree)].map(([path, sig]) =>
    makeIndexEntry(path, sig.hash, statSync(join(workDir, path))),
  )
  saveIndex(gitDir, entries)
  return entries.length
}

cmdCheckout 拿到目标后,先调它恢复现场,最后才动 HEAD。目标是分支名就查 refs/heads/；是 40 位哈希就直接进 detached。名字解析的顺序,与官方文档 gitrevisions 的查找规则同向。从简口径在这里声明:真 git 切换前会检查未提交的改动,可能因为「改动会被覆盖」拒绝你。mini-git 不做这个检查:被跟踪的文件无条件用目标提交的版本覆盖,未跟踪的文件一律保留。清单的重建走 makeIndexEntry,stat 字段来自检出的那一刻。等于把目标 tree 摊平后逐文件重新 add 了一遍,文件模式也照磁盘重取。

收束:分支是标签,HEAD 是指着标签的那只手 ​

开篇两个现象一起收口。建分支眨眼完成,因为分支只是一个 41 字节的文件,往 refs/heads/ 里一放,内容抄一遍当前提交名——对象库里的快照模型历史全体分支共享,谁也不复制谁。detached HEAD 的警告不是在骂你,是在替你的提交着急:HEAD 直接记着哈希时,新提交推进的是 HEAD 自己,任何分支文件都不含它,切走之后只剩哈希这一条找回的路。第 5 章埋的两笔账都在本章兑现:readHeadHash 迁进 refs.ts 正式化成 resolveHead,三形状语义原样平移、测试原样平移；手写 refs/heads/main 的别扭,从此消失。四步流水线:loadIndex、writeTreeFromIndex、commitTree、updateRef。

零件柜这章进的东西。三个词:引用、符号引用、detached HEAD。一个新文件 src/refs.ts,七个函数；index.ts 交出 readHeadHash 后剩八个。三条命令:branch、checkout、commit。commit 这条是第一条端到端的 porcelain:底层命令的拼装成果,一次写成历史。新欠两笔:其一,detached 丢弃的提交最终命运(可达性这把尺子),第 8 章祖先与 merge-base 时收；其二,refs 目录里这份分支清单,第 10 章握手时原样变成引用发现的输出——两个仓库对话,先报的就是各自有哪些引用。另有一串从简口径:checkout 不做脏改动保护；commit 不查空清单；branch 不收起点参数；引用只有松散文件,没有 packed-refs。正文各处已就地声明,差异附录集中登记。

三道迁移题,先押答案再展开,卡住按提示回查。

1. 同事在 detached HEAD 里 commit 了一笔,切回 main 后喊「提交丢了」。按本章机制,提交丢了吗？真 git 里怎么救？mini-git 为什么救不了？

没丢。提交对象躺在对象库里,只要哈希还在(比如终端缓冲、reflog、聊天记录里),cat-file 与 log 都读得到。真 git 的救法是 git branch rescue <哈希>,给这笔提交补一个引用就回到了视野里。mini-git 的 branch 不收起点参数,只能建在当前 HEAD 上,所以救不了——除非手工写引用文件,回到第 5 章那种 echo 时代。这条差距登记在差异附录,补齐它只需给 cmdBranch 加一个可选的起点参数。回查「commit:四步流水线」与「detached HEAD:警告在怕什么」。

2. 反事实:假如 updateRef 每写一个引用,都顺手把对象库整体复制一份。哪些现象会变,哪些本章结论会塌？

变的:建分支从瞬时变成随历史规模线性变慢,对象库体积随分支数翻倍——「建分支 O(1)」的实物证据没了。不塌的:哈希一个都不变。内容寻址只认对象头加内容的字节,与「谁引用它、复制了几份」无关；两个分支指向同一提交,读到的还是同一串 40 位名字。塌掉的只是实现效率,不是名字与内容的对应关系。回查「分支是一个 41 字节的文件」。

3. 新仓库,add 过 4 个文件但一次都没 commit,HEAD 还指着未出生的 main。这时手工把 .git/HEAD 改成 ref: refs/heads/other(other 不存在),mini-git status 输出几段、各几行？

一段,四行「新文件」。HEAD 指向不存在的分支,resolveHead 走到 unborn 返回 null,HEAD 那张表摊成空；暂存区对空表比出四条已暂存的新文件。工作区与暂存区一致,未暂存段为空；工作区没有清单之外的文件,未跟踪段也为空。unborn 形状不报错,正是 init 之后、首笔提交之前那段时间的常态。回查三形状表与第 5 章「三态对比」。
