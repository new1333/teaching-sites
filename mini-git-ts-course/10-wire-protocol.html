一根管道上的对话:pkt-line 与引用发现 ​

克隆大仓库的人,都见过那面翻滚的进度墙:remote: Enumerating objects: 3871, done. 滚过去一行,百分比才开始慢慢爬。可 git 另有一句命令从不碰这堵墙——git ls-remote。对着一个几十万提交的远端敲下去,回车即答:每条分支的名字和哈希,几行清单立刻到手,不下载一个字节。「它那里有什么」这个问题,凭什么不用先把仓库搬下来？

更早的一步藏在克隆开头。那行 Enumerating 出现之前,两端其实先对了一次暗号:各自报一遍自己手上有哪些引用,报完才谈搬什么、怎么搬。这次对暗号有名字,也有精确到字节的格式;本章就把这轮对话拆开,在 mini-git 里重写一遍——服务端起一根 TCP 管道,客户端连上去,把对端的清单原样列出来。

零件是现成的。第 6 章把分支拆成了 refs/heads/ 下 41 字节的小文件,把 HEAD 拆成了符号引用。清单里的 40 位哈希指向一笔笔 commit 对象,第 2 章的 SHA-1 与内容寻址担保它们跨机器可验。第 6 章收束时还立过一笔账,原话是:「refs 目录里这份分支清单,第 10 章握手时原样变成引用发现的输出」。「原样」二字今天兑现——你会亲眼看到服务端编清单的循环体,就是第 6 章那两个老函数。

本章分三段推进。「知道远端有什么」为什么是一个独立的、便宜到不成比例的问题,先讲清这一层。然后拆 pkt-line——这根管道上的帧格式,四个字符的长度前缀如何在一根没有边界的字节流里圈出消息。拆完格式就落进 mini-git。src/pkt.ts 做编解码,src/serve.ts 做服务端与客户端,加 serve、ls-remote 两条命令,先红后绿。

一句不搬东西的远端命令 ​

先清算一条流传很广的直觉:远端操作必须下载完整仓库,才知道那边有什么。替它说句公道话:这个直觉有扎实的来源——你接触远端的场景几乎全是 clone 和 pull,每一次都真的在搬对象;HTTP 世界的常识也是「想知道文件有什么,先把它下载下来」。「远端=搬运」在日常经验里没有反例。不成立的地方恰好卡在信息量上:「有什么」需要的不是对象库,是引用清单;而清单小得可以忽略。算一笔账:一条分支一行,40 位哈希、一个空格、一个引用名、一个换行,前缀 4 字节——main 分支一行 61 字节,HEAD 行更短,50 字节。一个 1000 条分支的仓库,整张清单约 60 KB,不到一张截图;即使远端躺着几十万个松散对象,清单也只有这么点。清单行自己也不是对象:没有对象头,不用 zlib 压缩,不进对象库;它比 tree 对象的条目还朴素——tree 条目好歹带着文件模式,清单行只有哈希与名字。ls-remote 回车即答,不是网速快,是问题小。

「先报清单,再谈搬运」在真协议里是一个正式的阶段,本章第一个新词落定。**引用发现(reference discovery)——客户端连上服务端后,双方交换各自引用清单的第一步:一条引用一行,哈希加引用名;清单交换完,才知道后面要谈什么。**它的正本是协议文档 pack-protocol(真 git 传输协议的技术说明)。文档描述连接后的头一件事,原话拆四截。第一截:「When the client initially connects」——客户端一连上。第二截:「the server will immediately respond with」——服务端立刻回话,不等对方开口。第三截:「a listing of each reference it has」——一份它拥有的全部引用清单。第四截:「(all branches and tags)」——分支与标签都算。每条带什么,同一句的尾巴:「along with the object name that each reference currently points to」——引用此刻指向的对象名。括号里关于版本协商的半句先跳过,mini-git 按最朴素的形状实现,这条分岔就地登记。

清单的排序也有规定,同一节的原话拆两截。前半:「The stream MUST be sorted by name」——清单流必须按引用名排序。后半:「according to the C locale ordering」——排的是 C 语言环境的字节序。另有一条 MUST 用转述:HEAD 有效时必须排在第一行,HEAD 无效(比如还没生过提交的仓库)则一行都不许出现。mini-git 的服务端照单全收:排序复用第 6 章 listBranches 的字典序——纯 ASCII 分支名下,JavaScript 的排序与 C 字节序结果相同。

所以 ls-remote 在真 git 的命令版图里被归进底层命令一列:它只查询、不改动任何状态。清单到手就收工,对象一个不碰。这也是它快得反常的全部原因。

一根没有边界的管道 ​

清单要送到对面,得先回答一个传输层的问题:TCP 是一根字节管道,只保证字节按序到达,不保证「一条消息」整块到达。你在发送端一次写入三行清单,对端可能一次收到两行半,也可能一次收到全部外加下一行的一半——字节从哪里剪开,完全由网络心情决定。本章的测试里有一条就是干这个的:把一帧从中间剪成两片,分别喂给解码器。

要在一根没有边界的管道上认出消息,就得把边界写进字节本身。git 的答案就是本章第二个新词。**pkt-line——git 传输协议的帧格式:每帧开头四个字符写十六进制总长度,长度把前缀自己也算进去,载荷原样跟在后面。**帧格式的细则写在协议文档 protocol-common 里。pack-protocol 的对话,全部建立在这层格式上。定义原话拆三截。「A pkt-line is a variable length binary string.」——pkt-line 是一段变长的二进制串。「The first four bytes of the line, the pkt-len,」——这行的头四个字节,名叫 pkt-len。「indicates the total length of the line, in hexadecimal.」——它以十六进制指出整行的总长。长度把自己也算进去,原话再拆两截:「The pkt-len includes the 4 bytes」——长度里含着那 4 个字节。「used to contain the length's hexadecimal representation.」——正是前缀自己的十六进制表示。

文档给了一张示例表,四个金样,一字不改搬来:

线上字节载荷
0006a\na\n
0005aa
000bfoobar\nfoobar\n
0004空载荷

拿第一行人肉走一遍。载荷 a\n 是 2 字节,加上前缀 4 字节,总长 6,十六进制写作 0006。前缀四个字符 0、0、0、6,载荷是 a 和换行——整帧六个字符,每个恰好一字节。第三行同理:foobar 加换行是 7 字节,总长 11,十六进制 b,前缀写满四位就是 000b。注意两件事。第一,载荷里的换行计入长度——文档另有一条规则:非二进制行应该以换行收尾,收尾换行只要存在就计入总长;接收端有就剥掉、没有也不追究。第二,前缀是四个 ASCII 字符,不是二进制数:十六进制转储扫过去,四个可读字符一眼就能认出帧界,你马上会在验证节用到这一点。

再来算一条真实尺寸的。文档示例清单里有这样一行(哈希与引用名都是文档原文):

text
教学示意 · pack-protocol 文档示例清单里的一行
7217a7c7e582c46cec22a130adf4b9d7d950fba0 refs/heads/master

动笔算:40 位哈希 + 1 空格 + 17 字符引用名 + 1 换行 = 59 字节载荷,加前缀 4,总长 63,十六进制 3f。文档里这一行实际的前缀正是 003f。恭喜,你已经能手工给任意一行标出长度前缀与载荷边界了——拿纸算一遍再对照,这是本章验收的第一条。

「长度前缀多此一举,换行分行不就够了？」——第三条直觉,先给足面子。文本协议按行分帧确实常见,HTTP 头就这么干;引用行的载荷又恰好是文本,拿换行切看起来天衣无缝。它失效的场景在载荷本身:协议文档明说一帧可以装二进制数据,解析与格式化例程必须 8-bit 干净。下一部分的对象传输阶段,线上跑的就是二进制的包数据——里面任何位置都可能出现换行字节,按换行切帧会把一帧腰斩。长度前缀不管载荷是什么,四个字符圈出边界;顺带还有一个算得出来的好处:接收端读完四个字符就知道还要再读几个字节,一次到位,不用扫描。

「那协议消息总该是 JSON 这类自描述格式吧？」——第二条直觉,公道话更多。日常接口十有八九是 JSON,字段名即文档,抓包即调试,「协议=JSON」是再合理不过的默认。不成立的地方在于它把两层东西当成了一层:pkt-line 只是装帧,不是序列化。它不描述字段、不描述含义,只回答「这一帧到哪里为止」;「哈希 空格 引用名」这个含义是协议约定死的,靠两端都读过同一份文档来对齐。git 不用 JSON 的算术账也算得出来:清单行的格式是固定三段,字段名写进每一行纯属浪费;后面要装的二进制包数据放进 JSON 还得先转义加膨胀。一层便宜的帧,配一份人读的文档,就是全部。

最后一样零件是收尾记号。清单送完,得有个字说「报完了」,这个字是四个 0。文档原话拆三截:「A pkt-line with a length field of 0 ("0000"), called a flush-pkt,」——长度为 0000 的帧有个专名 flush-pkt。「is a special case」——它是特例。「and MUST be handled differently than an empty pkt-line ("0004").」——必须与空载荷帧 0004 区别对待。0000 不是「零字节的载荷」,是「这一节说完了」。文档还有一句转述:实现不应该发送 0004 空帧——要表达「空」,发 flush。尺寸也有上限:载荷至多 65516 字节,整帧至多 65520,超过就是违规,mini-git 在编码与解码两头都按这个数设卡。

零件齐了:一条「哈希 空格 引用名 换行」的清单行,套进 pktEncode 的壳,一行一帧,清单末尾补一个 flush。这就是引用发现流的全部。

pktEncode:四字符前缀 ​

ts
// src/pkt.ts · pktEncode
export function pktEncode(payload: string | Buffer): Buffer {
  const body = Buffer.isBuffer(payload) ? payload : Buffer.from(payload, 'utf8')
  if (body.length === 0) {
    throw new Error('pktEncode:空载荷的帧(0004)文档明说 SHOULD NOT 发——要发空节,发 flush')
  }
  if (body.length > MAX_PAYLOAD) {
    throw new Error(`pktEncode:载荷 ${body.length} 字节,超过上限 ${MAX_PAYLOAD}(整帧 65520)——拆成多帧发`)
  }
  const prefix = (body.length + 4).toString(16).padStart(4, '0') // 65520 = 0xfff0,恰好四位装得下
  return Buffer.concat([Buffer.from(prefix, 'ascii'), body])
}

主体三行:载荷定型为 Buffer(字符串按 utf-8 编,字节载荷原样通过——0x00 到 0xff 都不转义,8-bit 干净就是这么落地的);前缀 = 载荷长 + 4,转十六进制补足四位;拼接返回。两道卡对应文档的两句 SHOULD NOT 与 MUST NOT:空载荷拒发,超长拒发。Buffer 在第 3 章出场过,这次它干的还是老本行——按字节办事,不问字符。

pktDecode:能收半个帧 ​

ts
// src/pkt.ts · pktDecode
export function pktDecode(buf: Buffer): { frames: PktFrame[]; rest: Buffer } {
  const frames: PktFrame[] = []
  let i = 0
  while (i + 4 <= buf.length) {
    const hex = buf.toString('ascii', i, i + 4)
    if (!/^[0-9a-f]{4}$/i.test(hex)) {
      throw new Error(`pktDecode:第 ${frames.length + 1} 帧的前缀 '${hex}' 不是 4 位十六进制`)
    }
    const len = parseInt(hex, 16)
    if (len === 0) {
      frames.push({ kind: 'flush' })
      i += 4
      continue
    }
    if (len < 4) {
      throw new Error(`pktDecode:前缀 '${hex}' 短过 4,连它自己的长度都装不下——这不是一个帧`)
    }
    if (len > MAX_PAYLOAD + 4) {
      throw new Error(`pktDecode:前缀 '${hex}' 的整帧超过 ${MAX_PAYLOAD + 4},mini-git 不收这种帧`)
    }
    if (i + len > buf.length) {
      break // 整帧(前缀含在内共 len 字节)还没到齐,留给下一个分片
    }
    frames.push({ kind: 'data', payload: buf.subarray(i + 4, i + len) })
    i += len
  }
  return { frames, rest: buf.subarray(i) }
}

关键在最后一组判断与前缀自身那 4 字节的账:i + len > buf.length 说明这帧没到齐,此时停下,把从 i 开始的一切原样塞进 rest——包括已经读到的半个前缀。调用方的用法因此固定:收一片、解一片,没解完的 rest 与下一个网络分片拼上再解。TCP 从中间剪开消息这件事,就被这个返回形状消化掉了。编码严发、解码宽收:0004 空帧照解成空载荷,前缀按文档口径用小写编码、解码大小写都认;但坏输入不放过——非十六进制、短过 4、超 65520,各报各的错。

服务端:清单编成流,连上就送 ​

ts
// src/serve.ts · encodeRefAdvertisement
export function encodeRefAdvertisement(gitDir: string): Buffer {
  const lines: string[] = []
  const head = resolveHead(gitDir)
  if (head !== null) {
    lines.push(`${head} HEAD\n`) // 与分支行同款形状,只是名字叫 HEAD
  }
  for (const branch of listBranches(gitDir)) {
    lines.push(`${readRef(gitDir, `refs/heads/${branch}`)} refs/heads/${branch}\n`)
  }
  if (lines.length === 0) {
    return Buffer.concat([pktEncode(`${ZERO_ID} capabilities^{}\n`), FLUSH_PKT])
  }
  return Buffer.concat([...lines.map((line) => pktEncode(line)), FLUSH_PKT])
}

第 6 章那笔「原样」的账在这里结清:循环体就是 listBranches 配 readRef,清单内容一个字节没改,只是从「躺在 refs 目录里」变成「套上帧壳准备上线」。resolveHead 返回 null 时(unborn 仓库,分支没生过提交),HEAD 行不发,对齐「HEAD 无效则不许出现」的 MUST。连一条分支都没有的空仓库,按真协议的空清单口径发一条零号占位行:40 个 0 加名字 capabilities^{}。真协议这一行后面还挂着 NUL 字节加能力清单(谈版本、谈可选功能的协商位),mini-git 没有能力可谈,只留零号名字——这条分岔就地声明,差异附录集中登记。detached HEAD 也顺理成章:符号引用解开是裸哈希,resolveHead 照样返回它,HEAD 行照样第一行发出去。

ts
// src/serve.ts · startRefServer
export async function startRefServer(
  gitDir: string,
  opts: { host?: string; port?: number } = {},
): Promise<RefServer> {
  if (!existsSync(join(gitDir, 'objects'))) {
    throw new Error(`serve:'${gitDir}' 不是 mini-git 仓库(没找到 objects),无引用清单可送`)
  }
  const host = opts.host ?? '127.0.0.1'
  const sockets = new Set<Socket>()
  const server = createServer((socket) => {
    sockets.add(socket)
    socket.on('error', () => {}) // 一条连接的异常不拖垮整个服务
    socket.end(encodeRefAdvertisement(gitDir))
  })
  server.on('error', () => {}) // listen 失败由下面的 once 统一报
  await new Promise<void>((resolve, reject) => {
    server.once('error', reject)
    server.listen(opts.port ?? 0, host, () => resolve())
  })
  const { port } = server.address() as AddressInfo
  return {
    server,
    host,
    port,
    close: () =>
      new Promise<void>((resolve) => {
        for (const sock of sockets) sock.destroy()
        sockets.clear()
        server.close(() => resolve())
      }),
  }
}

node:net 的最小用法都在这了:createServer 给一条连接一个回调,socket.end 一次性完成「写入加收线」——每条连接先收到整段清单,再收到连接关闭。端口号传 0 是请操作系统随机分配一个空闲端口,测试全部走这条路,收尾 close 把监听句柄和活跃连接一并拆掉,不留泄漏。注意清单是每条连接现编现送:不缓存,对端引用变了,下一条连接拿到的就是新值。端口默认听 127.0.0.1——这是教学服务,只接待本机。

客户端:攒齐再解,见 flush 才认账 ​

ts
// src/serve.ts · discoverRefs(拼版:去缩进、省 try/catch 的主逻辑,终态含第 11 章加的半关闭一行)
socket.on('error', (err) => {
  socket.destroy()
  reject(new Error(`ls-remote:连不上 ${host}:${port}(${err.message})——对端起 mini-git serve 了吗?`))
})
socket.on('data', (chunk: Buffer) => chunks.push(chunk))
socket.on('close', () => {
  const { frames } = pktDecode(Buffer.concat(chunks))
  if (!frames.some((f) => f.kind === 'flush')) {
    throw new Error('ls-remote:流读到头也没等到 flush 收尾帧——对端发的不是 mini-git 的引用发现流')
  }
  resolve(parseRefLines(frames))
})

拼版说明:close 回调里还有一层 try/catch 把解码错误转成 reject,上面是主逻辑。收线(close)是天然的分界——字节到齐了,Buffer.concat 拼起来一次解码;没等到 flush 的流不认账,连不上的地址报可读的错而不是把 ECONNREFUSED 甩脸。parseRefLines 把每个数据帧剥掉行尾换行、拆成「哈希 + 空格 + 引用名」,哈希按大小写不敏感收(文档的 MUST),坏行当场报错不猜。零号占位行在 discoverRefs 的返回里如实出现,只在显示层滤掉。

ts
// src/cli.ts · cmdServe 与网络命令落点(拼版:三段在终态中不相邻)
async function cmdServe(cwd: string, args: string[]): Promise<string> {
  const usage = '用法:mini-git serve [端口];端口可省,默认 9419,只听 127.0.0.1'
  if (args.length > 1 || (args.length === 1 && !/^\d+$/.test(args[0]))) {
    throw new Error(usage)
  }
  const port = args.length === 1 ? Number(args[0]) : 9419
  if (port < 1 || port > 65535) {
    throw new Error(`${usage};端口是 1-65535 的整数`)
  }
  let gitDir: string
  if (existsSync(join(cwd, '.git', 'objects'))) {
    gitDir = join(cwd, '.git') // 普通仓库:骨架在 .git 壳里
  } else if (existsSync(join(cwd, 'objects')) && existsSync(join(cwd, 'HEAD'))) {
    gitDir = cwd // 裸仓库:目录本身就是仓库
  } else {
    throw new Error(`当前目录不是 mini-git 仓库(普通仓库要有 .git/objects,裸仓库要有 objects),先运行 mini-git init 或 mini-git init --bare`)
  }
  const started = await startSyncServer(gitDir, { port })
  return `mini-git serve 已上线:${started.host}:${started.port}(每条连接先送引用清单,再听来意;Ctrl+C 停止)`
}

// src/cli.ts · cmdLsRemote
async function cmdLsRemote(_cwd: string, args: string[]): Promise<string> {
  const usage = '用法:mini-git ls-remote <主机:端口>;目标是 mini-git serve 的地址,恰好一个'
  if (args.length !== 1) {
    throw new Error(usage)
  }
  const refs = await discoverRefs(args[0])
  return refs
    .filter((r) => !(r.hash === '0000000000000000000000000000000000000000' && r.name === 'capabilities^{}'))
    .map((r) => `${r.hash}\t${r.name}`)
    .join('\n')
}

// src/cli.ts · runNetCli
export async function runNetCli(argv: string[], cwd: string = process.cwd()): Promise<string> {
  const [cmd, ...args] = argv
  if (cmd === 'serve') {
    return cmdServe(cwd, args)
  }
  if (cmd === 'ls-remote') {
    return cmdLsRemote(cwd, args)
  }
  if (cmd === 'fetch') {
    return cmdFetch(cwd, args)
  }
  if (cmd === 'push') {
    return cmdPush(cwd, args)
  }
  if (cmd === 'clone') {
    return cmdClone(cwd, args)
  }
  return runCli(argv, cwd)
}

上面代码块是第 11 章扩容后的终态。本章动手时,cmdServe 只有 startRefServer(requireGitDir(cwd), { port }) 一行,runNetCli 也只挂 serve 与 ls-remote 两条。下一章接 fetch/push/clone 时,serve 换成 startSyncServer——送完清单改听来意,目录探测多了裸仓库一路,runNetCli 长到五条。本章测试针对的行为没变,旧测试原样全绿。

端口默认 9419,挨着真 git daemon 的 9418 但少 1——故意的。mini-git 的 TCP 上跑的不是真 git 协议:不冒用它的端口,也不冒充能与真 git 服务互通。ls-remote 的输出形状对齐真 git:哈希、Tab、引用名,一行一条。ls-remote 不要求当前目录是仓库——它一个对象都不碰,连本地的 index 文件、工作区、暂存区都不看,「远端有什么」的全部信息就是那张清单。

收束:两个仓库如何开口说第一句话 ​

ls-remote 之所以回车即答,是因为它问的问题小到不成比例:一份引用清单,一条分支一行,一行六十来字节。两个仓库要谈搬运之前,先各自把这张清单递过去,git 管这一步叫引用发现;清单在网上走的是 pkt-line。四个字符的十六进制长度圈出帧界,长度把前缀自己算进去,载荷原样跟在后面,0000 一到,这一节就算说完。克隆开头那行 Enumerating 之前,真 git 的两端交换的就是这一层。你的 mini-git 今天在自己的 TCP 上把它重写了一遍,连十六进制转储里那四个字符的前缀都亲手认过。

本章最特别的事实是:对象库里一个新对象都没有。快照模型原封未动,本章只搬清单、不造对象;三态对比、merge 提交那些家当,一行没动。进门的东西倒也不多。两个词:pkt-line、引用发现。两个新文件:src/pkt.ts 装着 pktEncode 与 pktDecode。src/serve.ts 装着 encodeRefAdvertisement、startRefServer、discoverRefs。两条命令 serve 与 ls-remote,外加一个异步入口 runNetCli。

差异照例就地声明、差异附录集中登记。承载层:mini-git 用自己的裸 TCP,真协议跑在 SSH/HTTP 上(git daemon 的 git:// 占 9418,mini-git 用 9419 且互不相认)。能力协商:真协议的引用行可带 NUL 加能力清单,空清单行也带;mini-git 一概不发。广告范围:真 git 分支与标签都列,mini-git 只有 refs/heads。会话长度:真协议 flush 之后还有 want/have 协商与 packfile 传输,mini-git 送完清单即收线——对象怎么搬、搬哪些,packfile 为什么不做,下一章正面回答。

第 6 章的旧账结清:「原样」兑现到循环体,listBranches 加 readRef,清单从 refs 目录走上网络,一个字节没改。新的一笔当场立据。你在验证节亲眼看着 ls-remote 打出那几行——此刻它只是一张被看了一眼就合上的清单。下一章它要当谈判的底牌:fetch 拿它算「我缺哪些对象」,push 拿它算「对方会不会拒我」,空仓库那张零号占位行也会在 clone 空仓库时再见面。清单还是这张清单,一个字节不用重算。

1. 下一章 fetch 的第一句话是 `want 37aba2a3c548f65b6c8d36bc47039e879ddc0687\n`(客户端向服务端点名要的对象)。它的 pkt-line 前缀四位是什么?为什么与 HEAD 行恰好同前缀?

"want " 五字符 + 40 位哈希 + 换行 = 46 字节载荷,加前缀 4,总长 50,十六进制 0032。HEAD 行是 40+1+4+1 也是 46 字节载荷——前缀只看总长,不看内容,两行同长自然同前缀。顺带注意:want 行也是「关键词 + 哈希」的定长文本行,与引用发现行同一门手艺。回查金样表与「人肉走一遍」的跟算。

2. 一帧 `000bfoobar\n` 被网络剪成 `000bfo` 和 `obar\n` 两片先后到达。第一片单独喂给 pktDecode,得到什么?两片拼上再喂呢?

第一片 6 字节:前缀读出 000b,整帧应有 11 字节,到齐的只有 6 字节。所以 0 帧,rest 是整个 000bfo(6 字节,含已读的半个前缀)——不是空 rest:没到齐的帧连同前缀一起留下,这正是 rest 的用途。两片拼上再喂:一帧 data 载荷 foobar\n,rest 为空。回查 pktDecode 的 break 分支与分片测试。

3. serve 还开着,你用第 6 章的老手艺手工 echo 一个新分支文件进 refs/heads/(41 字节),不重启服务再 ls-remote 一次。新分支会在清单里吗?凭的是哪一行代码?

在。每条连接都现调 encodeRefAdvertisement,清单不缓存——startRefServer 的连接回调里那句 socket.end(encodeRefAdvertisement(gitDir)) 就是凭据。注意清单内容不会被内核缓存也不会被 mini-git 记住:引用发现拿到的是「连接时刻」的清单,这对下一章的谈判是重要前提——两端各拿各的当下事实来对暗号。回查「服务端:清单编成流」一节。
