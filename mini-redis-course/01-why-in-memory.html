磁盘太慢了：Redis 到底解决什么问题 ​

同一台机器、同一张网卡：用 MySQL 按主键查一行，慢查询日志里躺着的是几毫秒；换 Redis 取同一个键，只要几十微秒。CPU 一样、内存条一样、网线一样，却差出两个数量级。硬件没变，差在数据住在哪、走什么路：MySQL 的家底放在磁盘上，Redis 把全部数据搬进了内存。这一章就把这笔账算清楚——算完你会发现，「快」只是表象，真正要弄懂的是：磁盘到底慢到什么程度、为什么所有存储系统都在拿内存当救兵、Redis 给自己选了个什么位置。

一次读的旅程：数量级的账 ​

先把标尺立起来。下面这组数字出自 Jeff Dean 那份著名的《Latency Numbers Every Programmer Should Know》。权威清单登记的是 Jonas Boner 收录的 gist 转录版，行业引用了十几年：

旅程中的一站数量级换算成 ns
内存随机访问一次~100ns100
SSD 随机读一页~150µs150,000
机械盘寻道一次~10ms10,000,000
同机房网络一个来回~500µs500,000

数量级标尺不是精确值：新的 NVMe SSD 更快、机器各有差异，但介质之间的鸿沟至今没有消失。换算关系先记住：1ms = 1,000µs = 1,000,000ns。于是机械盘一次寻道是内存一次访问的 10,000,000 ÷ 100 = 100,000 倍——介质之间隔着三到五个数量级，这就是整本书的地基。

现在把「查一行数据」拆成旅程，两辆车对比着开。共同项先剔掉：同机房网络一个来回 ~500µs，两边都要付，它不制造差距。

MySQL 按主键查一行，服务端内部要经过这几站：

  • 解析 SQL、生成执行计划——CPU 活，粗估百微秒量级；
  • 沿 B+ 树往下走 3~4 层，每层访问一页（B+ 树：MySQL 索引长成的多层目录；页：磁盘按固定大小读写的数据块）；
  • 页是热是冷决定命运：热页泡在内存里的缓冲池（InnoDB 专门划出来暂存磁盘页的那块内存），一次 ~100ns 级；冷页要落盘做一次随机读，机械盘 ~10ms、SSD ~150µs；
  • 锁与事务簿记、把行数据拷出去——又是几十微秒。

Redis 的 GET 一个键，服务端内部只剩三小步：

  • 解析一行命令——微秒级；
  • 哈希表一次定位（哈希表：按 key 直接算出存储位置的结构，这本书会亲手写一个）、一次字符串比较——0.1~1µs；
  • 值本来就是内存里的对象，取引用、序列化、回包——微秒级。

账面结论：两边都是热数据时，差距只有几倍，差在解析与簿记这些路径开销上；一旦 MySQL 要碰一次冷页，差距立刻被那 ~10ms 的寻道拉开到百倍以上。数量级的差距来自介质，倍数的差距来自路径。

缓存：所有存储系统的通用解法 ​

上面那张表里藏着一个事实：数据库工程师比谁都清楚磁盘慢。所以 MySQL 根本不是「每次都读盘」——InnoDB 一启动就划一大块内存当缓冲池，把常用的页泡在内存里，命中就不碰磁盘。你看，数据库自己就在做缓存（cache）——把慢介质取来的数据在快介质上暂存一份，下次直接拿快的。用空间换时间，这是所有存储系统面对同一个物理事实给出的同一个答案。

缓冲池有两个天生的软肋，正好引出后面的主角：

  • 数据比内存大时，命中注定不完全，冷页的 ~10ms 罚金躲不掉；
  • 数据库的通用路径（SQL 解析、事务簿记）一分都省不掉。

于是工程上干脆把缓存从数据库里拿出来、放到旁边，做成独立一层。最常见的姿势叫旁路缓存模式（cache-aside）：读先查缓存、没有再查库并回填；写先写库、再删缓存。缓存站在数据库旁边，不在中间挡路。好比常用的工具放手边桌面上、不常用的塞仓库——手边的拿起来快，但得多记一份「放哪了」。

先看读路径：

text
读路径：未命中一次，之后全走内存
客户端              Redis（缓存）           MySQL（库）
  │ GET user:1        │                      │
  │──────────────────>│ 哈希表里没有          │
  │<──────────────────│ 返回 nil             │
  │ SELECT ...        │                      │
  │─────────────────────────────────────────>│ 返回那一行
  │ SET user:1（回填，带 TTL——time to live，键的存活期限，到点作废）│
  │──────────────────>│ 从此命中              │
  │ GET user:1（第二次）→ 直接返回，不再碰库  │

读路径的账：第一次付一次查库的钱，之后每次只付内存访问加网络往返。用标尺算：缓存命中时服务端内部是微秒级，省下的是可能高达 ~10ms 的冷页罚金——这就是缓存的全部经济逻辑。

写路径的赛跑：缓存不只是「把读变快」 ​

介绍缓存的文章常到「读变快」就收笔了，你大概也这么以为：缓存嘛，就是个读加速器。但缓存系统一半的复杂度在写侧：数据从此有两份（库里一份、缓存里一份），任何写都要回答「先动谁」。推荐顺序是先写库、再删缓存，下次读自然回填新值。可两个动作不是原子的，中间有不一致窗口：

text
写路径的赛跑：推荐顺序也关不上的窗口
t1  A（写）：UPDATE user:1 —— 开始执行，尚未提交
t2  B（读）：GET user:1 —— 缓存里没有（miss）
t3  B（读）：SELECT 读库 —— 读到的还是旧值
t4  A（写）：事务提交，库里已是新值
t5  A（写）：DEL user:1 —— 删掉缓存
t6  B（读）：SET user:1 旧值 —— 回填
结果：旧值躺回缓存，之后每个读都命中它——直到 TTL 到期或下一次写

时间线上，B 在 t3 读走了旧值、在 t6 才回填，恰好跨过了 A 在 t5 的删除——脏数据就这么住进了缓存。换成「先删缓存再写库」更糟：从删除到提交之间的所有 miss 都会读走旧值再回填，窗口更大。没有零窗口的免费方案，工程上的兜底是给每条缓存配 TTL：就算脏了，也最多脏到过期为止。这本书讲到「过期删除」时，你会亲手把这个兜底写出来。

Redis 给自己选的位置 ​

账算完了，该回答书名里的问题：Redis 到底是什么。答案有三层。

第一层：它是一个键值存储（key-value store）——只会两件事的数据库：按一个键存一个值、按键取回，像一个大号 JS 对象，但活在另一个进程里。没有表、没有 JOIN、没有 SQL。

第二层：它是一个内存数据库（in-memory database）——数据平时全部住在内存里。这是它全部速度优势的来源，也是全部麻烦的来源：内存断电就忘，按 GB 计的价格比磁盘贵上一到两个数量级。所以 Redis 配了两套持久化（把写命令记账成日志、定期拍全量快照，第四部分亲手写它们），但持久化是补丁，不是主业。

第三层，也是 Redis 最准的自述：数据结构服务器（data structure server），官方介绍长期就这么描述它。只存字符串的话，内存数据库并不比「MySQL 加全量缓冲池」强多少；Redis 的真本事是把列表、哈希、集合、有序集合这些结构连同操作一起搬进内存——你不再把一百万行拉回应用侧再排序，而是让排序、截取、计数发生在数据身边。一句话：让计算靠近数据。

误区一：「Redis 比 MySQL 快，是因为它更先进」 ​

这个直觉很有市场，也确实事出有因：Redis 发布更晚（2009 年）、C 语言写成、单线程没有锁竞争、专做一件事——听着就像新一代产品对老古董的降维打击。

但旅程表已经把答案算好了。把 MySQL 的热数据全泡进缓冲池（100% 命中），一次主键点查也是百微秒量级，和 Redis 只差几倍——差的是 SQL 解析与事务簿记这类路径开销，不是数量级；数量级的差距要等冷页落盘才出现。所以 Redis 的快 = 介质（全内存）+ 路径（O(1) 定位、无解析），快是选型的结果，不是先进性的证明。

反过来看更清楚。Redis 不是没试过「数据放磁盘」：早期版本有个 Virtual Memory 特性，内存不够时把冷值换出到磁盘，2.4 版标记废弃、2.6 版整段移除。原因写在物理里：换出去的值一次访问就是一次随机读，而 Redis 是单线程的，一个键能卡住全部请求；同时它也不再是「全内存、微秒级」的那个东西——两头的优势各丢一半。同理，拿 Redis 当持久主库会在容量与断电上翻车：数据量逼着你买天价内存，持久化与恢复还要打折。它的正业是缓存、计数器、排行榜、消息队列这类「热数据 + 高频访问」的位置。

顺带记一个词：缓存同一时刻大面积失效、请求全部砸向数据库的现象叫缓存雪崩——Redis 重启缓存清空就是最典型的触发。这也是持久化对缓存层同样重要的原因：重启后快速回血，别让库挨那一刀。

演练：亲手把账算一遍 ​

拿纸笔，四步：

text
纸笔演算：一次冷读的代价
1. 换算：1ms = 1,000µs = 1,000,000ns
2. 机械盘寻道 ÷ 内存访问 = 10,000,000 ÷ 100 = 100,000（十万倍）
3. SSD 随机读 ÷ 内存访问 = 150,000 ÷ 100 = 1,500（约三个数量级）
4. 吞吐推论：单线程串行、每次读卡一次寻道 → 1s ÷ 10ms = 每秒 100 次
   同一个线程只做内存访问 → 1s ÷ 100ns = 每秒 10,000,000 次

第 4 步就是「把热数据放进内存」的吞吐含义。真实系统还要付网络栈与系统调用的钱，但量级摆在那里：每秒百次与每秒千万次之间，隔着你用户能不能忍。

验证：先猜，再跑 ​

现在轮到你动手。本机装了 Redis 的话（没装也不亏，上面的纸笔演算不挑环境）：

  1. 先猜：redis-cli --latency 测的是客户端到服务器的往返延迟。你猜 avg 会落在哪个数量级——10ms、1ms，还是 0.1ms？把猜测写下来再跑。
  2. 跑：执行 redis-cli --latency，应看到一行持续刷新、含 min / max / avg 三个数（单位 ms）与样本数的统计，Ctrl+C 结束。
  3. 对照：本机回环通常落在 0.1ms 上下的数量级（机器不同会浮动），几乎一定远小于 10ms 的寻道。若你的 Redis 在远端，avg 会涨到毫秒级——那正是旅程表里共同项「同机房往返 ~500µs」的样子。

猜对了，说明你已经开始用数量级思考；猜错了更好，你刚刚亲手校准了一次直觉。

收束：快从哪里来，代价在哪里 ​

回到开头的现象：同一台机器，MySQL 几毫秒、Redis 几十微秒。现在你能亲口拆解它了——差距的大头来自介质（冷页落盘的三到五个数量级），其余来自路径（SQL 解析、B+ 树逐层、事务簿记，对上 O(1) 哈希定位），网络是两边都付的共同项。你也看清了：缓存是所有存储系统面对慢磁盘的通用解法；cache-aside 的写路径藏着一段关不上的赛跑；Redis 这个内存数据库兼数据结构服务器，快是选型的结果，代价是容量与断电——这两笔代价，正好是这本书后半程要一一拆解的题。

自查三问（先自己答，再展开对）：

  1. 有人给你一个「数据全放 SSD」的数据库：单键读取会落在哪个数量级？它相对 Redis 和相对机械盘 MySQL，各丢掉了什么？
  2. 换一种交错：B 在 t3 读走旧值后动作变慢，回填（SET 旧值）落在 t5 的 DEL 之前——这一局缓存最终是干净的还是脏的？还需不需要 TTL 兜底这一回？
  3. 「MySQL 缓冲池 100% 命中时，Redis 只快几倍」——那 Redis 依然稳赢的三样东西是什么？
第 1 问答案

单键读取落在百微秒量级（SSD 一次随机读 ~150µs 起步）。比 Redis 慢两三个数量级；比碰机械盘的 MySQL 快约两个数量级。丢掉的是内存的微秒级延迟，又没换来磁盘的廉价海量容量——两头不讨好，这正是 Redis 的 Virtual Memory 被移除的原因。锚点：「一次读的旅程」的标尺表、「误区一」一节。

第 2 问答案

干净。回填进来的旧值随后就被 t5 的 DEL 删掉了，缓存落空，下一个读 miss 会去库（此时已是新值）取新回填。但这只是运气好的一种交错——B 的回填稍微再慢半拍就落回原时间线的脏局，所以 TTL 兜底不能因为这一局干净就省掉。锚点：「写路径的赛跑」时间线。

第 3 问答案

一是数据保证全在内存，不靠缓冲池的命中率吃饭；二是路径短，没有 SQL 解析与事务簿记；三是计算靠近数据，列表、有序集合这些结构级操作在服务端完成。锚点：「Redis 给自己选的位置」。
