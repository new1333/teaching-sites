一台是不够的：复制、哨兵与集群 ​

先接第 9 章末尾留的尾巴：照片与账本救得了断电，救不了「一台机器整个没了」——机房掉电、主机宕机，盘上的 dump.rdb 与 appendonly.aof 一起陪葬。这一章把这台机器之外的世界讲清楚：数据怎么搬到第二台机器（主从复制），谁在机器挂掉时自动接管（哨兵），数据大到一台装不下时怎么切给一群机器（集群）。先立一块牌子：本章是视野章，三个机制都讲原理、不进 mini 实现，能力对账在章末交清。前九章攒下的零件全程用得上——第 9 章末尾那句承诺现在兑现：主从之间第一次的全量同步（把全部数据完整搬一遍），发的正是一张 RDB。

凌晨三点：单机的三道天花板 ​

先看一个运维之夜的剧本。这样的夜晚，各家公司的故障复盘里反复上演：凌晨 3 点 17 分，缓存主库所在的主机宕机，进程没了、端口不通，所有写请求开始报错——登录态写不进、计数器停摆。更糟的在后面：这台缓存一空，业务的缓存命中率归零，原本被 Redis 挡在前面的查询全部砸向 MySQL，几分钟后数据库 CPU 打红，告警电话把值班工程师从床上叫起来。他赶到机器前重启实例、等 AOF 重放完，前后十几分钟。写停摆加读雪崩的这十几分钟，就是单机的天花板塌下来的声音。

复盘那一夜，单机其实有三道天花板，一道比一道高：

  • 读吞吐：一台机器的 CPU 与网卡是有数的，读流量涨十倍，一台再快也接不住；
  • 可用性：进程、主机、机房，任何一层挂了都全场停摆，恢复速度等于人跑过来的速度；
  • 容量：内存比磁盘贵一到两个数量级（第 1 章算过这笔账），一台机器内存装得下的数据就那么多。

Redis 给三道天花板配了三个解法，本章一个一个来：主从复制（把数据搬去第二台机器）、哨兵（机器挂了自动换班）、集群（把数据切给一群机器分摊）。

原理：先搬数据，再派人看着，最后分家 ​

主从复制：一份命令流的两种用法 ​

主从复制（replication）——一台 Redis 作为主库（master）接受写入，另外几台作为从库（replica）连上它，把自己变成主库的实时副本。锚点还是圣经里那句：师父带徒弟，入门先抄一遍全部作业（全量），之后师父每写一页、徒弟同步一页（增量）。它一次办成两件事：数据有了第二份（主机没了数据还在），读可以分给从库（读扩容）。

从库第一次连上主库，要先做全量同步（full synchronization）——把主库当时的全部数据搬过来。复制文档把这次搬运拆成三步：主库启动一个后台保存进程产出 RDB 文件，同一时刻开始缓冲所有新到的写命令；后台保存完成，主库把这份 RDB 传给从库，从库存到盘上、装进内存；最后主库把缓冲住的命令补发给从库。三阶段时序图如下：

对照第 9 章，这台机器你全认识。后台保存就是 BGSAVE：fork 出子进程，靠写时复制拍出冻结的那一瞬。第 9 章末尾那句「fork 那台『拍照不停写』的机器下一章再开一次」，在这里兑现：全量同步发的就是一张 RDB，fork 与 COW 的原理一个字不用改。拍照那几秒主库照常接客；照片里没有的新写命令全攒在增量缓冲里，照片送到后一并补上。所以从库的最终状态等于照片加补发，缺一不可。若几台从库同时上门要全量，主库只拍一张照片分着发（文档口径）——fork 的账不随从库数翻倍。真货还有个省磁盘的做法：2.8.18 起支持无盘复制，子进程不落盘、把 RDB 直接从网络发出去，视野提一句。

全量同步只是第一次。之后的日常，靠主库把每条改变数据集的命令转发给从库——文档说主库靠「发送一串命令流」让从库跟上，这串流覆盖三类变化：客户端写入、键过期或淘汰、其他一切改动主库数据集的动作。第二类你特别熟：第 8 章 dropKey 补记的那条 DEL，账本的另一半读者正是从库——主库发给 AOF 与发给从库的是同一份记账，过期、淘汰这类「服务器自发的删除」在两边都合成 DEL。顺带一提，从库自己不做删除决策：文档明说从库不主动过期键，等主库的 DEL 到了才删；读请求则用自己的逻辑时钟挡住已过期、死讯未到的键——第 6 章惰性删除的「读时判断」，到从库上是只挡不删的版本。

命令流是异步的。主库执行完一条写命令，先回客户端 OK，再把命令发去从库，不等确认。这笔账先记在这里，收束处要算：它意味着日后换主的那个瞬间，可能有几条已经回过 OK 的写还躺在路上。

从库怎么知道自己没掉队？主库给复制流的每个字节编号：offset，每产出一字节加一，哪怕没有从库连着也照加。再配一个 replication ID 标记「这是哪一段历史」。文档的说法：一对 (replication ID, offset) 唯一标识主库数据的一个版本；offset 相当于这段历史里的逻辑时刻。从库断线重连时用 PSYNC 报上自己收到的 (ID, offset)：主库一看要的这段还在，就只补缺口——这就是增量复制（partial resynchronization）；缺口没了，就再拍一张 RDB 从头来。留住「这段历史」的，是主库内存里的一个环形缓冲：复制积压缓冲（replication backlog）——命令流不断写进圈里，最老的不断被挤出去。补发的账怎么算，演练槽推演。

误区一：「加了从库，不就是高可用了吗」 ​

这个直觉很有市场，逻辑看上去也顺：数据有三份了，挂一台还有两份，系统当然高可用。对了一半——数据确实冗余了，但数据冗余不等于自动接管。拆开看：

第一，从库默认是只读的。2.6 起 replica-read-only 默认开启，写命令打到从库上直接回错误——业务把写流量切过去，只会收获一片报错。

第二，没有任何进程有「提拔」的权力。主从复制只搬数据，不做决定：主库挂了，从库们干等着，等的就是有人来办「你，从今天起是主库」这道手续。凌晨三点那十几分钟，正是人肉办手续的时间——赶到机房、确认主库真挂了、挑一台从库、改配置、通知客户端改地址。

所以准确的话术是：主从复制给高可用备好了料（第二份数据、只等提拔的从库），但自动故障转移（failover——主库挂了自动把某个从库提成新主、大家改认新主人）是另一层东西的活。补上这一层的，是哨兵。

哨兵：三个旁观的看门人 ​

哨兵（Sentinel）——几个独立于 Redis 之外的看门进程，做三件事：盯主库与从库的心跳；主库挂了就主持故障转移；给客户端当问路台——「现在的主库在哪台」。用 redis-sentinel 可执行文件或 redis-server --sentinel 启动，默认监听 26379 端口。

为什么至少三个、还要放不同的机器上？文档给过一个两台的死局：主库 M1 与哨兵 S1 同机，另一台是从库 R1 加哨兵 S2。M1 那台机器一挂，S1 陪葬——只剩 S2 一个哨兵，凑不齐多数派，故障转移永远无法授权，系统就此僵死。文档的原话很干脆：永远至少部署三个哨兵，放在三个不同的盒子（box，指会独立故障的机器或虚机）里。

判定主库挂掉分两级。单个哨兵在 down-after-milliseconds 内没等到对 PING 的有效回复，先标 SDOWN（subjectively down，主观下线——「我一个人觉得它挂了」）；这不算数，网络抖一下也会误判。凑够 quorum 个哨兵都报告 SDOWN，才升级 ODOWN。quorum 是哨兵配置里写定的「至少几台同意」（objectively down，客观下线）——文档强调这靠哨兵间相互询问达成，不是什么强共识算法。这里有一对容易混的词，值得钉牢：quorum 管「认定」，majority 管「授权」。文档的例子：五台哨兵、quorum 设 2——两台同意，就足以把主库标成 ODOWN、触发流程；但真正动手要先当选 leader、拿到多数（至少三台）的投票。这道双重闸门防的是脑裂（集群裂成两半、各自都以为自己是正统）：少数派那侧永远凑不齐多数，永远无法单方面换主。

故障转移的流程，文档写得像一份操作手册。达到 ODOWN 后，哨兵们先竞选 leader，拿到多数授权的那个来主持；它从从库里挑一个提拔——先剔除断线太久的，再按 replica-priority 小者优先（运维手工设的优先级）；同优先级比谁的 offset 大（收到的数据更新）；再比 run ID（每个实例启动时领到的随机唯一编号）图个确定性。然后对选中者下 REPLICAOF NO ONE（「你自由了，你是主库了」），其余从库改认新主，客户端向哨兵要新地址。回到凌晨三点：down-after 设 5 秒的话，从主库僵死到新主上线是几十秒的事——值班工程师翻个身继续睡，命中率先回血。

诚实账也收在这里。文档反复声明：因为复制是异步的，哨兵体系不保证故障发生时已确认的写都还在——提拔上来的从库，可能正缺最后那几条。缓解手段有（min-replicas-to-write：主库发现没有足够从库跟上就拒写，视野一句），根除没有——这是异步复制的天性，换同步要付延迟的代价。

集群：16384 个抽屉 ​

第三道天花板是容量：一台机器的内存装不下整库。思路直觉又古老——分片（sharding，把数据切开分给多台机器），但怎么切是门学问，这里埋着本章第二个误区。

「分片嘛，hash(key) mod 节点数呗」——经典哈希取模，很多系统就这么做，直觉无可指摘。但算一笔扩容的账它就露馅：模的基数是节点数 N，加一台机器 N 变了，几乎每个键除以新的 N 落点都变——扩容一台，全量数据搬家。演算见演练槽，先把 Redis 的做法讲完。

Redis Cluster 不用按节点数取模，用哈希槽（hash slot）：把整个键空间切成固定的 16384 个槽，键属于哪个槽永远不变——CRC16(key) mod 16384。CRC16 是一种按字节算的校验码，这里拿来当哈希函数用；变的是「槽归哪个节点管」这张对照表。文档的例子：三节点集群，节点 A 管槽 0 到 5500，B 管 5501 到 11000，C 管 11001 到 16383。要加一台新节点 D？从 A、B、C 各匀一些槽给它；要下掉 A？把 A 的槽搬去 B 和 C。文档强调搬槽不需要停任何操作——取模的基数永远不变，变的是槽与节点的对照表，扩容只搬被匀出去的槽里的键，不动全量。

槽还给多键操作立了规矩：多键命令、事务、Lua 脚本，都只能在同一个槽内做。为此 Redis 给了 hash tag：键名里花括号 {...} 中的内容才算哈希。文档的例子：user:{123}:profile 与 user:{123}:account 共享同一个 tag，永远落在同一个槽，可以一起进多键命令。

为什么偏偏是 16384？antirez 本人在 Redis 仓库 issue #2576 的公开回答给了两条理由，都是账。其一，节点间的心跳包要带上「我管哪些槽」的完整配置，用的是一张原始位图——16384 个槽正好 2KB，换成 65536 个槽就是 8KB，心跳包太贵；其二，集群的设计上限就是一千个主节点上下，16384 个槽在这个规模下足够分。

集群把前两件解法也带上了：每个主节点配从节点做复制，主节点挂了它的从节点顶上——故障转移内置，不再需要单独的哨兵层；多数主节点不可达时集群整体停写，又是多数派那道闸。文档的建议是最小三主，生产推荐三主三从共六个节点。异步复制照旧，丢最后几条确认写的窗口也照旧——解法在升级，诚实账一条没少。

本章边界：视野章，一件也不进 mini ​

把开头的牌子再立一次：复制、哨兵、集群，本章一件都不进 mini 实现。原因不是偷懒：这三个机制每一件都是多进程协同——网络分区、多数派投票、配置传播，单是「两台机器对同一事实达成一致」就够写一本书；本书的主线是「一台机器内部怎么做到快、省内存、不丢数据」，到第 9 章已经走完。多机的世界，这一章交地图，不交砖头。

但要说清楚你已经握着什么。全量同步的核心是 RDB——你写过 dump 与 load，fork 与 COW 你画得出页表图；增量与日常同步是命令流——你写过 AOF 的记账，dropKey 补 DEL 的另一半读者就是从库；从库追平数据靠重放——第 8 章的 restore 一行不改就能用；哨兵的心跳是 PING——第 2 章你写的第一条命令。零件你全有，缺的只是把它们摆上多台机器的协议与胶水。终章对账会回到这一条：与真 Redis 相比，mini 缺的不是单机内核，是多机的那一层。

演练：三张纸，推演三遍 ​

拿纸笔，三步。

一、全量同步时序推演。拿上面的时序图代入具体数字：主库 10 万个键，BGSAVE 拍照 2 秒；这 2 秒里主库收到三条写命令——SET x 1、DEL y、ZADD board 5 alice。逐条推：这三条进照片了吗？没有，fork 那一瞬数据已冻结，照片里 x 还是旧值、y 还活着。它们去了哪？增量缓冲。从库什么时候拿到？RDB 传完后的补发流里。所以从库的最终状态，是「10 万键、2 秒前的样子」再叠加这三条命令。再推一步：如果主库只发照片、不补发缓冲，从库会缺什么？那 2 秒里的全部写入——x 是旧值、y 还在。增量缓冲不是可有可无的礼貌，是照片定格的那一瞬与现在之间的桥。

断线 10 秒：主库每秒约 1KB 写命令 → offset 涨到 11,000
重连：从库 PSYNC 报 (同 ID, 1,000) → 缺口 [1,000, 11,000)，共约 10KB
backlog 环形缓冲 1MB，圈得住最近 1MB → 缺口全在圈内
→ 增量复制：只补发这 10KB，照片不用重拍

断线 30 分钟：主库写了约 2GB → offset ≈ 2,147,485,000
backlog 还是那只 1MB 的圈，只圈最近 1MB（2,147,485,000 − 1,048,576 ≈ 从 2,146,436,000 起）
从库要的 1,000 早已冲出圈外 → 缺口不在圈内
→ 全量同步重来：再拍一张 RDB，再传一遍

跟着算一遍，就能回答那个运维问题「从库闪断要不要紧」：断得短，缺口在圈内，补几 KB 命令就好；断得久，RDB 重拍，fork 的毫秒停顿与全量传输再来一次。backlog 越大越经得起断，代价是主库常驻内存——又一笔空间换时间的账。

三、16384 槽取模演算：

text
取模演算：四个键，CRC16 值分别为 3、8、14、23
按节点数取模（N=3）：3%3=0  8%3=2  14%3=2  23%3=2 → 节点 0、2、2、2
加一台后（N=4）：    3%4=3  8%4=0  14%4=2  23%4=3 → 节点 3、0、2、3
四个键三个换了主人——加一台机器，几乎全体搬家

按固定槽（mod 16384）：槽号就是 3、8、14、23，永远不变
A 管 0-5500、B 管 5501-11000、C 管 11001-16383 → 四键全归 A
新节点 D 接走 B 的 5501-6000 这段槽：这四个键一个不用动
搬家的是「被搬的槽」里的键——扩容只动搬过去的抽屉

这张表算完，「集群按 key 取模」这个直觉错在哪就有数了：不是错在不该取模，是错在模错了对象——模的是固定的 16384，不是节点数。

验证：先猜，再跑 ​

本机装了真 Redis 的话（没装也不亏，上面三张纸不挑环境）：

  1. 先猜：CLUSTER KEYSLOT 算键的槽号，单机实例也能算。你猜 "foo" 的槽号是多少？写下猜测再跑 redis-cli cluster keyslot foo——文档教程里的实测值是 12182，落在 0 到 16383 之间。再跑 cluster keyslot {user:1}:profile 与 cluster keyslot {user:1}:account——先猜：两个数一样吗？应看到完全相同——hash tag 里都是 user:1，CRC16 只算花括号里的它。
  2. 先猜：INFO replication 的输出里，单机实例也自称 master——每台 Redis 都是自己那份数据的主库，还带着 master_replid 与 master_reploffset 两个字段。记下 offset，执行一条 SET name mini，再看 offset——你猜它动不动？应看到立刻变大。文档口径：复制流每产出一字节 offset 加一，哪怕没有从库连着。涨的量与这条命令按第 2 章 RESP 帧格式编码后的字节数同一量级——自己算算是多少（*3 那一帧，三十三字节上下）。

收束：从一台到一群，账还是那些账 ​

回到凌晨 3 点 17 分。那一夜现在有三种结局可讲：裸单机——十几分钟写停摆、读雪崩，等值班工程师跑过来；加了主从——数据在从库上安然无恙，但提拔的手续还得人来办，写照样停；主从加哨兵——几十秒新主上线、客户端改认新主人、命中率先回血。再往后，数据大到一台装不下，集群把键空间切成 16384 个槽分给一群机器，扩容搬槽不搬家。同一份诚实账贯穿三种结局：异步复制意味着最后几条已确认的写可能没送到新主手上——高可用买的是「很快恢复」，不是「一条不丢」；要一条不丢，回头看持久化，或付同步复制的延迟税。

六个新词各收一句。主从复制——从库先抄一份全量（一张 RDB），之后靠命令流逐条跟上主库。全量同步——第一次同步的三部曲：拍 RDB、传输、补发增量缓冲。增量复制——断线重连只补缺口，靠 PSYNC 报上的 (ID, offset) 与主库的 backlog 环形缓冲。哨兵——几个旁观的看门进程，quorum 认定挂了、多数授权换人，自动完成故障转移。故障转移——把某个从库提成新主、大家改认新主人的换班手续。哈希槽——键空间切成 16384 个固定槽，扩容搬槽、不动全量。

自查三问（先自己答，再展开对）：

  1. 把演练一改两个参数再来一遍：BGSAVE 拍照拖到 5 秒才传完。期间到达的是 SET token:s9 vip、DEL cart:2、ZADD rank 7 bob——这三条命令各出现在照片、增量缓冲、补发流的哪一处？从库追平后，三条的效果分别在不在？
  2. 五台哨兵（S1 到 S5）、quorum 为 2。某夜网络分区：主库与 S1、S2 在一侧，且主库真的挂了；从库 R2、R3 与 S3、S4、S5 在另一侧。少数侧会发生故障转移吗？多数侧呢？两边的判据分别是什么？
  3. 纸上算：四个键的 CRC16 值是 5、11、19、31。按节点数取模，三节点时各归谁？加到四节点后各归谁、几个键搬了家？换成 16384 槽制，槽号各是多少？若 A 管 0 到 5500、B 管 5501 到 11000、C 管 11001 到 16383，四键各归谁？新节点 D 接走 B 的 5501 到 6000 这段槽，这四个键要搬吗？
第 1 问答案

照片里没有——fork 那一瞬数据已冻结，token:s9 是旧值、cart:2 还活着。增量缓冲里有——拍照与传 RDB 那 5 秒的新写命令全部攒在那里。补发流里有——RDB 传完，缓冲区清空式地发给从库。所以收完后效果在：token:s9 是新值、cart:2 没了、rank 里多了 bob。若只发照片不补发，这 5 秒的写全缺。锚点：原理「主从复制」的时序图、演练第一步。

第 2 问答案

少数侧（S1、S2）：两台各自 SDOWN，互相一问凑齐 quorum=2，ODOWN 成立；但当选 leader 需要 5 台中的多数（3 票），它们只有彼此——故障转移不发生，写继续停。多数侧（S3 到 S5）：它们与主库也不通，同样各自 SDOWN、凑成 ODOWN；三台不小于多数，选得出 leader，可以提拔 R2 或 R3。一句话判据：quorum 只够「认定挂了」，动手要多数——正是防脑裂的那道闸。锚点：原理「哨兵」一节。

第 3 问答案

mod 3：2、2、1、1——前两个键在节点 2（设为 C），后两个在节点 1（B）。mod 4：1、3、3、3——四个键全部换了主人。槽制下槽号就是 5、11、19、31，永不改变；四键全落在 A 的 0-5500 段里。D 接走的是 5501-6000，这四个键一个不搬——搬家与否只看槽在不在被搬的范围。锚点：演练第三步的取模演算表。
