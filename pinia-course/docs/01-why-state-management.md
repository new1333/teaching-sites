# 状态管理的四种尝试与它们的极限

一个购物车角标，从页面根组件出发，途经侧边栏、菜单容器、菜单项、图标包装层，最后才到角标组件——五层 props 接力，中间三层根本不关心这个数字，却都得为它留一个转发口。你把中间某层删掉，链路就断；你想给角标加个「满了变红」，得沿着链路把 prop 一路改下去。这不是你代码写得差，这是「组件状态」被错当成「应用状态」的必然结局：**有些状态本来就不属于任何一棵组件子树**。

这一章我们把「不用状态管理库」的四条路各走一遍，踩到它们各自的坑，最后提炼出 store 必须回答的四个问题——全书就是在回答这四问。

## 尝试一：props/emit 钻孔

最朴素的路：状态放在共同的祖先组件，用 props 往下传、emit 往上抛。

小项目里它完全够用。翻车发生在状态需要跨越三层以上的时候：每插入一个中间组件，就要为不相干的数据加一对 props/emit；删除一个中间层，链路断掉。更隐蔽的是**来源不可追溯**——角标组件里的 `count` 是谁传进来的？沿着 props 一层层往上翻，五分钟后再回来，你已经忘了要找什么。

props 钻孔的本质问题：**它假设状态有一个「属于」的子树**。可购物车数量、登录态、主题色这类状态属于整个应用，硬塞进组件树，就是在用错误的拓扑装正确的数据。

## 尝试二：模块顶层的共享 ref

于是你学了一招「组合式函数共享状态」：

```ts
// stores/counter.ts
import { ref } from 'vue'

// 模块顶层，只执行一次
const count = ref(0)

export function useCounter() {
  return { count }
}
```

单例有了，钻孔消失了，看起来很美。然后两个 bug 找上门：

**热更新丢状态**。开发时你改了这个文件里的任何一行，Vite 会重新执行模块，模块顶层的 `count = ref(0)` 重新跑一遍——用户刚刚操作出来的状态，保存一次代码就丢失归零。开发体验上的小事？它意味着「状态的存活周期」和「模块的存活周期」被绑死了。

**SSR 串号**。服务器是长驻进程，模块顶层的 `ref` 在**所有请求之间共享**。用户 A 的请求把 `count` 改成 3，`await` 让出事件循环的间隙，用户 B 的请求进来读到 3——A 的购物车数量渲染进了 B 的页面。这不是理论风险，是线上事故的标准剧本：**模块级单例没有「应用」的边界**，而服务器上同时活着无数个应用实例。

这条路的本质问题：状态有了全局的家，但这个家**不归任何应用所有**，也就无法随应用创建、随应用销毁、随应用隔离。

## 尝试三：事件总线与 provide/inject

再换思路：状态不动，让消息飞。事件总线（mitt 之类）把「谁改了状态」变成事件广播。

它解耦得恰到好处——也恰到好处地**过了头**。排查一个状态为何不对，你面对的是一张散落的事件网：谁在 emit？谁在 listen？事件名打错一个字母，静默失败。事件总线把「数据流」变成了「控制流」，而人脑推演数据流靠的是「看数据在哪里被读写」，不是「猜哪个事件被谁消费了」。

provide/inject 呢？它在组件树里挖了一条竖井，绕过中间层——比钻孔好。但 inject 的作用域仍然是「子树」：兄弟子树拿不到；而且注入的东西没有身份——两个插件注入同名的 key，后装的覆盖先装的。它解决的是「传得烦」，没解决「放哪、归谁」。

## 尝试四：Vuex

最后请出前辈 Vuex。state、getters、mutations、actions、modules，该有的都有：状态在组件树外有家（store），变更有唯一通道（commit mutation），变更可追踪（devtools 时间旅行）。

它翻车在**写一个变更要动三处**：state 里声明字段，mutation 里写同步修改，action 里写异步逻辑再 commit。改一个字段名，三个文件跟着改。更痛的是 TypeScript：`store.dispatch('cart/addItem', item)` 的字符串 dispatch 让类型检查形同虚设，你得手写一整套类型桥接。

Vuex 证明了「统一的家 + 可观测的变更」是对的，它的代价是把**过程**（mutation）当成了 API 的中心。Pinia 的诞生宣言就是从这里出发的：去掉 mutation、让 action 直接改状态、让 TypeScript 原生推断——**把过程藏进库，把直觉还给开发者**。

## 四问：store 必须回答什么

四条路各撞一堵墙，墙后面立着四个问题。任何状态管理方案——包括你接下来要亲手写的 pinia-mini——都必须给出回答：

1. **放哪**：状态住在组件树之外的一个「家」里，按领域切成一个个 store，每个 store 一棵状态树（state tree）。
2. **归谁**：家要归应用所有——一个应用一个容器（Pinia instance），随应用创建、销毁、隔离；SSR 下并发请求各自有容器，互不串门。
3. **怎么共享**：任意组件调用 `useCounterStore()` 拿到的是同一个实例——单例身份（store identity）由容器担保，而不是由模块语法担保。
4. **怎么改、怎么观测**：改状态走公开的通道（action、`$patch`），变更可以被订阅（`$subscribe`、`$onAction`）——调试、持久化、日志都挂在这两个钩子上。

这四问不是并列的，是有依赖次序的：

```text
            ┌─ 放哪（状态树）
            │
一个应用一个容器 ─┤
            │
            └─ 怎么共享（单例身份）
                    │
                    ▼
          怎么改 / 怎么观测（订阅）
                    │
                    ▼
              插件 / SSR / 生产化
```

容器是最底层的地基（第 3 章），单例身份建立在容器上（第 4 章），三件套与两种语法长在单例上（第 5、6 章），批量变更与订阅再往上垒（第 7、8 章），最后是扩展与生产化（第 10、11 章）。这个次序就是本书的章节次序——每一章只回答一问。

## 小结

props 钻孔输在「状态没有正确的拓扑」；模块级单例输在「状态没有应用的边界」；事件总线输在「数据流变成控制流」；Vuex 输在「把过程当 API」。四堵墙拼出四问：放哪、归谁、怎么共享、怎么观测。下一章先补齐要用的 Vue 响应式原语——它们是后面十章每一行代码的地基。
