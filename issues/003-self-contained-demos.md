# 自包含演示：build 章正文要不要「不进伴生仓也能验证」的片段

## Question

build 章正文要不要、以什么强度要求「读者不克隆伴生仓也能亲手验证」的自包含演示（REPL 可跑片段 / 数值演算）？

证据（用户直觉点 1「代码演示太少」的根因）：
- 第 1 章（principle）全部 3 个代码块自包含可复跑；进入 build 章后该标准被静默放弃：第 5–12 章正文 20+ 个 ts 代码块中自包含的仅 2 个（第 11 章 DUTY_TABLE 常量、第 1 章 REPL），其余全部依赖伴生仓上下文（引用正文未定义的 `CpuCore`/`word`/`fetch` 等）。
- outline 第 1 章验收明文要求「node REPL 可跑的自包含示例」——该标准进入 build 章后无替代说明地消失了（round3-ch5-8.md 通病 3）。
- 后果：阅读态（不切终端）读者能获得的验证渠道为零，与「前端熟手」读者画像错配。

要决定的选项：
1. chapter-writing 硬要求补一条：承重知识点至少有一种「跟着算一遍/跑一遍」的载体，其中机制类概念优先数值演算——注意四步教法的「演算」步已有此意，但它只覆盖大纲声明过的 new_concepts，未声明的知识点（第 9 章 9 个知识点大多如此）无兜底；
2. 只进评审智能体轴 1 判定标准，不动写作硬要求；
3. 不动（承认 build 章正文天然引用伴生仓，靠 005 的可感知成果载体替代）。

约束：不得变成「每章 N 个代码块」式配额；自包含示例仍须零仓库痕迹。
