# 正文↔伴生仓一致性闸门：根治幽灵代码

## Question

正文标注「src/xxx（节选）」但伴生仓已重构、代码对不上（幽灵代码），用什么机制根治？

证据（全部经主智能体复核坐实）：
- 第 8 章两段标「src/ppu/index.ts · renderBackground（节选）」的代码引用 `ntBase`/`row`/`col`，而 companion 实际的 renderBackground 是 coarseX/coarseY/fineY 滚动相机版——变量都不存在；companion 为滚动功能重构后，正文引用未回写。
- 第 7 章标「writeReg 的 $2006 分支（节选）」的代码与实际实现不符（实际经 t 暂存寄存器再同步 v）。
- 第 4 章标「step（本章形态）」的代码在读者可达的任何地方不存在——companion 是表驱动终态，「本章形态」躺在读者不可见的 `.course/snapshots/pre-ch-5/`，正文/README 无一字指引。
- 现有防线为什么没拦住：lint 只查代码块「是否标注出处」，不查出处真实存在；章评审时点上一致（轴 2 有此要求），但后续章重构破坏前章引用时无人回扫；全书评审（阶段 3.5）轴里没有「正文↔代码引用一致性」。

要决定的选项（可组合）：
1. 机械 diff 闸门：解析正文代码块首行出处注释（路径+函数）→ 与 companion 当前源码比对相似度，挂进每章门槛后 + 终检（可脚本化，挂 009 的 final-check 扩展）；
2. 锚定终态：正文代码切面一律取自「全量门槛通过后的最终代码」，禁止引用演进中间态；
3. 重构回扫义务：后续章重构波及已发布正文引用的函数时，回写前章正文（写进章写作智能体职责与主智能体编排）；
4. 中间态代码的锚定规则：「本章形态」类代码要么禁用，要么必须给读者可达的获取方式（如随附文件），不能躺在内部快照目录。
