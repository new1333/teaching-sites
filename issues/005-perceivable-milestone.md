# 可感知成果：里程碑要能被读者看见/听见/玩到

## Question

「里程碑可被读者感知」要不要成为 skill 的验收形态之一？以什么强度、什么表述写进哪份文件？（用户直觉点 2「没有可实时看到运行结果的组件」的正面修复。）

证据：
- 大纲 acceptance 全部以「测试转绿」为验收形态，没有任何一条要求「正文引导读者看到/听到/玩到成果」——交互载体在大纲层就没有位置（round3-ch9-12 通病 3）。
- 后果全景：渲染两章（8/9）全书零图片，「图形对了颜色全错」里的「图形」读者从头到尾没见过；第 11 章讲声音，全章无任何可听载体，自查题却问「divider=0 与 10 的包络**听感**差在哪」；第 12 章终点承诺「出画面、出声音」，正文 12 章零次提及试机台命令（`pnpm dev` 仅 about.md 和 companion/README 出现）。
- 讽刺点：companion 实际有一个 230 行、功能完整的浏览器试机台（canvas 出帧 + Web Audio + 键盘手柄 + 换卡 + `?rom=` 分享），正文与它彻底脱钩——资产存在，规范没要求接线。

要决定的选项（待 004 调研输入后细化）：
1. 底线版：骨架「验证」段扩展——里程碑可感知的章，验证小节必须给「亲手开机」指引；成果载体（试机台/入口命令）在正文与 README 双落点；
2. 静态版：+ 渲染/音频/可视化类章在正文嵌成果静态产物（截图/音频）；
3. 交互版：+ 按课程形态分档，形态允许时用内嵌交互组件（成本与可移植性取决于 004）；
4. 大纲层：companion 形态字段/acceptance 模板增加「可感知验证」槽位。

约束：表述必须可移植（「渲染/音频/可视化」按主题描述，不绑定具体域）；形态不允许的课程（纯 CLI/纯配置）不硬造交互，退到指引或明确声明不可感知。
